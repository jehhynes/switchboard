# Switchboard architecture

Requirements live in [prd.md](prd.md). This document describes components, state and protocols. Implemented: the hub lifecycle, the core's store, settings, playbooks and [flow decisions](#core-decisions), the GitHub source, the Claude Code runner and classifier, the hub runtime, the report command, the Zoho Desk and Forum sources, the pool with picks, shown with unstarted work items in the Unstarted group, the [dock](#dock) with its [Settings window](#settings-window), and the [VS Code extension](#vs-code-extension) that serves each item window.

Session and triage mechanics come from Ground Control (`D:\git\ground-control`), where they are verified. M IDs below refer to its [mechanics.md](../../ground-control/docs/mechanics.md). Re-verify them in Switchboard's own mechanics.md before relying on a version-fragile one.

## Packages

The application icon is a patch panel with four thick socket rings and a bold bright cyan connection, on a rose-to-plum gradient tile that stays visible against a dark taskbar, with transparency outside its rounded tile. `extensions/switchboard/assets/icon.png` supplies the VS Code extension listing at 256 pixels. The dock executable, main window and Settings window use `apps/dock/src/Switchboard.Dock/Assets/dock.ico`, containing 16, 20, 24, 32, 40, 48, 64, 128 and 256 pixel versions of that artwork. Chrome's extension icon uses 16, 32, 48 and 128 pixel PNGs in `extensions/chrome/assets`, copied into its unpacked build.

History tabs use light and dark monochrome SVGs of the patch panel; the status bar uses the `switchboard-logo` product icon from `assets/switchboard.woff`. Their vector source is `extensions/switchboard/assets/mark.svg`. Run `python tools/build-icon-font.py` with `fonttools` installed to regenerate the font, the History SVGs and a simplified colour vector variant `apps/dock/src/Switchboard.Dock/Assets/dock.svg`. For future raster exports, use `extensions/switchboard/assets/icon.png`: resize it with bicubic interpolation and preserve alpha for each listed Chrome PNG size and each PNG frame in the dock ICO. The vector generator does not rewrite these raster files.

npm workspaces, TypeScript strict, Node ≥ 22.13, Vitest, esbuild and vsce, following Ground Control's layout. Only `extensions/switchboard` imports `vscode`. Implemented so far: `packages/core`, `packages/github`, `packages/zoho`, `packages/forum`, `packages/claude`, `packages/codex`, `packages/hub`, `apps/hub`, `apps/dock`, `extensions/switchboard`, `extensions/chrome`, `extensions/firefox` and `extensions/gnome-shell`. `apps/dock` is C# on .NET 10 with Avalonia 12; its workspace scripts run `dotnet build` and `dotnet test`, so `npm run verify` covers it.

The ad-hoc source is local and lives in `packages/hub`. State, the hub bundle, its record and its log live in the Switchboard home, `~/.switchboard`. Settings and playbooks live in the config folder, so the operator can keep them in a git repository. The config folder is the VS Code setting `switchboard.configDir` (machine scope): an absolute path, or one starting with `~` for the user profile. When the setting is empty, it is the Switchboard home. For a relative path, the extension shows an error and uses the Switchboard home. Each window reads the setting on every hub start, so all windows agree on one hub. When the setting changes, a window whose hub reads another folder stops it; every window then reconnects to one hub started on the new folder, and the keeper does not count that stop as a failure.

## Components

| Component | Responsibility |
|---|---|
| Hub | Separate Node process that runs the core: polls sources, creates work items, runs triage, starts setup and task sessions, enforces one session in a turn per ticket (PRD R17), serves the windows, the dock and the report command. |
| Source plugins | Supply tickets, decide whether each is in the assigned state, and build each ticket's triage context: GitHub, Zoho Desk, Forum, ad-hoc. |
| Playbook loader | Reads the playbooks in settings.json and renders their templates. |
| Classifier | Runs one-shot triage and returns structured output. |
| Runner | Starts, stops and tracks agent sessions for one provider, behind the `SessionRunner` interface in `packages/core/src/runner.ts`, which the hub runtime calls: Claude Code and Codex. |
| Worktree linker | Links worktrees to tickets from session reports, falling back to branch-name convention. |
| Store | Local SQLite database holding tickets, work items, triage results, sessions and worktrees. |
| VS Code extension | Starts the hub, opens claimed sessions in the item window's Claude view or Codex sidebar, runs the dock's commands, opens a worktree's changes, shows a ticket's history and notifications of work on the operator's turn, and shows the dock from its status bar item. |
| Dock | Lists the work items beside VS Code, switches to each item window, runs the controls, and edits the settings. |

## Data model

```
Ticket     id, source, sourceKey, ref, sourceId, title, url, assigned, pool, snoozed, snoozedUntil, snoozeComment, sortAt, scopeAt, lastPolledAt, repoRoot
WorkItem   id, ticketId, playbook, status, stage, stageAt, taskPrompt, guidance, warning, error, unassignedAt, queuedAt, createdAt, statusAt, runStartedAt, readyAt, orderAt, scopeAt, doneAt, doneReason, approvalPrompt, approvalSummary, approvalReport, approvalHeld, parentId
Triage     id, ticketId, workItemId, context, playbook, immediacy, severity, model, startedAt, endedAt, error
Worktree   id, ticketId, path, branch, linkedBy (report | convention)
Link       id, ticketId, label, target, reportedAt, mentioned (found in the ticket's text by triage, PRD R61; cleared for good once a session reports it)
Paste      id, workItemId, label, file, reportedAt
Comment    id, workItemId, at, text
Session    id, workItemId, kind (setup | task), provider, nativeSessionId, shortId, cwd, state, stateAt, stateDetail, outcome, outcomeDetail, startedAt, endedAt, released, releasing, question, retiredIds, pendingFork, external
```

- `Ticket.assigned` is the assigned state the last complete poll saw, and `Ticket.pool` whether it saw the ticket in the pool. `Ticket.ref` is the reference people use, set by the source when it builds the ticket: `#<n>` for GitHub and ad-hoc, `#<ticket number>` for Zoho, `T<topic id>` for Forum; core holds no per-source rule. `Ticket.sortAt` is the source's sort time, which orders the Unstarted group: Zoho's `customerResponseTime`, Forum's last public post, and for GitHub the later of the operator's latest assignment and the Status field's `updatedAt`. `Ticket.scopeAt` is when the ticket last entered the source's scope (PRD R53). Each polled ticket carries the source's `enteredAt`, or null, and core stores the source's time whenever it has one, because a source's scope can be wider than the assigned state and the pool: a GitHub issue on another status, or a Zoho ticket another engineer holds. Without one, the ticket keeps the time it has, or takes the poll's time when it has none and is assigned or in the pool. Ad-hoc tickets enter scope when created. A pool triage has a `ticketId` and no `workItemId` until a pick creates the work item and attaches it. `Ticket.repoRoot` is the repo an ad-hoc prompt chose; it is empty for other sources, which use their `repoRoot` setting.
- `Ticket.sourceKey` is the key people use, such as a GitHub issue number or a Zoho ticket number. `Ticket.sourceId` is the source's internal ID when API calls need a different one, such as Zoho's internal ticket ID. A schedule's ticket holds its `scheduleText` there, and a task report's ad-hoc ticket `task` ([Flow](#flow)). `Ticket.adhocKey` is the ad-hoc key of a ticket a ticket report moved to a source (PRD R83), null otherwise: new ad-hoc keys count it (`Store.adhocKeys`), so it is not used again, `windowOf` names the item window by it, and rows and History label the moved work item by how it was made while it has no playbook. The moved work item is the ticket's first, because an ad-hoc ticket has one; the snapshot marks it `moved`, so a later work item of the ticket is not labelled.
- `Triage.context` is the clipped text the classifier received, with the current time. Keeping it shows why a playbook was chosen.
- `Triage.focus` is the URL of the page or comment the classifier chose (PRD R79), null on a failed or running triage and on triages from before migration 25, which adds it. The snapshot's `WorkItemView.focus` and `PoolView.focus` are core's `effectiveFocus`: the `focus` of the latest triage with a playbook, else the ticket's URL, so a running or failed triage keeps the earlier focus. A pool ticket's Triage again deletes its earlier triages, so it shows the ticket's URL until the new triage succeeds.
- `WorkItem.status` takes the values in PRD R34. `WorkItem.error` holds the cause shown for `failed` or `blocked`.
- `WorkItem.readyAt` is when the work item first became `awaiting-approval` or `finished`, set by the flow's `setStatus`; nothing else changes it, Retry included. A new work item, a returned ticket's included, starts with both null. `WorkItem.orderAt` is the operator's position in Ready for review (PRD R73), or null. Migration 20 adds both, turns `blocked` work items whose error is "The session finished its turn." or "The session ended." into `finished` with no error, and sets `readyAt` to `statusAt` on `awaiting-approval` and `finished` work items.
- `WorkItem.unassignedAt` records that the ticket left the assigned state while a session or the triage of a sessionless work item was running (PRD R10). `WorkItem.queuedAt` orders queued starts.
- `WorkItem.taskPrompt` is the rendered prompt the task session ran, or the typed prompt for an ad-hoc work item.
- `WorkItem.guidance` is the trimmed text of Start with guidance… (PRD R77), set by a `start` or `pick` action's `guidance` and cleared on `session-started` of a task session, whose prompt has it appended, so a failed start keeps it for Retry; a plain Start sets it to null. It is not in the activity log's changes, because the action's event detail holds it. Migration 24 adds it.
- `WorkItem.doneReason` is `session`, `operator` or `unassigned`.
- `WorkItem.parentId` is the work item whose session sent the `task` report that created this one (PRD R68), or null. Migration 15 adds it.
- Migration 16 rebuilds `workItems` with `AUTOINCREMENT` IDs and deletes the work items done as `unassigned` that never had a session and have no child work item (PRD R10). Migrations run with foreign keys off, because a table rebuild drops a parent table, and each fails unless `PRAGMA foreign_key_check` is empty before it commits.
- `WorkItem.warning` is set when the work item ends because its ticket left the assigned state with no done report (PRD R10, R11).
- `Session.state` is the observed state, `Session.stateDetail` the error kind of a `failed` turn, and `Session.outcome` the reported or decided outcome (PRD R36). `Session.released` records that the release stop was sent, so it is sent once (PRD R39), and `Session.releasing` that it has not finished: the session is not opened, and Stop and Delete still stop it. `Session.question` is a Codex session's reported question, `{id, text}` as JSON, which it waits on once its turn ends (PRD R70); the ID tells two reports of the same text apart for the roster read. Migrations 22 and 23 add them; neither is in the activity log, whose report event names the question.
- `Session.retiredIds` lists the native IDs of the copies a fork retired, stored comma-separated like `reports` and left out of the activity log, and `Session.pendingFork` the short ID of a fork waiting for the background process's release (PRD R78). Migration 26 adds both.
- `Session.external` marks a session the operator registered from a window Switchboard did not open (PRD R81); the roster read that ends the session clears it. Migration 27 adds it, left out of the activity log.
- A session's `cwd` follows its playbook's `workdir`: the ticket's worktree when one exists, otherwise the source's repo root.
- `Paste` is a drafted text a session named for the operator to copy (PRD R60). It belongs to the work item, not the ticket, because a returned ticket's new work item drafts new texts; `(workItemId, label)` is unique, so a later paste with the same label replaces the file and keeps its place. Migration 14 adds the table.

## Hub lifecycle

Implemented. Follows Ground Control's hub (GC R35, M25).

- **Start:** extension activation copies `dist/hub.js` to `~/.switchboard/hub.js` when it differs. It accepts a running hub only when the hub's `build`, a hash of its bundle, matches the bundle installed at that moment, and its `configDir` matches the window's config folder. It asks any other hub to stop and starts a new one only after the old one has gone; if the old hub refuses, the window reports it. Otherwise it starts one detached with VS Code's executable and `ELECTRON_RUN_AS_NODE=1`, with `ELECTRON_*`, `VSCODE_*` and `NODE_OPTIONS` removed from its environment. Output goes to `~/.switchboard/hub.log`.
- **Record:** the hub listens on `127.0.0.1` on an ephemeral port and writes `~/.switchboard/hub.json` with `protocol`, `version`, `build`, `configDir`, `execPath` (its `process.execPath`: VS Code's executable when a window started it, Node.js when started by hand or by tests; `''` read from an older hub), `port`, `token`, `pid` and `startedAt`. A record without `configDir`, from an older hub, reads as an empty one, so a window replaces that hub. The hub holds a lock for its lifetime: a named pipe `\\.\pipe\switchboard-<hash of home>` on Windows, `~/.switchboard/hub.sock` elsewhere. Only the lock holder writes or removes the record, so concurrent starts leave one hub, and the OS releases the pipe when the hub dies. A hub that cannot take the lock waits up to 5 seconds for the holder's record and otherwise exits. A forced exit on Windows leaves the record behind, so clients accept it only when `GET /status` with the token returns the recorded pid.
- **Endpoints:** `GET /hub` returns identity without a token. `GET /status`, `GET /events`, `GET /dock/events`, `POST /window`, `POST /window/withdraw`, `POST /window/focus`, `POST /window/theme`, `POST /dock/show`, `POST /dock/click`, `POST /poll`, `POST /config/read`, `POST /config/check`, `POST /config/save`, `POST /config/delete`, `POST /shutdown`, `POST /report`, `POST /contract`, `POST /register`, `POST /ticket`, `POST /action`, `POST /open`, `POST /claim` `POST /volume` and `POST /history` require `Authorization: Bearer <token>`. `/events` sends a `state` event with the whole snapshot when it opens and after every change, built once per burst of changes in one turn of the event loop (`setImmediate`), because each build blocks the hub for hundreds of milliseconds, and `claim` when something is left for a window ([VS Code extension](#vs-code-extension)), and `/dock/events` a `dock` event with the [dock view](#dock) the same way, plus `show` when `POST /dock/show` asks for the dock's list (409 when no dock stream is open) and `config` after the hub reloads the settings or playbooks. Each window opens `/events?workspace=<file>&focused=<0|1>`, with an empty `workspace` for a window that is not an item window, and posts `POST /window/focus {workspace, focused, at}`, with `at` the time of the change, when it gains or loses focus. The hub adds `windows` to each dock message, `{open, front, count}`: the workspace files of connected item windows, the one that last gained focus and still has it, or null, and how many windows are connected; it sends the dock view again when a window connects, disconnects or changes focus. A blur from a window that is not in front, or from a window that is not an item window, changes nothing; a report older than that window's latest report or than the last change applied is ignored; a focus report from an item window whose stream has closed is ignored; and a reloaded window, whose new stream opens before the old one closes, is listed once and keeps its focus. The `/config/*` routes serve the [Settings window](#settings-window). `/action` takes an operator event (`adhoc`, `start` with `{workItemId, guidance?}`, `approve`, `mark-done`, `retry`, `stop`, `open-question` with `{workItemId, nativeSessionId}`, `move` with `{workItemId, after}`, where `after` is a work item ID or null, `reset-position` with `{workItemId}`) and answers 409 with the core's refusal; for `open-question` and `move` it keeps only those fields, and it refuses a `start` or `pick` whose `guidance` is neither a string nor null (PRD R77). `/history` takes `{ticketId, revision?}` (PRD R59). `/contract` takes `{nativeSessionId}` and answers `{contract}` for the latest session with that Claude session ID, or 404, for the contract hook ([Claude Code runner](#claude-code-runner)). `/register` takes `{nativeSessionId, title}` for the register command and answers `{key, contract}`, or 409 with the refusal ([Session reports](#session-reports)).
- **Dock start** (PRD R71): `HubStarter` in the dock. Once the dock's `/dock/events` stream answers a record's token, it keeps that record's `execPath` and `configDir` in `~/.switchboard/dock-hub.json`, a file of its own so the UI's `dock.json` writes cannot race it; a record without them changes nothing. When `HubClient` finds no hub, by a missing record or a stream that fails or ends, it calls `HubStarter.Start`, which starts a hub only once none has answered for 5 seconds (`Grace`, from the first failed attempt, reset when a hub answers), so a VS Code window replacing the hub, as for a new config folder, wins the hub lock, and at most once per 30 seconds: with nothing kept it starts nothing; with a missing runtime or `hub.js` it names the path; otherwise it runs `<execPath> ~/.switchboard/hub.js --home=<home> --config=<configDir>` without `ELECTRON_*`, `VSCODE_*` and `NODE_OPTIONS` and with `ELECTRON_RUN_AS_NODE=1`, as `startHub` does. Elsewhere than Windows it runs through `/bin/sh`, which appends the output to `hub.log` and `exec`s the hub, so the hub keeps its log after the dock exits; on Windows it starts the runtime directly, unlogged, because `cmd.exe` would expand a `%NAME%` in a path. A started hub that has exited by the next attempt is reported with its exit code and the log's path, rather than as starting. The hub's lock keeps concurrent starts by the dock and a window to one hub. `HubClient.NotRunningText` holds what the dock says meanwhile.
- **Clients:** each window holds one `/events` stream, and the dock one `/dock/events` stream; either counts as a client. A dock that runs forwarded clicks opens its stream with `?click=1`; `POST /dock/click {rowKey}` sends a `click` event to the newest such stream only, so one dock runs it and an older dock never gets it, and answers 202 once sent (accepted, not completed) or 409 "The dock is not running." with none (PRD R65, R69, R71). The hub exits 30 minutes after its last stream closes, but not while any session is active or a debrief runs (PRD R43, R55). A stream that sends no response headers within 5 seconds counts as refused. When a stream ends, the window finds or starts a hub and reconnects. It gives up and shows an error after three consecutive failures; a connection that lasts under 10 seconds counts as a failure.
- **Browser endpoint:** for the browser extension, which cannot read `hub.json`, the hub also listens on the fixed port `127.0.0.1:47615` (`BROWSER_PORT` in core). It serves, without a token, `GET /snoozed`: `{"urls": [...]}`, the URLs of tickets snoozed now, from every source; and `GET /cards` (PRD R67): `{"cards": [{url, playbook, group, snoozed, links}]}`, one per ticket URL, built from the snapshot by `cardsOf` in `packages/hub/src/cards.ts`. A card covers each work item and pool ticket of a polled source with a URL that the dock lists, so an unsnoozed done work item only while Done lists it (from `doneSince`) and a snoozed ticket while Snoozed lists it, because a card for a row the dock does not show could not open it; `url` is the ticket's URL as stored, `playbook` the name the dock shows (`<namespace>:triage` during triage, null before triage chooses one), `group` the dock's group (`blocked`, `review`, `progress`, `unstarted` or `done`, from `groupOf`; a pool ticket is `unstarted`), `snoozed` the ticket's flag, and `links` the targets of the ticket's links (PRD R52, R69), from `WorkItemView.links` or `PoolView.links`. A ticket with several work items gives the pool entry, otherwise the open work item, otherwise the latest one. `/snoozed` stays, because the browser extension is loaded separately and can be older than the hub. It also takes `POST /snooze {url, until}`, where `until` is epoch milliseconds or null, finds the assigned or pool ticket whose URL matches, ignoring case, and sends the core's `snooze` event (PRD R66): 200 `{done: true}`, 404 when no ticket in scope has the URL, 409 with the core's refusal for a past time, 400 for another body or one over 16 KB. `POST /unsnooze {url}` finds the ticket the same way and sends the core's `restore` event, with the same answers. Both POST routes answer 403 to an `Origin` that does not start with `chrome-extension://` or `moz-extension://` and 415 to a content type other than `application/json`, before reading the body. A web page's JSON request needs a CORS preflight, which fails because the endpoint sends no CORS headers, and a `no-cors` request goes out as `text/plain`, so only an extension with host permission for the port can snooze or unsnooze; any such extension can, because an unpacked extension's ID depends on its folder ([mechanics.md](mechanics.md) M23). The routes send no CORS headers, so web pages cannot read them, and answers 403 to a `Host` other than `127.0.0.1:<port>` or `localhost:<port>`, against DNS rebinding. A hub that cannot take the port, such as a second hub for another home, logs it and runs without the endpoint.
- **Entry point:** `hub.js [--home=<dir>] [--config=<dir>] [--idle-ms=<ms>] [--browser-port=<port>]` serves, reading settings and playbooks from `--config`, or from the Switchboard home without it; `--browser-port=0` serves no browser endpoint, as in the spawn tests; `hub.js --stop` stops the running hub; `hub.js report …` sends a session report.
- **Runtime:** the hub opens the store, loads settings and playbooks and reloads them on change, polls each enabled source every `pollIntervalSeconds`, then reads `git worktree list` in its repo root for the branch convention, sending `worktree-found` only for a ticket that has no worktree yet. Entries that git marks `prunable`, such as one whose directory was deleted, are left out of both the convention and report validation. While any session has started, it reads the roster every 30 seconds and hook markers every 5 seconds. Before a roster read or a release stop can end a setup session, it reads the convention again, so an unreported worktree still counts.
- **Startup:** the hub runs `<sessions.nodePath> --version` and shows a failure with the hook errors, because the hooks and session reports run that Node.js and a hook that cannot start fails silently. It checks once for each agent the hub starts, with the PATH that agent gets: the hub's, with that agent's absolute `sessions.claudePath` or `sessions.codexPath` directory first, and names the agent that lacks Node.js. A Claude background session started by an already running Claude service has that service's environment, which the check does not cover. A change to any of the three paths runs the check again. It installs each agent's hooks when `sessions.installHooks` is on, runs again any triage it abandoned, asks each session's runner about any session still `starting` (`reconcile`): Claude's fails it with "The hub stopped while the session was starting.", and Codex's completes, waits for or fails it from its run record, or answers `pending` when the process query fails, which the hub asks about again at each roster read; then it reads the roster (PRD R43).
- **Platforms:** Windows, and Linux under GNOME on Wayland, run the hub, the extension, the browser extension and the dock (PRD § Scope); the dock reserves a screen edge on both, and on Linux brings item windows forward through the GNOME Shell extension ([Dock](#dock)). On both, the hub runs under VS Code's own executable in Node mode, source commands run through Git Bash on Windows and `bash` elsewhere, and Claude's and Codex's hook scripts run with `node`. Paths compare without case or separator differences on every platform, as on Windows, so on Linux two paths that differ only in case count as one.
- **Home override:** when `SWITCHBOARD_HOME` is set in VS Code's environment, the extension passes it to the hub as `--home`. Both the variable and `--home` name the directory that holds `.switchboard`, in place of the user home, so the Switchboard home is `<override>/.switchboard`. The extension then ignores `switchboard.configDir`, so the config folder is `<override>/.switchboard` too. It does not change the user profile that Claude and `gh` see. Live acceptance depends on it.

## Rows

- The row rules, the groups and their order, each row's controls, click, time, priority and texts, live in `packages/hub/src/rows.ts`, which imports only types and browser-safe core modules, so the History webview bundles it as `@switchboard/hub/rows`; `dockView` in `dock.ts` turns them into the texts the [dock](#dock) draws.
- Groups follow PRD R27, in the order Ready for review (`review`), Blocked on you (`blocked`, only when it has rows), In progress (`progress`), Unstarted, Snoozed, Done (`dockView` orders them; `listGroups` builds them). `groupOf` in `packages/core/src/group.ts` checks Done, then Unstarted (`unstarted`, `triaging`, and `failed` at triage, `failedAtTriage`), then Ready for review (`readyAt` set, `queued`, questions, blocks and failures included), then Blocked on you (`blocksOnYou`: `blocked`, `failed`, or a question: a `waiting` active session, or a `setup`, `running` or `awaiting-approval` work item whose latest session ended with outcome `opened`, `waitsOnQuestion`), then Unstarted for `queued`, else In progress. Blocked on you, Ready for review, In progress and Unstarted start open; Done and Snoozed start closed. An empty Ready for review says "Nothing is ready for review.", an empty In progress "Nothing is in progress.", an empty Unstarted "Nothing waits to be started." (`GROUP_EMPTY`); the dock shows this text in italics in the muted colour, aligned with a row's text.
- `listGroups` orders Blocked on you by `clockOf`'s start, oldest wait first; Ready for review by `reviewOrder` in `group.ts`, `orderAt ?? readyAt` then ID, which the flow's `move` also uses; In progress by `clockOf`'s start, `runStartedAt`; each then by ID.
- `turnOf` in `group.ts` gives `operator` in Blocked on you and for a `blocksOnYou`, `awaiting-approval` or `finished` work item in Ready for review or In progress, `agent` for the other work items there, and null in Unstarted and Done. `needsYou` is an unsnoozed work item on the operator's turn; the status bar counts it and the notifications follow it. `stripeOf` gives an unsnoozed row on the operator's turn `error` (failed), `warning` (blocked or a question) or `turn` (any other Ready for review row), and null on the agent's turn and elsewhere.
- The main control (`mainControl`) is: Open in Claude on a row whose active session waits in its background process (PRD R70), even when it is `awaiting-approval`; Start on an Unstarted row (`start` for a work item, `pick` for a pool ticket), Approve on an `awaiting-approval` row, Retry on a `failed` row with no active session, or Triage again on a pool row whose triage failed; a `blocked` or `finished` row has none, because a click opens its session, and neither does an In progress or Done row. ## VS Code extension

The extension makes each VS Code window an item window's helper; it has no view of its own (PRD R71).

## Dock

The dock compares group content before rebuilding its list, including nested action data. A focus report carries the whole view on both platforms; when the groups are unchanged, their controls stay attached. While the pointer is pressed, the dock holds the latest view until after release, loss of capture or deactivation, so even a changed elapsed-time label cannot replace the pressed row before its click runs. Starting a row drag releases the held view, since a drag suppresses the click and needs current rows for its drop target. Linux's window tracking still receives each view.

PRD R71. `apps/dock` (`Switchboard.Dock.exe` on Windows, `Switchboard.Dock` on Linux) is a C# .NET 10 app with Avalonia 12.1.3. Window management sits behind `IWindows` and `IVsCode` (`Switching/Platform.cs`). On Windows they are `Win32Windows`, `VsCodeInstall` and `AppBar` in `Platform/`, described below. `npm run publish --workspace @switchboard/dock` publishes it to `~/.switchboard/dock/`.

- **Linux.** Under GNOME on Wayland an app cannot list, raise or watch another app's windows (mechanics M38). The dock runs under XWayland, so `App` docks it with `MainWindow.DockOnX11` when its window is an X11 window, else floats it (`Float`), and uses `ShellWindows` when the GNOME Shell extension's service is on the session bus at start, else `HubWindows`. Either way `HubWindows.Update` takes the view's `windows` ([Hub lifecycle](#hub-lifecycle)): a change of `front` to an item window selects its row (`MainWindow.ShowItemWindow`), and an item window that leaves `open` clears the selection, as on Windows.
  - **Docking.** `DockOnX11`, before the window shows, sets `_NET_WM_WINDOW_TYPE_DOCK` (`X11Dock`, libX11 on its own display connection). Mutter keeps a dock window above other windows, on every workspace and out of the taskbar, and leaves it inside a strut, from which it moves a normal window (M39). - **Auto-hide** (PRD R71). Turning it off unregisters it and reserves the strip. The window keeps its full strip and layout while hidden: `SetWindowRgn` limits its drawing and hit testing to the outer 3 device-independent pixels, converted to physical pixels at the current scale (`DockPlacement.Sliver`), and covers that edge with `SliverView`, the same 3 device-independent pixels wide, which draws the dock's background and, from `MainWindow.SliverBars`, each coloured row stripe cut to the list's view at its height in the window, recomputed after each layout while hidden and drawn without a layout of its own. Repeated placement calls do not restart an active hide countdown. A separate 100 ms timer reconciles the native topmost style, even while hidden, because Avalonia caches its `Topmost` property and does not notice external z-order changes. The dock checks visible windows in front-to-back order on its monitor, skipping tool windows, minimized or cloaked windows and the desktop. It yields when the first relevant window is full-screen and restores topmost when an ordinary window covers it or no relevant window remains. Focusing a window on another monitor does not raise it over full-screen content; shell full-screen notifications request the same check.

A move that changes the edge or monitor saves the edge and the monitor's device name, or no name for the primary monitor, and reserves the strip there; losing the pointer capture ends the drag where the dock last docked.
- **State.** `<Switchboard home>/dock.json` keeps `width` (200 to 800, default 320), `edge` (`left` or `right`; anything else reads as `left`), `monitor` (a device name such as `\\.\DISPLAY2` on Windows, a RandR output name such as `HDMI-2` on Linux, or null for the primary monitor), `autoHide` (default false), `theme` (default `system`), and `groups`, the groups the operator opened or closed; Blocked on you, Ready for review, In progress and Unstarted start open. Done's date bands are not kept: `DockViewModel` holds their open state in memory under `done:<band>`, so each dock start opens Today and Yesterday and closes the others, and `DockSettings.Load` drops `done:<band>` keys an older dock kept. Kept choices under keys the view does not send, such as `needs` and `working`, have no effect. `GroupViewModel` splits its shown rows into `BandViewModel`s by `band`; a group other than Done has one band with no heading. One dock runs per desktop (`Local\Switchboard.Dock` mutex); closing it ends the app, even with the Settings window open. `--home` or `SWITCHBOARD_HOME` names the folder holding `.switchboard`, as for the hub.
- **Connection.** `HubClient` reads `hub.json`, opens `/dock/events` with the token, and reads `hub.json` again 2 seconds after the stream ends or fails. Besides `dock`, the stream sends `show`, from a VS Code window's status bar item (`POST /dock/show`), which activates the dock, `config`, which makes an open Settings window read the files again, and `click`, a click VS Code forwarded (it opens the stream as `/dock/events?click=1`); the dock skips any other event. Each attempt sets the state: a 404 means a hub older than the dock, and the dock asks for a window reload; anything else without a stream reads as not running, and the dock starts a hub ([Dock start](#hub-lifecycle)).
- **Look.** Colours are VS Code's Light Modern and Dark Modern theme values, chosen by the Settings window's General → Appearance → Dock theme setting (`system`, `vscode`, `light` or `dark`, kept in `dock.json`, default `system`). The Settings window drafts the dock theme alongside the configuration draft; Save persists it to `dock.json` and applies it to every dock window and popup. Discard restores the saved choice, and closing with a changed theme asks to save or discard it. A failed dock save keeps the previous theme and reports the error. System follows the operating system; Light and Dark override it. In VS Code mode, the dock uses the focused window's `activeColorTheme.kind`, reported by the extension on focus, theme changes and connection to the authenticated `POST /window/theme` route as `{theme: 'light' | 'dark', at}`. High-contrast kinds map to light or dark. The hub retains the latest timestamped report in memory and includes `theme` in dock snapshots, ignoring older reports. The dock uses System until a report arrives and while disconnected. The last report remains in force when VS Code loses focus or closes, until another window reports or the hub restarts. Custom palette colours are not copied. `App.axaml` defines the dock's own brushes and also redefines the Fluent theme's control keys (`TextControl*`, `ComboBox*`, `Button*`, `AccentButton*`), so the Settings window's inputs and buttons take VS Code's input, secondary-button and button colours without per-control styles; a `link` button class draws the Settings window's file path in VS Code's link colour; marks use `codicon.ttf` from `@vscode/codicons`, and Running and Triaging spin.

## Browser extension

`extensions/chrome` is a Manifest V3 extension (PRD R56, R74), built by `npm run build` into `extensions/chrome/dist`, which the operator loads unpacked from `chrome://extensions` with Developer mode on, and reloads there after a rebuild.

`extensions/firefox` builds the same source for Firefox into `extensions/firefox/dist`, and `npm run package --workspace @switchboard/firefox` zips it into `extensions/firefox/switchboard-firefox.xpi`. Release Firefox installs only signed extensions, so the operator installs the `.xpi` in Firefox Developer Edition or Nightly with `xpinstall.signatures.required` set to `false` in `about:config`, or loads `dist/manifest.json` from `about:debugging` until Firefox restarts. The build changes only what Firefox requires ([mechanics.md](mechanics.md) M42), and `src/firefox.mjs` refuses a Chrome manifest or `content.css` it no longer recognises:

- The manifest is Chrome's with `background.scripts` in place of `background.service_worker`, an add-on ID `switchboard@switchboard`, a minimum version of 140, and the hub's host permission without its port, `http://127.0.0.1/*`, because Firefox matches nothing with a pattern that has a port. Below, "service worker" means Firefox's background script, which also stops when idle and is woken by the same events.
- esbuild replaces the global `chrome` with `browser`, whose calls return promises, and sets `FIREFOX`, so a query mark's removal passes `loadReplace` to `tabs.update`: Firefox can commit the marked URL before the load restarts, and the unmarked load then replaces its history entry. `content.css` loads the font from `moz-extension://__MSG_@@extension_id__/codicon.ttf`, which Firefox resolves to the extension's UUID.
- Firefox lists MV3 host permissions as optional; when they are not granted, the board shows nothing, and the operator grants them in the extension's Permissions tab in `about:addons`.
- Firefox has no `tab.pendingUrl`, so a tab's kind is read from `tab.url`, which is `about:blank` for a new tab whose first navigation has not committed.

- The content script runs on every `https://github.com/*` page, because GitHub opens a project without a page load, and acts only while the page has `[data-board-column]` elements. The service worker reads `GET /snoozed` and sends `POST /snooze` for it, because a content script on github.com cannot read a loopback address; the manifest's only host permission is `http://127.0.0.1:47615/*` in Chrome and `http://127.0.0.1/*` in Firefox.
- It reads the snoozed URLs when a board appears, every 60 seconds, when the tab becomes visible and after a snooze from the page. A failed read counts as none snoozed.
- A card's issue is its title link (`h3[id^="board-card-title-"]` inside an `a`), compared as `owner/repo#number` in lower case. GitHub empties the content of a card out of view, a hidden one included, so the script keeps each card's issue by `data-board-card-id`; a card it has never seen rendered stays shown until it renders.
- It marks a snoozed card `data-switchboard-snoozed` and a shown column `data-switchboard-shown`, and `content.css` hides marked cards in columns that are not shown. The link is a centred button appended to the column's scrolling card list (`[data-dnd-drop-type="card"]`), so it follows the last card shown. A `MutationObserver` on child lists reapplies the marks 50 ms after GitHub renders; a pass that changes nothing makes no mutation, so the script does not trigger itself.
- Card pills (PRD R67): `src/pills.ts` reads `GET /cards` through the service worker (message type `cards`), with the same triggers as the snoozed read, and runs its own `MutationObserver`. It puts a `.switchboard-pill` span after the card header's issue reference (`[id^="board-card-header-title-"]`) of each card whose title link's issue key matches a card's `url`; GitHub issue URLs are the only ones that match. The pill's text is the playbook, its namespace in a muted span, or the group name when the playbook is null; `data-switchboard-group` is the group, or `snoozed`; an unsnoozed card in `blocked`, or in `review` with the mark `send`, `review` or `finished`, also gets `data-switchboard-yours`, which `content.css` gives GitHub's attention colours. A card's `mark` is the row's mark from `markOf` in `group.ts`, so the board and the dock share one rule; the pill puts it first as a `span.switchboard-mark` with `data-switchboard-mark` holding the same codicon's glyph from `MARK_GLYPHS` in `packages/core/src/group.ts`, at 16px in the codicon font, which the build copies from `@vscode/codicons` to `dist/codicon.ttf` and `content.css` loads through `web_accessible_resources`, and the tooltip adds `MARK_TITLES[mark]`. The `running` and `triaging` marks spin even when the browser reports `prefers-reduced-motion`, as the dock's do. The font, unlike an SVG of the same paths, renders the 1px strokes evenly at fractional display scales, and GitHub's content security policy does not block the extension's font. A card with a null or missing mark, as from an older hub, has no icon; an unknown mark fails the read. A pass leaves an unchanged pill alone, so it makes no mutation. A failed read, including a 404 from an older hub, removes every pill. `groupOf`, `triageLabel` and the `Card` type are in `packages/core/src/group.ts`, which imports only types, so the History webview and the browser extension import it as `@switchboard/core/group` without bundling the store.
- Card menu (PRD R66, R69): `src/menu.ts` watches `body` with a `MutationObserver` for a `ul[role="menu"]` that GitHub's Primer renders in `#__primerPortalRoot__`, outside the card, when a card's More actions button opens. `menuCard` finds the card by the button in a `[data-board-card-id]` whose `aria-labelledby`, the id of its More actions tooltip, matches the menu's. Before the menu paints, it appends a copy of the menu's divider and items cloned from the menu's first plain item, so they keep GitHub's hashed class names, with ids, shortcuts and trailing visuals removed and a codicon as the leading visual: **Open in Switchboard** (`vscode`) for any card whose issue `GET /cards` lists, and outside `done`, **Snooze in Switchboard…** (`clockface`) or, when the card's `snoozed` is true, **Unsnooze in Switchboard** (`debug-restart`). A menu with no plain item to copy gets none. Each pass compares the wanted items, kept in the menu's `data-switchboard-items`, and replaces them only when they differ, so an open menu follows a cards read that changes the card's group or `snoozed` or drops it, and a pass that changes nothing makes no mutation. The issue's card comes from the cards read that the pills already make (`watchPills` passes each read it accepts, not one a later read overtook, to an `onCards` callback, from which `main.ts` keeps `cardsByIssue`), so a hub that does not answer, or one older than `/cards`, adds no items. Primer's focus zone includes the appended items for ArrowDown. An item runs on click, Enter or Space, stops the event reaching GitHub, and dispatches Escape on the menu, which GitHub closes, returning focus to its button.
- Snooze (PRD R66): `snoozeMenus` in `src/snooze.ts` opens a fixed-position popup in `body` under the More actions button, or above it when the viewport has no room below, and focuses its first choice after GitHub's focus return. It lists `snoozeChoices` from `@switchboard/core/snooze`, a subpath export that keeps the store and other Node modules out of the browser bundle. A choice goes to the service worker as `{type: 'snooze', url, until}`, which it posts to `POST /snooze`; Unsnooze sends `{type: 'unsnooze', url}` for `POST /unsnooze` with no popup, both with `Content-Type: application/json`. On success the popup closes, the board reads `/snoozed` again, which hides or shows the card, and the pills read `/cards` again, so the menu and pill take the new state; on failure the popup shows the hub's error. A scroll outside it, Escape or a click outside closes it.
- Open in Switchboard (PRD R69): besides the card menu's item, a click on a `.switchboard-pill`, or Enter on it, since the pill is focusable (`tabindex=0`, `role=link`), is caught by capturing listeners on the document in `src/open.ts`, before GitHub's handlers would open the card's side panel, and navigates to the `vscode://` URI of the card's title link; the pill's tooltip says it opens in VS Code. The browser extension does not read a card's `links`.
- Switchboard tab group (PRD R74): the dock's `Switcher.OpenUrl`, which every link the dock opens goes through, adds `Switcher.TabBookmark` (`#switchboard-tab`) to a URL with no bookmark, and otherwise `Switcher.TabParameter` (`switchboard-tab=1`) last in the query, before the bookmark, which stays unchanged; `TAB_BOOKMARK` and `TAB_PARAMETER` in `src/tabs.ts` hold the same strings. The service worker checks every top-level `webNavigation.onBeforeNavigate`, because Chrome's URL filters ignore the bookmark, and for a URL `dockLink` recognises on the first navigation of a tab that `tabs.onCreated` reported (`firstNavigations`), as Chrome creates one for a link from Windows, so a reload, Back or Forward to a URL that still has the bookmark is not placed again, runs `placeTab`, one navigation at a time (`tabPlacer`), so a second click that arrives first finds the group and tab the first left: a query mark is removed with `tabs.update` at once, which restarts the navigation; the tab joins the window's group titled `Switchboard`, found with `tabGroups.query` or created cyan; and when the group has another tab of the same kind, the new tab moves to that tab's index, read again after joining, and that tab closes; when it has left the group meanwhile, nothing moves or closes. `webNavigation.onCommitted` removes a bookmark mark by loading the URL from `bookmarkRemoved`, with a bare `#`, a same-document navigation that adds a history entry; without the `#` Chrome loads the page again. A tab is never focused, because Chrome opens a link from Windows in a new active tab and brings its window forward. A link's kind is `tabKind`: `github.com/issues`, `github.com/pull`, else host and first path segment. A placed tab keeps the kind of the link it was placed for, because a site such as Zoho Desk redirects the link to another address; `placedKinds` keeps it in `chrome.storage.session` under one `placedKind:<tab ID>` key per tab, so concurrent writes for different tabs do not overwrite each other, and session storage outlives the service worker. `tabs.onRemoved` and `tabs.onUpdated` with a `groupId` of -1 or of another group drop a tab's kind when it closes or leaves the group. A tab with no kind, dragged in or placed before the browser restarted or the extension reloaded, which clear session storage, has the kind of its address. The `tabs` permission lets the extension read the group's URLs, `tabGroups` find and name the group, `webNavigation` see the navigation, and `storage` keep the kinds ([mechanics.md](mechanics.md) M28).
- The DOM hooks are GitHub's, not a contract; `test/fixtures/column.html` records them from the public roadmap board on 2026-10-07, and `card-menu.html` a card of the operator's signed-in board and its opened More actions menu on 2026-10-08, scrubbed to `github/roadmap#1090`.

## Settings window

PRD R54. A separate, resizable dock window, **Switchboard Settings**, one at a time; Open Settings in the dock's header menu brings the open one forward. The page logic is plain C# in `apps/dock/src/Switchboard.Dock/Settings/` (`EditorState`, `SettingsFields`, `SettingsPages`, `SettingsEditor`), and `Views/SettingsWindow.cs` draws it.

- The hub reads and writes settings.json through `packages/hub`'s `config.ts`: `POST /config/read` answers `settings` (`path`, `version`, `value` and `error`, valid or not), the permission modes, Codex's permission modes, the providers, template variables and source kinds the fields offer, `inUse`, the open work items per playbook, `enabled`, whether each configured source is on, and `configDir`; `POST /config/check {settings}` answers `{errors}`; `POST /config/save {value, version, configDir}` writes the whole file as formatted JSON and answers `{saved, version}` with the version of the text written, or 409 `{errors}`. A save for another `configDir` is refused with 409. Checks (`checkSettings`) use what the hub applies on load, `parseSettings`, the own `parse*Config` of each source that is on and `parsePlaybook` for each entry, plus `templateError` for `setupPrompt` and each template, because the hub finds an unknown variable only when rendering the classifier instructions or a session prompt fails. A playbook's errors read `playbooks.<name>: <error>`. The hub's watcher reloads what the window writes, as it does a hand edit, and then sends `config` on the dock stream, which makes the window read the file again; so does each new connection of the dock's stream, such as to a hub started on another config folder. A read from another folder drops the draft and says so on the window's status line. The window needs a running hub.
- The navigation lists **General**, each configured source with **Add** entries for the sources not configured, the schedules with **New schedule**, and the playbooks by namespace with **New playbook**. Each namespace's name opens its table page. A page whose part of the file has unsaved changes (`sessions` and `triage`, `sources.<name>`, `schedules.<name>`, `playbooks.<name>`, or any playbook of a namespace) shows a dot, and a page with errors shows an error mark.
- A schedule page (`schedule:<name>`, PRD R82) edits `schedules.<name>`: Playbook, a choice of the file's task playbooks; Repo root; Runs (`every`), whose Only by hand removes the key; and, by `every`, Day as a weekday choice for `week` or a whole number for `month`, and Time (`at`) for any period. Changing Runs removes `day`, and Only by hand also removes `at`, and redraws the page. **Remove schedule** removes the entry from the draft. The New schedule page (`new-schedule`) takes a name, checked as lowercase letters, digits and hyphens not already used, and Create adds an empty entry and opens its page, whose errors name the fields to fill.
- The window holds one draft of the whole file (`EditorState.Draft`) and the version it started from, and never saves on its own. A bar across the bottom of the window holds the status (**Saving…**, **Saved** or **Unsaved changes**, with the number of errors, or that the file cannot be read), a warning when settings.json changed on disk under the draft, and **Save** and **Discard**. Save, or Ctrl+S from any field, is unavailable while settings.json changed on disk under the draft; otherwise it first runs a check due for an edit, lists the errors in the bar instead of saving while any stands, and otherwise sends the draft; a refusal stays in the bar until the next edit, discard or successful save, and the draft is kept. An edit made during a save continues from the version written; a second Save during a save, including Save in the close question, waits for it. Discard drops the draft and reads the file again. Closing the window with unsaved changes asks **Save changes to settings.json?** with Save, Discard and Keep editing; a refused Save keeps it open. Closing the dock closes the window without asking. Add source, Remove source, Create on the New playbook page and Delete change only the draft; Delete asks in a modal window, which names how many open work items use the playbook, read from the hub when Delete is pressed. Text typed on the New playbook page before Create is not a change to the file.
- Each field is a row: its label on the left, with an info icon when the field has help (`Field.Help`), shown only in the icon's tooltip, and the input on the right. A multiline box grows with its text, up to 20 lines for a prompt and 8 for a list, and then scrolls. Adjacent checkboxes with the same `Field.Group` share one row under that label, each explained by its own tooltip. A source's `Advanced` section (`Section.Advanced`) starts collapsed, stays open across redraws once opened, and opens when a check places a new error on one of its fields.
- The settings pages edit their sections of the draft. A field left empty removes its key, so the default applies, and the placeholder shows that default. `automationAgentIds` is the exception: its default is not empty, so an absent key shows the default list, and an emptied list is saved as `[]`. Keys the window has no field for are kept. A source's own errors block a save only while the source is on, so a source that is off can be saved incomplete. Source pages have no on/off field; the navigation notes a source that is off. Adding a source adds `{}`, off until the operator turns it on in the dock's header; removing a source deletes its key, and its work items stay.
- A playbook page edits its entry under `playbooks`. A triage playbook shows only its description, its kind, Rates importance and its classifier instructions. A task playbook has a **Start** row with Automatically (`autoStart`) and Needs a worktree (`requiresWorktree`), a **Reports** row with a checkbox for each of its `reports`, and, while `approval` is checked, an **Approve sends the work** checkbox below them; unchecking `approval` clears `approvalSends`. **Return of** lists `returnOf`, one playbook per line, and **Focus page** chooses `focus`: Any page, The ticket or The pull request; changing the kind to triage clears both. The window writes an entry with only non-default keys, except `autoStart` and `requiresWorktree` on a task playbook, in the order description, kind, autoStart, requiresWorktree, workdir, reports, approvalSends, returnOf, focus, rates, provider, permissionMode, model, template; the permission mode offers the modes of the playbook's agent, and its default and the model's name that agent's `sessions` settings; the template is kept as typed. An edit that returns an entry to its fields on disk restores the entry as the file has it. An entry the window cannot read into fields, including one with a key the hub does not accept, shows its error and Delete, so the operator fixes it by hand or deletes it.
- A namespace page (`namespace:<namespace>`) is a table of the namespace's playbooks: one row per playbook, whose name opens its page and whose description is the name's tooltip, and one checkbox column per flag (`SettingsFields.TableColumns`): Auto and Needs worktree under **Start**, each report and Sends (`approvalSends`, enabled only with Approval) under **Reports**, and Repo root (`workdir: repoRoot`), for task playbooks; Rates for triage playbooks. A cell that does not apply to the row's kind, or a row whose entry cannot be read, has no checkbox. A checkbox edits the draft, the row shows a dot while it differs from the file, and the row's errors show under it; an update changes the drawn checkboxes in place, so a click during a check is not lost. A namespace with no playbooks left says so.
- The draft is checked 250 ms after the last edit and after each read; an answer to an older check is dropped. The window places each error on the field whose path it names (`FieldOfError`, `PlaybookFieldOfError`); an error that names no field shows at the top of its page. While the operator types, only the navigation, bar, notes and errors are redrawn, so the field keeps focus; a full redraw, such as after a reload, puts focus and the caret back in the same field.
- settings.json is read with a SHA-256 version. A save sends the version the draft started from, the hub refuses it when the file on disk no longer matches, and a successful save answers the version it wrote. With no draft, a read shows the file, and a draft equal to the file as read before or after is dropped; any other draft whose file changed is kept, with the bar's warning, and cannot be saved, so the operator discards it to take the file on disk. Writes go through a temporary file and a rename, like the source toggles.
- The settings.json path, shown on each page, opens the file in the VS Code window used last, through the dock's `openUrl` window command.

## Store

- One SQLite database, `~/.switchboard/switchboard.db`, opened through Node's built-in `node:sqlite` (M1). No native module, so VS Code's Electron upgrades do not require rebuilds.
- The hub is the only process that opens the database. The extension and the `switchboard report` CLI go through the hub's HTTP server, so there is no cross-process locking.
- WAL mode; one write transaction per flow step, so a crash leaves each work item in its last committed state.
- Core accesses the database only through a store interface, which isolates changes to the `node:sqlite` API. Tests use `:memory:`.
- Schema changes are numbered migrations applied by the hub at startup, recorded in `PRAGMA user_version`.
- Activity log (PRD R59): `events` holds each flow event that wrote a row or was refused (`at`, `type`, `actor` of `operator`, `session`, `source`, `triage` or `hub`, the ticket, work item and session it names, `detail` as JSON without prompts, contexts or polled lists, and `refused`), and `changes` each row it wrote (`entity`, `entityId`, `op` of insert, update or delete, the owning ticket, work item and session, and `fields` mapping each changed field to its old and new value). `handle` opens an event with `Store.beginEvent` before applying it, and a `wake` event first for snoozes that end; `#insert`, `#update`, the worktree, link and paste upserts and `deleteTriage` read the row before writing and log the difference in the same transaction. Operator actions, reports, failed starts and failed stops are stored even when they change nothing; other events only when they change a logged field. Comments (PRD R87) are written with `Store.addComment`, which does not log the row: the `comment` event's detail holds the text, as the snooze event's holds `Ticket.snoozeComment`. Fields that change on every poll or status change (`lastPolledAt`, `sortAt`, `scopeAt`, `statusAt`, `runStartedAt`, `stageAt`, `queuedAt`, `stateAt`, `releasing`, a link's or paste's `reportedAt`) and the order fields `readyAt` and `orderAt` are not logged, so a move shows in History as its `move` event, with `after` as its detail; `taskPrompt`, `approvalPrompt` and `context` are logged as `true`; text over 2000 characters is cut. A refusal naming no known ticket is not stored. The hub logs a refusal the flow never sees with `Runtime.refuseReport`, which calls `recordRefusal`: a `/report` request that fails validation and names a session, a worktree report naming no git worktree, and a link report its source refuses. It keeps only the report's kind and short text fields, never a prompt. `deleteWorkItem` deletes the work item's changes and its triages' (found by `entityId`, because a pick attaches pool triages logged without a work item) and events left with no changes. The migration stores a `recording` event, whose time is `recordedSince`, and `reconstructed` events with a `fact` for what the existing rows showed: work item created, done, last stage and an approval, blocked or failed status; triage start and end; session start and end; links and pastes. The tables have no foreign keys and are kept forever. `historyRevisions` holds a counter per ticket that every write to its log advances, deletions included; `historyRevision` reads it.
- Which sources are on is in the `sourceStates` table, because the dock's header toggles it (PRD R3).
- Not in the database: settings and playbooks, in `settings.json`, which the operator edits and can keep in git; session transcripts, which Claude Code stores, and which sessions find by `nativeSessionId`; the [debrief](#friction-debriefs) state and log, which the friction-review skill reads; and the pending opens and window commands in `window-queue.json` ([Open in VS Code](#claude-code-runner)), which expire after 2 minutes.

## Playbooks

A playbook is an entry under `playbooks` in settings.json, keyed by its name, `<namespace>:<name>`; `template` holds its prompt template and the other keys its settings. Switchboard has no built-in namespaces or playbooks; the entries define them.

```json
"playbooks": {
  "support:defect": {
    "description": "Zoho ticket reporting behavior that may be a defect",
    "autoStart": false,
    "requiresWorktree": false,
    "permissionMode": "auto",
    "reports": ["done"],
    "template": "Research Zoho ticket {{ticket.sourceKey}}.\n{{ticket.context}}\nReport progress with `{{report}} stage {{session.id}} <stage>`."
  }
}
```

- Template variables: `{{ticket.source}}`, `{{ticket.sourceKey}}`, `{{ticket.ref}}`, `{{ticket.title}}`, `{{ticket.url}}`, `{{ticket.context}}`, `{{session.id}}` and `{{report}}`. `{{report}}` is the report command prefix, `<node> "<home>/hub.js" report`, where `<node>` is `sessions.nodePath`. Rendering fails on an unknown variable.
- Keys: `description` (required, one line), `template` (required), `autoStart` (default false), `requiresWorktree` (default false), `provider` (`claude` or `codex`; default `sessions.provider`, PRD R22), `permissionMode` and `model` (defaults from the `sessions` settings of the playbook's agent; a Codex playbook's mode must be `auto`, `plan`, `dontAsk` or `bypassPermissions`), `kind` (`task` by default, or `triage`), `reports` (a task playbook's list of `done`, `approval`, `worktree`, `playbook` and `paste`; none by default), `approvalSends` (Approve sends the session's work, which sets the approval row's mark; false by default, and allowed only when `reports` lists `approval`), `rates` (a triage playbook's classifier rates immediacy and severity, which its body must define; false by default), `returnOf` (a task playbook's list of playbooks whose earlier work items Returned also counts, PRD R51; each a valid name other than its own, none by default), `focus` (a task playbook's page, `ticket` or `pr`, that triage's focus must be on, PRD R79; any page by default), and `workdir` (`worktree` by default: the ticket's worktree when one exists, otherwise the repo root; or `repoRoot`: always the source's repo root, for playbooks whose skills belong to that repository). Any other key, or a value of the wrong JSON type, leaves the playbook out. `parsePlaybooks` in core reads each entry on its own, in name order, which is the order the classifier lists them, so an invalid playbook is left out with its error, `<name>: <error>` in the dock, and the rest load.
- `description` tells the classifier when to choose the playbook. Adding a playbook is adding its entry: the hub reloads settings.json, and the classifier sees its description. Edit the triage playbook only for a rule that must take precedence over the descriptions.
- A triage playbook's body may use only `{{playbooks}}`, which renders the task playbooks in the source's namespace as `- name: description` lines where the instructions need them. A body without it gets the same list appended under "Choose one playbook:". Any other variable fails the triage, and the settings editor refuses to save it.
- A source's triage playbook has `kind: triage`. Its body is the classifier's system prompt. Triage playbooks are never offered to the classifier as choices.
- Each source's `namespace` setting limits the classifier's choices to that namespace's task playbooks, such as `dev` for GitHub and `support` for Zoho Desk and Forum.
- Every Claude session gets the report contract as `--append-system-prompt`, and every Codex session as `-c developer_instructions=…` on each run, apart from its prompt, so the session list shows only the prompt, and each gets it again from the contract hook after each compaction (mechanics M30, M31). A Codex session's contract offers the `question` report, with its question also written as its final message, in place of `AskUserQuestion`. The contract opens with the line `Report to Switchboard with these commands:`, the line the Support `support-process` skill looks for: the commands the session may send, with the session ID, each with its condition and the cap on its text (PRD R23). The contract leaves out `task`, which the hub still accepts, so a session sends one only through a skill the operator invokes (PRD R68). A playbook's task session gets `stage`, `link`, `task` and the playbook's `reports`; with neither `done` nor `approval`, the contract tells it to end its turn when the work is finished, so the work item becomes `finished`, in Ready for review. Setup and approved-prompt sessions get `stage`, `worktree`, `done`, `link` and `task`, and an ad-hoc prompt gets all but `playbook`. The session row stores its reports, and the hub refuses any other report with "This session's report contract does not offer the <kind> report." and CLI exit code 3. It reports a `link` for each GitHub issue or pull request that tracks or delivers the work, not a related, base or parent one. Before applying a `link`, the hub calls the ticket's source's `checkLink`, when it has one: the GitHub source reads a pull request in its configured repository (`PULL_REQUEST_QUERY`) and refuses it unless it closes the issue in that repository or its head branch names the issue by `branchPattern`, which covers a stacked pull request that does not close the issue, and refuses a pull request number GitHub cannot resolve. A pull request URL is recognised by `new URL` on `http` or `https` and the host `github.com`, so a port, a tab such as `/files` or a fragment does not skip the check. A pull request that closes more issues than the 50 one read lists, none of them the ticket, is left unchecked. The hub logs the refusal with `Runtime.refuseReport` and the CLI exits 3. Other links, other sources, a failed check and a check over `REPORT_CHECK_MS` accept the link, the last two with a log line (PRD R52). When the session needs the operator for a question or a choice, or cannot continue without them, it asks with `AskUserQuestion` and waits, which keeps its context live and gives the row the Answer a question mark as `waiting`, in Blocked on you unless the work item has been ready; it writes no file and sends no report for a question. When its work is ready but posting or publishing it needs the operator's approval, it reports `approval` with the prompt that would do it, such as `/review-pr pr:123 publish`, a summary of what the prompt publishes, and the file holding the drafted text, if any, and ends its turn; Approve runs the prompt in a new session with no memory of this one, so the prompt names what it acts on. Before an approval, a session offered `paste` reports each drafted text the operator pastes into the source by hand, such as a Support customer reply, with its label and file. The operator's skills read these commands through their `sb-session-reports` skill, which writes each as a `switchboard <kind> <arguments>` call. `{{report}}` lets a template add its own report calls.

## Triage

Triage follows Ground Control's classifier (GC R38, M31).

1. The source plugin builds the triage context: it fetches the ticket's text, clips each field at a word boundary to a size limit, and formats it with authors, status changes and assignees. Ground Control clips the issue body and each comment to 2,000 characters. The hub puts a `Current time: YYYY-MM-DD HH:MM UTC` line before the context, in the form sources use for event times, so the triage playbook can tell how recent a request is.
2. The hub chooses the classifier from `sessions.provider` before reading the source context. `triage.model` is its optional model override; `triageModel` drops recognized names belonging to the other provider, logs the fallback and records a null model on the triage. Unknown names pass through. The configured value is preserved. For Claude, the classifier runs `claude -p --output-format json --json-schema <schema> --no-session-persistence --setting-sources "" --tools "" --strict-mcp-config --system-prompt <triage playbook with the playbook descriptions rendered in, then, when the context has anchors, how to choose the focus>`, with the context on stdin. Stdin avoids the Windows 32,767-character command-line limit (M31). Because `--setting-sources ""` also skips the `env` block of Claude's user settings (M3), `claudeRouting` passes that block's `ANTHROPIC_BASE_URL`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_API_KEY`, `ANTHROPIC_CUSTOM_HEADERS`, `HTTPS_PROXY`, `HTTP_PROXY`, `NO_PROXY` and `NODE_EXTRA_CA_CERTS` string values in the run's environment, over the hub's own. Model variables stay out, so triage keeps its model; Bedrock and Vertex are not carried, because they need further provider-specific variables.
   For Codex, `classifyCodex` runs `codex exec --json --ephemeral --ignore-user-config --ignore-rules --skip-git-repo-check` in a temporary folder under the Switchboard home, with the configured Codex executable and environment. It uses a read-only sandbox and no approvals, disables project instructions, web search, shell tools, apps and hooks, and sends the triage prompt and context on stdin. `--output-schema` and `--output-last-message` name temporary files removed after success or failure. `codexRouting` parses `config.toml` and carries the model endpoint that `--ignore-user-config` drops (M42) as `-c` overrides placed before the classifier's own: `model_provider`, `openai_base_url`, and the selected provider's `model_providers` entry written as one inline table, so its credentials appear in the process's arguments. A missing settings file or `config.toml` carries nothing; one that cannot be read or parsed fails triage without running the classifier, because the run would bypass the operator's endpoint, and the error names the file without quoting it. A failed or incomplete turn, process error, timeout or invalid result fails triage; it does not retry on Claude.
3. The schema is `{playbook: enum of the source namespace's task playbook names}`, plus `immediacy?: URGENT | BLOCKING | NON-BLOCKING` and `severity?: HIGH | MED | LOW` when the triage playbook has `rates: true` (PRD R50), and `focus?: enum of the context's anchor ids` when the source returns anchors (PRD R79). Claude reads `structured_output`; Codex reads its last-message file and requires every schema property. Both use core's `validateClassification`. Without `rates`, it discards any rating the model returns; a value outside the enum is stored as empty.
4. The focus (PRD R79): a source's `ContextResult.anchors` lists `{id, url, page}` for each page and comment it tags in the context, such as `[c3]`; the GitHub source tags the issue `[ticket]`, its pull request `[pr]`, and every comment with a URL `c1`, `c2`… by `createdAt` across the issue, pull request and review-thread comments, ties in section order. Zoho Desk and Forum return none, so their schema has no `focus`. A choice whose playbook has `focus` renders as `- name: description (page: pull request)` or `(page: ticket)`. The hub sends the chosen id and the anchors with `triage-succeeded`, and the flow stores `focusUrl(anchors, id, playbook.focus)` in `Triage.focus`: the chosen anchor when it is on the playbook's page or the playbook has none, else the playbook's page anchor, else the ticket's.
5. Nothing new (PRD R80): the core's `triage` action carries `handled`, `{at, playbook}` of the ticket's other work item with the latest `at`, where `at` is the `startedAt` of its first task session with a `shortId`, so a start that failed does not count, or its `doneAt` when the operator marked it done without a session; null for a pool triage or when no work item qualifies. A source's `ContextResult.activityAt` is the time of the latest activity by anyone but the operator that can ask for an action, null when there is none, and omitted by a source that does not report it. The GitHub source takes the latest `createdAt` of the issue, pull request and review-thread comments and `submittedAt` of the pull request's reviews, and the `committedDate` of its head commit, which the pull request line shows as `Head commit: <login>, <time>`, whose author is not one of `logins`, bots included, with a commit whose author has no GitHub account counted as someone else's; Zoho Desk and Forum omit it. Only activity the context holds counts, so a non-operator comment clipped out by five later issue comments is missed; a reply in a review thread past its first three comments counts through its review. A rebase updates `committedDate`, and a pushed commit made long before the push keeps its old date. With `handled`, the hub puts an `Earlier work: …` line after the current time naming the earlier playbook and time, which makes earlier activity background. When `nothingNew(handled, activityAt)` holds, `activityAt` is null or no later than `handled.at`, compared to the millisecond, the line adds that nothing is newer and the hub sends `stale: true` with `triage-succeeded`; the flow then leaves the work item `unstarted` whatever the playbook's `autoStart`, with `error` set to `MESSAGES.nothingNew`, which the row's line 3 shows and Start clears, and logs `stale` in the event's detail, which History shows.

Triage has no tools, settings, MCP servers or saved transcript, so it is not a session and does not count toward the one-session-in-a-turn rule (PRD R17). The hub runs at most one triage per work item at a time, at most `triage.concurrency` at once (default 2), with a `triage.timeoutSeconds` limit (default 180).

A classifier error, an unparsable result, a timeout, or a playbook name outside the enum fails the work item with that error (PRD R37). A triage interrupted by a hub shutdown is not a failure: the work item stays `triaging`, and triage runs again when the hub starts.

## Flow

1. Poll a source. For each ticket, compare its assigned state with `Ticket.assigned`. A poll that fails or is incomplete, such as one that hits the page limit, updates nothing.
2. When a ticket enters the assigned state, create a work item (`triaging`) and run triage.
3. Store the triage result. If the playbook's `autoStart` is false, or the triage found nothing new (PRD R80), the work item is `unstarted` until the operator starts it (`start`). `awaiting-approval` is used only for an approval report, and `approve` applies only to it.
4. If the playbook's `requiresWorktree` is true and the ticket has none, start a setup session (`setup`) running the source's `setupPrompt`. The setup session succeeds when a worktree is linked, by report or by the branch convention, and the session's process ends, or, for a released session, its turn ends (`setupState`), since an interactive tab keeps the process. If its process ends with no worktree linked while the ticket is assigned, the work item fails; a turn end without one leaves it in `setup`. The failure reads "Setup ended without a worktree."; a later resume of that session (`running` or `waiting` after `ended` or a turn end) returns the work item to `setup`.
5. Render the playbook and start the task session (`running`). `sessionPrompt` fills its session ID and then appends `WorkItem.guidance`, when set, after a blank line; an approved prompt takes none (PRD R77). It reports stages, a worktree link if it creates one, and done or approval.
6. When the task session reports done, the work item is done with reason `session`. When its turn or process ends with no report, the work item is `blocked`, with the done or approval report the prompt offered as its reason, or `finished` when the prompt offered neither (`endRun`). A turn that ends `failed` blocks it with the error kind, because the session can still be resumed. A `blocked` or `finished` work item whose session runs again becomes `running`.
   - When a session of an `awaiting-approval` work item changes to `running` with no detail, as when the operator answers its question or resumes it, the work item becomes `running` with `approvalHeld` set and keeps its approval fields. A change to `waiting` leaves it in `awaiting-approval`. A new approval or done report from that run applies as usual. A turn end, a process end or an operator stop with no report returns it to `awaiting-approval` with the kept approval, and `error` holds the cause of a failed turn or a stop. Any other status, such as `blocked` after a done report while the ticket is assigned, keeps the approval fields; only Approve, or Retry after the approved run failed to start, starts their prompt. Core clears `approvalHeld` on every other status change. A run whose `running` state Switchboard never sees change, such as a resume between two roster reads with hooks off, holds nothing.
7. When a ticket leaves the assigned state, an open work item that never had a session is deleted with its triages and pastes, and one with no active session is done with reason `unassigned` and no warning. A sessionless work item whose triage is running gets `unassignedAt` instead, so the triage row keeps its `triage.concurrency` slot; the triage's success, failure or cancellation deletes it, unless the ticket returned and cleared `unassignedAt`. Work item IDs are `AUTOINCREMENT`, so a deleted ID is never reused, and a late result for a deleted triage finds no row and is ignored. With an active session, that is deferred until the session reports or ends (PRD R10).

Pool tickets (PRD R47, R48):

- When a poll shows a ticket newly in the pool, the core starts a pool triage for the ticket; its result or error stays on the ticket.
- A pick of a pool ticket whose triage has a result creates the work item with that playbook, attaches the pool triage, and queues it as an operator start, skipping the wait in step 3. The task session's skill claims the ticket.
- A ticket that enters the assigned state while it has an open work item gets no second work item; the claim made by the task session is seen this way.

An ad-hoc prompt creates a ticket and an `unstarted` work item, with the typed prompt as the task prompt and the chosen repo root as the working directory; Start then goes to step 5. The `adhoc` action's `start: true`, sent when the operator checks Start automatically, makes the work item `queued` at once, so it goes straight to step 5 (PRD R6). A `task` report creates the same ticket and `unstarted` work item, with its `parentId` set (PRD R68). A `register` event creates the same ticket and work item, `running`, with no task prompt and the session's working directory as the repo, and the session already started, released and external (PRD R81). A task report's ticket has `sourceId` `task`, and Delete sets it on each follow-up of the work item it deletes, so the origin outlasts `parentId`. With no playbook, the row's playbook slot is `adhocLabel` in `group.ts`: `task` when `parentId` is set or the ticket's `sourceId` is `task`, `registered` with no task prompt, else `ad-hoc`; History's section is titled the same way from the history's `prompted` flag.

Schedules (PRD R82) live in `packages/core/src/schedule.ts` and the flow's `runSchedules`. On each `tick`, before the event itself, `handle` walks `settings.schedules`. Each schedule's ticket has source `schedule` (`SCHEDULE_SOURCE`), key and ref its name, no URL, `assigned` true, the schedule's `repoRoot`, and the title of its playbook's description, else its name; the walk inserts it when first seen and updates its title and repo root when they change. `Ticket.lastPolledAt` is when the walk last checked the schedule, set at insert and on every tick, and `Ticket.sourceId` is `scheduleText(schedule)`, such as `every week on fri at 12:00` or `by hand`. A `sourceId` that differs from the schedule's text, because the schedule moved or was removed and added again, counts as no check: the walk stores the new text and the time and makes no run. A schedule ticket whose name settings.json no longer lists gets a null `sourceId`. History shows each change of it as `Runs <text>` or `The schedule was removed from settings.json`. `latestDue(schedule, now)` gives the latest local time at or before now that the schedule came due: today's or yesterday's time, the latest such weekday, or this or last month's day, cut to the month's last day; null for a schedule with no `every`. When it is later than the last check, the walk logs a `schedule` event with `{name, dueAt, skipped}` and, unless the ticket has an open work item (`skipped`), inserts a run: a work item with the schedule's playbook and no triage, `queued` when the playbook has `autoStart`, else `unstarted`, and `failed` with the cause when the playbook is missing or not a task playbook; the ticket's `scopeAt` becomes now, so the in-queue time counts from the run. A time before the schedule was first seen, moved or added again is not after the last check, so it does not run; one that passed while the hub was stopped is, so it runs once. The `run-schedule` action (Run now) refuses an unknown name and a ticket with an open work item, and otherwise inserts a `queued` run. A run starts in step 5 with `cwd` the ticket's `repoRoot`. The done report's source read finds no `schedule` source, so it is accepted unchecked (PRD R10); the snapshot counts no `returned` for it, and `retry` queues a failed run, which fails again while its playbook is missing or not a task playbook, as `startSession` checks.

Steps 4 and 5 start a session only when no other session of the ticket is `starting`, `running` or `waiting` and a slot is free; otherwise the work item is `queued` (PRD R17, R38). An `idle` or `failed` session, such as the approval session kept open in the VS Code Claude view, holds nothing back, so a work item can have several live sessions. Its active session is its latest session while that has not ended; only the active session holds a slot, and only the latest session changes the work item's status.

## Core decisions

`packages/core` decides; the hub acts. `handle(store, event, context)` runs inside one store transaction, applies one event, and returns the actions for the hub to run, or a refusal for an operator action or report that does not apply. The context carries the clock, settings, loaded playbooks, the report command prefix and a session ID generator. The hub runs each action and sends its result back as an event, so every failure reaches the work item.

## Claude Code runner

- Start: `claude --bg --permission-mode <mode> --settings '{"worktree":{"bgIsolation":"none"}}' -n <name> [--model <model>] --append-system-prompt <contract> <prompt>`, with no shell, so a leading slash command survives. Claude records the system prompt with the contract and sends that record on later turns and resumes, also from a process started without the flag, until a compaction; a woken background session reuses its saved flags (mechanics M30). The name is `switchboard · <playbook> · <source> <key>`. Claude's background service owns the process, so sessions survive VS Code and the hub. `--bg` ignores `--session-id`; the runner parses the short ID from `backgrounded · <id> · <name>` and matches it as a prefix against `claude agents --json` (GC M1, M33; mechanics M5). The start is confirmed when the roster lists it with a pid; a new entry has no pid for its first seconds. A session listed `blocked` with no pid on two reads in a row is waiting on a prompt before it starts, such as approving the project's MCP servers (mechanics M41): the start succeeds with `startPrompt`, and the core stores the session as `waiting` with the state detail `START_PROMPT` (`@switchboard/core/group`). The roster lists a gone process the same way, so `observe` keeps a `blocked` entry without a pid alive only for a session stored so; once the operator answers through Open in terminal, the pid appears and the roster and markers decide its state. Hook markers do not change it until then. The rows offer Open in terminal as its main control and no Open in Claude, and the core refuses `open-question` for it. A process that dies at the prompt leaves the same entry, so that session waits until the operator stops it. Otherwise a session not listed with a pid within 60 seconds fails the start.
- Permission mode: `auto` by default. In 101 Ground Control runs to 2026-10-03, the 95 in `auto` never waited for or were refused a permission; the only permission stall was in manual mode. Questions (`AskUserQuestion`) stall in every mode and show as `waiting`. The operator answers them, so Switchboard neither disallows the tool nor keeps a Bash allowlist.
- CLI: each `claude` command the hub runs (starts, stops, roster reads, triage, debriefs) runs `sessions.claudePath`, read at each use: `claude` by default, looked up on the hub's PATH. An absolute path's directory goes first on that command's PATH (`executableDirOnPath`), as for Codex. A command that cannot find the CLI reports `Claude Code was not found at <path>. Install it or set sessions.claudePath.`; one whose working directory is missing reports that directory instead. Open in terminal runs `sessions.claudePath` in the item window's terminal, which looks a bare name up on that window's PATH; the hub adds it to the terminal command as `executable` when a window claims the command, so a window gets the setting as it is then. An absolute path's directory goes first on the terminal's PATH, as for the hub's own runs.
- Environment: pass `CLAUDE_CONFIG_DIR` through exactly as the hub inherited it, and never set it. Setting it, even to `~/.claude`, moves where Claude reads folder trust (GC M62). Strip `ELECTRON_*`, `VSCODE_*` and `NODE_OPTIONS`.
- Trust: `--bg` exits 1 with `Workspace not trusted` in a directory Claude has not trusted; a linked worktree inherits its main checkout's trust (GC M62). The failed start shows that message (PRD R41).
- Background sessions inherit the service's environment, not the caller's, so per-run values such as the Switchboard session ID travel in the prompt (M33).
- Liveness: poll `claude agents --json` (without `--all`) every 30 seconds for every session a start confirmed, so a session resumed after its release is seen again. The roster alone decides liveness: a session is active while the last successful roster read lists it with a pid, and `ended` once a successful read that looked for it does not, so a start confirmed during a read is not ended by it. An entry without a pid is a process that is gone (GC M33). A failed read changes no session. Reads run one at a time; a read asked for during another runs once that one finishes, so an older result never ends a session a newer read revived. Hook markers only set the state of a live session, because a killed process leaves its last marker behind (GC M20). The roster `state` is the fallback when no hook marker exists: `working` maps to `running`, `blocked` to `waiting`, and `done` or `stopped` to `idle`.
- State: hook markers decide the observed state, following GC's mapping (GC M2, M20). The hub watches `<home>/activity/` and reads all markers 50 ms after a change, and also every 5 seconds. When the folder is removed or replaced, or the watch fails, it watches again after 1 second. Each new marker from an ended session can mean the operator resumed it, so the hub reads the roster once for it instead of waiting for the 30-second timer, and reads it again when another such marker arrives during that read:
  - `UserPromptSubmit`, `PostToolBatch` and `PermissionDenied` mean `running`, as do `SessionStart` with `source=compact` and `PostToolUse` or `PostToolUseFailure` for `AskUserQuestion` or `ExitPlanMode`, which end a question's wait before the rest of its batch resolves. A result of another tool does not end a wait, because a parallel tool can finish while one still waits for permission. After the operator approves a permission, the session stays `waiting` until the approved tool's batch resolves.
  - `PermissionRequest`, `Elicitation`, `PreToolUse` for `AskUserQuestion` or `ExitPlanMode`, and `Notification` of type `permission_prompt`, `worker_permission_prompt` or `agent_needs_input` mean `waiting`.
  - `Stop` means `idle`, or `running` with the detail `turn ended with background tasks` while background tasks remain.
  - On an interactive roster entry, `SessionStart` with another source means `idle`: a tab or terminal that resumed the session has run no turn, though the roster lists it `busy` while it loads (mechanics M25).
  - `StopFailure` means `failed`, with its error kind and message.
- Hooks:
  - The hub installs async command hooks for those events plus `SessionEnd` in `<CLAUDE_CONFIG_DIR or ~/.claude>/settings.json`. It preserves other entries, refuses to edit malformed JSON, adds missing entries at startup, and gives its own entries `sessions.nodePath` as their command. Its own entries are those whose command names `node` or `node.exe` and whose only argument is its script, so an operator's entry that only mentions the script stays. The `sessions.installHooks` setting is on by default; when it is off, the roster alone decides state. Turning it on while the hub runs installs both agents' hooks at once; turning it off leaves them installed, stops reading their markers and clears the hook errors.
  - The hook runs `<sessions.nodePath> "<home>/hook.mjs"`. It skips subagent events, always exits 0 and prints nothing, and writes `<home>/activity/<nativeSessionId>.json` atomically: `{v, sessionId, event, at, cwd, notificationType, source, toolName, backgroundTasks, error, errorMessage}`, with `errorMessage` capped at 500 characters. `SessionEnd` deletes the marker.
  - A debrief fork runs with `FRICTION_DEBRIEF=1`, and the hook writes no marker for it.
  - The hub also installs a synchronous `SessionStart` hook with matcher `compact`, `<sessions.nodePath> "<home>/contract.mjs"` with a 10-second timeout, because compaction drops the contract from the system prompt and a process resumed without `--append-system-prompt`, such as a VS Code tab, rebuilds the prompt without it (mechanics M30). The hook skips subagent events, posts the session ID to `POST /contract` with the token from `<home>/hub.json`, waits up to 5 seconds, and prints `{hookSpecificOutput: {hookEventName: "SessionStart", additionalContext: <contract>}}`; Claude saves that context in the transcript after the compaction, so later resumes keep it. For another session, or when the hub does not answer, it prints nothing and exits 0. With `sessions.installHooks` off, a session compacted outside its background process loses its contract.
- Forks (PRD R78, mechanics M36): `findForks` in `packages/claude/src/fork.ts` runs on each roster read. A candidate is a roster entry with a pid, not `background`, whose session ID is no session's current or retired native ID, in the project directory of a target: each work item's latest Claude session with a native ID (`forkTargets`). `relationOf` answers `newer`, `older` or `unrelated`: a retired ID is `older`; a copy belongs to the session's family when its first assistant `requestId` (outside subagents) is in the transcript of the current copy or of a retired one in the same project directory, and is `newer` when its transcript's birth time is after the current copy's. The newest `newer` copy of each session goes in the roster event's `forks`, with the state its marker gives, else the roster's.
  - `Transcripts` indexes each transcript once per pass: the path (`<projects>/<slug>/<id>.jsonl`, then the case-insensitive listing, or every project directory when the caller has no working directory), the birth time, and the request IDs, read incrementally from the last offset with an incomplete last line kept for the next read. A file with another identity (`ino` or birth time) or a shorter one is read again from the start; a rewrite in place to the same or a larger size is not detected, because Claude only appends. A transcript that is not found is looked for again after 60 seconds.
  - The hook marker records the session's `cwd`. A changed marker of a native ID that is no session's, in a Claude session's project directory, starts a roster read, so a fork is found at its first hook rather than the 30-second timer.
  - The report command sends `CLAUDE_CODE_SESSION_ID`, which Claude sets in the Bash tool's environment, as `nativeSessionId`. For a Claude session whose current copy it is not, `relation` decides: `older` refuses the report with "Session <id> was replaced by fork <shortId>, so the report was not recorded.", `newer` records it and starts a roster read, and `unrelated` records it. The hub checks again just before it applies the report, because a roster read can continue the session as a fork while the report's worktree, link or assignment check runs. A Codex session's report ignores it, because a Codex process can inherit it.
  - `POST /contract` resolves a native ID that is no session's through `forkOf`, so a fork that compacts before it is continued gets its session's contract.
- Release: when a session's turn ends (`idle` or `failed`), run `claude stop <id>` once (PRD R39). A `waiting` session is not released, because it is mid-turn. A session whose background process has ended, by release, stop, failed start or leaving the roster, is never released again, and neither is a session the roster lists as interactive, so a session the operator resumed in a VS Code tab is never stopped by Switchboard. Before a release stop, the hub also reads the roster and skips the stop unless the session is listed as a background process. An interactive roster entry, such as a VS Code tab, has no `state`; its `status` (`idle`, `busy` or `waiting`) gives `idle`, `running` or `waiting`.
- Stop: `claude stop <id>`, 15-second timeout. A failed stop leaves the session stoppable. Never `claude rm`, which can delete the worktree. Only a `release` stop checks the roster first; an operator stop and an `open` stop do not.
- Open in terminal (PRD R28): `controlsOf` in `packages/hub/src/rows.ts` adds a `terminal` window command `{sessionId, cwd, name, shortId, active}` for the latest session: with its short ID while it runs in its background process, else `shortId: null`, with `active` true for a session that is released but not ended, which the roster lists as interactive, as in a terminal or a VS Code tab. A starting session gets none, and neither does an `external` one (PRD R81). With `dock.openVSCode: always` the dock leaves it for the item window through `POST /window`; with `review` it runs in the dock's terminal ([Dock](#dock)). `openTerminal` in `extensions/switchboard/src/open.ts` shows the terminal the window opened for that mode and session while it runs; otherwise it opens an `active` session with Open in VS Code, because resuming a live session starts a copy (M18), and opens a VS Code terminal named `Switchboard · <ticket key>` running `claude attach <short ID>`, or `claude --resume <session ID>` in `cwd`, for the others. Leaving an attach keeps the session running (M7, M9), but release still stops an attached session when its turn ends. The roster lists a resumed session as interactive, so it is never released.
- Open in VS Code (from a History link, PRD R59, and in an item window, PRD R29): resumes the session or focuses it where `claudeCode.preferredLocation` puts it. With `sidebar`, the window calls `claude-vscode.editor.open(<native session ID>, …, { programmatic: 'honor-preferred-location' })`, which opens it in Claude's sidebar unless a tab already holds it (GC M63); otherwise `claude-vscode.primaryEditor.open(<native session ID>)`, which always uses a tab. Claude's tab and sidebar list only the sessions of its window's first folder, and opening another session there starts an empty one (GC M6, M7, M52). So when the session's directory is the window's first folder, the window opens it directly. Otherwise the window posts `{sessionId, cwd}` to the hub's `POST /open` and opens that folder with `vscode.openFolder` and `forceNewWindow`, which focuses a window already on it. A window claims a pending open for its folder with `POST /claim {folder, workspace, focused}` when it connects to the hub, whenever it gains focus, and on a `claim` event naming its workspace file, and opens it; `folder` is empty for a window with none, `workspace` is the window's `.code-workspace` file or null, and `focused` is VS Code's window focus. The reply also holds `commands`, the dock's pending window commands (`POST /window`) for that workspace file, and while `focused` also those for any window, oldest first, so a window reconnecting in the background does not take what the dock left for the window it brought forward. The window runs `openTabs` before opening any claimed session and the others (`openChanges`, `openTerminal`, History, `openLink`) after it; a failure there or in a command shows its error and the rest still run. `/window` accepts only `changes`, `terminal`, `history`, `log` and `openUrl` commands with the fields their handlers read, and `openTabs` with a workspace file, and a pending command expires after 2 minutes. An open the dock posts names its item window's workspace file, and only a claim with that file takes it (PRD R71). A pending open expires after 2 minutes. `WindowQueue` in `packages/hub/src/windowQueue.ts` holds the pending opens and commands and writes them, with the next command ID, to `<Switchboard home>/window-queue.json` on each change, and a starting hub reads that file, because the first window started after an extension update replaces the hub before it claims what the dock left for it. `/open` and `/window` answer 500 when the file cannot be written, so no command ID is handed out twice; a claim or withdrawal is kept in memory even then. A pending open is kept per folder and workspace file, so two item windows on one folder each claim their own. The hub logs each session left and claimed.

## Codex runner

`CodexRunner` in `packages/codex` implements `SessionRunner` for Codex (mechanics M31). The runtime builds one runner per provider and sends each action to the runner its `provider` names: `start-session` and `stop-session` carry it, because a deleted session's row is gone when its stop runs. The roster read and the marker pass ask each runner about its own sessions; when one runner's read fails, its sessions stay as they were, and the other runner's read still applies. Startup installs both runners' hooks, and a hook error shows each runner's message. Every Codex process gets `CODEX_HOME` set to Codex's home, `CODEX_HOME` as the hub inherited it or `~/.codex`, so the runs and the hook trust read the same hooks.json. Each Codex process the hub starts (runs, hook trust, debriefs) runs `sessions.codexPath`, read at each spawn: `codex` by default, looked up on the hub's PATH. The hub inherits the PATH of the VS Code window that started it, which can lack a Codex installed through nvm, so such an install needs its full path. An absolute path's directory goes first on those processes' PATH, because npm's launcher runs `node` from PATH and nvm keeps `node` beside it. A run, the hook trust and a debrief that cannot find the CLI report `Codex was not found at <path>. Install it or set sessions.codexPath.`; a missing working directory, which also fails with ENOENT, is not reported so. Open in terminal runs `sessions.codexPath` the same way.

- **Runs.** A session's background run is one `codex exec` process the hub spawns detached, with stdin closed, no shell, and stdout and stderr in `<home>/codex/<sessionId>.jsonl|.err`. The run record `<home>/codex/<sessionId>.json` (`RUN_RECORD_VERSION` 2) holds the work directory, mode, model and contract, the thread ID, the spawn time and the process; a record of another version is not read: its session ends at the next roster read without its process being ended, and a stop or open of it fails with that reason. A process is named by its PID and creation time together, because PIDs are reused: on Windows one `Get-CimInstance Win32_Process` query per roster read gives the creation time as a file time; on Linux `/proc/<pid>/stat` gives the start time in clock ticks since boot, with no command run. The run's process is Codex itself (`isCodex`: `codex.exe` or `codex`), the process the hook script finds. On Linux `codex` on PATH is npm's Node launcher, which starts Codex as a child with the same arguments, so a start whose spawned process is not Codex records the tagged Codex process instead, or leaves it to be found by its tag (mechanics M38). Ending a process ends its descendants at once: `taskkill /T /F` on Windows, `SIGKILL` on Linux to the process and each descendant found in `/proc`, the root only while its start time matches the identity the runner checked, and each member only while its start time still matches the scan's, so a PID taken by another process meanwhile is spared. A start that times out looks for the Codex process by its tag when it has no identity yet, so a launcher's child that started late is ended too. Every command line carries `-c switchboard_run="<sessionId>"`, which Codex ignores, so a hub that stopped between a spawn and writing its PID finds the process by its tag.
- **Arguments.** `codex exec --json <mode> -c developer_instructions=<contract> -c switchboard_run=<tag> [-m <model>] -C <cwd> -- <prompt>`. Each mode is `-c` overrides (`modeArgs`): `auto` is the workspace-write sandbox with network and escalations reviewed automatically, `plan` read-only, `dontAsk` workspace-write with network and no escalation, `bypassPermissions` no sandbox; `default` and `acceptEdits` need a person and are refused. Commands in the sandbox cannot use the operator's credentials, so skills that call `gh` need `bypassPermissions`. A prompt that starts with `/<skill>` starts with `$<skill>`, which Codex injects (`codexPrompt`).
- **Start.** Writes the record, spawns, writes the process, then waits up to 60 seconds for `thread.started`: the full thread ID is both the native and the short ID, and History shows its last 8 characters. A process whose creation time cannot be read at once is waited on by its PID and found later by its tag. A process that exits first fails the start with the last line of its stderr, such as Codex's refusal outside a git repository; one that prints no thread in time is ended. After a hub restart, `reconcile` finds an untracked process by its tag and completes the start when its log holds the thread, waits for a live process, and fails it otherwise; when the process query fails it answers `pending`, and the runtime asks again at each roster read.
- **State.** `reduce` in `src/reducer.ts` is the only place that decides a Codex session's liveness and state; the roster read (`observe`, with the process query) and the marker pass (`markers`, with `process.kill(pid, 0)` and the creation times the last query read) both call it. In order: a hook marker written since the run was spawned by a live process other than the run's means the operator resumed the thread, as in the VS Code panel, and the session is interactive, with the marker's state, ended by the rollout's `task_complete` or `turn_aborted` for its turn because Codex fires no hook for a failed turn; a question whose reporting turn has ended keeps the session `waiting`; a live run is running until its log holds the turn's end; a turn end is listed until the session is released, so it is delivered once even when the process exited first; otherwise the session has ended. A marker reading that only the roster read can decide, such as a process that disappeared or a new interactive owner, carries `recheck` and no state.
- **Stop.** A release or an open waits up to 15 seconds for the run's process to exit, since its turn has ended, then ends it; an operator stop ends it at once. Either ends a process only after reading its creation time again, so a reused PID is never ended. An interactive session is never stopped.
- **Serialization.** Every read and change of a session's record runs in that session's queue, after a refresh that finds the run's process by its tag when the record holds none. A failed process query is returned as the error and changes nothing.
- **Open and terminal.** A row's `session` and `question` opens and History links carry the provider, and `/claim` answers the provider of the session it hands over, from the store. The item window checks and activates `openai.chatgpt`, resolves `vscode://openai.chatgpt/local/<thread>` (using `vscode.env.uriScheme`) through `vscode.env.asExternalUri` to target that window, then calls `vscode.open` on the result (mechanics M43). Codex reveals its sidebar and selects the thread; any existing editor tab stays open. Missing or disabled extensions and thrown activation, URI-resolution or open errors are shown by the caller. VS Code owns the URI-handler confirmation; Switchboard neither grants it nor treats a completed request as an acknowledgement that history loaded. Open in terminal runs `codex resume <thread>` in the session's directory once the background run has ended, and is not offered while it runs, because Codex has no attach. Controls, the dock's menu and History say Open in Codex for a Codex session; the dock runs the open on a question row by its `open-question` action, not its label.
- **Questions** (PRD R70). A Codex session's contract offers the `question` report in place of `AskUserQuestion`. The flow stores it on the session with a new ID while the session runs in its background process, and ignores it from a session the operator resumed; the reducer makes the session `waiting` once the reporting turn has ended. The row offers Open in Codex only while the session waits on a reported question, not on a permission prompt. A roster read across which a question was reported is not applied to that session, and the next read decides it. An open stop, an interactive owner and the session's end clear the question; an open stop leaves the work item's status as it was, as for Claude.
- **Hooks.** With `sessions.installHooks`, `installHooks` writes `<home>/codex-hook.mjs` and adds synchronous entries to `<CODEX_HOME or ~/.codex>/hooks.json` for SessionStart, UserPromptSubmit, PreToolUse, PermissionRequest, PostToolUse, Stop and SessionEnd, and `<node> "<home>/contract.mjs"` on SessionStart, which acts only on `source: "compact"` because Codex hooks have no matcher in use; each command runs `<node> "<script>"`, where `<node>` is `sessions.nodePath`; it keeps other entries, finds its own as a Node.js command whose only argument is its script, and updates only that entry in a group it shares, and refuses a file that is not a JSON object; an asynchronous Stop hook does not run before an `exec` process exits. It then runs the trust exchange with `codex app-server` (`trustHooks`), which trusts only entries whose command is Switchboard's. A change to `sessions.codexPath` or `sessions.nodePath` runs this install and trust again (a `sessions.nodePath` change also reinstalls Claude's hooks), so its hook error clears without a hub restart. Installs of one runner run in turn, so an older result never replaces a newer one. The hook writes `<home>/activity/<thread>.json` with `provider: "codex"`, the event, turn, rollout path, and the PID and creation time of the first `codex*` process among its three nearest ancestors, found on SessionStart and UserPromptSubmit and kept for the turn's later events; it skips `FRICTION_DEBRIEF=1`, and SessionEnd deletes the marker. UserPromptSubmit, PreToolUse, PostToolUse and SessionStart after a compaction mean `running`, PermissionRequest `waiting`, Stop `idle`.

## Session reports

### Handled assignments (R85)

`report handled <sessionId> <ticket URL> [--release <assignment key>]` posts to `/handled`. It is available in every session contract when a skill directs it. The response contains `assignmentKey`; the skill retains it for an optional conditional release. Registration requires an open target assigned to the operator and the current session of an open work item. It cannot target the reporting work item's own ticket.

`tickets.handledAssignmentKey` is nullable text, the only added storage. Existing events and changes retain target-ticket registration and clearing evidence, with reporting session/work-item IDs in event detail. Deleting the reporting work item preserves this evidence. Core refuses ticket identity adoption of an active handled target; consolidation of an inactive target transfers its audit. Ended-key audit prevents a delayed registration retry from restoring handling.

`Source.assignmentAt(url)` returns the ticket, its opaque operator assignment key and fresh queue eligibility, or a read error. GitHub reads assignees and paginated assignment events directly by issue number; the key combines the issue node ID and the event that began the current continuous assignment across configured operator logins. Event IDs distinguish changes within one second. It also reads the configured project's current status to correct stale search eligibility. It never infers assignment changes from status history. Incomplete history, changed pagination snapshots and failed reads are errors.

The runtime serializes registration and polling per source. Every poll directly reads registered targets, including those absent from project search, and applies assignment reconciliation with the poll atomically. Core guards work creation, triage and session dispatch. Registration refuses a target whose open work already has a session, including an emitted start; otherwise it removes unstarted duplicates before acknowledgement. A new assignment clears the key and permits normal work even when consecutive polls both show actionable assignment. Explicit release compares the supplied key and uses freshly read eligibility before scheduling work.


### Report transport

Sessions report through the hub bundle, which posts to the hub's loopback HTTP server. The prompt carries the Switchboard session ID and the bundle's absolute path, because a background session has no Switchboard environment and `switchboard` is not on PATH. `node` below is `sessions.nodePath`; a session started before a change keeps the command its prompt holds. Bash, PowerShell and cmd run the command, and they agree only on a first word with no spaces, quotes or shell characters, so `parseSettings` refuses a `sessions.nodePath` with any of them or whose name is not `node` or `node.exe`, and turns its backslashes into forward slashes.

```
node "<home>/hub.js" report stage <sessionId> <stage>
node "<home>/hub.js" report worktree <sessionId> <path>
node "<home>/hub.js" report done <sessionId>
node "<home>/hub.js" report approval <sessionId> --prompt <prompt> [--summary <text>] [--report <path>]
node "<home>/hub.js" report link <sessionId> --label <text> --target <url>
node "<home>/hub.js" report playbook <sessionId> <name>
node "<home>/hub.js" report paste <sessionId> --label <text> --file <absolute path>
node "<home>/hub.js" report task <sessionId> --prompt <prompt> [--repo <repo root>] [--title <text>]
node "<home>/hub.js" report question <sessionId> --text <question>
node "<home>/hub.js" register --title <text>
```

- The contract asks for the approval summary; the CLI and the hub accept its omission, and `done` takes no text. The CLI resolves a relative `--report` against its working directory, and the hub refuses a report path that is not absolute.
- Git Bash rewrites an argument that starts with `/` to a path under its Windows root, so `/sb-ship 16416` arrives as `C:/Program Files/Git/sb-ship 16416`. When `MSYSTEM` is set, the CLI reads the root from `cygpath -m /` and restores an approval prompt that starts with it (mechanics M20).
- The CLI's usage text, printed for a malformed report, leaves out `task`, `register` and `ticket`, as the contract does (PRD R68, R81, R83).
- `report ticket <sessionId> <url> [--playbook <name>]` (PRD R83) posts `{sessionId, url, playbook, nativeSessionId}` to `/ticket`, outside `/report` and `REPORT_KINDS`, so no session's stored `reports` or contract text changes. `Runtime.ticket` refuses a retired copy before and after the lookup, as `report` does; asks each enabled source's `ticketAt` in turn, behind `REPORT_CHECK_MS`, and refuses when none answers for the URL, the lookup fails or is late, or the ticket is closed, because the move needs the ticket's title and state, and when the source was turned off or reconfigured during the lookup; then sends the `ticket` event. History shows a refused or repeated report, whose event notes no `adhocKey`, as a request. On success the CLI prints `Moved to <key>.`, the instruction to follow the contract that follows in place of any earlier one, a blank line and the session's contract, which `/contract` also restores after compaction; a retry prints them again. Its exit codes are a report's.
- `register` (PRD R81) registers the Claude session that runs it. It reads the native session ID from `CLAUDE_CODE_SESSION_ID` and exits 1 without it, posts `{nativeSessionId, title}` to `/register`, and waits up to 30 seconds, longer than the hub's 15-second roster read, and on success prints `Registered as <key>.`, or `Already registered as <key>.`, a blank line and the session's report contract. Its exit codes are a report's. `Runtime.register` answers the key and contract of a session whose current native ID it is, with `already: true`, so a retry after a lost reply recovers the contract; refuses a native ID in a Claude session's `retiredIds` or one the runner's `relation` finds `newer` or `older`, as a copy of that session; then asks the Claude runner's `live`, which reads `claude agents --json` and returns the entry with that full session ID and a pid: its short ID, else the session ID's first 8 characters, which `entryFor` matches as a prefix on later roster reads, and its `cwd`; no such entry refuses the registration. It then sends the `register` event and answers the work item's key and the contract, which `/contract` also restores after compaction, because the session's native ID is now a session's.
- The CLI's home is the directory that holds the `hub.js` it runs from, so a session started by a hub with `--home` reports to that home.
- The CLI finds the hub through `hub.json` and never starts one. Timeout: 10 seconds for the `/status` check and again for the request; 30 seconds each for `register`. Repeating a report is safe, because each report sets a value and a repeated `task` adds nothing.
- When no hub answers, the CLI exits 2 and prints that the hub is not running, or, when the process `hub.json` names still runs, that the hub with that pid did not answer. The hub stays up while sessions are active, so this is rare; the work item then ends `blocked`, and the operator marks it done.
- Exit codes: 0 recorded, 2 no hub, 1 usage, 3 refused (an unknown session, a report the session's report contract does not offer, a link its ticket's source refuses, or a path that `git worktree list` run in that path does not show as a worktree). A worktree can belong to a different repository than the source's repo root, as when a Support session in `D:\git\support` reports an widgets worktree.
- Before applying a task session's `done`, the hub polls the ticket's source and applies that poll. When the poll still lists the ticket as assigned, the hub sends the report with `assigned: true`: the flow sets the session's outcome to `done` with an `outcomeDetail` that starts with `UNCONFIRMED_DONE` and names the report's time, and leaves the work item's status. The hub then polls the source again 30 seconds later (`RECHECK_MS`), after any read in flight, because GitHub issue search can list an issue as assigned for seconds after its unassignment (mechanics M34), and sends `done-checked` with that `outcomeDetail` as its token: still assigned blocks the work item with "The session reported done, but the ticket is still assigned to you.", otherwise it is done; a failed read, one over 6 seconds or a source turned off accepts the report. `done-checked` changes nothing unless the session still has that token and the work item is `running` or `awaiting-approval` (`awaitsRecheck`), so a resume into `running` or `waiting`, which clears the outcome, an approval report after the done report, which clears the token, a later done report, which replaces it, and Mark done each make the check change nothing. A stopped hub skips the recheck, and `startup` schedules one for each work item whose latest session `awaitsRecheck`, at most one per token. When a poll finds the ticket outside the assigned state, the flow marks such a work item, or a blocked one whose task session reported done, done even while that session is still active, such as idle in a tab. The CLI still exits 0. A failed poll, a poll that takes over 6 seconds (`REPORT_CHECK_MS`, inside the CLI's 10-second timeout), a setup session, or an ad-hoc ticket skips the check (PRD R10). Reads of one source run one at a time, so a scheduled poll that started earlier cannot apply after the check's poll; a scheduled poll is skipped while a read is in flight, and a queued read does not start after the hub stops or its source is turned off.
- A report for a work item that is already done does not reopen it: `done` sets the session's outcome, `worktree` links the ticket's worktree, `link` adds the ticket's link, and `stage`, `approval`, `playbook` and `paste` are ignored.
- `playbook` names a task playbook in the work item's namespace; the hub refuses any other with "<name> is not a task playbook in the <namespace> namespace." It sets the work item's playbook only, so the session keeps the reports its prompt offered.
- `task` (PRD R68) creates an ad-hoc ticket and an `unstarted` work item whose `parentId` is the reporting session's work item, whether or not that work item is done. The title is `--title`, or the prompt's first line when it is left out or blank. The repo is `--repo`, which the CLI resolves against its working directory, or the reporting ticket's `repoRoot`, else its source's `repoRoot` setting. The core compares it with the configured repo roots (`repoRoots` in core, the list the ad-hoc prompt box offers) ignoring case, separators and a trailing separator, stores the configured spelling, and otherwise refuses with the list of repo roots. The CLI restores a prompt that Git Bash rewrote, as for `approval`. A report whose prompt equals that of an open work item from the same parent adds nothing, so a repeated report is safe.
- `link` takes an http(s) URL; the CLI and the hub refuse any other target with exit 1. Migration 8 deleted the local-file links of earlier sessions, after copying an open approval's newest one to its `approvalReport`. A link to a target the ticket already has replaces its label.
- `paste` (PRD R60) takes a non-empty label and a `--file` that names one file wherever it is read: on Windows a drive or UNC path, not `\x` or `D:x`, which depend on the reader's current drive or directory; elsewhere a POSIX absolute path. The CLI and the hub refuse any other file with exit 1 instead of resolving it, because the extension reads the file later, outside the session's working directory. Under Git Bash with path conversion off (`MSYS_NO_PATHCONV`), the CLI turns a drive path such as `/d/git/support/x.md` into `D:/git/support/x.md`; with conversion on, Git Bash has already done so (mechanics M20). The hub stores it on the session's work item when the session is the latest, replacing a paste with the same label.

## Friction debriefs

It also needs at least 10 main-transcript tool calls after the last debriefed message, in a range whose debrief has not failed. The due session with the oldest transcript goes first, one fork at a time.
- **Codex sessions:** a Codex session's own thread is a candidate on the same terms, read from its rollout, `<Codex home>/sessions/YYYY/MM/DD/rollout-*-<thread>.jsonl`, whose write time gives its last turn (`findRollout` in `packages/codex/src/debrief.ts`). `codexDebriefRange` counts the `function_call`, `custom_tool_call` and `local_shell_call` records of the turns after the last debriefed turn, through the last completed one, and names a later range by its first user message that Codex did not add, such as its AGENTS.md instructions. The fork is `codex exec fork --json --ephemeral -c approval_policy="never" -c sandbox_mode="read-only" <thread> -` in the session's `cwd` with the prompt on stdin, `CODEX_HOME` and `FRICTION_DEBRIEF=1`, and a 10-minute timeout; `{{subagents}}` is `none`. - **Roster:** before each Claude fork the hub reads the state and `claude agents --json`, skips a session listed with a pid that is not idle, and checks the setting and the 60-minute limit again. An idle background session and a stopped one can be forked (mechanics M19).
- **Fork:** `claude -p --resume <nativeSessionId> --fork-session --session-id <new uuid> --no-session-persistence --output-format json` in the session's `cwd`, the prompt on stdin, `FRICTION_DEBRIEF=1`, a 10-minute timeout. No model, effort, tool or MCP flag, because each changes the prompt prefix and loses the cache. `{{scope}}` is the whole conversation, or the work after the first message after the last debriefed one, named by its first 200 characters. `{{subagents}}` lists the subagents written within 55 minutes whose type can be resumed (not `codex`, `Explore` or `Plan`), with new messages since their last debrief; their transcripts are copied to `<project>/<forkId>/subagents/` for the run, because a fork looks for them under its own ID, and removed after it.
- **Codex threads:** a session's fork, whether it succeeded or failed, marks `pending` in the state each thread that an `mcp__agent-delegate__*` result names in the range, in the main transcript or a subagent's transcript written after the range starts, and every pending thread is then asked once, at the next scan when the hub stopped or a write was held, through agent-delegate's command: `<node> <Claude root>/tools/agent-delegate/debrief.mjs <thread> --prompt <prompt> [--since <its last debrief>]`, with the hub's own executable, `ELECTRON_RUN_AS_NODE=1` and `FRICTION_DEBRIEF=1`, and a 10-minute timeout. Exit 0 with the friction JSON appends a `codex` log line with the session as `parentSessionId`; exit 3, a thread with no turn since, records nothing new; anything else is reported in the hub log and the state's `lastError`, and not retried. A missing command skips the threads.
- **Answer:** the last `result` event whose text, without a code fence, is `{"friction": [...]}` or a bare array, each item with non-empty `what`, `source`, `workaround`, `cost` and `evidence`. The last `result` event gives the cache use and cost.
- **Record:** a success appends a log line (`v`, `at`, `provider`, `sessionId`, `parentSessionId`, `cwd`, `fromMessageUuid`, `throughMessageUuid`, `skills`, `toolCalls`, `cache`, `friction`, `startedAt`, `subagents`, `delegated`), on a fresh line when the file ends inside one, then merges into the state as it is on disk, so another writer's entries are kept: the last message covered, and the fork's start as each shown subagent's last debrief. A failure, including a fork that throws, records the range and its error in the state and the hub log, and is not retried; the next debrief covers that range with any later work. A write that fails is held, and no fork starts until a later scan writes it. A hub that stops between the two writes asks about that range again.
