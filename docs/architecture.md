# Switchboard architecture

Requirements live in [prd.md](prd.md). This document describes components, state and protocols.

Session and triage mechanics come from Ground Control (`D:\git\ground-control`), where they are verified in its [mechanics.md](../../ground-control/docs/mechanics.md); IDs from there carry a `GC` prefix. Unprefixed M IDs are entries in Switchboard's own [mechanics.md](mechanics.md). Re-verify a version-fragile Ground Control mechanism there before relying on it.

## Packages

npm workspaces, TypeScript strict and Node ≥ 22.13, following Ground Control's layout. Only `extensions/switchboard` imports `vscode`. `apps/dock` and `apps/pane-helper` are C# on .NET, the dock with Avalonia, and build and test through their workspace scripts like the TypeScript packages.

| Package | Responsibility | Depends on |
|---|---|---|
| `packages/core` | Domain types, source and runner interfaces, store, playbook loader and renderer, flow rules | — |
| `packages/claude` | Claude Code runner, classifier, debrief fork and [Code Mode sessions](#code-mode-sessions) | core, conversation, the holder client |
| `packages/codex` | Codex runner, classifier, run records and hooks ([Codex runner](#codex-runner)) | core |
| `packages/holder` | The [terminal holder](#terminal-holder): its host, client, attach client and protocol. The client imports no native module; the host is installed per build in the Switchboard home with its native terminal dependency | nothing in Switchboard |
| `packages/conversation` | Shared conversation log, rules and artifacts, and Claude's transcript, screen and guarded input mechanics ([Conversation](#conversation)) | core |
| `packages/voice` | The voice process and its protocol and client ([Voice](#voice)). The main entry imports no native module; the process is installed per build in the Switchboard home with its native audio dependencies | core |
| `packages/github`, `packages/zoho`, `packages/forum` | The GitHub, Zoho Desk and Forum sources | core |
| `packages/protocol` | Types only: the wire types of the conversation API and the web page's routes ([Conversation API](#conversation-api)) | core and conversation types |
| `packages/web` | The web page's front end and theme, served by the hub ([Web page](#web-page)) | protocol; browser-safe core and conversation modules |
| `packages/hub` | The hub: polling, flow execution, the loopback HTTP/SSE server, session reports, debriefs, supervision of the terminal holder and the voice process, window scopes, the conversation service and the web page's routes | core, the sources, the runners, conversation, protocol, web, holder and voice |
| `apps/hub` | The hub's entry point and its commands, bundled as one file | hub |
| `apps/dock` | The [dock](#dock) and its [Settings window](#settings-window), on Windows and Linux | the hub's dock stream and config routes |
| `apps/pane-helper` | The Windows [pane helper](#pane-helper) the hub runs | the hub, over stdin and stdout |
| `extensions/switchboard` | The VS Code side of each item window: hub lifecycle, claimed sessions, the dock's commands, changes, history, the status bar item and the Conversation view ([VS Code extension](#vs-code-extension)) | core, conversation, holder and the hub client |
| `extensions/chrome` | The [browser extension](#browser-extension) for GitHub project boards and the Chrome pane | browser-safe core modules, the hub's browser endpoint |
| `extensions/firefox` | The Firefox build of `extensions/chrome`, from the same source | `extensions/chrome` |
| `extensions/gnome-shell` | The GNOME Shell extension through which the dock lists, raises and watches windows on Linux ([Dock](#dock)) | — |

The ad-hoc source is local: the core's flow creates its tickets from the operator's prompts and from task reports, and nothing polls it. State, the hub bundle, its record and its log live in the Switchboard home, `~/.switchboard`. Settings and playbooks live in the config folder, so the operator can keep them in a git repository. The config folder is the machine-scoped VS Code setting `switchboard.configDir`: an absolute path, or one starting with `~`; empty means the Switchboard home, and a relative path is reported as an error and also means the Switchboard home. All windows agree on one hub: each reads the setting at every hub start, and when it changes, a window whose hub reads another folder replaces that hub, and the other windows reconnect to the new one.

## Components

| Component | Responsibility |
|---|---|
| Hub | Separate Node process that runs the core: polls sources, creates work items, runs triage, starts setup and task sessions, enforces one session in a turn per ticket (PRD R17), and serves the windows, the dock, the web page and the report command. |
| Source plugins | Supply tickets, decide whether each is in the assigned state, and build each ticket's triage context: GitHub, Zoho Desk, Forum, ad-hoc. |
| Playbook loader | Reads the playbooks in settings.json and renders their templates. |
| Classifier | Runs one-shot triage and returns structured output. |
| Runner | Starts, stops and tracks agent sessions for one provider behind the `SessionRunner` interface in `packages/core/src/runner.ts`, which the hub runtime calls: Claude Code, Codex, and Claude Code's [Code Mode sessions](#code-mode-sessions). |
| Worktree linker | Links worktrees to tickets from session reports, falling back to branch-name convention. |
| Store | Local SQLite database holding tickets, work items, triage results, sessions and worktrees. |
| VS Code extension | Starts the hub, opens claimed sessions in the item window, runs the dock's commands, and shows a worktree's changes, a ticket's history and the window's conversation. |
| Conversation layer | Runs in the hub: follows each live Code Mode session's transcript and screen, keeps its conversation, and serves each window its own work item's ([Conversation](#conversation)). |
| Dock | Lists the work items beside VS Code, switches to each item window, runs the controls, and edits the settings. |
| Voice process | PRD R105: a Node.js process per Switchboard home, started by the hub while a window wants it, that decides which session the voice speaks for and speaks the replies the hub offers ([Voice](#voice)). |
| Terminal holder | PRD R94: a Node.js process per Switchboard home, started by the hub, that holds Code Mode sessions in pseudo-terminals, replays their screens to attached terminals, and lists and kills them ([Terminal holder](#terminal-holder)). |

## Data model

The store owns the durable state; the schema and its migrations are in `packages/core/src/store.ts`.

| Entity | Records |
|---|---|
| Ticket | One ticket of a source: its keys, assigned and pool state, snooze, scope time, repository, blockers and, for an ad hoc conversation, its host window. |
| WorkItem | One pass of work on a ticket under one playbook: status, stage, prompts, guidance, review position and how it ended. |
| Triage | One classifier run and the context it was given. |
| Worktree | A worktree linked to a ticket, by report or by convention. |
| Link | A link reported by a session, or found in the ticket's text by triage (PRD R61) until a session reports it. |
| Paste | A drafted text a session named for the operator to copy (PRD R60). |
| Comment | An operator comment on a work item (PRD R87). |
| Message, Reply, Checkpoint | A Code Mode session's conversation and how far its transcript has been read ([Conversation](#conversation)). |
| WindowBinding | Each item window's primary work item, selected conversation and scope generation ([Window scope](#window-scope)). |
| Session | One agent session of a work item: kind, provider, native IDs, working directory, observed state, outcome, and the provider-specific state the hub needs to recover or continue it. |

- **Source boundary.** A source sets each ticket's `ref`, the reference people use (such as `#<n>`, `owner/repo#<n>` outside the home repository, or a Forum `T<topic id>`), its `sourceKey` and, when its API needs a different one, `sourceId`; core holds no per-source rule. `Ticket.sortAt` is the source's sort time, which orders the Unstarted group. `Ticket.repo` is the ticket's repository in lowercase; empty means the source's home repository ([Repo roots](#repo-roots)).
- **Scope time** (PRD R53): `Ticket.scopeAt` is when the ticket last entered its source's scope. Core stores the source's own entry time whenever the source gives one, because a source's scope can be wider than the assigned state and the pool; otherwise a ticket keeps the time it has, or takes the poll's time when it first appears assigned or in the pool.
- **Pool triage.** A pool triage belongs to the ticket until a pick creates the work item and attaches it. A ticket that leaves the pool without a pick loses its finished pool triages. A triage still running for it is kept until it ends, so it still counts toward triage concurrency and a work item on that ticket waits for it rather than starting a second; a ticket that returns to the pool drops that running triage and is triaged afresh.
- **Moved tickets** (PRD R83): a ticket a ticket report moved from ad hoc to a source keeps its ad-hoc key, so the key is never used again and its item window keeps its name.
- **Blockers** (PRD R90): `Ticket.blockers` is the open blockers from the last complete poll that reported them; a source that does not report blockers leaves the stored list unchanged. A queued work item waits while the list is not empty.
- **Triage record.** `Triage.context` keeps the clipped text the classifier received, so the operator can see why a playbook was chosen. The focus a row opens (PRD R79) is that of the latest triage with a playbook, else the ticket's URL, so a running or failed triage keeps the earlier focus.
- **Work item times.** `WorkItem.readyAt` is set once, when the work item first becomes `awaiting-approval` or `finished`, and nothing else changes it, so the work item keeps its place in Ready for review when it runs again. `WorkItem.orderAt` is the operator's position in Ready for review (PRD R73).
- **Prompts and guidance** (PRD R68, R77): `WorkItem.taskPrompt` is the prompt the task session ran, or an ad-hoc or task work item's own prompt, which Start with prompt… may replace; a playbook's prompt cannot be replaced. `WorkItem.guidance` is kept until a task session starts with it appended, so a failed start keeps it for Retry. `WorkItem.reportedPrompt` keeps a task report's original prompt, so a repeated report finds its open child even after its prompt was replaced, and `WorkItem.parentId` names the work item whose session sent it.
- **Ending** (PRD R10, R11): `WorkItem.doneReason` is `session`, `operator` or `unassigned`; `unassignedAt` and `warning` record a ticket that left the assigned state while work ran.
- **Session state.** `Session.state` is the observed state, with a detail naming why a session waits (a start prompt or a permission prompt) or that its turn ended with a question open in its conversation and `Session.outcome` the reported or decided outcome (PRD R36). `Session.released` records that the release stop was sent, so it is sent once (PRD R39). Native IDs a fork retired (PRD R78), a Codex session's reported question (PRD R70), a registration (PRD R81), a Continue in Background under way (PRD R89), a usage limit (PRD R111) and a Code Mode session's launch and process tree are stored on the session so a restarted hub can recover or continue it; they are left out of the activity log, whose events name them.
- **Persona** ([Personas](#personas)): a Code Mode session records its persona, the version of the tone section its prompt last got, and whether the operator pinned it.
- **Conversation rules.** No session records a rules version: every session is read as if it carries the current conversation rules.
- A session's `cwd` follows its playbook's `workdir`: the ticket's worktree when one exists, otherwise the source's repo root.
- A `Paste` belongs to the work item, not the ticket, because a returned ticket's new work item drafts new texts; a later paste with the same label replaces the earlier one in its place.
- **Migrations** run with foreign keys off, because a table rebuild drops a parent table, and each fails unless `PRAGMA foreign_key_check` is empty before it commits.
- **Snapshot cost.** The snapshot reads work items through indexed queries, so its cost does not grow with the done history.

## Hub lifecycle

Follows Ground Control's hub (GC R35, GC M25). One hub runs per Switchboard home; windows, the dock, the web page and session reports all reach it through its record.

- **Start:** extension activation installs the builds the extension carries (the hub bundle, the web page's assets, and the holder, voice and pane helper builds) into the Switchboard home; `hub.js install` run from an extension's `dist` does the same without VS Code, since installing an extension activates nothing in open windows. A window accepts a running hub only when it reads the window's config folder and either is the installed build or restarts onto it by itself (Restart onto a new build, below), because stopping such a hub could cut off a typed message or a session start. Otherwise it asks that hub to stop, reports a refusal, and starts a new hub only after the old one has gone. A window starts the hub detached under VS Code's executable in Node mode, without the Electron, VS Code and `NODE_OPTIONS` variables of its own environment, logging to `~/.switchboard/hub.log`.
- **Record:** the hub listens on `127.0.0.1` on an ephemeral port and writes `~/.switchboard/hub.json` with `protocol`, `version`, `build` (a hash of its bundle), `configDir`, `execPath` (the runtime it runs on), `port`, `token`, `pid`, `startedAt` and, from a hub that restarts onto a new build by itself, `restarts: true`; a record without `configDir` or `execPath` reads as no hub. The hub holds a lock for its lifetime, a named pipe on Windows and `~/.switchboard/hub.sock` elsewhere; only the lock holder writes or removes the record, so concurrent starts leave one hub. A forced exit on Windows leaves the record behind, so clients accept a record only when `GET /status` with its token returns the recorded pid.
- **Endpoints:** on the hub's port, `GET /hub` returns identity without a token, the [web page](#web-page)'s routes use its own sign-in, and every other route requires `Authorization: Bearer <token>`. `/events` is a window's stream: `hello` with the window's key ([Window scope](#window-scope)), a `state` event with the window's scoped snapshot when it opens and after every change, and `claim` when something is left for a window ([VS Code extension](#vs-code-extension)). `/dock/events` is the dock's: a `dock` event with the [dock view](#dock) the same way, `needs` when work items start needing the operator, `show` when a window asks for the dock's list (409 when no dock stream is open), and `config` after the hub reloads the settings or playbooks. A window opens its stream naming its workspace file, or its folder for a folder window, and reports each focus change with the time of the change. The hub tracks focus by stream, so folder windows are told apart, and adds `windows` to each dock view: the connected item windows and folder windows, the item window in front, and how many windows are connected. Focus reports are ordered: a blur from a window not in front, a report older than the last applied, and one naming no open stream change nothing, and a reloaded window is listed once and keeps its focus. `/action` takes an operator event and answers 409 with the core's refusal. `/history` (PRD R59) answers 403 "Not in this window." for a ticket outside the window's scope. `/contract` gives the contract hook its session's contract ([Claude Code runner](#claude-code-runner)), and `/register` registers a session or answers 409 with the refusal ([Session reports](#session-reports)). `/attach` gives the [attach client](#attach-client) the terminal holder's address for a session, resuming an ended Code Mode session first, with 404 for an unknown session and 409 for any other refusal. `/holder/list`, `/holder/stop` and `/holder/restart` list and stop held sessions and [restart the holder](#restarting-the-holder) ([Visibility](#visibility-of-held-sessions)), answering 404 for an ID that names no held session and 409 with any other refusal.
- **Restart onto a new build:** the hub watches the installed bundle, and when it is another build, restarts onto it once it is quiet: no request in flight, no session starting, being attached, resumed or ended, no message being typed or sent, no holder restart, triage, source or roster read, operator action, voice speech, enrolment or utterance being heard, or debrief running, no phone that has yet to take the voice back after the last restart, and the hub not stopping. It logs each reason it waits for. The successor takes over the hub lock once the old hub releases it; meanwhile the old hub answers every `POST` 503 "The hub is restarting onto a new build; try again in a few seconds.", which the session report commands retry. The old hub checks it is still quiet once the successor is ready, and otherwise ends the successor and waits again. A successor that fails is ended and logged, the old hub keeps running its own build, and windows keep accepting it, until another build is installed or `hub.js restart` asks again. The terminal holder and its sessions keep running across the restart. A handover file (`hub-handover.json`) names the successor while it loads, so a hub started meanwhile by a window or the dock waits for it rather than take the lock first, and carries what the old hub hands the successor: the voice's device and the paired device's sign-in that holds it, the target and its generation, Speak replies and the mic, so a restart is transparent to the voice ([Remote access](#remote-access), Voice on a phone). The file is written before the old hub lets go of anything; a write that fails ends the successor, and the old hub keeps running its own build. From the handover on, the old hub sends the voice process nothing, so neither the phone's socket closing nor its windows leaving move the voice. Windows and the dock reconnect to the new hub, and a web page reconnects and reloads for the new build, except that a page whose phone has the voice, or is taking it back, puts the reload off until the voice leaves it, because a reload ends the phone's audio until its next tap; a window's own extension code changes only when it reloads. `hub.js restart` (`POST /restart`) asks for the same restart onto whichever build is installed, its own included, and reports what the hub waits for; it is refused when no bundle is installed or a restart is already under way.
- **Snapshot worker.** The snapshot and the dock view are built in a worker thread, once per burst of changes, because a build reads the store for long enough to hold back conversation events on the main thread. The worker opens the store read-only and builds in one read transaction, so a commit between two queries cannot mix two states, and the hub publishes each snapshot and dock view whole, so no view mixes two builds. A worker that fails is logged and replaced by builds on the main thread. `buildSnapshot` in `packages/hub/src/snapshot.ts` is the projection both run.
- **Dock start** (PRD R71): the dock keeps the runtime and config folder of the last hub it connected to, in a file of its own, and starts a hub with them when none answers. It waits a grace period first, so a VS Code window replacing the hub, as for a new config folder, wins the hub lock, and starts at most once per interval. A started hub that has exited is reported with its exit code and the log's path rather than as starting. The hub's lock keeps concurrent starts by the dock and a window to one hub.
- **Starting without VS Code** (PRD R117): `hub.js start` reports the running hub when one answers for the home; otherwise it starts the installed bundle detached on the runtime that runs the command, with the given config folder or the Switchboard home, and waits for its record. A VS Code window accepts that hub when it is the installed build and reads the window's config folder, and otherwise replaces it.
- **Login start and `switchboard:` link** (PRD R117): `hub.js autostart on` registers a login-time start and a handler for `switchboard:` links, which the web page's offline page opens ([Web page](#web-page)); each runs `hub.js start` for this home. Neither passes the link's URL to the command, so a page that opens a `switchboard:` link can only start the hub. The login entry is per home and the link per user, so the last home to turn it on owns the link. It refuses, changing nothing, under VS Code's runtime, without an installed bundle, and for a path the entries could not quote safely. `hub.js autostart off` removes only the entries that start this home's bundle, so entries another home or program wrote under the same names stay.
- **Clients:** each window holds one `/events` stream, and the dock one `/dock/events` stream. A dock that runs forwarded clicks says so when it opens its stream; `POST /dock/click` sends the click to the newest such stream only, so one dock runs it, and answers 202 once sent (accepted, not completed) or 409 "The dock is not running." (PRD R65, R69, R71). The hub runs until it is stopped (`hub.js --stop`, `POST /shutdown`), whether or not any client is connected (PRD R43, R117); only tests make it exit when idle. When a stream ends, the window finds or starts a hub and reconnects, and shows an error after repeated failed or short-lived connections.
- **Browser endpoint:** for the browser extension, which cannot read `hub.json`, the hub also listens on the fixed port `127.0.0.1:47615` (`BROWSER_PORT` in core). Without a token it serves `GET /snoozed`, the URLs of tickets snoozed now, kept because the extension is loaded separately and can be older than the hub, and `GET /cards` (PRD R67), one card per ticket URL the dock lists, with the playbook name, group, snooze flag and link targets the dock shows. A ticket with several work items gives the pool entry, else the open work item, else the latest. `POST /snooze {url, until}` and `POST /unsnooze {url}` find the assigned or pool ticket by URL, ignoring case, and send the core's `snooze` or `restore` event (PRD R66): 200, 404 when no ticket in scope has the URL, 409 with the core's refusal, 400 for another body or an oversized one. Both answer 403 to an `Origin` that is not `chrome-extension://` or `moz-extension://` and 415 to a content type other than `application/json`, before reading the body, so a web page's request either fails its CORS preflight or is refused, and only an extension with host permission for the port can snooze; any such extension can, because an unpacked extension's ID depends on its folder ([mechanics.md](mechanics.md) M23). The endpoint sends no CORS headers, so web pages cannot read it, and answers 403 to a `Host` other than the loopback address and port, against DNS rebinding. A hub that cannot take the port, such as a second hub for another home, logs it and runs without the endpoint. `GET /pane` upgrades to the Chrome pane's socket ([Pane socket](#pane-socket)), or without an upgrade answers whether the pane is on; every other upgrade is refused.
- **Entry point:** one bundle, `hub.js`, serves the hub, reading settings and playbooks from `--config` or the Switchboard home, and runs its commands: `--stop`, `start`, `restart`, `install`, `autostart`, `report` for session reports, `attach` for the [attach client](#attach-client), `holder` to list and stop held sessions, and `web` for [web page](#web-page) links and [remote access](#remote-access) pairing. Flags move or turn off its fixed ports, as tests do, and shorten the Code Mode idle limit for tests and live acceptance, which the hub then logs.
- **Terminal holder** (PRD R94, R95, [Terminal holder](#terminal-holder)): `HolderLink` in `packages/hub/src/holder.ts` finds or starts the holder. The flow ends the sessions of a holder that is gone and is told of a held session past the idle limit.
- **Runtime:** the hub opens the store, loads settings and playbooks and reloads them on change, and polls each enabled source on its interval. After a poll it reads `git worktree list` in the source's repo root for the branch convention and links only tickets that have no worktree yet; entries git marks `prunable`, such as a deleted directory, count neither for the convention nor for report validation. While any session has started it reads the agents' rosters and hook markers. Before a roster read or a release stop can end a setup session, it reads the convention again, so an unreported worktree still counts.
- **Startup:** the hub checks that `sessions.nodePath` runs, for each agent with the PATH that agent gets, and shows a failure with the hook errors, because hooks and session reports run that Node.js and a hook that cannot start fails silently; a change to the Node.js or agent paths checks again. It installs each agent's hooks into the operator's own Claude and Codex settings when `sessions.installHooks` is on, runs again any triage it abandoned, and asks each session's runner about every session still `starting` (PRD R43). A runner adopts a start only on an unambiguous match, so the hub never takes over or stops a process it cannot identify: an unconfirmed or ambiguous start stays owned with a visible warning, reports from it are refused until its identity is confirmed, and Stop session clears an overdue start with no matching process without stopping anything. Then it reads the roster.
- **Platforms:** Windows, and Linux under GNOME on Wayland, run the hub, the extension, the browser extension and the dock (PRD § Scope); on Linux the dock brings item windows forward through the GNOME Shell extension ([Dock](#dock)). Source commands run through Git Bash on Windows and `bash` elsewhere, and hook scripts run with `node`. Paths compare without case or separator differences on every platform, so on Linux two paths that differ only in case count as one.
- **Home override:** when `SWITCHBOARD_HOME` is set in VS Code's environment, the extension passes it to the hub as `--home`. Both name the directory that holds `.switchboard`, in place of the user home, and the config folder is then that `.switchboard` too, whatever `switchboard.configDir` says. It does not change the user profile that Claude and `gh` see. Live acceptance depends on it.

## Rows

- The row rules (groups and their order, each row's controls, click, time, mark and texts) live in `packages/hub/src/rows.ts` and the core's `group.ts`, which import only types and browser-safe modules, so the dock and the History webview draw the same rows from the hub's view and have no rules of their own; `dockView` in `dock.ts` builds the [dock](#dock)'s view from them.
- Groups follow PRD R27, in the order Ready for review, Blocked on you (only when it has rows), In progress, Unstarted, Snoozed, Done. A work item belongs to the first that applies: Done; Unstarted while unstarted, triaging or failed at triage; Ready for review once it has been ready, even while it runs again, waits, asks a question, blocks or fails; Blocked on you while it is blocked, failed or waiting on a question; Unstarted while queued; else In progress. Ready for review is ordered by the operator's position, else by when the work item became ready (PRD R73); Blocked on you and In progress by when the wait or the run began.
- **Turn.** Blocked on you is on the operator's turn, and so is a work item in Ready for review or In progress that blocks on the operator, awaits approval or has finished; the others there are on the agent's turn. Unstarted and Done rows have no turn, and neither does a hosted conversation whose session is idle between turns, because an open conversation between turns is not working. An unsnoozed work item on the operator's turn needs the operator: the status bar counts it and the notifications follow it.
- **Controls.** Each row has at most one main control, the action that row most needs: open a session where it waits, Start, Approve, Retry, or Triage again; a row has none when its click already opens what it needs, and In progress and Done rows have none. Every applicable control is in the row's menu, and hub controls carry the action the surface posts to `POST /action`. Ready for review rows can be moved within the group and reset to their ready order (PRD R73).
- **Marks and details.** The row mark shows what differs within the group, with its meaning in the tooltip (PRD R27), and `markOf` in `group.ts` decides it; the glyph and icon tables beside it are shared by every surface, so each draws the same mark. A queued row names what it waits for, from `queueWaits` in `packages/core/src/queue.ts`, the same check the scheduler uses before it starts it. Rate-limited rows stay on the agent's turn ([Rate limits](#rate-limits)).
- **Time** (PRD R27, R53): each group measures from its own start: Blocked on you from the block or wait, Ready for review from `readyAt`, In progress from the run's start, Unstarted and Snoozed from the ticket's scope time, and Done from the work item's scope time to its end. A run that waits or moves from setup to running stays one run, and time spent queued is not counted. A done work item keeps its own copy of the scope time, because the ticket's moves when the ticket returns.
- **Stage staleness** (PRD R58) is computed from the latest of the stage report, the run's start and the time the session last began running. The hub sends a view at least every minute (the `tick` timer), so ages stay current without other events.
- The Unstarted group holds unstarted, triaging and failed-at-triage work items, queued work items not yet ready whose live session does not wait on the operator, and pool tickets with no open work item, of enabled sources only, sorted together by importance, then oldest first. A pool ticket can be started only once its triage has a result, and the core refuses a pick without one.
- **Terminal until review** (PRD R71): `dock.openVSCode` and `dock.openTerminal` decide whether a row's click and its open controls go to the item window or to a terminal running the session's CLI, or the attach client for a Code Mode session ([Code Mode sessions](#code-mode-sessions)). A terminal is named by the work item and session, so an attach and a later resume share it and another session never takes it; the row's window is unchanged, so History, Open changes and closing still use it.
- Endpoint additions for the pool: `/action` also takes `pick` with `{ticketId, guidance?}` and `retriage-pool` with a `ticketId`.
- **Snooze** (PRD R49): a `snooze` action carries the ticket, a wake time or null for indefinite, and an optional comment; the hub refuses a malformed one with 400 and the core refuses a wake time that has passed with 409. The choices come from `snoozeChoices` in `packages/core/src/snooze.ts`, which the browser extension also uses, so every surface offers the same times. The core ends every due snooze at the start of each event, and the hub's `tick` makes a wake need no other event. Every end of a snooze clears its comment, and a new snooze replaces the old one. A poll that finds a ticket neither assigned nor in the pool ends its snooze.
- **Source toggles** (PRD R3): `POST /sources {name, enabled}` turns a source on or off in the store, not in settings.json, and rebuilds the polls. A configured source with no stored state is off, and loading settings forgets sources they no longer list, so a source removed and added again starts off. A toggle sends `config` on the dock stream. An unknown source, or `adhoc`, is refused with 409. A disabled source is not polled and its pool is hidden; its work items stay.
- **Refresh:** `POST /poll` polls each enabled source now and restarts its interval; a source with a read in flight is not read again. With no source built it answers 409 with each enabled source's build error, or says no source is on.

- **Pull requests** (PRD R92): a source that can read pull requests (the GitHub source) reads, after each of its successful polls, the pull request links of every ticket with a work item not done, whatever the ticket's source, skipping one it last read as merged or closed. The hub keeps the results, state, review decision and checks, in memory by URL and adds them to the snapshot's links; a window's scoped snapshot carries only its own work items'. A window coming to the front reads them again, rate-limited and queued behind any read of the same source; a failed read is logged and keeps what was read. No webhooks.

## VS Code extension

The extension makes each VS Code window an item window's helper. Its views are the Switchboard pane, which shows that window's work items (PRD R71, R92), and the [Conversation view](#conversation-view); it has no row commands, and shows nothing global.

- **Claims.** A window claims the commands the hub left for it (`POST /claim`, [Open in VS Code](#claude-code-runner)) on `hello`, whenever it gains focus, and on a `claim` event for its destination. When `POST /window` or `POST /open` names a destination, the hub sends `claim {workspace}` only on the `/events` streams of the window keys bound to it ([Window scope](#window-scope)), an item window's file or a folder window's folder, because VS Code reports no focus change to a window the dock brings forward when it is already open (observed 2026-10-09: Open report's commands waited unclaimed until `code <workspace>` focused the window); a command for any window is not announced. The window runs `openTabs` first, then opens the claimed session, so a session in an editor tab is in front, then the other window commands: Open changes, History, Show hub log and `openUrl`. A Markdown file opens in the Markdown extension's preview editor, one tab per file, which Toggle Preview turns into the text editor in place, so editing a draft adds no second tab (mechanics M27). The hub logs each window command left, withdrawn and claimed.
- **Item window tabs** (PRD R72): the hub's `windowTabs` (`packages/hub/src/dock.ts`) lists, for an item window's workspace file, the focus of each of its work items (PRD R79) and the report of each `awaiting-approval` one; links are not tabs. The window opens each once: the first `state` after activation only records them, and later ones open a focus that differs from its work item's last one and a report not seen before, so a later triage's new focus opens, while a report whose work item returns to `awaiting-approval`, or a work item that returns with the same focus, does not open again. A folder window opens no tabs. A URL opens in VS Code's integrated browser, reusing a tab already on that URL, or on the URL a Zoho Desk ticket link redirects to; the Simple Browser is not a fallback, because it shows one page at a time. The integrated browser's command is not a public API (mechanics M27), so a VS Code upgrade can break it.
- **Closing done item windows** (PRD R76): an item window closes itself once its primary work item and every conversation it hosts ([Hosted conversations](#hosted-conversations)) are done with no live session, and it saw one of them not done, so a work item that moves to another window does not close this one. With `dock.openVSCode: review` it also closes once its work has left review, unless a session was resumed in a tab or a terminal. It closes only after `switchboard.closeDoneWindowsAfterMinutes`, counted from the later of the work becoming done and the window losing focus, while `switchboard.closeDoneWindows` is on, and never with an unsaved editor or document; focus or work that is no longer done cancels it. A folder window never closes. A close that fails shows a warning.
- **Open changes** (PRD R57): the window opens a multi-diff editor of the worktree against its merge base: the commits since the merge base, the index and the working tree with untracked files, one row per file, from `changesPlan` in `packages/core/src/changes.ts`, which the web page's Changes tab shares ([Web page](#web-page)). The list is capped, and the title says so. A conflict counts as a modification. Three constraints come from VS Code's Git API: the repository root it answers is checked against the path, because it can answer with another repository (mechanics M21); the merge base comes from `getMergeBase`, never `getBranchBase`, which writes to the git config; and each opening closes the ticket's open changes editor and uses a new source URI, because VS Code reuses an editor with the same source URI without updating its rows. The multi-diff editor command is private (mechanics M21).
- **History** (PRD R59): a `switchboard.history` webview tab per ticket, which a reload restores. It reads `POST /history {window, ticketId}` with the window key of its `/events` hello, and the hub answers only for the window's own work item's ticket or one whose History command the window claimed ([Window scope](#window-scope)): the ticket, its work items with their sessions, triages and pastes, its pool triages, worktree, links and activity events, and a `revision`; or 409 for an unknown ticket. A read that sends the shown `revision` gets `{unchanged: true}` when it is current. A visible tab reads again on stream `state` events, throttled, and a hidden one when shown. The pure `historyView` (`packages/hub/src/history.ts`), which the webview bundles and the hub runs for the [web page](#web-page), turns the reply into entries, so the two cannot drift: one entry per work item whose rows an event changed, and waiting time as the union of logged needs-you statuses and `waiting` session states. A redraw changes only what differs, so focus, a text selection, the filter's caret and the scroll position stay. Its links open a session with [Open in VS Code](#claude-code-runner) while it is not running in its background process, or a Code Mode session's attach terminal in every state (**Code Mode sessions** below), a worktree as a folder, and a URL or file.
- **Switchboard pane** (PRD R92): webview views in the Explorer and in Source Control. `paneModel` (`src/paneModel.ts`) builds the pane from `dockView`, so it shows the dock's rows, with their pills, marks and main control, for this window's workspace file only, plus the latest status of this window's Conversation view on its own work item and the voice status with Talk here; it shows no unread count ([Unread](#unread)) and nothing global. A redraw keeps a focused control focused. A pill opens as an item window tab does. The main control runs as the dock's does, from the latest snapshot: a hub control after its confirmation or input; Open in terminal as a `terminal` window command for this window, claimed at once, so the hub adds the agent's CLI; or else the row's click (**A row's click from VS Code** below). A row no longer in the window runs nothing.
- **Side bar widths** (PRD R91): while `switchboard.rememberSideBarWidths` is on, the extension keeps the widths the operator drags each side bar to at each window width, shared by every window of the profile, and sets the side bars from them when the window's width changes, between the nearest kept widths. VS Code has no API that reads or sets a side bar's width, so the pane's page reports the window's and the pane's sizes, which only a visible view reports correctly (mechanics M61), the editor layout gives the editor area's width, the window's frame, sashes and activity bar are taken as fixed offsets (mechanics M61), and widths change only by VS Code's width step commands. It therefore needs the pane in the primary side bar and one editor group, keeps the editor area above its minimum, pauses below `switchboard.sideBarWidthsMinWindow`, and leaves the focus where it was. To measure at all, it expands the Explorer's pane once per workspace. Reset Side Bar Widths forgets every kept width. It logs each kept width and restore to the `Switchboard Side Bars` output channel.
- **A row's click from VS Code** (PRD R65, R69): `openRow` (`src/open.ts`) runs a row's click as the dock's **Click** does, from the window's latest snapshot: a row without a window opens its focus (PRD R79); a hosted conversation's row posts `POST /dock/select {rowKey}`; `question` posts `open-question` and waits for the session to end; `session` posts `POST /open {sessionId, cwd, workspace}`; a `terminal` or `select` row is the dock's to run, through `POST /dock/click {rowKey}`, which answers 409 when no dock runs. It then opens the workspace file in a new window, which VS Code answers by bringing forward the window that has it, or opening one; VS Code holds the foreground after the operator's click on its notification or link, so Windows lets it, where it would refuse the dock (mechanics M26). The item window claims the session when it gains focus, and this window at once, because it does not gain focus again. A second click on the row being opened is ignored, and a click on another row replaces it, as in the dock.
- **Notifications of work on the operator's turn** (PRD R65) are the dock's, because a window sees only its own work item ([Dock](#dock)).
- **Open in Switchboard** (PRD R69): `vscode://switchboard.switchboard/open?url=<ticket URL>` reaches the extension's URI handler, which takes everything after `url=` as the ticket URL, so a URL with its own `&` survives, and posts `POST /open-url {url}`. The hub answers one row of the dock view, with its terminal commands: the first in list order whose ticket URL matches, then the first whose ticket has a matching link, comparing URLs by `urlKey` (`packages/core/src/group.ts`), under which any tab of a GitHub issue or pull request is the same URL. It is the one exception to the [window scope rule](#window-scope), because the operator asked for it, and the click runs in VS Code because Windows refuses the dock's `SetForegroundWindow` without the latest input (mechanics M26); a row whose click stops a session for its question runs in the dock (`POST /dock/click`), because it waits for a snapshot the window cannot see. With no row the hub answers 404, and the window says no work item has the URL.
- **Status bar item** (PRD R64, R71): shows the dock (`POST /dock/show`), and starts the installed dock when no dock stream is connected or no hub answers. How many work items need the operator is the dock's to show, since a window sees only its own work item.
- **New Claude Session in Editor Tab** (PRD R75): opens a new Claude Code editor tab with `claude-vscode.editor.open` and `{programmatic: 'pin-to-panel'}`, which writes no preference (mechanics M29).
- **Continue in Background** (PRD R89): moves the session of the active Claude tab, or of the Claude sidebar, to its background process and closes the window. It refuses, asking the hub nothing, unless that session is the window's only Claude session, no Open in terminal terminal is open, and nothing is unsaved. It posts `POST /background {label, hostPid, workItemIds}` with the tab's label (null for the sidebar), its extension host's process ID and the window's work items; on 200 it asks `POST /background/check` whether that process is still the window's only Claude session, then closes the tab, which ends its process, and the window. From the sidebar it only closes the window, because hiding the sidebar leaves its process running (mechanics M55). A refusal, a changed window, or a tab that would not close shows a warning and closes nothing more, and the hub's wait then leaves the session in its tab.
- **Hub log.** Each window follows `hub.log` in the `Switchboard Hub` output channel, a plain channel with the `log` language, so lines keep the hub's own timestamps. Switchboard: Show Hub Log and the dock's `log` window command show it without taking focus.
- **Code Mode sessions** (PRD R95): a Code Mode session opens only as its attach client ([Attach client](#attach-client)), never in a Claude view: the hub sends its Open in terminal, and turns a claimed open of it, into a `terminal` command with `codeMode: true`, and `/claim` adds the executable, `sessions.nodePath`, and `hub.js attach <Switchboard session ID>`. The window runs it without a shell in a terminal keyed by the Switchboard session ID, so a Claude session ID change finds the same terminal, and shows that terminal again while the client has not exited. A window reload forgets which terminal is the session's, because VS Code restores a terminal without its command, so the next Open in terminal opens a second attach client. History's links for a Code Mode session say Open in terminal in every state and post `POST /open` with the window key; the hub answers the destination window, which claims it at once when it is this window, else is brought forward to claim it. Every failed hub request shows a warning with the hub's refusal, or says the hub did not answer, with a Show Hub Log button.
- **Conversation view** ([Conversation view](#conversation-view)): `ConversationView` in `src/conversation.ts`.

The command palette offers only what no visible control does, and the voice commands only while the voice is on (`switchboard.voiceEnabled`); every command stays registered.

## Dock

PRD R71. `apps/dock` is a C# Avalonia app for Windows and Linux. Window management sits behind `IWindows` and `IVsCode` (`Switching/Platform.cs`), with Windows implementations in `Platform/`.

A new dock view updates the list in place, keyed by group, date band and row, so keyboard focus, the selection and the scroll position survive it; the held sessions and Settings windows update in place the same way. While the pointer is pressed the dock holds the latest view until release, so a view cannot replace the pressed row before its click runs; a row drag releases it.

- **Linux.** Under GNOME on Wayland an app cannot list, raise or watch another app's windows (mechanics M38). The dock runs under XWayland: it docks as an X11 dock window, else floats, and finds and raises windows through the GNOME Shell extension's service when it is on the session bus at start, else through the hub. Either way it follows the window in front through the hub's view of connected windows ([Hub lifecycle](#hub-lifecycle)): a change of the front window to an item window selects its row, and an item window that closes clears the selection, as on Windows.
  - **Docking.** As a dock window, which Mutter keeps above other windows, on every workspace and out of the taskbar (mechanics M39), the dock takes the strip at the kept edge of the kept monitor, matched by RandR output name, or of the primary monitor when that is gone, within Mutter's work area for that monitor, because the X work area is one rectangle for all monitors (M39), and reserves it with struts, except at an edge another monitor adjoins, where a strut would also reserve that monitor's rows. Mutter does not focus a dock window on a click, so the dock takes the focus itself after a press that was not on a row, when a click or command did not finish, and on `show`; a press on a row leaves the focus where the click puts it, because taking it on the press lost the click (M39). It moves below a full-screen window on its monitor.
  - **Extension.** `extensions/gnome-shell` exports `switchboard.Shell` at `/switchboard/Shell` on the session bus: `Windows() → a(ts)` and `Terminals() → a(ts)` list VS Code's and Ptyxis's normal windows, front first, by Mutter window ID and title (mechanics M47); `Activate(ts) → b` brings one of those windows to the front, maximized, on the monitor with the given connector; the `TerminalFocused(s)` and `TerminalUnfocused` signals report a Ptyxis window gaining and losing the focus, since VS Code windows report theirs through the hub; `OpenUrl(s) → b` opens an http or https URL with a launch context that lets the browser come to the front, and the dock falls back to `xdg-open` when it refuses, fails or is missing, but not when it times out, since it may still open the link (mechanics M54); `FullScreen() → as` and `FullScreenChanged(as)` give the monitors a full-screen window covers. Any client on the session bus can call it, including to open a web URL with the browser in front.
  - **With the extension.** Each call has a short timeout; while calls fail, such as after the extension is turned off, the dock answers as without it, and tries the shell again on the next call.
  - **Without the extension.** The dock knows an item window only while it is connected to the hub, and shows it with `code <file>`, whose result it cannot confirm, so a window command waits for the next VS Code window to gain focus. The dock stays above full-screen windows.
  - **Floating.** For a window that is not an X11 window, the dock is an ordinary window at the kept edge, moved by its title and resized by its grip, with no auto-hide.
- **View.** `dockView` in `packages/hub/src/dock.ts` builds what the dock shows from the snapshot with the row rules of `rows.ts` ([Rows](#rows)), so the dock adds no rules of its own: notes, groups in list order with their rows, controls, window commands, pastes, links and Done date bands, the snooze choices (PRD R49), the sources, repo roots and schedules. `apps/dock/test/fixtures/dock.json` is a recorded view that the hub's tests compare `dockView` with and the C# tests parse, so the two sides keep one shape.
- **Search before Done** (PRD R63). `POST /dock/search {text, since}` answers `{rows, more}`: up to a fixed limit of the Done rows of work items done from `since` (epoch milliseconds, 0 for all time) to the snapshot's Done range, not snoozed, whose search text holds every word of `text` ignoring case, newest first, banded by the month they were done, with `more` when more matched. The hub reads the range's search texts once per snapshot, so searches as the operator types filter in memory. `POST /dock/select` finds such a row's work item in the store when the snapshot does not list it.
- **Window.** A row's window (`windowOf`): a hosted conversation's is its host's ([Hosted conversations](#hosted-conversations)), so its workspace file is the host's and the hub leaves it alone; a folder-hosted conversation's is a folder window, with no workspace file and no `sb:` title. Otherwise its first folder is the latest session's `cwd`, else the worktree, with the worktree second when it differs; a row has no window without either, or while the latest session is `external` and not ended, because the session lives in the operator's own window (PRD R81). Its name is the ticket key, or the ad-hoc key for a ticket a ticket report moved (PRD R83), the first folder's name when it is not the worktree, and a short hash of the first folder's path, such as `gh-18941-3f2a91`, so two folders with the same name, or a moved worktree, get different windows; its file is `<Switchboard home>/windows/<name>.code-workspace`. Its `open` is `question` while the active session waits in its background process, `session` for the latest session when none is active or the active one was released, `url` for a row without a window whose focus is a URL, and otherwise null.
- **Workspace file.** `writeWorkspaceFile` is the one writer for the hub, before it sends a dock view, and the extension, before its own [row click](#vs-code-extension). The file holds the folders, a window title that ends in `sb:<name>`, by which the dock finds the window, with each `$` of the ticket title replaced by a fullwidth `＄` because VS Code drops text after a `$` (M26), and `extensions.ignoreRecommendations: true`, because VS Code keeps a dismissed recommendation prompt per workspace, so every new item window would ask again (M50). It writes a file only when its text differs, because VS Code applies any change to the open window. A view from a hub older than the dock names no file, and the dock asks for a window reload.
- **Terminals** (PRD R71). The dock opens a session's terminal in the terminal app, Windows Terminal or Ptyxis, titled with the session's terminal name, and finds it again by that title. Its environment has no `ELECTRON_*` or `VSCODE_*` variables and none of Claude Code's session markers, keeping other `CLAUDE_CODE_*` settings as the hub's sessions do. Open in terminal opens the dock's terminal or the item window's VS Code terminal as `dock.openTerminal` gives the row, and with both, the one the session is already live in. A `handoff` first stops the session for its question, as a click does. The dock reports to the hub (`POST /dock/focus`) the Code Mode session whose attach terminal is in front, or null, when it changes and when it connects ([Voice](#voice)). **Answer in terminal** is a main control that runs the row's click. Clicks VS Code forwards arrive as `click` events on `/dock/events?click=1`.
- **Click target** (PRD R71). `dock.openIn` chooses where a row's click opens: `web` shows the work item on the installed web page used last, otherwise the click opens in VS Code; an Alt-click runs the other, and a click VS Code forwarded or a main control that is the row's click always opens in VS Code. For the web page, the dock posts `POST /dock/page {rowKey}`, which answers `{marker}` once the installed page used last was sent `show {workItemId, marker}`, `{url}`, the page's address at the work item, when no installed page is open, and 404 for a row with no work item. On Windows the dock then brings forward the window whose title holds `[sb-show <marker>]`; on Linux the page selects the work item where its window is.
- **Code Mode sessions** (PRD R94, R95): the dock's terminal for a Code Mode session runs its attach client, `<sessions.nodePath> <home>/hub.js attach <Switchboard session ID>`, named by the Switchboard session ID, so the dock finds the same window after a Claude session ID change. More Actions has **Held sessions**, a window listing the view's `held`, the holder's sessions with orphans first, which opens a session's attach terminal (not an orphan's, which `POST /attach` refuses) and stops one after a confirmation (`POST /holder/stop {id}`), unavailable once its process has exited. While an orphan exists the view's `heldNote` shows above the groups and opens that window. The view's `holderNotice` shows under it with **Restart and resume** while the notice has a `confirm`, which posts `POST /holder/restart {detail}` after the confirmation, and `holderResult` shows until dismissed ([Restarting the holder](#restarting-the-holder)).
- **Click.** A row without a window opens its `open` URL, its focus (PRD R79); the ticket's URL stays for Open ticket. A hosted conversation's row first posts `POST /dock/select {rowKey}`. A folder-hosted row opens VS Code on its folder and waits for the view to list a connected folder window on it; only a folder window on that folder claims what was left for it, never an item window that holds the folder. For `question` the dock posts `open-question` and waits for the row's `open` to become `session` with the same session; for `session` it posts `POST /open {sessionId, cwd, workspace}`, which only the window opened from that workspace file claims, so another window on the same folder does not take it ([Open in VS Code](#claude-code-runner)). When the click is cancelled, or VS Code or the window does not come within the wait, the dock posts `POST /open/withdraw {id}`, so no window opens a session from a click the operator gave up on. Before it opens an item window it posts `POST /window {workspace, command: {type: 'openTabs'}}`, so the new window opens its [tabs](#vs-code-extension) (PRD R72), withdrawn only when VS Code does not start; the hub refuses `openTabs` without a workspace. On Windows the dock brings the item window forward, moved to the dock's monitor and maximized, from the click itself, because Windows lets a process bring another window forward only while its own input is the latest (M26). A click on another row cancels the running click, which then makes no further request or switch; a click on the row being switched to is ignored; and a question is never stopped twice. Each failure shows on the dock's status line, which clears itself after a while unless the pointer is on it.
- **Foreground.** On Windows the dock watches the foreground window and selects the first row, in list order, whose window name the title's last `sb:<name>` gives (M26), never a folder-hosted row, opening its group and scrolling to it; when an item window closes, a selected row with that window is cleared (M26).
- **Controls** (PRD R71). A selected row shows its main control: Open in Claude, Open in Codex and Answer in terminal run the click, a prompt before start's Open in terminal opens the terminal, and any other posts its hub action. Copy puts an `awaiting-approval` row's draft on the clipboard. A window command (Open changes, History, Open report) posts `POST /window {workspace, command}` for the row's workspace file and switches to its item window as a click does, or, for a row without a window, goes to the VS Code window nearest the front; when the switch is cancelled or fails the dock posts `POST /window/withdraw {id}`, so the window that comes to the front next does not run it. A right-click or the Menu key opens the row's menu with every control the row has, grouped; a control with `confirm` posts only after a confirmation, and one with `input` asks for its text first. Failures and refusals show on the status line in the warning colours, and information in neutral ones. Every dock menu, its submenus and the dock's tooltips stay on the monitor of their anchor, within its work area widened to the dock's strip, or Mutter's work area for that monitor as an X11 dock window, opening away from the dock's edge, because Avalonia's own placement limits a popup to the monitor it was created on.
- **Order** (PRD R73). Ready for review rows can be dragged to a new place, which posts `{type: 'move', workItemId, after}` with the row above, or null at the top; Escape cancels. Alt+Up and Alt+Down move the selected row. F8 and Shift+F8 select the next or previous row on the operator's turn in Blocked on you and Ready for review, wrapping, and run its click.
- **Pinned headings** (PRD R27). The heading of the group at the top of the list stays pinned while its rows scroll under it, until the next heading pushes it up, and a row the keyboard reaches is scrolled into view below it.
- **Keyboard** (PRD R71). Rows, group and date band headings and every pill take the keyboard focus. A row the keyboard reaches is selected and scrolled into view, so Tab reaches its buttons; Up and Down move between rows and headings; Enter runs a row's click, the Menu key or Shift+F10 opens its menu, Enter or Space opens or closes a heading and opens a pill's link. A new view keeps the focus on the row's controls, or on its group's heading when its new group or band is closed.
- **Line 2** (PRD R27, R52). A row's second line (`PillLine`) gives the playbook the width its comment icon and pills leave, ending in an ellipsis. With too little room, pills shrink to their icon instead of being cut: first the pills wider than 56 pixels, longest first, while the playbook keeps its width; then, once the playbook is down to 60 pixels, the rest longest first; Returned last. Pills that do not fit even as icons are left out whole, the last first and Returned only when it alone does not fit. A compact pill keeps its link and click and has its full text and URL in its tooltip. A pill's label is never cut, and the pills show whole again when the dock widens. The web page lays out line 2 with CSS alone, never measuring it, so a redraw cannot change it (the operator's decision, 2026-11-22): the comment icon, the playbook and the ticket key are never cut, the key wrapping under the playbook where both do not fit on one line and the playbook or host wrapping where it alone is wider than the line, and the link pills and Returned do not shrink to icons but are left out whole where they do not fit, Returned first, then the links from the last.
- **Dialogs.** Every dock dialog shares one layout and keys: the focus starts on the first input; Enter runs the main action, except from a focused button, an open list or a multi-line box, where Ctrl+Enter does; Escape cancels. A destructive action, such as Delete or Stop, is drawn in the danger colour, is never run by Enter, and opens with the focus on Cancel.
- **Header.** The title row keeps Close showing on a narrow dock, hiding a control that does not fit whole. It holds one icon per source kind, which turns that kind's source on or off (`POST /sources {name, enabled}`), or, for a kind with several sources, opens a menu of them; Search; Auto-hide; More Actions; and Close. More Actions holds New ad-hoc session…, New conversation in a folder… ([Hosted conversations](#hosted-conversations)), Held sessions, Refresh sources (`POST /poll`), Show hub log, which the VS Code window nearest the front shows, and Open Settings ([Settings window](#settings-window)). The search box filters the rows whose search text, the title, key, linked pull requests and issues, playbook, group and worktree branch, holds every word ignoring case, opening every group and date band with a match and hiding the rest; a ticket or link key matches at once. A range past the first also asks the hub for older Done rows (**Search before Done**), which join Done until the filter or range changes. New ad-hoc session posts `adhoc` with the prompt, a repo root or any chosen folder, the provider and whether to start, or `run-schedule` for a schedule (PRD R82); a refusal keeps the window and its prompt, and a second Create cannot create a second work item. A foreground item window whose row the search hides clears the search.
- **Docking.** On Windows the dock is an app bar on the kept edge of the kept monitor, matched by device name, else the primary one: it reserves its strip, at the kept width in device-independent pixels at the monitor's scale, and holds every later move and resize to it, because Avalonia moves a window it resizes into the monitor's work area, which starts at the dock's own inner edge. It works around Avalonia not resizing on a DPI change (M26), stays hidden until it has drawn in its strip, and reserves the strip again when the taskbar, the displays or another app bar change, so a dock whose monitor was unplugged docks on the primary one. Dragging the inner edge resizes it, keeping its outer edge, and the strip is reserved again on release, so other windows move once.
- **Auto-hide** (PRD R71). The header's pin turns auto-hide on and off, kept in `dock.json`. With auto-hide on, the dock reserves nothing and registers as its edge's auto-hide bar, which Windows refuses when another app holds that edge, and hides all the same. Hidden, it keeps its layout but draws and takes the pointer only in a 3-pixel sliver at the outer edge, showing the rows' coloured stripes; a short hover shows it, as do activation and a `show` event. It stays open during a resize or drag, while one of its menus, flyouts or owned windows is open, under the pointer or focused; the Settings window, which has no owner, does not keep it open. Hiding closes its menus. The dock stays topmost, even while hidden, except when the front window on its monitor is full screen.
  - **On Linux,** auto-hide needs the X server's Shape extension; without it the pin does not show and the dock places itself as with auto-hide off. Hiding shapes the window to the sliver; showing shapes it to the whole window rather than removing the shape, because Mutter kept drawing only the sliver after the shape was removed (mechanics M49), and once a shape is set each resize sets it again, or Mutter can keep clipping to the old width (M51). The same windows keep it open as on Windows: its dialogs, through their transient-for chain, and its menus and tooltips, which Avalonia gives no owner, as override-redirect windows of its own process. Avalonia closes a menu only when the dock loses the focus, so the dock takes the focus as a menu opens and closes its menus once the focus moves to another window. A hidden dock shows before it opens a dialog, because a modal dialog blocks the pointer moves that would show it.
- **Moving.** Dragging the header's title docks the dock at the nearer left or right edge of the monitor under the pointer, and keeps that edge and monitor.
- **State.** The dock owns `<Switchboard home>/dock.json`: its width, edge and monitor (null for the primary), `autoHide`, `theme`, the folders New ad-hoc session chose recently, and the groups the operator opened or closed. Done's date bands are not kept: each dock start opens Today and Yesterday. One dock runs per desktop, and closing it ends the app. `--home` or `SWITCHBOARD_HOME` names the folder holding `.switchboard`, as for the hub.
- **Connection.** The dock reads `hub.json` and opens `/dock/events` with its token, reading `hub.json` again after the stream ends or fails. Besides `dock`, the stream sends `show` (the status bar item's `POST /dock/show`), `config`, which makes an open Settings window read the files again, `click`, a click VS Code forwarded, and `needs`; the dock skips any other event. A 404 means a hub older than the dock, and the dock asks for a window reload; anything else without a stream reads as not running, and the dock starts a hub ([Dock start](#hub-lifecycle)). While it has no current view the last rows stay, dimmed and disabled, a row control is refused, and while no hub runs a **Start hub** button starts one at once and shows why it could not.
- **Needs you** (PRD R65). The hub compares each snapshot with the one before and announces the work items that started needing the operator on one surface, never after a hub start's first build. `alerts.surface` picks it among the pages that may notify: `auto` the installed page used last, `web` that or else any such page used last, and `dock`, or no such page, the dock. The dock gets `needs {items: [{rowKey, message}]}` and shows each message in its status toast, whose click runs the row's click. A page gets `needs {items: [{workItemId, message}], sound}` on its conversation stream and shows the message under its list header and as a browser notification per work item, which selects the work item ([Web page](#web-page)); `sound` is set only when the voice played no chime and spoke no alert for it, so one event makes one sound.
- **Look.** Colours are VS Code's Light Modern and Dark Modern theme values; custom palette colours are not copied. The Settings window's dock theme (`system`, `vscode`, `light` or `dark`, kept in `dock.json`) is saved with the configuration draft and applies to every dock window and popup. `system` follows the operating system. `vscode` follows the theme kind the extension reports on focus, theme change and connection through `POST /window/theme {theme: 'light' | 'dark', at}`, high contrast mapped to light or dark; the hub keeps the latest report in memory and sends it in dock views, ignoring older ones, and the dock uses `system` until a report arrives and while disconnected. The Settings window's controls take VS Code's input and button colours, and marks are codicons.

## Browser extension

`extensions/chrome` is a Manifest V3 extension (PRD R56, R113) that the operator loads unpacked. On GitHub project boards and tables it hides snoozed cards, shows each card's playbook and status, and adds Switchboard's items to a card's menu; in Chrome it also keeps the [Chrome pane](#chrome-pane)'s window.

`extensions/firefox` builds the same source for Firefox and changes only what Firefox requires ([mechanics.md](mechanics.md) M52); the build fails when Chrome's manifest or stylesheet no longer has the shape it adapts.

- **Firefox differences.** Firefox runs a background script in place of the service worker, needs an add-on ID, and matches nothing with a host pattern that has a port, so its host permission covers every port of the loopback host. It has no key-derived ID and no messages from web pages, so it has no Chrome pane and asks for none of the pane's permissions. Firefox lists MV3 host permissions as optional; until the operator grants them, the board shows nothing.
- **Firefox distribution.** Release Firefox keeps only add-ons that addons.mozilla.org signed, so the build is signed as an unlisted add-on, which is not published, and each signed version is kept as a release of the private GitHub repository at the commit it was built from. addons.mozilla.org signs each version once, so each build's version is Chrome's with a build number added, and signing refuses a version already released or lower than one released. Firefox cannot download from the private repository, so the add-on does not update itself. The `@switchboard/firefox` workspace's scripts sign, release, run a development copy and package an unsigned build.

- **Hub access.** A content script on github.com cannot read a loopback address, so the service worker makes every hub request. The hub serves the extension on a fixed loopback browser endpoint, because an extension cannot read `hub.json`. The endpoint sends no CORS headers, so web pages cannot read it, and refuses a Host other than the loopback address, against DNS rebinding. Its routes are `GET /snoozed` (the snoozed tickets' URLs), `GET /cards` (each ticket's card: playbook, group, mark, the dock row's stripe colour and whether it is snoozed, PRD R67), `POST /snooze` and `POST /unsnooze` (PRD R66), and `/pane` ([Pane socket](#pane-socket)). The manifest's only host permission is that endpoint; a copy for another device adds its page's origin.
- **Another device** (PRD R121; [mechanics.md](mechanics.md) M128). The VS Code extension carries the build (`dist/chrome`), and an install puts it in `<home>/web/chrome/` beside the page's other files. The signed-in page downloads it from `/page/switchboard-extension.zip` as one `switchboard-extension` folder. A paired device's copy adds `remote.json` with the page's HTTPS origin and a host permission for that origin; this computer's copy is the build as it is. With `remote.json` the service worker reads and posts `/v1/browser/snoozed`, `cards`, `snooze` and `unsnooze` on that origin instead of the loopback endpoint. They are page routes: the request passes the remote access checks and needs the page's sign-in, which Chromium sends with an extension's requests to a host it has permission for, `SameSite=Strict` as it is, so the copy holds no secret and works only in the browser that paired; a post must also come from an extension's `Origin` with a JSON body, as on the endpoint. Such a copy opens no pane socket, and Open in Switchboard opens the card's work item on the page (`/page/#w=<id>`, from the card's `workItemId`) in a new tab. Firefox would need its signed build, which cannot take a file per hub, so the page offers only the Chrome build.
- **Failure contract.** A failed snoozed read counts as none snoozed. A failed cards read, including a 404 from an older hub, removes every pill and adds no menu items. A card with an unknown group, mark or stripe fails the read; one with no mark or stripe, as from an older hub, draws without it.
- **Snoozed cards** (PRD R56). The content script acts only on a page with a project board or table, and hides the snoozed cards of each column or group behind a toggle that shows them. GitHub renders only the cards and rows in view and empties the rest, so the script remembers each card's issue from when it last rendered, counts a group's snoozed rows from what it has seen in the current view, and leaves a card it has never seen rendered shown.
- **Pills** (PRD R67). Each card or row whose issue matches a card from `/cards` shows a pill with the playbook, or the group when there is none, and the work item's mark. The hub computes group and mark with core's `groupOf` and `markOf` (`packages/core/src/group.ts`), so the board and the dock follow one rule; that module imports only types, so a browser bundle imports it as `@switchboard/core/group` without the store.
- **Card menu** (PRD R66, R69). The menu that GitHub opens for a card or table row gains **Open in Switchboard** for a ticket `/cards` lists and, outside Done, **Snooze in Switchboard…** or **Unsnooze in Switchboard**. The items follow each accepted cards read while the menu is open. Snooze choices come from core's `@switchboard/core/snooze`, which keeps Node modules out of the browser bundle. After a snooze or unsnooze succeeds the board and pills read again; a failure shows the hub's error.
- **Open in Switchboard** (PRD R69). The menu item, or a click or Enter on a pill, opens `vscode://switchboard.switchboard/open?url=<ticket URL>`, whose handler in the VS Code extension does what a click on the ticket's dock row does, before GitHub would open its side panel.
- **Page updates.** A pass over the page changes only what differs, so it does not trigger its own mutation observer and a focused pill or menu item keeps its focus.
- **Chrome pane** (PRD R113, Chrome only). The manifest's `key` fixes the extension's ID, so an unpacked copy from any folder has the ID the hub checks, and `externally_connectable` lets loopback pages, on any port, send it a wake or a pairing token. Chrome logs every refused WebSocket handshake as an error on the extension's page, so the extension opens the [pane socket](#pane-socket) only when it holds a credential or a token and `GET /pane` says the pane is on, backs off while the hub does not answer, and stops after repeated refusals until the page sends a new token or the browser restarts. A ping keeps the service worker alive. Once paired it carries out the hub's messages one at a time, in order: `window` opens or reuses the pane window and titles its page with the marker; `tabs` keeps one tab per listed http or https URL, brings the active one to the front and closes the tabs it opened for URLs no longer listed, leaving tabs the operator opened. It sends `closed` when the pane window closes and ignores any other message.
- **GitHub's DOM.** The selectors are GitHub's, not a contract; the fixtures in `extensions/chrome/test/fixtures` record them, with the date each was captured.

## Chrome pane

PRD R113, behind `web.chromePane`, Windows only: the selected work item's links of the installed web page, in a normal tabbed Chrome window that the hub's pane helper places over the page's Browser tab, with or without the dock. Four parts take part: the hub's pane socket and state ([Pane socket](#pane-socket), [Pane state](#pane-state)), the extension's pane window ([Browser extension](#browser-extension)), the page's Browser tab and its area report ([Web page](#web-page)) and the pane helper the hub runs ([Pane helper](#pane-helper)). The mechanisms rest on a spike on one machine and Chrome 157 ([mechanics.md](mechanics.md) M103) and can break with any Chrome update.

### Pane socket

`PaneLink` in `packages/hub/src/paneLink.ts` is the hub's end, over a WebSocket server written for this one use (`paneSocket.ts`), so the hub bundle needs no library.

- **Upgrade.** `GET /pane` on the browser endpoint, from a loopback `Host`, with an `Origin` of exactly `chrome-extension://<PANE_EXTENSION_ID>` (core's `hubRecord.ts`), the ID Chrome derives from the public `key` in the extension's manifest. Anything else, and every upgrade while `web.chromePane` is off, is refused with 403. Turning the setting off closes every socket.
- **Frames.** Masked, unfragmented JSON text frames of bounded size, with ping, pong and close; a frame outside that closes the socket with the matching RFC 6455 close code.
- **Pairing.** A new socket must soon send `{type: 'hello', credential}` or `{type: 'pair', token}`. A credential matching the kept one gets `{type: 'paired'}`; any other gets `{type: 'unpaired'}`, after which the socket may send a token. The signed-in page gets a token from `POST /v1/conversation/pane-pair {window}` (page commands only, 403 otherwise; 409 while `web.chromePane` is off), which answers `{token, extensionId}`. A token is random, good once and for a short time, and a new one replaces the last. A matching token gets `{type: 'paired', credential}`, a new random credential that replaces the kept one, so an earlier pairing stops working; a wrong, used or expired token gets `{type: 'unpaired', error}`. The hub keeps only the credential's SHA-256, in `<Switchboard home>/chrome-pane.json`, never the credential. An unpaired socket that sends anything else is closed, few unpaired sockets stay open, and a silent socket is closed.
- **Paired.** One paired socket at a time; a newer one replaces it. Its messages other than `hello`, `pair` and `ping` go to the [pane state](#pane-state), and only it receives the hub's.
- **Why both checks.** Any extension can put the same public key in its manifest and get the same ID, and an extension allowed to rewrite request headers could send this Origin, so the Origin keeps out web pages and ordinary extensions, and the credential, handed over only through the signed-in page, keeps out the rest. The token travels from the page to the extension in Chrome's `runtime.sendMessage`, which only the extension with that ID receives.

### Pane state

`PaneState` in `packages/hub/src/pane.ts` decides which page owns the pane, what it shows and where.

- **Owner and column.** The page posts `POST /v1/conversation/pane-rect {window, rect}` (page commands only, 403 otherwise; 400 for another body), `rect` being its Browser tab's area under the tab strip in CSS pixels with the page's scale and viewport, or null. The hub takes an area only when it is at least a normal Chrome window's minimum width (mechanics M103), else null. A page posts null whenever another tab is chosen, so the pane hides and its page keeps it. A page owns the pane when no page does, and the page that last gained its own focus takes it over once it has a column, so a page in the background never moves it; a change of owner, or the owner's stream closing, starts over.
- **Tabs.** The owner's tabs come from its selected work item's dock row: the ticket URL, then each http or https link, once each and bounded in number, with the pull request's tab in front while the row is in Ready for review and the ticket's otherwise. After them come the web links the page opened from its conversation for that work item (`pane-open {window, url}`, a local command, http or https only), the last opened in front, kept per page and work item. `pane-open` is refused while the pane is off, no extension is paired or the pane helper will not run, so the page opens the link itself, and it starts again a pane the operator closed or a failure stopped. They go to the extension as `{type: 'tabs', urls, active}` only when they change.
- **Handshake.** The hub runs the [pane helper](#pane-helper) only while `web.chromePane` is on, a paired extension is connected, a page owns the pane and no failure or close stopped it. The pane is active while that holds and the helper is ready. Becoming active makes a random marker and sends the extension `{type: 'window', marker}`; the owner page puts the marker in its title, and the helper gets it in its order, so the helper can find both windows by title. When the helper reports `found`, the page's title marker goes and the tabs follow.
- **Helper.** A ready helper gets `{type: 'pane', marker, rect}` when either changes and on each report of the owner page: `marker` null when the pane is not active, `rect` null to hide it. It reports `ready` once it runs; `found`, `shown` and `hidden` for the current marker; `lost` when either window was recreated, which starts over with a new marker; and `failed` with why, which stops the pane and shows why on the page until the page shows another work item. A report for another marker is ignored. A helper that stops starts the pane over with a new marker once one is ready again; while none will be started again, the page shows why.
- **Closed.** When the extension says the pane window closed, the pane stops until the page shows another work item, so a window the operator closed does not come straight back.
- **Page.** Each page gets a `pane` event when its state changes: whether the setting is on, the extension's link state (`none`, `unpaired` or `paired`), the marker while the helper has not found its window, whether the pane shows over its column, and the last failure, or else why the helper does not run.
- **Focus.** While the helper reports the pane window in front, the owner page counts as focused for the voice ([Voice](#voice)) even after the page reported losing focus.

### Pane helper

`apps/pane-helper` builds `Switchboard.PaneHelper.exe`, a .NET 10 console program for Windows that keeps the pane window over the page's column. It needs no dock and shows no UI. `ChromePane` holds the decisions against the `IPaneNative` interface, which `Win32PaneNative` implements, and `PaneGeometry` and `PaneTitles` hold the arithmetic and window choices as pure code; the Windows mechanisms they rely on are recorded in [mechanics.md](mechanics.md) M103.

- **Install.** The VS Code extension's build publishes it, framework-dependent, and activation, or `hub.js install` without VS Code, installs it per build into `<Switchboard home>/pane-helper/<build>/` as it installs the terminal holder, keeping the build a running helper loaded. It needs the .NET 10 runtime, as the dock does.
- **Protocol.** It runs as `Switchboard.PaneHelper.exe --home <Switchboard home>`. stdin and stdout carry one UTF-8 JSON object per line: the hub's `{type: 'pane', marker, rect}` orders ([Pane state](#pane-state)), and the helper's reports `{state, marker, focused?, reason?}`, which the hub validates. stderr goes to the hub log; the helper also logs to `<Switchboard home>/chrome-pane.log`. When stdin closes or stdout no longer takes a line, it lets the pane go and exits.
- **Orders.** A new marker lets go of the windows it had and finds the pane window by its marker title and then the page's window by its marker, or by its title when Chrome names an app window differently (mechanics M103); not finding them in time reports `failed` naming the missing window. A null marker lets go.
- **Placing.** Found, the pane window becomes owned by the page's window and is placed over the column, so it moves, hides and shows with the page; a column of null hides it and a column shows it again in place. The helper never activates the pane or takes the foreground, aligns again after any move or resize of either window, and leaves a minimized window alone. It reports `lost` when either window is destroyed, and `focused` whenever the pane window comes to or leaves the front.
- **Failure.** A placement that Windows refuses or that does not hold, after limited retries, reports `failed`, and the helper lets go with the pane shown and no longer owned, a plain Chrome window, until another marker. Any other letting go, on another marker or none, as when the page reloads or the helper stops, hides the pane first, so no tab shows it until a page's Browser tab places it again.
- **Supervision.** `PaneHelper` in `packages/hub/src/paneHelper.ts` starts the current installed build while the pane state wants it, with the hub's environment without VS Code's variables, and records it in `<Switchboard home>/pane-helper.json` so an install keeps its build. Not on Windows, or with no installed build, it starts nothing and the page shows why. A helper no longer wanted gets its stdin closed and is killed if it does not exit. One that exits on its own is restarted with a growing delay; after repeated quick exits the hub stops trying and the page says so until the helper is no longer wanted. Closing the hub stops it.

## Settings window

PRD R54. A separate, resizable dock window, **Switchboard Settings**, one at a time, that edits settings.json; its page logic is plain C# in `apps/dock/src/Switchboard.Dock/Settings/`. The web page's Settings uses the same hub routes ([Web page](#web-page)).

- **Hub owns the file.** The hub reads, checks and writes settings.json, and the window needs a running hub. `POST /config/read` answers the file (its path, version, value and any error), the config folder and what the editor offers: permission modes, providers, template variables, source kinds, the open work items per playbook and which sources are on. `POST /config/check {settings}` answers `{errors}`. `POST /config/save {value, version, configDir}` writes the whole file as formatted JSON and answers `{saved, version}`, or 409 `{errors}` when the file changed since `version`, the folder is not the hub's current config folder, or the settings have errors.
- **One authority for errors.** Checks (`checkSettings` in `packages/hub/src/config.ts`) apply what the hub applies on load: the settings parser, each enabled source's own parser and each playbook's, plus a check of template variables, because the hub otherwise finds an unknown variable only when rendering fails. A source's errors count only while it is on, so a source that is off can be saved incomplete. A playbook's errors read `playbooks.<name>: <error>`.
- **Optimistic concurrency.** A file's version is the SHA-256 of its text. A save names the version its draft started from and is refused when the file on disk no longer matches; a successful save answers the version it wrote, so editing continues over it. Writes go through a temporary file and a rename, so the hub's reload never reads a half-written file. The hub's watcher reloads the written file as it does a hand edit, and then sends `config` to the dock and every page, which read the file again.
- **Draft.** The window holds one draft of the whole file and never saves on its own. Save is refused while the file changed on disk under the draft or while any error stands; a refusal keeps the draft. A draft equal to the file is dropped on a read; any other draft whose file changed is kept with a warning and cannot be saved, so the operator discards it to take the file on disk. Closing the window with unsaved changes asks whether to save; closing the dock closes it without asking.
- **What a save writes.** A field left empty removes its key, so the default applies, except where the default is not empty, such as `automationAgentIds`, whose emptied list is written as `[]`. Keys the window has no field for are kept. An entry the window cannot read into fields shows its error, so the operator fixes it by hand or deletes it. Removing a source deletes its key and leaves its work items.
- **Paired devices.** General's paired devices ([Remote access](#remote-access)) use the hub-token routes `/page/devices`, `/page/pair` and `/page/revoke`, which change nothing in settings.json.

## Store

- One SQLite database, `~/.switchboard/switchboard.db`, opened through Node's built-in `node:sqlite` (M1). No native module, so VS Code's Electron upgrades do not require rebuilds.
- The hub is the only process that opens the database; its snapshot worker thread reads it through a read-only connection. The VS Code extension, the dock and the report command go through the hub's HTTP server, so there is no cross-process locking.
- WAL mode; one write transaction per flow step, so a crash leaves each work item in its last committed state.
- Core accesses the database only through a store interface, which isolates changes to the `node:sqlite` API. Tests use `:memory:`.
- Schema changes are numbered migrations applied by the hub at startup, recorded in `PRAGMA user_version`.
- Activity log (PRD R59): `events` holds each flow event that wrote a row or was refused, with its time, type, actor (`operator`, `session`, `source`, `triage` or `hub`), the ticket, work item and session it names, its detail and any refusal; `changes` holds each row it wrote, with each changed field's old and new value. Each change is logged in the transaction that writes it. Operator actions, reports, failed starts and failed stops are stored even when they change nothing; other events only when they change a logged field. Details leave out prompts, contexts and polled lists, except a start's prompt when the operator changed it (PRD R77); fields that change on every poll or status change, and the order fields, are not logged, and long text is cut. A refusal the flow never sees, such as a report that fails validation, is logged by the hub with only the report's kind and short fields, never a prompt; a refusal naming no known ticket is not stored. The tables have no foreign keys, so a log outlives the rows it describes, and are kept forever except that Delete purges a work item's activity. The log began with its migration, which recorded what the existing rows showed as reconstructed events. A per-ticket revision counter, advanced by every write to its log, lets a reader tell whether its copy is current.
- A Code Mode session's conversation (messages, replies, statuses and their speech state), its transcript readers' checkpoints, the windows' bindings and the web page's sign-ins (`pageSessions`, [Web page](#web-page), [Remote access](#remote-access)) are written outside the activity log ([Conversation](#conversation)).
- Which sources are on is in the `sourceStates` table, because the dock's header toggles it (PRD R3).
- Not in the database: settings and playbooks, in `settings.json`, which the operator edits and can keep in git; session transcripts, which Claude Code stores, and which sessions find by `nativeSessionId`; the [debrief](#friction-debriefs) state and log; and the pending opens and window commands in `window-queue.json` ([Open in VS Code](#claude-code-runner)), which expire after a short time.

## Repo roots

PRD R16, R21. `packages/core/src/repo.ts` owns a ticket's folder. A ticket records its repository, `owner/name` in lowercase, or none, which means its source's home repository, the source's `repo` setting. A ticket's root is, in order: the ticket's own `repoRoot`, as an ad-hoc, schedule or reported ticket has; the source's `repoRoot` with `{owner}` and `{name}` filled in, when it holds `{name}`; that `repoRoot` for the home repository when it does not; otherwise an error naming the setting and repository. Two repositories, in any sources, that resolve to the same folder, compared as Windows compares paths, are refused for both, so neither runs in the other's clone; a refused root fails the start even when the ticket has a linked worktree. Session start, the R68 task report's default and allowlist, the R6 repo list (each home root and each stored repository's root, never a pattern) and worktree linking use this one rule. A source's `repoRoot` may hold `{name}` and `{owner}` once each, `{owner}` only with `{name}`; `sources.adhoc.repoRoot` and a schedule's `repoRoot` name one folder. Switchboard never clones: when a pattern gave the folder, a start fails with `No clone of <repo> at <path>.` when it is not a checkout, and any other missing folder fails the start.

## Playbooks

A playbook is an entry under `playbooks` in settings.json, keyed by its name, `<namespace>:<name>`; `template` holds its prompt template and the other keys its settings. Switchboard has no built-in namespaces or playbooks; the entries define them.

```json
"playbooks": {
  "support:defect": {
    "description": "Zoho ticket reporting behavior that may be a defect",
    "autoStart": false,
    "requiresWorktree": false,
    "permissionMode": "auto",
    "reports": ["done"],
    "template": "Research Zoho ticket {{ticket.sourceKey}}.\n{{ticket.context}}\nReport progress with `{{report}} stage {{session.id}} <stage>`."
  }
}
```

- Template variables are the ticket's source, key, ref, repository, number, title, URL and context, the session ID and `{{report}}`, the report command prefix (`TEMPLATE_VARIABLES` in `packages/core/src/template.ts`). Rendering fails on an unknown variable.
- Keys (`parsePlaybook` in `packages/core/src/playbook.ts` is authoritative): `description` and `template` are required. `kind` is `task` or `triage`. A task playbook sets whether it starts on its own (`autoStart`) and needs a worktree (`requiresWorktree`), its agent (`provider`, PRD R22) with permission mode and model, the reports its sessions may send beyond the defaults (`reports`), whether Approve sends the session's work (`approvalSends`, only with the `approval` report), which other playbooks count toward Returned (`returnOf`, PRD R51), the page triage's focus must be on (`focus`, PRD R79), and whether it runs in the ticket's worktree or always in the repo root (`workdir`). A triage playbook sets whether its classifier rates immediacy and severity (`rates`). Omitted keys take defaults, a playbook's agent settings from that agent's `sessions` settings. Any other key, or a value of the wrong type, leaves that playbook out with its error while the rest load.
- `description` tells the classifier when to choose the playbook, so adding a playbook is adding its entry. Edit the triage playbook only for a rule that must take precedence over the descriptions.
- A source's triage playbook has `kind: triage`. Its body is the classifier's system prompt and may use only `{{playbooks}}`, which renders the choices as `- name: description` lines; a body without it gets the list appended. Triage playbooks are never offered as choices.
- Each source's `namespace` setting limits the classifier's choices to that namespace's task playbooks, such as `dev` for GitHub and `support` for Zoho Desk and Forum.
- Report contract (PRD R23). Every session gets the report contract as system instructions apart from its prompt, so the session list shows only the prompt, and again after each compaction (mechanics M30, M31). The contract opens with the line `Report to Switchboard with these commands:`, which skills may look for, so that line does not change; it lists only the reports the session may send, with the session ID and each report's condition. A playbook's task session may send `stage`, `link` and the playbook's `reports`; with neither `done` nor `approval`, the contract tells it to end its turn when the work is finished, so the work item becomes `finished`, in Ready for review. Setup and approved-prompt sessions may send `stage`, `worktree`, `done` and `link`, and an ad-hoc prompt all but `playbook`. The contract leaves out `task`, which the hub still accepts, so a session sends one only through a skill the operator invokes (PRD R68). The hub refuses any report the session's contract does not offer, and the report command exits with code 3.
- Questions and approvals. A Claude session that needs the operator asks with `AskUserQuestion` and waits, which keeps its context live and puts the row in Blocked on you; a Codex session, which cannot wait mid-turn, sends the `question` report and ends its turn. When the work is ready but publishing it needs the operator's approval, the session reports `approval` with the prompt that would publish it, a summary and any drafted file, and ends its turn; Approve runs the prompt in a new session with no memory of this one, so the prompt names what it acts on. Before an approval, a session offered `paste` reports each drafted text the operator pastes into the source by hand.
- Link checks (PRD R52). A session reports a `link` for each GitHub issue or pull request that tracks or delivers the work, not a related, base or parent one. When the ticket's source can check a link, the hub asks it first: the GitHub source refuses a pull request in its repository that neither closes the issue nor names it in its head branch, and one GitHub cannot resolve. A check that fails or takes too long accepts the link with a log line.

## Triage

Triage follows Ground Control's classifier (GC R38, M31).

1. The source plugin builds the triage context: the ticket's text, each field clipped at a word boundary, with authors, status changes and assignees. The hub puts the current time before the context, so the triage playbook can tell how recent a request is.
2. The classifier runs on `sessions.provider`, with `triage.model` as an optional override; a model name known to belong to the other provider is dropped with a log line, and unknown names pass through. The run has no tools, settings, MCP servers or saved transcript, and a Codex run also no project instructions, web search, apps or hooks; it gets the triage playbook as its system prompt and the context on stdin, which avoids the Windows command-line length limit (M31). Skipping the user's settings also skips the model endpoint they configure, so the hub carries that endpoint into the run: for Claude, the routing and proxy variables of the user settings' `env` block (M3), not model variables; for Codex, the model provider and endpoint from `config.toml` (M42). A missing file carries nothing; one that cannot be read or parsed fails the triage without running it, because the run would bypass the operator's endpoint. A failed run does not fall back to the other provider.
3. The result schema is `{playbook}`, an enum of the source namespace's task playbook names, plus immediacy and severity when the triage playbook has `rates: true` (PRD R50), and `focus` when the source returns anchors (PRD R79). Core's `validateClassification` checks both providers' results; without `rates` any rating is discarded, and a rating outside its enum is stored as empty.
4. The focus (PRD R79): a source's context can tag pages and comments with anchors, each with its URL and page; the GitHub source tags the issue, its pull request and each comment, and Zoho Desk and Forum return none. A choice whose playbook has `focus` names its page in the choices. The flow stores the chosen anchor when it is on the playbook's page or the playbook names none, else the playbook's page anchor, else the ticket's.
5. Nothing new (PRD R80): the `triage` action carries when an earlier work item of the ticket handled its activity, and with which playbook: the start of its first task session that started, or when the operator marked it done without one, or a handled-assignment registration (PRD R85). A source can report the time of the latest activity by anyone but the operator that can ask for an action; the GitHub source counts comments, reviews and the head commit in the context, and Zoho Desk and Forum report none. The hub tells the classifier about the earlier work, so earlier activity is background. When no activity is later than the earlier work, the triage is stale: the work item stays `unstarted` whatever the playbook's `autoStart`, with an error the row shows and Start clears, and History shows it.

Triage has no tools, settings, MCP servers or saved transcript, so it is not a session and does not count toward the one-session-in-a-turn rule (PRD R17). The hub runs at most one triage per work item at a time, at most `triage.concurrency` at once, each within `triage.timeoutSeconds`.

A classifier error, an unparsable result, a timeout, or a playbook name outside the enum fails the work item with that error (PRD R37). A triage interrupted by a hub shutdown is not a failure: the work item stays `triaging`, and triage runs again when the hub starts.

## Flow

1. Poll a source. For each ticket, compare its assigned state with `Ticket.assigned`. A poll that fails or is incomplete, such as one that hits the page limit, updates nothing.
2. When a ticket enters the assigned state, create a work item (`triaging`) and run triage.
3. Store the triage result. If the playbook's `autoStart` is false, or the triage found nothing new (PRD R80), the work item is `unstarted` until the operator starts it. `awaiting-approval` is used only for an approval report, and Approve applies only to it.
4. If the playbook's `requiresWorktree` is true and the ticket has none, start a setup session running the source's `setupPrompt`. Setup succeeds when a worktree is linked, by report or by the branch convention, and the session's process ends or, for a released session, its turn ends, since an interactive tab keeps the process. A Code Mode setup session (PRD R95) also succeeds at a turn end with a worktree linked, since its process runs between turns, unless the turn stopped at a usage limit ([Rate limits](#rate-limits)). A process end with no worktree linked while the ticket is assigned fails the work item with "Setup ended without a worktree.", or blocks it when the session stopped at a usage limit ([Rate limits](#rate-limits)); a turn end without one leaves it in `setup`, and a later resume of the session returns a failed or blocked one to `setup`.
5. Render the playbook and start the task session (`running`). The operator's guidance from Start follows the rendered prompt after a blank line; an approved prompt takes none (PRD R77). The session reports stages, a worktree link if it creates one, and done or approval.
6. When the task session reports done, the work item is done with reason `session`, unless the hub's read of the ticket still lists it as assigned; then a second read settles it, done, or `blocked` when the ticket is still assigned (PRD R10). When its turn or process ends with no report, the work item is `blocked` with the missing report as its reason, or `finished` when the prompt offered neither done nor approval. A turn that fails blocks it with the error, because the session can still be resumed. A `blocked` or `finished` work item whose session runs again becomes `running`. A Code Mode or Codex app-server task turn that ends while its conversation holds an open question leaves the work item `running`, waiting on the operator, unless the session reported, the ticket left the assigned state, an approval is held for the turn or the work item is a hosted conversation; the turn settles as above once no question is open, answered, withdrawn or dismissed, or when the session ends (PRD R103). A message that answers no question leaves the wait in place for the next turn's end; a dismissal outside a turn ends it at once.
   - When a session of an `awaiting-approval` work item runs again, as when the operator answers its question or resumes it, the work item becomes `running` and holds its approval. A new approval or done report from that run applies as usual. A turn end, a process end or an operator stop with no report returns it to `awaiting-approval` with the held approval, and the cause of a failed turn or a stop as its error. Only Approve, or Retry after the approved run failed to start, runs an approval's prompt. A run whose `running` state Switchboard never sees, such as a resume between two roster reads with hooks off, holds nothing.
7. When a ticket leaves the assigned state, an open work item that never had a session is deleted with its triages and pastes, and one with no active session is done with reason `unassigned` and no warning. A sessionless work item whose triage is running is marked instead, so the triage keeps its slot, and is deleted when the triage ends unless the ticket returned. Work item IDs are never reused, so a late result for a deleted triage is ignored. With an active session, this waits until the session reports or ends (PRD R10).

Pool tickets (PRD R47, R48):

- When a poll shows a ticket newly in the pool, the core starts a pool triage for the ticket; its result or error stays on the ticket.
- A pick of a pool ticket whose triage has a result creates the work item with that playbook and the pool triage, and queues it as an operator start, skipping the wait in step 3. Switchboard does not claim the ticket (PRD R48).
- A ticket that enters the assigned state while it has an open work item gets no second work item; the claim made by the task session is seen this way.

An ad-hoc prompt creates a ticket and an `unstarted` work item, with the typed prompt as the task prompt and the chosen repo root as the working directory; Start then goes to step 5, and Start automatically queues it at once (PRD R6). A `task` report creates the same kind of ticket and work item as a follow-up of the reporting work item (PRD R68), and its origin outlasts the parent's deletion. A `register` event creates one `running` with the registering session already started, released and external, and no task prompt (PRD R81). A work item with no playbook is labelled `task`, `registered` or `ad-hoc` by its origin (`adhocLabel` in `group.ts`).

Schedules (PRD R82) live in `packages/core/src/schedule.ts` and run on each `tick`, before the event itself. Each schedule has a ticket of source `schedule` keyed by its name, assigned, with the schedule's repo root, kept in step with settings.json; History shows each change of the schedule's timing and its removal. When the latest time the schedule came due is after the last check, the walk logs a `schedule` event and, unless the ticket has an open work item, inserts a run: a work item with the schedule's playbook and no triage, `queued` when the playbook has `autoStart`, else `unstarted`, and `failed` with the cause when the playbook is missing or not a task playbook. A schedule that was moved or added again counts its times from then, so it does not run for a time before; a time that passed while the hub was stopped runs once. Run now refuses an unknown name and a ticket with an open work item, and otherwise queues a run. A run starts in step 5 in the ticket's repo root. Its done report is accepted without a source read, because no source holds the ticket (PRD R10).

Steps 4 and 5 start a session only when no other session of the ticket is `starting`, `running` or `waiting` and a slot is free; otherwise the work item is `queued` (PRD R17, R38). An `idle` or `failed` session, such as the approval session kept open in the VS Code Claude view, holds nothing back, so a work item can have several live sessions. Its active session is its latest session while that has not ended; only the active session holds a slot, and only the latest session changes the work item's status.

## Core decisions

`packages/core` decides; the hub acts. `handle(store, event, context)` runs inside one store transaction, applies one event, and returns the actions for the hub to run, or a refusal for an operator action or report that does not apply. The context carries the clock, settings, loaded playbooks, the report command prefix and ID generators. The hub runs each action and sends its result back as an event, so every failure reaches the work item. The `FlowEvent` and `FlowAction` types in `packages/core/src/flow.ts` list every event and action; the table groups the main events by sender.

| Events | From |
|---|---|
| `poll`, `poll-failed` | A source read. `poll` lists the source's tickets from a complete read; a ticket missing from it has left the assigned state. `poll-failed` changes nothing. |
| `triage-succeeded`, `triage-failed`, `triage-cancelled` | The classifier. A cancelled triage runs again. A triage that cannot start, because the source's triage playbook is not set or loaded, no task playbook matches, or the triage prompt does not render, is stored as a failed triage with the error, so the work item counts as failed at triage. |
| `session-started`, `session-start-failed` | The runner's `start-session`. |

The flow continues a session as its fork only when the session is its work item's latest and holds no background process; it then retires the copy's native ID and applies the fork's state. Otherwise the fork waits as pending, and while it does the row offers no Open in Claude and Open the question is refused, because it would open the copy the fork retires. |
| `report` | The report command: `stage`, `worktree`, `done`, `approval`, `link`, `playbook`, `paste`, `question` or `task`. |

Actions are `triage`, `start-session`, `stop-session` and `resume-session`. After every event the core starts triage for `triaging` work items, then pool triage for pool tickets without a result, up to `triage.concurrency` in all; then it starts `queued` work items in queue order while fewer than `sessions.concurrency` active sessions hold a slot, skipping a ticket that has another session `starting`, `running` or `waiting` (PRD R17). A work item's active session holds a slot while the work item is in `setup` or `running` and not waiting on a question, and its ticket is not snoozed. A task that follows a setup session starts when the setup session ends, without waiting for a slot, and for a Code Mode setup session when its turn ends with a worktree linked (PRD R95).

## Claude Code runner

`ClaudeRunner` in `packages/claude` implements `SessionRunner` for Claude Code background sessions; Claude's background service owns each process, so sessions survive VS Code and the hub. Mechanics come from Ground Control (GC M IDs) and [mechanics.md](mechanics.md).

- **Start.** `claude --bg --permission-mode <mode> --settings '{"worktree":{"bgIsolation":"none"}}' -n <name> [--model <model>] --append-system-prompt <contract> <prompt>`, with no shell, so a leading slash command survives. Claude records the system prompt and resends it on later turns and resumes, also from a process started without the flag, until a compaction; a woken background session reuses its saved flags (mechanics M30). The name, `switchboard · <playbook or session kind> · <source> <key> · <Switchboard session ID>`, gives an interrupted start a stored identity before the launcher answers. `--bg` ignores `--session-id`, so the runner reads the short ID from Claude's `backgrounded · <id> · <name>` line and matches it against `claude agents --json` (GC M1, M33; mechanics M5). The start is confirmed when the roster lists the session with a pid; one not listed with a pid in time fails the start.
- **Start prompt** (PRD R41, mechanics M41). A session the roster keeps listing `blocked` with no pid waits on a prompt before it starts, such as approving the project's MCP servers. The start succeeds as `waiting` with the detail `START_PROMPT`; the operator answers through Open in terminal, and the core refuses `open-question` for it. Because the roster lists a process that died at the prompt the same way, only a session stored so keeps such an entry alive, and it waits until the operator stops it.
- **Permission mode.** `auto` by default. In 101 Ground Control runs to 2026-10-03, the 95 in `auto` never waited for or were refused a permission; the only permission stall was in manual mode. Questions (`AskUserQuestion`) stall in every mode and show as `waiting`. The operator answers them, so Switchboard neither disallows the tool nor keeps a Bash allowlist.
- **CLI.** Every `claude` command the hub runs (starts, stops, roster reads, triage, debriefs) and Open in terminal run `sessions.claudePath`, read at each use; an absolute path's directory goes first on that command's PATH. A command that cannot find the CLI says so and names the setting.
- **Environment.** Pass `CLAUDE_CONFIG_DIR` through exactly as the hub inherited it, and never set it: setting it, even to `~/.claude`, moves where Claude reads folder trust (GC M62). Strip VS Code's `ELECTRON_*` and `VSCODE_*` variables and `NODE_OPTIONS`. Background sessions inherit the service's environment, not the caller's, so per-run values such as the Switchboard session ID travel in the prompt (GC M33).
- **Trust.** Claude refuses to start in a directory it has not trusted; a linked worktree inherits its main checkout's trust (GC M62). The failed start shows Claude's message (PRD R41).
- **Liveness.** The roster alone decides liveness: a session is active while the last successful roster read lists it with a pid, and `ended` once a successful read that looked for it does not. An entry without a pid is a process that is gone (GC M33). A failed read changes no session, and reads run one at a time, so an older result never ends a session a newer read revived. Every session a start confirmed is polled, so a session resumed after its release is seen again. Hook markers only set the state of a live session, because a killed process leaves its last marker behind (GC M20); the roster's own state is the fallback when no marker exists.
- **State.** Hook markers decide the observed state, following Ground Control's mapping (GC M2, M20); `markerState` in `packages/claude/src/hooks.ts` is authoritative. Its rules: a prompt, a resolved tool batch or an answered question or plan means `running`; a permission request, an elicitation, a question or plan, or a waiting notification means `waiting`, and a result of another tool does not end a wait, because a parallel tool can finish while one still waits for permission; `Stop` means `idle`, or `running` while background tasks remain, with a detail that counts the agents, shells and other tasks among them (mechanics M124); `StopFailure` means `failed` with its error, and `rate_limit` is a usage or rate limit ([Rate limits](#rate-limits)). A wait's detail tells a permission prompt from a question (mechanics M57). A tab or terminal that resumed the session has run no turn and is `idle`, though the roster lists it busy while it loads (mechanics M25). A new marker from an ended session can mean the operator resumed it, so it triggers a roster read.
- **Hooks.** With `sessions.installHooks` on (the default), the hub installs its hooks in Claude's user settings (`<CLAUDE_CONFIG_DIR or ~/.claude>/settings.json`). It preserves other entries, refuses to edit malformed JSON, adds missing entries at startup, and removes the entries of another Switchboard home whose hub does not hold its lock, never the profile's own `~/.switchboard`, so an acceptance hub that shares the operator's settings leaves the operator's hooks. With the setting off, the roster alone decides state; turning it on while the hub runs installs both agents' hooks, and turning it off stops reading markers and leaves the hooks installed.
  - The marker hook writes one marker per Claude session, `<home>/activity/<nativeSessionId>.json`, atomically, skips subagent events and debrief forks (`FRICTION_DEBRIEF=1`), always exits 0 and prints nothing; `SessionEnd` deletes the marker.
  - The contract hook runs synchronously on `SessionStart` for `compact` and `resume`, because compaction drops the contract from the system prompt and a process resumed without `--append-system-prompt`, such as a VS Code tab, rebuilds the prompt without it (mechanics M30). It asks the hub's `POST /contract` and returns the answer as additional context, which Claude saves in the transcript, so later resumes keep it. After a compaction the hub answers the session's contract, with the conversation rules for a held session; after a resume it answers only a session that needs the current conversation rules ([Conversation](#conversation)), because a resume keeps the prompt the session started with. For another session, or when the hub does not answer, the hook prints nothing. With hooks off, a session compacted outside its background process loses its contract.
- **Forks** (PRD R78, mechanics M36). On each roster read the hub looks for a fork of each work item's latest Claude session: a live interactive copy in the session's project directory whose first assistant request ID is in the transcript of the session's current or a retired copy. A copy created after the current one is `newer`, and the newest such copy continues the session; a retired copy is `older`. A check reads only the transcripts in the copy's project directory, because reading every session's transcript would hold up the hub's requests, such as `/register`. `packages/claude/src/fork.ts` holds the rules. A report from an `older` copy is refused, and one from a `newer` copy is recorded and starts a roster read; the hub checks again just before it applies a report. `POST /contract` resolves a fork not yet continued, so it gets its session's contract. A Codex session's report ignores the Claude session ID, which a Codex process can inherit.
- **Release** (PRD R39). When a background session's turn ends (`idle` or `failed`), run `claude stop` once, so the operator can resume it in VS Code. A `waiting` session is mid-turn and not released. A session whose background process has ended is never released again, and neither is one the roster lists as interactive, so a session the operator resumed in a VS Code tab is never stopped by Switchboard; before a release stop the hub checks that the roster still lists the session as a background process.
- **Continue in Background** (PRD R89, mechanics M55). `POST /background {label, hostPid, workItemIds}` from an item window finds the Claude tab's or sidebar's session among the live interactive roster entries whose process is a child of the window's extension host, and answers 200 with the moving process's `pid` once the flow stored the move, else 409 with the refusal. It refuses when the window holds another live interactive session, which the window's close would end, when the candidate is ambiguous or not one of the window's work items, and when the session has no background entry, because only a session that ran `claude --bg` has saved options to resume with. `POST /background/check {hostPid, pid}` answers whether that process is still the only live Claude process under the window, and refuses unless a move still waits for it with time left, so the window's close leaves the process time to exit. Once the tab's process has exited, the hub runs `claude --bg --resume <native ID> <prompt>` in the session's folder with no other flag, so Claude wakes the session with the options it started with and keeps its IDs; a copy Claude started instead is stopped and fails the move. The session is moved when the roster lists it as a background process with a pid. A move survives a hub restart and is never launched twice.
- **Stop.** `claude stop`; a failed stop leaves the session stoppable. Never `claude rm`, which can delete the worktree. Only a release stop checks the roster first.
- **Open in terminal** (PRD R28). A row's `terminal` command attaches with `claude attach <short ID>` while the session runs in its background process, and otherwise resumes it with `claude --resume <session ID>` in its folder. A session that is released but live, which the roster lists as interactive, opens with Open in VS Code instead, because resuming a live session starts a copy (mechanics M18). A starting session gets no terminal command, and neither does an `external` one (PRD R81). Where it runs follows the dock's settings ([Dock](#dock)); a window shows the terminal it already opened for the session, also after its extension host restarted. Leaving an attach keeps the session running (mechanics M7, M9), and release still stops an attached session when its turn ends; the roster lists a resumed session as interactive, so it is never released.
- **Open in VS Code** (PRD R29, R59). The window resumes or focuses the session where `claudeCode.preferredLocation` puts it, in Claude's sidebar or a tab (GC M63). Claude's tab and sidebar list only the sessions of the window's first folder, and opening another session there starts an empty one (GC M6, M7, M52), so every open goes through the hub to the session's own window ([Window scope](#window-scope)):
  - `POST /open {sessionId, cwd, workspace?, window?}` records a pending open for its destination window and answers that window's workspace file or folder and whether it is the asking window. The destination is the asking window when the session belongs to one of its conversations, else the session's own window, its host's for a hosted conversation. A workspace the caller names must be the session's own window, or the open is refused with 409, so no caller routes another work item's session to a window of its choice; only a session the store does not know goes where the caller names. A session with no window is refused with 409. The asking window opens a session meant for it at once, and otherwise opens the destination with `vscode.openFolder`, which focuses the window already on it.
  - `POST /window` records the dock's pending window commands (`changes`, `terminal`, `history`, `log`, `openUrl`, and `openTabs` for a workspace file). An open the dock posts names its item window's workspace file, and only a claim with that file takes it (PRD R71).
  - A window claims what was left for it with `POST /claim {folder, workspace, focused, window}` when it connects, when it gains focus and on a `claim` event. The hub hands an open only to the window whose key's binding is the destination, never by a folder or workspace the claim only names, so a folder window never takes an item window's open and two item windows on one folder, as for Support, never take each other's. Commands for any window go only to a focused window, so a window reconnecting in the background does not take what the dock left for the window it brought forward. Pending opens and commands expire.
  - The hub keeps pending opens and commands in `<home>/window-queue.json` and a starting hub reads it, because the first window started after an extension update replaces the hub before it claims what the dock left for it. `/open` and `/window` answer 500 when the file cannot be written, so no command ID is handed out twice.

### Code Mode sessions

Experimental, started only with `sessions.codeMode` on (PRD R93–R95). `CodeModeRunner` in `packages/claude/src/codeMode.ts` implements `SessionRunner` for Claude sessions with `Session.codeMode` set, through the [terminal holder](#terminal-holder)'s client and the same hook markers as `ClaudeRunner`. The runtime selects a session's runner by `Session.execution: "app-server"` ([Codex runner](#codex-runner)), else `Session.codeMode`, else its provider. Experiments: [mechanics.md](mechanics.md) M63–M83.

- **Setting.** The flow reads `sessions.codeMode` ([Settings](#settings)) for each new Claude session. A Code Mode start stores the Claude session ID and a launch ID on the `starting` session before the spawn, so a hub restarted during the start finds the process in the holder; a failed start clears them, so it is never resumed and Retry starts a new session. A resume keeps the session's own `codeMode`. Codex sessions never start in Code Mode. Code Mode needs `sessions.installHooks`; without it the start fails.
- **Command.** The holder spawns `claude --session-id <uuid> --permission-mode <mode> -n <name> [--model <model>] --append-system-prompt <sections> --settings <json> [<prompt>]` in the session's folder, with no shell and no `--bg`. The hub makes the UUID, so the Claude session ID is known before the start (mechanics M63). The appended prompt holds the contract; the "Code References in Text" and "Focus view in this editor" sections of the Claude VS Code extension's panel prompt, copied word for word so a session writes as the panel does; Switchboard's link section, which tells the session to start a relative link target with `./` because VS Code's terminal makes a relative path clickable only so (mechanics M83); and the conversation rules ([Conversation](#conversation)). `--settings` selects the classic renderer, whose finished output scrolls into the scrollback the screen copy reads, and Focus view, which the panel's Focus view section requires. The holder holds the process under the Switchboard session ID, which a Claude session ID change does not touch.
- **Environment.** The hub's environment without VS Code's variables, `NODE_OPTIONS`, Claude's session markers, the variable that forces the full-screen renderer, and the gateway credentials, with `CLAUDE_CODE_EXPERIMENTAL_CODE_MODE=1`, `SWITCHBOARD_LAUNCH=<launch ID>`, the session's artifact folder ([Artifacts](#artifacts)) and `TERM=xterm-256color`, because the holder emulates an xterm and without `TERM` Claude Code draws its prompt as `>`, which typing must also read for a session started before (mechanics M121); `CLAUDE_CONFIG_DIR` passes through as inherited. User settings `env` outranks the process environment, so `--settings` points Claude at the direct API with blank credentials, to use the subscription sign-in (mechanics M64). An `apiKeyHelper` in user settings cannot be overridden, so Claude starts without Code Mode and the start check fails it. Nested Claude runs inherit the environment but not `--settings` (mechanics M77).
- **Start check.** The start succeeds when the holder's retained start of output shows `Code Mode (experimental) is on` (mechanics M63) and a marker of this session ID and launch exists. It fails, and the process is killed, when Claude prints `Code Mode (experimental) isn't available:` (mechanics M64, M71), with Claude's line as the cause, when a marker arrives while the output lacks the line that Code Mode is on, when the process exits, or when the check runs out of time. Whichever line comes first counts, since later output can quote either. A live process showing a dialog, or with no marker of its launch after a short wait, is waiting on a dialog (mechanics M70): the start succeeds with `startPrompt`, and the evidence is checked again at its first marker.
- **Liveness and state.** The holder's `list`, read with each roster read, decides liveness: a session is alive while the holder lists its process live. A failed `list` fails only this runner's read. A held process is never classed as an interactive roster entry (mechanics M67). Markers count only with the session's ID and launch, so a killed launch's last marker is never read (mechanics M68). The background mapping applies, except: `SessionStart` `startup` means `running`, or `idle` for a session started with no prompt (mechanics M87); `resume`, `clear` and `fork` mean `idle`; and `compact` leaves the state as it was, because `/compact` typed in the terminal ends with no `Stop` while an automatic compaction runs mid-turn (mechanics M65, M68, M73). `AskUserQuestion` exists in Code Mode, so the contract keeps it (mechanics M65). While `sessions.installHooks` is off, a held session keeps its last state and its row says it is unobserved.
- **End rule** (PRD R95). A held session keeps running between turns: no turn end releases it, whatever its kind or its work item's state. The hub, not the holder, ends it, only through the idle end: no terminal attached, no input or output for `CODE_MODE_IDLE_MS` (1 hour, the PRD's limit), and a turn end, or any state while it is unobserved because hooks are off; never while it waits on its usage limit ([Rate limits](#rate-limits)). The end is deferred while a terminal is attached or attaching, and skipped when the session's marker shows a turn has started since; input after the turn end defers it briefly, since it may be a prompt whose marker is not written yet. A deferred end never holds back the next session's start, because R17 and R38 count only sessions running a turn. A release marks the session `releasing`, and `released` only once the holder confirms the exit, so no observation takes a pending end for an ended session. An idle held session costs about 430 to 480 MB working set and 690 to 760 MB private memory with the operator's MCP servers (mechanics M82).
- **Attach serialization.** Ending and attaching are serialized per session in the hub. `POST /attach {sessionId}` refuses an unknown session with 404 and a session that is not Code Mode with 409, then reserves the session against an end for a short time, so a release does not end a session whose terminal is connecting. The attach waits for every end or stop of the session in progress, answers at once while the holder lists the session live, `starting` included, so a start prompt can be answered, resumes an ended session, and refuses one still ending or starting. Concurrent attaches share one attempt, so a session is resumed once. The answer is `{port, token, session}` of the holder the hub is connected to.
- **Stop.** The holder's `kill` ([Ending a session](#ending-a-session)), offered while the holder lists the process live, after the turn too; the work item is then `blocked` "Stopped by you." as for a background session (PRD R40). Delete stops a Code Mode session whenever the holder lists its process live, including a `starting` one and one the operator resumed through Open in terminal. A failed stop leaves the process listed as an orphan.
- **Resume.** `POST /attach` for an ended session applies the resume guard, then spawns `claude --resume <id>` in the holder with the start's environment, a new launch ID and no prompt, which reads as idle (mechanics M68), with the mode and model a start of that work item would use now. Claude resends the start's recorded system prompt until a compaction (mechanics M30), so the resume appends the panel, link and conversation sections and the contract hook restores the contract. The hub stores the new launch on the still-ended session before the spawn, so a hub that stops during the spawn finds the process under it and adopts it. When the session is deleted or changed during the spawn, the hub ends the new process and refuses the attach. A resumed session is `idle`; its outcome and its work item's status stand until a new turn. Never resume while the holder lists the session live, because resuming a live session starts a copy (mechanics M18).
- **Registered sessions** (PRD R81). An ended registered session resumes in the holder and is held from then on; until then its row, the Conversation view and the web page treat it as an ended held session with Resume. The hub refuses the resume for a session that is not its work item's latest, while Claude's roster lists the session with a process, as in the operator's window, since a resume would run a second copy (mechanics M18), when that roster read fails, and for a session without a transcript, which `claude --resume` needs. Code Mode, the permission mode and the model come from the end of the transcript (mechanics M117), since Claude keeps a session in the mode it started in (mechanics M68, M119), else from the current settings. The resume puts the report contract first in the appended prompt, because the session's start never had it; a session that ran without Code Mode resumes without it, through the operator's own gateway and sign-in. Its conversation starts at that first resume: the transcript is read from where it ended then, because its earlier lines, often days of work in the operator's window, would otherwise all arrive as new messages and replies on every page that shows it. From then on it works as any held session.
- **Resume guard** (mechanics M69). A Bash command can outlive its `claude` outside its process tree. The hub keeps each held session's last-seen process tree, pids with creation times, and refuses a resume while any member is still running, naming the pids, or when the process table cannot be read. Stop session on the work item then ends those leftovers, one subtree root at a time so a reused pid is never ended. A process that left the tree is missed; a container that would end it is deferred (PRD Q10).
- **Holder loss.** When the holder's lock is free, the holder is gone, and the hub ends each active session it held with "The terminal holder stopped.", so interrupted work is never read as finished: a session in a turn or waiting on the operator blocks its work item, or returns it to `awaiting-approval` when its approval was held, as after a Stop; a session whose turn had ended, or that reported done, is released and its work item's status stands; a `starting` session fails its start. Nothing resumes it until the operator opens it. A holder whose record does not answer while its lock is held is a failed read, not a loss. Every holder lookup that finds the lock free applies the loss, so a start that replaces a gone holder does not hide it.
- **Identity** (PRD R78, R93). Code Mode sessions are never followed as forks. A report whose Claude session ID is not the session's is refused, and the contract hook answers only the session's own ID. `/clear`, `/branch` and `/resume <id>` in the terminal give the same process and launch a new Claude session ID (mechanics M73): once the roster lists the held process, or a member of its tree, with that ID (mechanics M67), the session moves to the new ID and the old one is retired; a retired ID the held process resumes is followed back. A marker with the launch and another ID but no such start is a nested `claude -p` (mechanics M77) and changes nothing. `/register` refuses a session that runs in the holder for a work item.
- **Reconcile.** After a hub restart the runner applies the start check to each `starting` session from the holder's retained start of output; a session the holder does not hold fails. Held processes of no active session are orphans ([Visibility](#visibility-of-held-sessions)); none is killed.
- **Open and terminal** (PRD R95). A Code Mode session's terminal command, in every state, runs `<sessions.nodePath> "<home>/hub.js" attach <Switchboard session ID>` ([Attach client](#attach-client)), so the terminal and its reuse survive a Claude session ID change. Its main control is Open in terminal wherever a background session's is Open in Claude, and the flow refuses `open-question`, because the Claude view refuses Code Mode; a claimed `session` open that names a Code Mode session becomes its attach terminal.
- **Exclusions.** Continue in Background refuses a Code Mode session, which the holder keeps running when the window closes. Debriefs skip Code Mode sessions, because `claude -p --resume` refuses them (mechanics M74). Triage, the report command and the contract hook are unchanged (mechanics M65, M66).

## Codex runner

New Codex sessions run as threads in Codex's app-server daemon (PRD R107): `AppServerRunner` in `packages/codex`, selected by `Session.execution: "app-server"`. A session without it keeps the [legacy exec runner](#legacy-exec-sessions) or the Claude holder. A stop action carries the provider and execution method, because a deleted session's row is gone when its stop runs.

- **Daemon and connection.** One app-server client per hub is shared by the runner, the conversation adapter and the debrief scheduler. It starts Codex's daemon under the session's Codex home and connects through `codex app-server proxy`. The daemon owns process lifetime: closing the proxy or the hub never stops it, and Switchboard never stops, restarts or updates it. Transport errors reject outstanding calls without replaying them, and a new connection invalidates stale requests and subscriptions. Codex's home, sign-in and configuration are inherited; tests and live acceptance inject a separate home.
- **Threads.** A start creates a thread with its permissions, model, report contract, conversation rules, artifact environment and persona tone, and records the native thread ID before it submits the prompt with a client message ID. A promptless hosted start leaves the thread idle. Native thread and turn events decide state; hooks do not. Reads rejoin after a connection loss and confirm starts from history. An unconfirmed start stays `starting` with a visible cause and recovery controls, and its prompt is never submitted again automatically. A missing thread does not prevent other sessions being observed.
- **Lifetime.** A task thread whose turn ended stays subscribed until the idle limit of a Code Mode session passes with no typing in its [Codex terminal](#codex-runner), and is never released while it waits on its usage limit ([Rate limits](#rate-limits)); a message resumes it. Setup, done and superseded sessions release their subscription after a turn; a release does not interrupt newly started work. Stop session interrupts the named active turn and unsubscribes only that thread, leaving other sessions and the daemon running.
- **Resume.** A message to an ended app-server session that is its work item's latest resumes its thread with the start's folder, permissions, artifact environment and model, which a thread the daemon loads again from disk takes and a loaded thread keeps its own sandbox against (mechanics M95), then sends the message under the new launch, or gives it back unsent with why. Concurrent resumes share one attempt. A thread resumed by another client, as by Open in terminal's `codex resume --remote`, reaches `POST /contract` through Codex's `SessionStart` hook and is resumed the same way.
- **Instructions.** The current instructions are injected as a developer context item when a resume needs an update and after a completed compaction, because resume overrides are ignored for loaded threads and compaction can drop injected updates (mechanics M92). The session stores the delivered instructions' hash and the compaction it followed, so unchanged instructions are not injected again on a restart, and history detects a compaction missed while disconnected.
- **Conversation.** `CodexConversationAdapter` imports native history and completed items into the shared conversation log, with no invented transcript lines, and leaves tool results out. Scope, history, events, delivery, unread, artifacts and speech stay in `ConversationService` ([Conversation](#conversation)). Each provider's adapter polls independently, so a slow Codex request cannot delay Claude reads.
- **Input and recovery.** `turn/start` accepts input at idle or during a turn, carrying the stored message ID as its client message ID. A known refusal or unsent write returns the draft; a transport failure never decides a thread's state. A lost response is reconciled from history, and unknown delivery stays visible as `uncertain`. Input is never replayed automatically. Selected skills and image mentions travel as native inputs; compaction is an API operation.
- **Requests.** Native requests, such as questions and command or file approvals, carry connection-scoped IDs and thread identity. Only the current window can answer, through `POST /v1/conversation/answer`, and the adapter validates the pending request and the offered choice. Unsupported request types use the native terminal. Rejoining replays pending requests (mechanics M92).
- **Open and terminal.** A claimed app-server open focuses Switchboard's Conversation view. Open in terminal runs `codex resume --remote <control socket> <thread>` against the same daemon. Switchboard never hands a live app-server thread to the Codex VS Code extension. Native terminals and the Conversation view can coexist.
- **Codex terminal in the holder.** For the web page's console ([Web page](#web-page)), the hub holds Codex's own terminal app on the session's thread in the [terminal holder](#terminal-holder), as a second client of the thread, started with `--no-alt-screen` so its finished output stays in the scrollback (mechanics M108). It starts when a console views a live app-server session whose thread has had a turn, since Codex cannot resume a thread before its first, and again after it exited. The hub still sends every message and answers requests through the API; what is typed in the terminal reaches the thread as from any client. The terminal keeps a released thread loaded, so it ends with every stop that leaves the thread, and the hub ends one still held for an ended or released session at its next holder read. Keys typed in it count as use for the idle release. Holder stops and the holder's restart end only the terminal, never the thread's turn.
- **Settings changed outside Switchboard.** Codex's terminal can change the thread's model, permissions and collaboration mode for every later turn, the hub's included (mechanics M108). Switchboard neither blocks nor reverts them, since the operator changes them on purpose; it compares each update with what the thread started with and notes in the conversation when the settings differ, and when they are back.

### Legacy exec sessions

`CodexRunner` in `packages/codex` implements `SessionRunner` for Codex `exec` runs (mechanics M31). The runtime sends each action to the runner its session's provider names, and the roster read and the marker pass ask each runner about its own sessions; when one runner's read fails, its sessions stay as they were and the others still apply. Every Codex process the hub starts (runs, hook trust, debriefs, Open in terminal) gets `CODEX_HOME` as the hub inherited it, else `~/.codex`, so runs and hook trust read the same hooks file, and runs `sessions.codexPath`, read at each spawn; an absolute path's directory goes first on PATH, because npm's launcher runs `node` from PATH and nvm keeps `node` beside it.

- **Runs.** A session's background run is one detached `codex exec` process with stdin closed and no shell, its output and a run record in `<home>/codex/`. A process is named by its PID and creation time together, because PIDs are reused, and is ended only after its creation time is read again. The run's process is Codex itself; on Linux `codex` on PATH is npm's Node launcher, so the runner records the tagged Codex process instead (mechanics M38). Every command line carries `-c switchboard_run="<sessionId>"`, which Codex ignores, so a hub that stopped between a spawn and recording its PID finds the process by its tag. Ending a process ends its descendants at once, sparing any PID another process took meanwhile.
- **Modes.** Each permission mode is a set of `-c` overrides: `auto` is the workspace-write sandbox with network and escalations reviewed automatically, `plan` read-only, `dontAsk` workspace-write with network and no escalation, `bypassPermissions` no sandbox; `manual` and `acceptEdits` need a person and are refused. Commands in the sandbox cannot use the operator's credentials, so skills that call `gh` need `bypassPermissions`. A prompt that starts with `/<skill>` starts with `$<skill>`, which Codex injects.
- **Start.** The start waits for Codex's `thread.started`; the thread ID is both the native and the short ID. A process that exits first fails the start with its last error line, such as Codex's refusal outside a git repository (PRD R41); one that prints no thread in time is ended. After a hub restart, `reconcile` finds an untracked process by its tag and completes, waits for or fails its start.
- **State.** `reduce` in `packages/codex/src/reducer.ts` is the only place that decides a Codex exec session's liveness and state. A hook marker from a live process other than the run's means the operator resumed the thread, as in the VS Code panel, and the session is interactive; a live run is running until its log holds the turn's end; a turn end is delivered once even when the process exited first.
- **Stop.** A release or an open waits briefly for the run's process to exit, since its turn has ended, then ends it; an operator stop ends it at once. An interactive session is never stopped.
- **Open and terminal** (PRD R29). The item window opens the thread in the Codex extension's sidebar through its `vscode://openai.chatgpt/local/<thread>` URI (mechanics M43); VS Code owns the URI handler's confirmation, and Switchboard does not treat a completed request as proof that history loaded. Open in terminal runs `codex resume <thread>` once the background run has ended, and is not offered while it runs, because Codex has no attach.
- **Questions** (PRD R70). A Codex exec session's contract offers the `question` report in place of `AskUserQuestion`. A question reported while the session runs in its background process makes it `waiting` once the reporting turn has ended, and the row offers Open in Codex only then; a question from a session the operator resumed is ignored.
- **Hooks.** With `sessions.installHooks`, the hub installs its marker and contract hooks in `<CODEX_HOME or ~/.codex>/hooks.json` under the same rules as Claude's, then trusts them through `codex app-server`, trusting only Switchboard's own entries. A change to `sessions.codexPath` or `sessions.nodePath` installs and trusts them again without a hub restart. Codex runs these hooks for every Codex session on the machine, so the hook acts only for a thread a run record names. The contract hook acts only on `compact` and `resume`, because Codex hooks have no matcher in use.

## Rate limits

PRD R111. A turn that stops at a usage or rate limit waits for its reset; evidence in [mechanics.md](mechanics.md) M100.

- **Reading a limit.** For a Claude session whose turn ended `failed` with `rate_limit` or `idle`, the hub reads the current turn's limit from the end of its transcript (`packages/claude/src/limit.ts`): a usage limit or a throttle, and its reset, exact from the refused request's data or read from its text relative to the line's own time, so a later read gives the same reset. A grace-allowance note before a turn that ended normally is a usage limit without a reset. Claude Code's own wait line marks a session Claude Code will continue itself; because Claude writes it just after the `Stop` hook, the hub reads the transcript again for a recent turn end. For a Codex app-server thread, a failed turn's usage or rate-limit error gives the limit, and the account's rate-limit updates give its reset. A turn end that settles a work item carries its limit, so a grace-allowance setup is never finished before its limit is known.
- **Keeping it.** The flow stores `Session.rateLimit` (`packages/core/src/limit.ts`): the reading, when the run first hit it, the launch it was found in, the hub's attempts and the next attempt's time, a margin after the reset. A session waits on its limit while it has one and its state is `idle` or `failed`; a turn that ends without a limit clears it.
- **Its work item.** A held Code Mode session or app-server thread waiting on its limit keeps its work item `running` or in `setup`, never finishes setup at that turn end, and is neither ended nor released until it continues or the hub gives up. When its work item is done or a newer session starts, nothing will continue it, so its limit is cleared. A background Claude session is released as usual, with its work item `blocked` or its approval waiting again, each saying the turn stopped at a usage limit; a limit the hub read is a wait, so it never fails the work item. A setup blocked so offers Retry, which queues it to run setup again, as for a failed one.
- **Continuing.** Each minute the hub continues each held session or app-server thread whose next attempt has come, when it is its work item's latest, under the launch the limit was found in, with its work item in `setup` or `running` and its ticket not snoozed. It types Claude Code's own continue text as a message no window sent, through the same queue and guards as a composer message ([Typing a message](#typing-a-message)), resuming an ended app-server thread first, and checks before the write that the session has not continued, its limit not changed and its work item still runs. Attempts back off; after a bounded number of attempts or time the hub blocks the work item with why and clears the limit. A session the operator typed in from an attached terminal during the wait is left to the operator: its limit is cleared and its work item blocked, saying why. `hub.log` records each attempt and skip.
- **The queue.** While a session of a provider waits on a usage limit with a reset ahead, the scheduler starts nothing in that provider until the reset; a throttle and a limit with no reset hold nothing.
- **Not continued.** A Codex exec run's limit and a background Claude session are not continued, and Codex's account limits are not checked before an attempt.

## Terminal holder

PRD R94. `packages/holder` holds Code Mode sessions, and the [Codex terminals](#codex-runner) of the web page's console, in pseudo-terminals. It knows nothing about Claude, Code Mode, hooks or work items: `CodeModeRunner` ([Code Mode sessions](#code-mode-sessions)) holds everything Claude-specific. It is built for Windows and Linux; its experiments ran on Windows only ([mechanics.md](mechanics.md) M63–M82). This section is the contract other clients, such as claude-collab's voice front end, code against.

### Responsibilities

- Spawn a program with arguments, working directory, environment and size in a pseudo-terminal (node-pty), under an ID and an opaque label the caller gives.
- Keep each session's screen and scrollback in `@xterm/headless`, and the start of its output, so start evidence outlives scrolling.
- Let clients attach: replay the screen, then stream output; pass their input and size to the program.
- End a session on request by closing its pseudo-terminal, so the program runs its own cleanup, and end its process tree if it does not exit soon after ([Ending a session](#ending-a-session)); report its exit, and exits it did not cause.
- Keep an exited session's screen for a while, so a client attaching after the exit sees the last screen and the exit code.
- List every session with its label, pid, folder, start time, last input and output times, attached clients, its process tree and the tree's memory.

Not its job: reading a screen for meaning, deciding when to kill or resume, retrying, resuming after its own restart, or keeping anything but its record.

### Protocol

`packages/holder/src/protocol.ts` defines the messages and limits.

- **Transport.** TCP on `127.0.0.1`, an ephemeral port, JSON lines in UTF-8.
- **Handshake,** the same in every protocol version. The first line, within a few seconds, is `{"type": "hello", "token": "<token>"}`; a wrong token or a late or malformed hello closes the connection with an `error`. A right one is answered `{"type": "welcome", "protocol": <n>, "build": "<build>", "pid": <pid>, "features": [...]}`, where `features` names the requests added within the protocol that this holder serves (`snapshot`, `write`, `view`); a client never sends a request the holder does not name, because an unknown type closes the connection. A client checks `pid` against the record and `protocol` against its own; with another protocol it sends only `list`, `kill` and `shutdown`, which keep their shape in every version, so any client can list and stop the sessions of a holder of another protocol.
- **Token.** One token grants everything: attaching and typing, spawning any program and killing any session (PRD R94).
- **Limits.** A client line over 1 MiB, an unknown type or an invalid field closes the connection with an error, and fields have length limits. A client accepts reply lines up to 64 MiB, because a `list` or `screen` reply can pass 1 MiB. A replay is sent in chunks paced to the client's reading, because a full replay is about 1 MiB (mechanics M72). A client that falls too far behind is dropped, never the session.
- **Requests,** each with an `id` that the reply echoes as `re`:
  - `spawn {session, label, file, args, cwd, env, cols, rows}` → `spawned {session, pid}`, or `error`, also for a `session` it holds live.
  - `list` → `sessions [{session, label, pid, cwd, startedAt, lastInputAt, lastOutputAt, exitedAt, exitCode, clients, tree, memoryBytes}]`, where `tree` lists the process tree's `{pid, created}`, the creation time telling a reused PID apart. The process table is sampled in the background, and `list` answers from the last sample (mechanics M75).
  - `kill {session}` → `killed {session, exitCode}` once the process has exited, or `error` at the deadline ([Ending a session](#ending-a-session)).
  - `screen {session}` → `screen {session, head, text}`: the retained start of the output and the visible screen as plain text.
  - `snapshot {session, scrollback}` → `snapshot {session, data, cols, rows, rev, keyAt}`: the screen and up to `scrollback` lines above it serialized with their attributes, as an attach replays them; `rev` rises on every output, resize and input, so a reader skips a screen it has read, and `keyAt` is when a key was last typed in a terminal. The conversation layer reads replies and the input box from it ([Conversation](#conversation)).
  - `write {session, data, key?}` → `written {session, rev}`: input from a client that is not attached, so no resize and no `clients` count; it sets `keyAt` only with `key: true`, a key typed in a terminal, and is refused for a session that is not held or has ended. The hub types the view's messages with it ([Typing a message](#typing-a-message)), and the web page's console its keys with `key` ([Web page](#web-page)).
  - `size {session, cols, rows}` → `sized {session, rev}` (`view` feature): resizes the pseudo-terminal without attaching, so the program draws for the console that types.
  - `watch` → `watching`, then a stream of `exited {session, exitCode}`, `attached {session, clients}` and `detached {session, clients}` on this connection.
  - `shutdown` → `error` while any process is live; otherwise `bye`, and the holder exits.
- **Attach.** `attach {session, cols, rows}`: the holder resizes the pseudo-terminal to the client's size, so the program redraws for it (mechanics M72), and sends the screen and scrollback as `replay {data}` lines and `replayed`, then `output {data}` as the program writes. The replay first resets the terminal modes the serializer only turns on and then restores the program's mouse encoding, which the serializer leaves out (mechanics M101), because the client reuses its terminal. The client sends `input {data}` and `resize {cols, rows}`. On exit the holder sends `exited {exitCode}` and closes. The last client to attach, resize or type sets the size. Input from several clients interleaves; the holder does not lock input.
- **View** (`view` feature). `view {session}`: the holder sends `resized {cols, rows}`, the size the program draws at, then the replay and `replayed`, then `output {data}` with a `resized` at each resize in its place among the output, and `exited` at the end. A viewer never resizes the pseudo-terminal and is not counted in `clients`; any message from it closes the connection with an error. The hub watches a session for the web page's console with it ([Web page](#web-page)).
- **Versions.** A field added within a protocol is optional, so an older client keeps working; any other change is a new `protocol` number.

### Record and lock

- `<home>/holder.json` holds `protocol`, `build`, `port`, `token` (32 random bytes, hex), `pid` and `startedAt`, written only by the lock holder and readable by the operator only, as `hub.json` is.
- The lock is the named pipe `\\.\pipe\switchboard-holder-<hash of home>` on Windows and `<home>/holder.sock` elsewhere; one holder runs per home. A holder that cannot take it exits, after retrying briefly while the recorded holder does not answer, because a holder ended by force can keep its pipe for a moment. A client accepts a record only when `welcome` answers with its pid, as for a hub record a forced exit left.

### Lifecycle

- **Start.** `HolderLink` (`packages/hub/src/holder.ts`), before a Code Mode start or resume and a Codex terminal's start, finds the recorded holder, or, when none answers and no process holds the lock, starts the installed build detached and hidden with `sessions.nodePath`, without VS Code's variables and `NODE_OPTIONS`, logging to `<home>/holder.log`; a holder that does not start fails the session's start with the reason and the log's path. The holder runs on the operator's Node.js, not VS Code's runtime, because node-pty is a native module. The hub's bundle imports only the holder client, which has no native dependency, so a missing or broken native module fails only Code Mode starts and Codex terminals (mechanics M76).
- **Install.** Extension activation, or `hub.js install` without VS Code, installs each holder build in its own folder, `<home>/holder/<build>/`, with the pinned node-pty's helpers and prebuilt binaries, because Windows refuses to replace a loaded `.node` file while a second build runs beside it (mechanics M76); `<home>/holder/current.json` names the build a hub starts. Installs take an install lock, so windows activating together take turns; an install never replaces a complete installed build, and removes build folders no holder runs or is about to start from. A failed install is written to `hub.log` and fails only Code Mode starts.
- **Version.** The build ID is the holder's own version, separate from Switchboard's: a hash over the path and content of every file of the holder's build (`writeManifest` in `extensions/switchboard/esbuild.js`), so it changes only when the holder's code, its dependencies or the bundler's output change, and nothing is bumped by hand. A running holder is **from an older build** when its `welcome.build` is not the installed build, or it lacks the protocol or a request this build sends (`olderHolder` in `packages/hub/src/holderCli.ts`); `hub.js holder list` and `holder stop --all` mark it so ([Visibility](#visibility-of-held-sessions)).
- **Hub restart, extension update, VS Code closing.** The holder and its sessions keep running. A hub accepts any holder that speaks its `protocol`; one of another build keeps running, and the dock and the web page offer to [restart it](#restarting-the-holder). A holder of another protocol that holds live sessions is kept, listed and stopped through the version-stable requests, and Code Mode starts and resumes fail until its sessions end; then the hub shuts it down and starts the installed build.
- **Idle exit.** The holder exits a while after it last held a live process, whatever clients are connected. The hub starts it again at the next Code Mode start or resume.
- **Exit.** Before it exits, when idle, on `shutdown` or on `SIGINT` or `SIGTERM`, the holder refuses further spawns and ends each live session as `kill` does; idle and `shutdown` exits come only when none is live.
- **Crash or logoff.** The pseudo-terminals close with the holder, and each `claude` exits within seconds (mechanics M69), but a shell command it was running can run on, unlike after a `kill` (mechanics M78); the hub applies [holder loss](#code-mode-sessions).

### Ending a session

Every end the hub asks for is a `kill`: a release after the turn, when the work item is done or a newer session starts, the idle end, Stop session, Delete and `hub.js holder stop`. The holder ends the program in two steps under one deadline:

- **Close.** Closing the session's pseudo-terminal leaves the program running, so Claude Code ends its shell commands, logs `SessionEnd` and exits within about 2 seconds (mechanics M78). A process a command left behind outside the tree runs on (PRD Q10). On Windows the holder keeps reading the output, so the last screen stays attachable; on Linux the close ends the reading, so the screen is the one before the close.
- **Tree kill.** When the program has not exited a few seconds after the close, or the pseudo-terminal cannot be closed, the holder ends the process tree, as the [Codex runner](#codex-runner) does, which skips Claude's cleanup and `SessionEnd`, and logs why.
- **Windows.** node-pty's own `kill()` kills `claude` before its cleanup can run (mechanics M78), so the close calls ConPTY's close through node-pty's private agent fields, after checking that they exist (`packages/holder/src/close.ts`). node-pty is pinned in `packages/holder/package.json` for this; the built-holder test fails when an upgrade breaks the close, and the holder falls back to the tree kill meanwhile.
- **Linux.** node-pty's `destroy()`, which closes the master side and sends the program `SIGHUP`. Not verified on Linux.

### Visibility of held sessions

- **CLI.** `hub.js holder list`, `hub.js holder stop <id>` and `hub.js holder stop --all [--yes]` (`packages/hub/src/holderCli.ts`) find the home as `report` does, so the extension's own bundle reaches the same hub and holder. With the hub up they go through `POST /holder/list` and `POST /holder/stop {id}`, so an active session stops through the flow as any Stop does; with the hub down they talk to the holder directly, whatever its protocol, and the hub's next roster read ends what they stopped. Each names a holder from an older build first. `list` shows every held session, orphans first, with its work item, IDs, folder, state, idle time, memory and attached terminals. `stop` takes a Switchboard session ID, a current or retired Claude session ID or its 8-character prefix, and refuses an ambiguous or unknown one. `stop --all` names the holder and the live sessions that end with it, ends nothing without `--yes`, and with it stops each live session, shuts the holder down and ends its process tree if it does not exit, so the next Code Mode start launches the installed build. The exit code tells done, a usage error, no hub or holder answering, and a refusal apart.
- **Orphans.** A live held process whose session is no active session of the store, such as after a failed Delete stop or a store reset, or one whose session ended while it still runs. Each roster read, whether or not a Code Mode session is active, lists the holder without starting one; a failed read keeps the last list. The hub logs each orphan once, lists it and offers Stop; it never kills one by itself.
- **Snapshot.** `held` (`HeldSession` in `packages/hub/src/held.ts`), absent when the holder lists none, is the holder's last list joined with the store, orphans first; the dock shows it as the held sessions list, with each held session's attach terminal, and a note while any is an orphan ([Dock](#dock)).

### Restarting the holder

A holder from an older build ([Lifecycle](#lifecycle)) keeps running while it holds sessions, so the hub never replaces it by itself; sessions are rarely all idle. The dock and the web page show a notice instead, and its Restart and resume, which a paired device's page leaves out ([Remote access](#remote-access)), does what `hub.js holder stop --all --yes` and a Resume of each session would.

- **State.** The snapshot's `holder` (`HolderState` in `packages/hub/src/held.ts`) gives the connected and installed builds, whether the holder is older, and the last restart's progress or result, with each session that did not resume; a window's scoped snapshot leaves it out ([Window scope](#window-scope)).
- **Notice.** While the holder is older or restarting, the notice says so and how many sessions a restart resumes: the live held sessions whose session the store holds active. Its confirmation names each session in a turn, since the restart interrupts it, and counts the sessions that end without resuming. After a restart it shows the result and any session that did not resume, until dismissed.
- **Restart.** `POST /holder/restart {detail?}` refuses a `detail`, the confirmation the operator accepted, that no longer matches the one the notice asks, so a session that started a turn while the operator read it is never interrupted unnamed; it also refuses while a restart runs, with no holder connected, and for a holder that is not older. Otherwise it answers at once and runs in the background: it stops every live held session as Stop does, shuts the old holder down, ending its process tree if it does not exit, and starts the installed build; a Code Mode start or resume meanwhile waits for it, and a session started in the old holder meanwhile is stopped too, for a bounded number of rounds before the restart fails without ending the holder. It then resumes each session that was active, as the web page's Resume does, and keeps each refusal as that session's failure. A resumed session is idle; its work item keeps the status the stop gave it until its next turn, as after any Stop and Resume.

### Attach client

`hub.js attach <Switchboard session ID>` (`packages/hub/src/attach.ts`), run with `sessions.nodePath`, finds the home as `report` does, posts `POST /attach {sessionId}`, which may resume an ended session ([Code Mode sessions](#code-mode-sessions)), and connects to the holder the answer names at the terminal's size. It puts the terminal in raw mode, writes the replay and output, and passes input and size changes. When the session exits it says so and offers Enter to attach again, which resumes the session, so the terminal a window or the terminal app keeps for the session is the one Open in terminal shows again. A refusal, a hub that is down or a connection the holder closes is reported with the option to try again. Closing it only detaches.

## Conversation

The conversation of a Code Mode or Codex app-server session, in its item window's Conversation view (PRD R96) and on the web page ([Web page](#web-page)): the operator reads the replies beside the session's terminal, types messages in the terminal or the composer (PRD R97), reads the session's latest status (PRD R98), opens the artifacts it writes (PRD R99), each unread until seen (PRD R100), switches between the window's work item and the conversations started from it (PRD R102, R104), and answers the lettered questions a session asks with a card (PRD R103). With `voice.enabled` on, the replies to its own messages are read aloud while the voice speaks for its session (PRD R105, [Voice](#voice)), and the operator can dictate messages to it (PRD R108, [Dictation](#dictation)).

### Conversation rules

The conversation rules (`conversationRules` in `packages/conversation/src/rules.ts`) are the contract between a session and the readers of its conversation. A Code Mode session's appended system prompt and a Codex app-server session's instructions carry them. They explain only the tags and shapes the hub and the view read, and say so:

- Every reply opens with its primary response, a few plain sentences that give its conclusion with no lists, tables, code, paths or URLs, and puts anything more after a `[details]` line of its own, as claude-collab's replies did; the view shows the primary response first, as a bubble, and the details smaller, whether or not the reply is spoken (operator decision 2026-11-22). A reply with no `[details]` line is all primary when it is short, else its first paragraph is ([Conversation](#conversation)).
- `[aside]` starts text written only to show progress; `[rewrite]` starts a reply that replaces the previous reply after a newer message; a `[status]` line of its own starts a status, which runs to the end of that text, with any reply before it ([Statuses](#statuses)).
- Questions are the other place the rules shape what a session writes, because the card's usefulness depends on it: a card only for a real decision between known alternatives, never to gather details or while the operator is mid-thought, and none for a low-stakes choice the session can make on its own recommendation; at most four numbered questions at the end of a reply, each with a slug id (`{#slug}`), an optional bold topic, a line of context, and two to four lettered options that say what each changes, the recommendation marked; `[withdraw: slug]` for a question no longer needed; answers arrive as an `[answers]` message, one line per slug ([Conversation view](#conversation-view), PRD R103). A Claude session is told to ask in a reply rather than with AskUserQuestion, even where the report contract or a skill says to, because that menu holds the whole session and the operator's messages until it is answered in the terminal, and the view cannot show it; an open question keeps the work item waiting on the operator when the turn ends. Questions in a status get no card. A Codex session may ask with `request_user_input`, which the view shows.
- An Artifacts section names the session's artifact folder, by its path and `CLAUDE_ARTIFACTS_DIR`, and explains artifact names, how each type opens, front matter and updating ([Artifacts](#artifacts)); it does not say when to write one.
- With `voice.enabled` on, a Spoken replies section explains that a `[spoken]` message's reply has its primary response read aloud, never its details, and the `[tone: …]` line an `[expressive]` message gets ([Voice](#voice)), and a Dictated messages section explains `[voice]`, `[voice] [partial]`, ignoring speech not addressed to the session, and the heard tag, `<!--heard:what came through=what was meant-->`, which the view hides ([Dictation](#dictation)). Both come before the artifact rules.
- A session with a [persona](#personas) gets its tone section last.

Apart from the primary response and questions, the rules set no length, shape, format or verbosity, so a session writes as it would without them, with its provider's defaults and the operator's output style (voice-design decision 21, which the primary response replaces for a reply's opening); a turn may write several replies between its tool calls (voice-design decision 24). A rule is added only for a tag something reads. No rules version is kept: the hub reads every session's tags as the current rules define them, and the contract hook gives a resumed or compacted session the current rules ([Claude Code runner](#claude-code-runner)).

### Window scope

A window sees only its own conversations, enforced in the hub (voice-design decision 26). The window key separates windows; the hub token stays a machine credential, so the rule is not a defence against software running as the operator.

- **Key.** Each window stream's `hello` carries a random window key (`WindowScopes` in `packages/hub/src/windows.ts`), which dies with the stream; a reload gets a new one. The hub derives everything from the key, so no conversation route takes a work item ID except `select`, which names one of the window's own conversations, or for the web page any work item, which then binds it ([Web page](#web-page)).
- **Binding.** An item window is bound by its workspace file. Its **primary work item** is the newest work item of that file's window that is not done, else the newest, because successive work items of a ticket share its worktree and window. Its **conversations** are the primary, then the ad hoc work items it hosts ([Hosted conversations](#hosted-conversations)) that are not done, newest first, and the selected one even when it is done, until another is selected. Membership never follows a folder: another work item in the same folder, as every Support work item is, never joins. The binding is stored, so a reload keeps it: the primary, the ticket and title it showed, so a deleted primary still names them, the **selected conversation** and its current session, and `scopeGen`. The selection starts at the primary, else the newest conversation; a successor work item that replaces a selected primary is selected in its place, and a selected conversation that leaves the list gives way to the primary. `scopeGen` rises whenever the selected conversation or its current session changes, so a command meant for the earlier one is refused. Within the selected conversation the window sees its current session only, the one started last.
- **Folder windows** (PRD R104). A window with no workspace file that names a folder is a folder window, bound to the folder's real path, so every spelling of it, in another case or through a link or junction, reaches one binding; a path that is not a readable folder, or no path, binds nothing and sees no work item. A folder window has no primary work item: its conversations are only those it hosts, never the item work in the folder, even when an item window's worktree or the Support folder is the same folder, and item windows never list them. With no conversation it still gets its scope, so the view offers New conversation…. Hosts are compared by `hostKey` (`packages/core`): without case on Windows and macOS, and a folder host with its case elsewhere, so two Linux folders that differ only in case stay apart. Known limit: a folder whose name ends in `.code-workspace` cannot host conversations, because a host link tells an item window's file from a folder by that suffix (`isFolderHost`).
- **State.** A window stream's snapshot holds its conversations' work items alone: no pool, no held sessions, and no source notes or source errors, which can name other tickets, with how many work items need the operator, without naming them.
- **History.** `/history` answers the primary's ticket, a conversation's ticket, or a ticket whose History command the window claimed through `/claim`; it refuses any other with 403. A claim that names no key a connected window holds leaves History commands queued for the next one.
- **Opens and claims.** A pending open names its destination window, an item window's workspace file or a folder window's canonical folder, and `/claim` hands it only to the window whose binding is that destination, never by a folder or a workspace the claim names ([Claude Code runner](#claude-code-runner)). So a Support window, or a folder window on an item's worktree, never claims another work item's terminal.
- **Moved to the dock.** Notifications of work items that start needing the operator, and the work items behind the needs count, belong to the dock ([Dock](#dock)). Open in Switchboard asks the hub for the one row the operator's URL names ([VS Code extension](#vs-code-extension)). The dock's and the CLI's routes (`/dock/events`, `/holder/*`, `/config/*`) stay global; the extension does not call them.

### Hosted conversations

An ad hoc conversation started from a window (New conversation… in an item or folder window, or Switchboard: New Conversation…), from the dock's New conversation in a folder, or from the web page ([Web page](#web-page)) is a work item like any other, with a dock row and the usual controls (voice-design § 3.1).

- **Making one.** The flow makes an ad hoc ticket with a placeholder title, in the window's first folder or a folder window's canonical folder, hosted by the window's binding (`Ticket.hostWindow`), and a `running` work item whose session starts at once at an empty prompt (`Session.promptless`), without waiting for a free slot, since the operator is there to use it. A Claude conversation is refused while Code Mode or `sessions.installHooks` is off. Its contract offers no `done` or `approval` report.
- **Provider choice.** The caller offers Claude and Codex from `POST /v1/conversation/providers`, with `sessions.provider` preselected; the dock skips its picker when the hub finds only one provider's CLI (PRD R104). A cancelled choice creates nothing. The choice is stored on the work item (`WorkItem.provider`) and kept by queued starts and retries. A work item's sessions start in its playbook's provider, else its own choice while it has no playbook, else `sessions.provider`, so a chosen Codex conversation that a ticket report moves onto a playbook starts its next session in that playbook's provider. Choosing never changes settings or an existing session.
- **Idle start.** A promptless session waits at an empty input box and reads as idle, not running (mechanics M87). The contract and the conversation rules reach it only through its system prompt and, on resume and compaction, the contract hook.
- **Open between turns.** A hosted conversation's turn end and its session's end leave its work item `running`, never finished or blocked for a missing report; a failed turn still blocks it. It holds a slot only while its session is in a turn, so an idle conversation never holds back the queue. Its row stays in In progress, with the idle mark and no turn while its session is idle or ended, a question card included (PRD R103). It ends by Mark done, Delete, or the held session's idle end (PRD R95), after which Open in terminal resumes it.
- **Title.** Its first message, typed or sent in the terminal, titles it by its first line while it still has the placeholder title.
- **Resume before a message.** A Claude session that ended before its first message has no transcript, which `claude --resume` refuses (mechanics M87), so resuming it starts it again under its session ID with its contract and no prompt.
- **Its window.** A hosted work item has no window of its own: the dock and the extension open its host window and never write a workspace file for it. A row click first stores the conversation, done or not, as the host binding's selection, or selects it in a connected host window (`POST /dock/select`). An item window closes on its own only when its primary and every hosted conversation are done; a folder window never closes on its own.
- **From the dock.** `POST /dock/new-conversation {folder, opId, provider?}` needs no connected window: it hosts and runs the conversation in the folder's canonical path, as a folder window's would be, stores it as that folder binding's selection, selects it in the folder windows open on it, never in an item window that holds the folder, and answers `{workItemId, folder}` with the canonical folder, which the dock then opens with the conversation selected. A repeated `opId` answers the first work item and makes none, whatever spelling of the folder it names, so the dock can resend a request whose answer was lost; the opIds are kept in memory only. It answers 400 for a malformed body or a path that is not a folder a session can run in, and 409 with the flow's refusal, storing nothing.

### Reading a session

`ConversationService` (`packages/hub/src/conversation.ts`) owns scope, delivery, events, unread, artifacts and speech. A provider adapter reads each session: the Claude adapter by the rules below, the Codex adapter from Codex's native history and events ([Codex runner](#codex-runner)). `ConversationLog` stores authoritative entries for either provider and applies tags, statuses and rewrites. The conversation library (`packages/conversation`) is ported from claude-collab. The hub reads each active Claude Code Mode session's conversation while it runs, and a last time when it ends:

- **Transcript, the authority.** Claude Code's transcript of the session is the record, followed through the session ID changes the hub confirms (`/clear`, `/branch`, `/resume`, mechanics M73), so a nested run's transcript is never read. A checkpoint per session lets a restarted hub resume where it stopped, and an entry the store already holds is never imported again. A new transcript after an ID change is read from its start when it holds nothing older than the last entry read (`/clear`), else from its end, because `/branch` and `/resume` copy history, with a note that the conversation continued from another session. A transcript can grow to hundreds of megabytes, and reading all of it holds up the hub, so the conversation reads only what was added since the checkpoint and bounded parts of the file: its start, for copied history, and its end before the checkpoint, to link replies to messages after a restart.
- **Read before a turn end.** When a held session goes idle after a turn, the hub reads its conversation at once, before the flow decides whether an open question keeps the work item waiting on the operator (PRD R103); a message that comes back not sent answers no question. A Codex app-server session's idle marker waits until the items the adapter holds back have been imported.
- **Entries.** An assistant message's text is a reply, one reply per API message although Claude Code writes a line per content block; a reply saved only as thinking is still a reply (claude-collab findings 2026-11-17). A user line from the operator is a message, origin `terminal`, and a slash command shows as `/name args`. Lines Claude Code makes up, such as an added Poll call or "No response requested.", tool results, meta, sidechain and compaction entries, command output, shell escapes, reminders and interruption notes are left out. A message the operator sends while Claude is busy is added `provisional` when Claude Code queues it and moves to where Claude received it (claude-collab findings 2026-11-19); queue entries Claude Code adds itself, such as task notifications and the plain-text notice that the operator stopped background agents (mechanics M118), are left out, and a sent message that Claude receives as such an entry, has not received when the session ends, or has not received when a message sent after it is received, as when an earlier run exited with it queued, is `withdrawn`.
- **Order.** The conversation is in transcript line order, never by the lines' timestamps, which are not in order (claude-collab findings 2026-11-19). The items not in the transcript yet, a provisional message or a reply's screen copy, follow in the order they were first seen. A withdrawn item never holds back the items after it.
- **Screen, an early copy.** While a session works and shortly after, the hub reads its screen from the terminal holder's snapshot, from a holder that offers it, to show a reply before its transcript line lands. Code Mode sessions run in Claude Code's classic renderer so that finished output scrolls into the scrollback, where it can be read. A copy holds the reply's text alone: rows Claude Code draws beside it, such as Focus view's row of running tool calls, end it (mechanics M120), because a copy with them never matches its transcript copy.
- **Hold.** A screen copy waits briefly for its transcript copy, which is then published alone; one that comes later replaces the screen copy in place. The two copies are matched by their letters and digits, so Markdown syntax, wrapping and quotes do not count, and a transcript copy's link counts both as its text and as its text with its target, because the screen draws a link with its target (mechanics M130). A screen copy that gets no transcript copy is withdrawn, as are those still waiting when the session ends; a withdrawn rewrite frees the reply it replaced. A restarted hub takes up the published screen copies the stopped one left waiting, so each is replaced or withdrawn as before rather than left as a reply.
- **Replies.** A reply is split into its kind, aside or reply, its rewrite tag, its text (`opening`), its status ([Statuses](#statuses)), its primary response (`speak`) and its tone line. The primary response is the text before the reply's first `[details]` line outside code, which the text leaves out; with none, a short reply (`PRIMARY_SHORT_MAX`) with no list, table, code, heading, quote or rule is all primary, and any other reply's is its first paragraph, up to the first such structure, so a reply that opens with one has none. An aside has none, and an older reply's `[speak]`…`[/speak]` passage, from before the `[details]` rule, stays its primary response; a tag quoted as code or mentioned mid-sentence is text. A rewrite replaces the newest earlier reply that is not an aside, withdrawn or rewritten. A reply answers the first operator message on its transcript parent chain (claude-collab findings 2026-11-19), so several messages delivered together get one reply and one message can get several; when the chain reaches no message, as in history copied by `/branch`, the reply answers the latest message before it. The store keeps each session's newest messages and replies up to a fixed retention (`CONVERSATION_RETENTION`), outside the activity log, and deletes them with their work item.
- A window whose current session ended while the hub was not reading it gets the rest of its transcript read when its stream opens.

### Typing a message

The composer's `send` command (PRD R97) types a message into the window's current session through the terminal holder, from claude-collab's `session.js`. `ConversationService.send` stores the message, origin `typed` and delivery `open`, answers with it at once, and queues it in the session's `SessionInput` (`packages/conversation/src/input.ts`), which types one message at a time per session, in order. Each message is one input transaction, which reaches only the session and launch the view showed, never types a message twice, and never types over the operator:

1. **Guards.** The message waits while Claude Code shows a numbered choice or confirmation (its wait for a usage limit's reset is not one, because it takes a message, mechanics M100), while the input box holds a draft, or while an attached terminal typed a key moments before. Typing in the attached terminal is never blocked. A screen read or write the holder does not answer in time fails the message.
2. **Input reservation.** `Runtime.reserveInput` serializes the transaction with an end, Stop, Delete or resume of the session, as an attach does ([Code Mode sessions](#code-mode-sessions), Attach serialization), refuses a session that ended or was resumed under another launch than the view showed, and defers a release of the held session while it types. The guards are read again under the reservation.
3. **Paste and Enter.** The text goes as one bracketed paste with a leading `/`, `!`, `#` or `&` escaped, so it is never a command; a leading `@` stays a file mention, because the escape loses the mention ([mechanics.md](mechanics.md) M88), and a slash command chosen from the composer's list keeps its `/`, so it runs ([Slash commands](#slash-commands)). Enter goes once the paste shows in the box, and is retried only while the text still sits there and the screen has changed since, so a stale screen never sends a blind Enter. The session, launch and current-session checks run again before every write. The write counts as input for the end rule's settle (PRD R95).
4. **Confirmation.** The message is `sent` once the transcript holds it, as a user entry or as the queue entry of a message typed while Claude works, written at or after the paste and found in what the transcript added since the paste, since Claude Code can write megabytes right after the message's line, read without Claude Code's paste wrapping and with a slash command read from its command tags ([mechanics.md](mechanics.md) M86, M88, M99). Otherwise the screen settles it, and it is never typed again. An empty input box, or one holding other text, means it went: it is `sent`. A box holding exactly the message, with no key typed in an attached terminal since the paste, is cleared one key at a time, each only while the checks pass, the transcript still lacks the message and the box still holds what is left of it ([mechanics.md](mechanics.md) M90), and the message is `not-sent`. A box holding the message with other text, one a terminal typed into, one that changed under a key, or one that cannot be read, is left as it is, and the message is `not-sent` with why. A message refused before its paste, or whose session ended, was resumed or was replaced by a newer session of its work item while it waited, is `not-sent` with why.

**Tags.** A message sent while its reply will be heard ([Voice](#voice)) is typed with `[spoken] `, and `[expressive] ` after it while `voice.expressive` is on; a message that holds dictated text with `[voice] ` after those tags, and a part of one still being spoken with `[voice] [partial] ` and never `[spoken]` ([Dictation](#dictation)). A slash command chosen from the list never gets them. The reader strips them, so the message shows and matches as the operator wrote it.

**Matching.** A typed message is added `provisional` and matched to the transcript line that carries its pasted text, written near when it was pasted. Its queue entry makes it `sent`; the line where Claude received it makes it `sent`, gives it that line's place and UUID instead of adding a terminal message, and the replies whose chain leads to that line answer it. A typed message is never withdrawn as a terminal one is.

**Not sent.** A message that ends `not-sent` leaves the conversation: the hub deletes it from the store and sends a last `message` event with its text and why to the windows showing its session and the window that sent it, on which every window drops it and the window that sent it puts its text back in the composer ([Conversation view](#conversation-view)). A repeated `send` of a recent such message is refused with why rather than typed again.

**Restart.** A message a stopped hub left `open` is settled by the next hub once a window showing its session opens its stream: one never pasted is `not-sent`; a pasted one is settled from the transcript and the screen as above, only in the launch it was typed into, and `not-sent` with why when the holder never shows the screen or no launch was kept. Since this hub does not know which window sent it, its last `message` event carries `giveBack: true`, and every window showing the session puts its text back in the composer.

**Known limit.** A key typed in an attached terminal between the last screen read and a clearing key is not caught, as a paste is not (voice-design decision 2); the clearing stops at the next read.

**Older holders.** Typing needs a holder that names `write` in `welcome.features`. A holder of the same protocol from an older build is never replaced while the hub runs, so `send` to one is refused with how to stop it and switch builds, and until then the session can be opened in the terminal ([Visibility of held sessions](#visibility-of-held-sessions)).

### Slash commands

The composer's `/` list (PRD R101) shows the slash commands of the window's current session, from `POST /v1/conversation/commands` (`SessionCommands` in `packages/conversation/src/commands.ts`): first the built-ins that finish without a menu in the terminal, `/clear` and `/compact`, since the view cannot answer a menu, then the skills the session's transcript lists, in their order, with their descriptions ([mechanics.md](mechanics.md) M88). Before the session's first message, and after `/clear` until the next, the transcript lists no skills, so only the built-ins show. A command chosen from the list is sent with `command: true` while the text is one line that still starts with that `/name`, and typed unescaped so it runs; `send` refuses `command` for any other text. A `/name` typed by hand without choosing it, or recalled, goes escaped, as a message.

### Context meter

The hub reads each shown session's context size and sends it as `SessionView.context`, `{used, window, compactAt, model}` or null while it is not known (PRD R114); the computation is `packages/conversation/src/contextMeter.ts`, shared with both front ends.

- **Claude.** `used` is the latest main-chain request's size in the session's current transcript, counted as Claude Code's own panel counts it, leaving out subagent, made-up and API error lines; a compaction boundary sets it to the size after compaction, and a new transcript file, after `/clear` or a resume, starts unknown. `window` comes from the request's model, looked up in a table copied from Claude Code's ([mechanics.md](mechanics.md) M105); the transcript does not say whether the long window is on, so a size past a model's standard window reads as its long window. `compactAt` is the threshold Claude Code's own panel uses, or, where lower, the size at which the transcript shows the session last compacted itself, since Switchboard does not read the settings that move it. An unknown model has a null `window` and `compactAt`.
- **Codex.** `used` and `window` come from the latest token-usage notification for the session's thread; `compactAt` is null, since Codex does not report it. It is unknown until the first notification after the hub started.
- **Meter.** One renderer, shared by the Conversation view and the web page, draws it in the composer's footer as a ring with no text, filling toward `compactAt`, else `window`, and warning as it nears it; an unknown size shows an empty track. Its menu repeats the size and can compact the conversation, which sends `/compact` through `send` as a chosen slash command, leaving the composer's draft alone.
- **Updates.** After each conversation read ([Reading a session](#reading-a-session)) the hub sends a window its `session` event again when the session's context differs from what that window was last sent, so the meter follows each request of a turn.

### Statuses

A status is the part of a reply after its own `[status]` line, outside fenced code, to the end of the reply's text (`splitStatus`, from claude-collab's `status.js`); the text before the line is the reply's `opening`, empty for a reply that is only a status. A tag quoted inline, in a code block or with text on its line is text. A status is taken only from a reply's transcript copy, never its screen copy, which can still be withdrawn or growing. Each reply has at most one status, updated in place when a later line of the same API message adds to it, and the newest status read is the session's. A reply that is only a status rewrites nothing, is not a rewrite target, and is left out of the timeline. The store keeps each session's newest statuses up to the same retention as replies, in the order read, outside the activity log, and deletes them with their work item.

Before a session's first status, a window's Status tab shows its work item's stage (`WorkItem.stage`, from `stage` reports) as a fallback status, never unread; with no stage either, the tab says the session has posted no status yet. The session's state is not repeated there.

### Unread

PRD R100. A reply or status is unread until the operator sees it; the store records when (`seenAt` on the `replies` and `statuses` rows).

- **Where.** An unread mark shows only where the operator would not otherwise think to look, such as an older conversation in the dropdown. No list of work items shows one: the operator looks at a Ready for review item anyway, and at an In progress one when it moves to Ready for review, not before. So the dock's rows, the web page's list and the Switchboard pane show none, and the snapshot and the dock view carry no count.
- **What counts.** A reply the timeline shows on its own (`countsUnread` in core): not a withdrawn screen copy, a reply a rewrite replaced, a reply that is only a status or a note Switchboard added. Of the statuses, only the session's latest, which the Status tab shows. A screen copy replaced in place by its transcript copy keeps its ID, so it is seen once, and a seen status or reply stays seen when it grows. Only a work item's current session counts, so an earlier session's items, which no window shows, never count.
- **Seen.** The view counts an item as seen once it has been in view for a second while the window has the focus, as PRD R100 defines in view, and reports it with the scope generation and session it was shown in (`seen`, [Conversation API](#conversation-api)); an item the hub did not accept is reported again, as is whatever is still unread after a reconnect. Each item is marked on its own, so seeing a newer one never clears an older one, and being in the window, a newer item or the window's focus alone does not count. A view that was never opened in a window, or is hidden, marks nothing.
- **Mark.** Unread has one mark and one colour everywhere, VS Code's activity bar badge colours, as the badge's own views use: a count, or a dot where it marks one item, such as a conversation in the dropdown or the Status tab ([Conversation view](#conversation-view)). The dot is named for a screen reader and on hover, Unread, or Updated for a status that is only New, and no tab or status carries a New label in its place. The selected conversation's own entry and button carry no dot, since its items are in front of the operator.
- **Counts.** The hub sends each window that lists a session's work item, while it is that work item's current session, `unread {workItemId, count}` when its count changes, checked after every message, reply or status added or changed, since a new item can push an unread one past retention, and after a `seen`. A window's dropdown entries carry each conversation's count (`ConversationEntry.unread`).

### Artifacts

An artifact is a file one level down in its work item's artifact folder, `<owner>/<file>` (PRD R99), from claude-collab's `artifacts.js`. The folder is `<session folder>/.wip/artifacts/w<work item ID>` (`artifactsDir` in core), its own per work item, so a later work item that shares the worktree never lists an earlier one's; the session finds it in `CLAUDE_ARTIFACTS_DIR` and in the conversation rules ([Code Mode sessions](#code-mode-sessions)). Artifacts are not stored; the folder is the record.

- **Watch.** `ArtifactFolder` (`packages/conversation/src/artifacts.ts`) watches the folder and gives each artifact a type by its extension (`markdown`, `html`, `image`, `audio`, `video`, else `file`) and, for a Markdown or HTML file, a kind and title from front matter `kind` and `title`, else its first `#` heading or `<title>`, else its file name. A name with a segment that starts with a dot is not an artifact, nor a file deeper down; a change in `<owner>/<stem>/`, the folder of files an artifact uses, is a change to that artifact. A file is resolved by real path, so a link or junction that leaves the folder lists nothing. A missing or deleted folder lists no artifacts until it appears.
- **Hub.** `ConversationService` watches the artifact folder of each work item that a window with a stream shows, and stops once no such stream remains. `hello` carries `artifactsDir` and `artifacts`, newest first, and each change goes as an `artifact` event to the windows of that work item only.
- **Opening** (`Artifacts.open` in `extensions/switchboard/src/artifacts.ts`). Only an artifact of the list the window was sent, resolved by real path inside `artifactsDir`, opens: Markdown in VS Code's Markdown preview, a picture in its image preview, an HTML page in its own panel, and audio, video and anything else with VS Code's default editor for the file.
- **HTML panel** (voice-design § 4.4). An HTML artifact opens in its own webview panel, apart from the Conversation view's message bridge, where its scripts run with no network access, no form posts, no `<base>`, and no link that leaves the page, and it loads local files only from the folder beside it inside the artifact folder; any other URL is emptied (`artifactPage` in `src/artifactModel.ts`). An open panel is drawn again when its artifact changes, and says so when it is deleted. Known limit: a script that sets `location` itself is not stopped.
- **Mermaid** (voice-design § 4.4). The extension extends VS Code's Markdown preview so a `` ```mermaid `` block draws as a diagram, offline and with Mermaid's strict security level, in the preview's light or dark theme; a diagram Mermaid cannot read keeps its source with Mermaid's error under it. It applies to every Markdown preview of the window, statuses included.

### Conversation API

Version 1, loopback, with the hub token; the web page reaches the same routes with its cookie and a page key in place of a window key, and adds its own routes ([Web page](#web-page)).

The page reads the API's views with the types in `packages/protocol`, the fields it reads, since it cannot import the hub, which bundles it. `packages/hub/src/protocol.ts` checks at build time that each hub view the page gets still carries every one of those fields with a type the page accepts, so a change to either side that breaks the other fails the hub's build. The VS Code view imports the hub's own types. Those types are the authority for the views' fields; this section states what the fields mean where the protocol depends on it.

Every command below is a `POST /v1/conversation/<name>` whose body names `window`, the window key, `scopeGen`, the scope generation the view was shown, and `opId`. Unless a route says otherwise, a key no connected window holds or a target outside the window's scope is refused with 403, a stale `scopeGen` with 409, and a malformed body with 400. A read repeats on a repeated `opId`; a command never repeats its change.

- `GET /v1/conversation/events?window=<key>`: an SSE stream for the window key, refused with 403 for a key no connected window holds. Each event is `{v: 1, seq, type, at, …}` with `id: <seq>`. `hello`, when it opens and on every reconnect, carries the window's whole state: its scope ([Window scope](#window-scope)), with the dropdown's conversations, the primary first; the sessions; the current session's newest items in conversation order, withdrawn ones left out, with `more`; the Status tab's status; the unread count; the artifact folder and artifacts; the voice state ([Voice](#voice)) and the view settings. `scope` followed by a fresh `hello` comes when the selected conversation or its current session changes, and `conversations` when a dropdown entry changes and the selection does not. The other events carry one change each: `session`, `message`, `reply`, `status` (a new or updated status of the current session, or its work item's stage before the first), `artifact` (with `removed: true` when it is gone), `unread {workItemId, count}` ([Unread](#unread)), `voice` and `settings`; `progress` while a reply of the window's session plays; and, to the window dictation goes to ([Dictation](#dictation)), `words` as an utterance's live words change and `draft` when the hub changed the composer's draft.
- **Sessions.** `SessionView.conversation` says what the view can do: `full` for a live Code Mode session with hooks on and for a Codex app-server session with a thread ID, ended or not, since a message resumes an ended one; `read-only` for a Code Mode session that ended or is unobserved; and `none` for a background session; each with its reason. `context` is the session's context size ([Context meter](#context-meter)). `persona` is set while `voice.enabled` is on and the session has a persona in the roster, and `canPin` while `voice.enabled` is on, the roster is not empty and the session is one the flow pins ([Personas](#personas)). `background` marks a `running` session whose turn ended while background tasks it started still run, so it is in no turn, with how many agents, shells and other tasks they are; it is null otherwise.
- **Messages and replies.** A window places each item by its `ord` and whether it is in the transcript yet (`provisional`, [Reading a session](#reading-a-session)), so an item moves when its transcript line is read. A typed message's `delivery` is `open`, then `sent`; a `message` event with `delivery: 'not-sent'` and `error` removes a message that typed nothing or that Claude Code did not take, with `giveBack: true` when every window showing the session is to put its text back in the composer; `delivery: 'refused'`, sent only to the window that dictated it, is a spoken turn the hub refused before storing anything. A dictated message carries its recognised pieces and whether it is a `[partial]` part ([Dictation](#dictation)), and one that spoke over a reply what the reply had said ([Voice check and barge-in](#voice-check-and-barge-in)). A reply carries its kind, what it answers, its rewrite links, its unread flag, its primary response and tone line, and its playback state ([Voice](#voice)).
- **Artifacts and statuses.** An artifact's `path` is `<owner>/<file>` in `artifactsDir`, and its `type` one of the [Artifacts](#artifacts) types. A status's `fallback` is true for the work item's stage ([Statuses](#statuses)), which is never unread.
- `history {sessionId, before, limit?}` answers `{items, more}`, the items before the item `before` names (null for the newest; one that is gone, or another session's, has none before it), in conversation order, at most 100; 403 for a session that is not the window's current one. It only reads.
- `statuses {sessionId, before, limit?}` answers `{statuses, more}`, the current session's statuses before `before`, newest first, at most 50; refused as `history` is. It only reads.
- `seen {sessionId, ids}` marks at most 200 replies and statuses of the window's current session seen, each on its own, and answers `{unread}`, the session's count; the windows showing it get each marked item again and `unread`. Refused as `history` is, and with 403, marking none, for an ID that is not a reply or status of that session; 400 for more IDs. Marking again changes nothing.
- `send {sessionId, launch, text}`, or `send {sessionId, launch, answers}` from a question card, whose text the hub writes (PRD R103), types `text`, at most 10,000 characters, into the window's current session ([Typing a message](#typing-a-message)) and answers `{message}` at once, with `delivery: 'open'`; `message` events bring its delivery. A repeated `opId` that passes the scope checks answers the message it added to that session and types nothing again. Refused with 409 and the session's reason when its conversation is not `full`, with 409 when `launch` is not the session's, and with 400 for an empty or longer text. `command: true` types a slash command chosen from the composer's list without the escape ([Slash commands](#slash-commands)); 400 for any text with it that is not one line starting with `/name`.
- `card-draft {sessionId, card, draft}` keeps a card's draft for every window, page and the voice, and `card-dismiss {sessionId, card, slug}` dismisses an open question; both answer `{done: true}`, 409 for a card or question that is not open, and send the windows showing the session a `questions` event ([Conversation view](#conversation-view), Question cards).
- `commands {sessionId}` answers `{commands}`, the current session's slash commands as `{name, description}` without the slash, the built-ins first ([Slash commands](#slash-commands)); refused as `history` is. It only reads.
- `providers {}` reads `{defaultProvider, installed}`, the current `sessions.provider` and the providers whose CLI the hub finds, from `sessions.claudePath` and `sessions.codexPath`, without creating work or changing settings. Creation routes accept only `claude` or `codex` when `provider` is present; any other value, null included, gets 400. A repeated creation `opId` keeps its first result even when the retry names another provider.
- `select {workItemId}` selects one of the window's conversations and answers `{scopeGen}`; the window gets `scope` and a fresh `hello`. 403 for a work item that is not one of its conversations; a stale `scopeGen` is not refused, since the command names its whole target.
- `new-conversation {provider?}` makes a [hosted conversation](#hosted-conversations) for the window, hosted by and run in its binding's folder, selects it and answers `{workItemId}`; a repeated `opId` answers the first work item. 403 for a key with no scope, 409 with the flow's refusal.
- `mic {on}` turns the mic on, moving the voice to the window's session first, or off, and answers `{on}`; 409 from a window the voice is not in. `composer {focused, draft}` tells the hub the composer's focus and draft, at most 10,000 characters, for the focus rule, and answers `{done: true}` ([Dictation](#dictation)).
- `talk-here`, `stop-speaking`, `speak-replies {on}` and `replay {replyId}` ([Voice](#voice)): 403 for `replay` of another session's reply, 409 with the voice's refusal, such as a window the voice is not in, `voice.enabled` off, a session that is not live or a reply with no primary response, and 404 from a hub with no voice; `speak-replies` answers `{on}`.
- `personas {}` answers `{personas}`, the roster as `{id, name, voice, style, personality}`, empty while `voice.enabled` is off; `persona {sessionId, personaId}` pins the persona to the window's current session, or clears its pin with a null `personaId`, and answers `{persona}`, the session's new `SessionView.persona` ([Personas](#personas)); 409 while `voice.enabled` is off and with the flow's refusal, such as an ID not in the roster.

### Conversation view

`ConversationView` (`extensions/switchboard/src/conversation.ts`) is the item window's view of its conversations (PRD R96–R104), in a secondary side bar container as Claude Code's own panel is, or in an activity bar container on a VS Code before 1.106 (mechanics M85). It is its container's only view. The extension owns the conversation stream for its window key: after each `/events` `hello` it opens the stream, applies its events to `ConversationState` (`src/conversationModel.ts`) and posts the whole state to the page, which only draws it (`src/webview/conversationRender.ts`); a stream that ends or does not open is opened again a few times, waiting longer each time, and then waits for the next `hello`. What the view and the web page draw alike (question parsing, message metadata, spoken bubbles, voice controls, menus, the picker and the composer's styles) lives in `packages/conversation`, so the two cannot drift.

- **Header:** the conversation dropdown (PRD R102, R104), the persona button (PRD R106, [Personas](#personas)) and Open in terminal. The dropdown's button and each of its rows draw a conversation the same way: its current session's state codicon, its title, the unread dot ([Unread](#unread)) and its provider's mark. State codicons come from `sessionIcon` in `packages/core/src/group.ts`, which takes them from the dock marks with the same meaning (`MARK_ICONS`), so the view, the web page, the pane and the dock draw one icon per meaning. New conversation… asks for the provider in the same menu and posts `new-conversation`; choosing a conversation posts `select`, after which the view and all three tabs start from that conversation's `hello`. The persona button opens the roster from `personas` and posts `persona`; it shows for a session that has a persona or can take a pin (`canPin`), and marks a persona not yet delivered to the session's prompt (`tonePending`). Every choice is made in the view's own menus: the view opens no quick pick or dialog, except that Switchboard: New Conversation…, for the keyboard, asks for the provider in a quick pick. A refusal shows in the menu that asked, or above the composer for a pin or a new conversation. A folder window with no conversation shows the dropdown with its folder's name, holding only New conversation…, and no composer.
- **Menus:** every menu the view opens (the conversation dropdown, the persona and provider menus, and the Status tab's earlier statuses) is drawn as VS Code's context menus, from its `menu.*` colours, and placed by `placeMenus` (`packages/conversation/src/menuPlace.ts` with `menu.css`, shared with the web page) on every draw, resize and scroll: under the button that opened it with their left edges lined up, extending right and down as a desktop menu does; lined up with the button's right edge instead only when it would pass the view's right edge and has more room to the left, and above the button only when it would pass the bottom and has more room above; its size capped to the room on the side it extends to, so a menu that fits on neither side scrolls inside the view. Up and Down move between the rows, Enter or a click chooses, and Escape or a press outside closes the menu, giving the focus back to its button.
- **Tabs:** Conversation, Status and Artifacts (PRD R98), drawn as VS Code's panel tabs, only the selected tab's panel shown at the view's full height. The composer, with the voice controls, stays at the bottom on every tab, so the operator can type or dictate from any of them; a message sent from another tab leaves that tab shown and says that its reply shows on the Conversation tab. An ended session's reason shows above the composer on every tab with **Resume**, which opens the session's attach terminal; an ended Codex app-server session, which a message also resumes, says so. The strip is one tab stop, moved with the arrow keys, Home and End. The Status tab carries the unread dot ([Unread](#unread)) while its status is unread or New, named Unread or Updated, and the Artifacts tab a badge with the count of artifacts new or changed since last opened. A tab's dot lies in its end padding, so showing it changes neither the tab's width nor its label's place. The page keeps the shown tab and the conversation's scroll position with `setState`. It draws each state by changing only the nodes that differ (`morph`, `src/webview/morph.ts`, matching children by `data-key`, `data-id` or `id`) and leaves a focused field's value alone, so a redraw keeps the focus, a selection, the caret, scroll positions and open menus. A window with no work item shows no tabs.
- **Status tab:** the session's latest status as Markdown (PRD R98, [Statuses](#statuses)), with its time, how long ago, the unread dot while New, a button that opens it in the Markdown preview and a menu of earlier statuses, paged through `statuses`. A status that replaces the one the page had for the same session, or the first after the stage, is New until a minute after the tab first shows it in a visible page or until it is opened in the preview. Before the first status the tab shows the work item's stage. The preview reads a `switchboard-status:` document from a `TextDocumentContentProvider` that serves only statuses this window was sent and forgets them when its work item or current session changes; since the preview would resolve a relative link against that URI, the provider turns each inline link to a path, relative to the session's folder or absolute, into a `file:` URL (`previewLinks`).
- **Timeline:** the conversation in its order ([Reading a session](#reading-a-session)), drawn as PRD R96 describes: the operator's messages as bubbles on the right, replies whole as Markdown at the theme's text size, with the text of every bubble, the operator's and a reply's primary response alike, at 110% of it, asides dimmed, notes centred and a rewrite in the place of the reply it rewrote, with the earlier version a click away. A message that was not sent, or was withdrawn, is left out; a provisional one is dimmed. Each item's metadata (its marks and time) is one line under it (`metaLine` in `packages/conversation/src/messageMeta.ts`, which the web page uses too); a day's divider comes before the first item and each turn that starts on a later day than the turns above it, so an item dated before them, such as a provisional message queued days ago, starts none; times show on the first item after each day's divider, or on every item with **Show message details**, a per-user choice the extension keeps in `globalState` and sends with each state as `details`. Each artifact written no earlier than the oldest item shown is a row placed by its write time (`placeArtifacts`), since an artifact has no transcript line, and opens it ([Artifacts](#artifacts)). A turn row sits after the newest item while the session is in a turn, starting or running other than with only background tasks left (`inTurn`), after any reply written mid-turn and in a turn that no message started, such as one a task notification starts; and, before a hook says a turn started, while no reply answers the operator's latest message or a later one (`awaitingReply`). It goes when the turn or the session ends, and shows no tool activity. **Show earlier messages** pages back with `history`.
- **Speech** ([Voice](#voice)): a reply's primary response is drawn as a bubble on the left, opposite the operator's messages, and its details after it smaller, the same whether or not it was spoken, and the primary response shows once: a reply that is all primary, besides questions that end it and show in its card, is only its bubble and card; otherwise the bubble shows first with **Show more** for the details (focused mode, voice-design decision 21), or the reply starts whole with `voice.expandReplies` on (`spokenBody` in `packages/conversation/src/spokenBubble.ts`). Besides Settings' Expand replies, the view's title menu has **Expand Replies** or **Collapse Replies** and the web page's view options menu an **Expand replies** checkbox under Show message details, on this computer's page only; each posts `expand-replies {on}`, which sets that one key in settings.json as a Settings save would, refusing a file Settings could not save, and the reload's `settings` event redraws every window and page. Unlike Show message details, it is one setting for every window and page, not a per-user choice. A passage not found in the reply's text leaves the whole reply plain. Routine speech states show nothing; a passage the operator spoke over (`interrupted`) shows the part not heard dimmed, and, with Show message details on, a reply whose speech `failed` is marked "Not spoken", its tooltip pointing to the voice log, as the web page does (`spokenMark` in `packages/conversation/src/messageMeta.ts`). R on a focused reply posts `replay`, and Escape while this window's session speaks posts `stop-speaking`. While `voice.enabled` is on, the composer's footer keeps the message tools on its left and every voice control in one cluster beside Send (voice-design report IA-3): while the voice is here, Speak replies and the mic button ([Dictation](#dictation)); while it is elsewhere, only **Talk here**, and only for a `full` session, since the hub refuses Talk here for any other. While the voice is here but no device has it, after the phone left, **Talk here** stands before Speak replies, and the status bar item and the Switchboard pane say Voice off, untoned, since it is a state rather than a problem, so a reply is never skipped unnoticed ([Remote access](#remote-access), Voice on a phone). There is no Stop button: while this window's session speaks, a click on Speak replies turns it off, which stops the reply playing at once ([Voice](#voice), What is spoken); while Speak replies is off a reply plays only as a Replay, and the same speaker then stops it and leaves Speak replies off; Escape stops speaking from the keyboard. The message tools and the context meter keep the footer's left and never shrink under their buttons, and the voice cluster, the mic and Send stay together on its right; where both do not fit, the right group wraps whole onto a line of its own, so no voice control is ever drawn beside the context meter. The web page draws the same cluster (`renderVoiceControls`). There is no voice status text: the mic button carries the mic's state. The footer's buttons are redrawn only when their HTML changes, so a state event between a press and its release does not swallow the click.
- **Question cards** (PRD R103): a reply, not an aside or a note, that asks numbered questions with options lettered from A gets a card under it; the Status tab shows a status's questions as plain Markdown, with no card. `parseQuestions` (`packages/conversation/src/questions.ts`) reads the Markdown outside fenced code into each question's slug, topic, text and context, and each option's label, description and `(recommended)` mark; a missing slug is derived from the topic or the first significant words, and one used twice in a reply gets `-2`. A numbered item without options is no question, and a letter out of order, a repeated number, or a lone run of options beside other questions gives no card. The `{#slug}` ids and `[withdraw: …]` lines are left out of every text the views show.
  - **State.** `questionLedger` (shared by the hub, the web page and the view) gives each question, keyed `reply:<reply ID>#<slug>`, a state: `open` once asked; `answered` or `dismissed` by the answers stored on a message; `withdrawn` by a later reply's `[withdraw: slug]` (or `all`), with its reason, or when a `[rewrite]` reply no longer asks it; `replaced` when a later reply asks the same slug while it is open. A rewrite keeps the state of the questions it asks again. A slug asked again after an answer opens a new question. A message that answers nothing changes nothing, so a question stays open until it is settled, and a turn that ends with one open gives the dock row the Answer a question mark until none is. Replies from before the cutover, `questionsLedgerSince` in the hub's page preferences, recorded at the hub's first start on this version, keep the earlier rules: the first message after a card answers or skips it, and a later reply supersedes it.
  - **Answers are linked, not inferred.** The hub resolves each message once, when it stores it, against the questions open then (`resolveAnswers`): `[answers]` lines by slug, `slug B`, a lone letter for the current question of the card the operator works in, and legacy `1A` against the newest card only; and stores the links in the message's `answers` column, `[]` when it answers none. A message stored before the column, or read from the transcript, is read by its text in conversation order. A card's Send posts `send {answers: [{card, slug, letters, other}]}`; the hub checks each against the ledger, refuses one no longer open, or a message over the length limit, with why, and writes the `[answers]` message (`answerMessage`), one line per question, `- slug: question → A) label; Other: text`, with `No answer (dismissed)` lines for dismissals no answer message has told the session yet.
  - **Drafts on the hub.** Each card's draft, its current question and the picks so far, is kept by the hub (`card-draft`) for every window, page and the voice, so a card started on one device goes on on another. A pick for a question asked again, by a rewrite or the same slug, moves to the new question when its options' labels match. An answer message that is not sent reopens its questions with their picks, and the dismissals it told are told by the next one. The hub sends a session's questions in `hello` and as `questions` events: the cutover, the open count across the conversation, the oldest open card, the drafts and the dismissed keys.
  - **The card** (`renderQuestionCard` in `packages/conversation/src/questionCard.ts` with `questionCard.css`, one renderer for the web page and the view) shows one question at a time, at most four at once with the rest after them: progress dots, the slug, the topic, question and context, full-width options with their descriptions, Other with a text area, a summary of the picks, and Back with Next, or Send on the last step, which sends the answered questions only ("Send 2 of 3"). A single-choice pick moves on after 200 ms. While the card has the focus, A–H pick, O opens Other, Enter goes on or sends and Backspace goes back. Dismiss is in its menu. Questions settled while others are open show as rows under it with their state and its reason or a link to the replacing question; a card with none open folds to its rows and a link to the answer. The card never scrolls or takes a touch gesture of its own, so a pan over it scrolls the conversation. It takes no answer while the composer could not send.
  - **Answers in the conversation.** An answer message shows as an Answers bubble, its tag hidden, each slug a chip, with a link to its card; any other message that answered questions quotes them over its bubble. A chip over the composer, on every tab, says how many questions are open across the conversation while the oldest open card is out of view, and goes to it.
- **Codex requests:** a Codex session's pending questions and approvals (`SessionView.requests`) show as cards at the end of the timeline, in place of the turn row; a click posts `answer-request`, which the extension sends to the hub's `answer` with no dialog, and a refusal shows in the card. A request the view cannot answer offers Open in terminal. A taken request leaves with the hub's next state.
- **Background work:** while the session's turn has ended but its background agents, shell commands or other background tasks still run (`SessionView.background`, from the state detail), a quiet line with the spinner says how many, such as "3 agents running", at the end of the timeline when no turn row is due, until a `Stop` lists none; the web page draws it too. A turn row, as for a message sent meanwhile, takes its place and shows no count.
- **Waiting in the terminal:** while the session waits on the operator in its terminal (`waitingFor` `question`, `permission` or `start-prompt`) and has no Codex request the view answers itself, the turn row says what it waits for, in the warning colour, with **Open in terminal**, whether or not a reply is due. The view does not answer the terminal's menu (voice-design § 5.1).
- **Composer** (PRD R97, R101, [Typing a message](#typing-a-message)): drawn by `composer.css` (`packages/conversation/src/composer.css`), which the web page shares. Enter posts the text with the scope generation, session and launch the page showed, which the extension sends with `send` unchanged, so a message is refused rather than sent to a session the page did not show; the extension posts it again once with the same `opId` when the hub does not answer. Shift+Enter adds a line. The box is read-only until the hub answers, empties once the hub took the message, and on a refusal keeps the text and shows why above the box. A message that ends `not-sent` comes back to the window that sent it, even after its scope moved: its text goes after any draft and a blank line, with why above the box, and only into its own conversation's draft (by `workItemId`), never into another conversation selected since; the extension keeps it until a loaded page takes it, since a hidden view's page is not kept. Each conversation has its own draft, refusal and chosen command, kept in the page's `setState` by work item, which VS Code keeps over a reload. The composer is disabled, with the reason, for a session that is not `full`, and hidden with no conversation. The model is not shown, since the hub does not keep it. The extras, as Claude Code's panel has them, are in `src/webview/composerExtras.ts`, with their decisions in `src/composerModel.ts`:
  - **File mentions.** `@` lists files and folders under the session's folder, or the window's first folder before the session has one, through `vscode.workspace.findFiles`, leaving out `files.exclude`, `search.exclude` and the folders Claude Code's panel leaves out. A chosen file goes in as the panel writes a mention: relative to the session's folder with forward slashes, absolute outside it, quoted where the panel quotes; a path with a double quote cannot be mentioned.
  - **Attached, dropped and pasted files.** The attach button opens VS Code's open dialog in the session's folder; files dragged from VS Code go in from the drop's URIs, which VS Code gives a webview only with Shift held, and files from the operating system's file manager, which carry no path in a webview, are refused with why. A pasted image is written by the extension (`writePastedImage` in `src/pastedImages.ts`) to `<os temp>/switchboard-pasted/` and mentioned, which Claude attaches as an image (mechanics M88); it never overwrites a file, refuses a folder that is a link or junction, and deletes only its own images there older than a week.
  - **Slash commands.** `/` as the box's first character lists the session's commands from `commands` ([Slash commands](#slash-commands)), asked again each time; the chosen one is sent with `command`.
  - **Message history.** Up on the box's first line and Down on its last walk the session's messages the view holds, typed and from the terminal; typing ends the walk.
  - **Context meter.** The selected conversation's context meter ([Context meter](#context-meter)); its Compact posts `send` with `command: true`, so a refusal shows above the box and the box's text stays.
  - **Draft.** A saved command is taken back with the draft only while the draft still starts with it.
- **Artifacts tab:** the window's work item's artifacts newest first (PRD R99, [Artifacts](#artifacts)); a click posts `artifact` and the extension opens it. `Artifacts` (`src/artifacts.ts`) keeps when each artifact was last opened in `workspaceState` by work item and path, and the artifacts of a work item a workspace has not seen before count as opened. The extension posts the paths still new or changed with each state. `switchboard.openArtifact` opens one by its path.
- **Unread:** unread replies and statuses take the unread mark (PRD R100, [Unread](#unread)); the dropdown's dots mark the conversations not selected that have unread items; the view's `WebviewView.badge` is the sum of every conversation's unread count (`totalUnread`), none at 0. The page reports what it showed ([Unread](#unread)).
- **Copy:** code blocks and replies from the transcript have copy buttons, as in Claude Code's panel; a code block copies its text and a reply its Markdown. The page posts `copy` and the extension writes the clipboard.
- **Markdown:** markdown-it with raw HTML off. A link posts its target, and the extension opens a web page with `openExternal` and a file at its line, relative to the session's folder (else the window's first folder), with `vscode.open`, and drops anything else.
- The view is not retained when hidden; its page asks for the state again and keeps its folds, scroll position and drafts with `setState`. The conversation follows its end until the operator scrolls away: only the operator's own scrolling decides, so a layout change that alters a height re-scrolls to the end rather than stopping the follow. Scrolled away, new items stay below and a **New messages** pill takes the operator back. The timeline is one tab stop moved with Up and Down; new replies are announced through an `aria-live` region, and `vscode-reduce-motion` stops the mic's pulse but not the spinning icons, which keep spinning under reduced motion on the web page and the dock too, since a still loading glyph reads as a half circle rather than work in progress (the operator's decision).

### Voice

PRD R105, voice-design slice 9 (speech out), PRD R106, slice 13 ([Personas](#personas)), PRD R108, slice 10 ([Dictation](#dictation)), slice 11 (voice in a session's terminal window, PRD R105 and R108), PRD R110, slice 14 ([Voice check and barge-in](#voice-check-and-barge-in)), and PRD R112, slice 12 ([Spoken alerts](#spoken-alerts)). Voice is off until `voice.enabled` is on ([Settings](#settings)).


- **The voice process** (`packages/voice`, `voice.js`) is a process of its own on `sessions.nodePath`'s Node.js, because its capture and playback (decibri) and its recognition (sherpa-onnx) are native modules, and it keeps them out of the hub. The extension carries its build, with its native platform packages, the turn model's process (`turn.js`), the GPU check (`gpucheck.js`) and the Windows helper scripts; `installVoice` installs it in `<home>/voice/<build>/` as the holder's build is installed, under its own install lock, keeping the running process's build. `<home>/voice/` also holds the operator's data (models, terms, hotwords, the glossary, voiceprints and the fragments logs), which an install never touches. One process runs per home, held by a lock and named by a record, `<home>/voice.json`, with its output in `<home>/voice.log` (Switchboard: Show Voice Log). It holds no conversation, session or work item state, and exits some minutes after its last hub left, or when the hub sends `shutdown`.
- **Supervision.** `VoiceLink` (`packages/hub/src/voiceLink.ts`) connects to the process the record names, checking that the welcome's `pid` is the record's; it replaces a process of another build or protocol with `shutdown`, since the process keeps nothing worth keeping, refuses a lock held with no answer, and otherwise starts the installed build detached, without VS Code's variables. `VoiceControl` (`packages/hub/src/voice.ts`) wants the process while `voice.enabled` is on and a scoped window is connected, a session's terminal window is in front, the target is a session followed to its terminal window, or an enrolment runs; it restarts a failed process at most once a minute and stops it some minutes after nothing wants it. Why the process cannot run shows in the dock, never in a window.
- **Protocol**, version 1 (`packages/voice/src/protocol.ts`): JSON lines over loopback TCP, the hub its only client; `hello {token}` → `welcome {protocol, build, pid, features}`, and a hub that connects replaces the one before. Hub to voice: `settings`; `targets {targets: [{sessionId, workItemId, repo?}], focus: {sessionId, via: 'window' | 'terminal'} | null}`, the targets being the `full` current sessions of scoped windows and the `full` sessions whose terminal window the dock has reported in front since they started, and the focus the session whose terminal window is in front, else the focused window's selected conversation's current session; `talk-here {sessionId}`; `speak {gen, replyId, sessionId, text, tone, turn, voice, style, personality}`, `turn` the message the reply answers and the voice fields the session's persona's, else the settings' ([Personas](#personas)); `cancel {replyId, off?}`; `stop`; `earcon {kind: 'needs-you'}`; `shutdown`; for dictation `mic {on, restore?}`, `typing {on}`, `context {sessionId, lastReply}` and `heard {heard, meant}` ([Dictation](#dictation)); `enroll {action}` ([Voice check and barge-in](#voice-check-and-barge-in)); `alert` and `alert-cancel` ([Spoken alerts](#spoken-alerts)); and `device`, `phone-played`, `phone-mic` and `phone-state` ([Remote access](#remote-access), Voice on a phone). Voice to hub: `active {gen, sessionId | null, reason: 'focus' | 'talk-here' | 'gone'}`, also as its greeting; `speech {gen, replyId, sessionId, state, atMs, said, reason?}`, `state` `playing`, `played`, `interrupted`, `skipped` or `failed`, and `reason` why the process itself skipped or stopped it (no device, the operator away, Stop speaking, Speak replies turned off, spoken over, a newer turn), which both logs name; `progress {gen, replyId, sessionId, chars, atMs}` while a reply plays; `audio {mic, engine, device, recognizer, error, halfDuplex?, fullDuplex?, roomHold?}`, also in its greeting, when capture's state, where recognition runs, or a capture, playback or speech failure changes; `words`, `piece`, `utterance`, `command` and `mic-off {reason}` ([Dictation](#dictation)); `enrollment {state, error}` ([Voice check and barge-in](#voice-check-and-barge-in)); `alert-done` ([Spoken alerts](#spoken-alerts)); `device {device}` in its greeting ([Remote access](#remote-access), Voice on a phone); and `phone-play`, `phone-pcm`, `phone-end`, `phone-flush`, `phone-stalled` and `phone-capture` while a phone has the voice ([Remote access](#remote-access), Voice on a phone).
- **The voice target** (`Router` in `packages/voice/src/routing.ts`): one session per machine, with a generation that rises at each change. It follows the focus after half a second (PRD R105); focus moving to another window's session drops the target at once, stopping speech and dropping what waits, so nothing plays until the new target is set. Talk here sets it at once: selecting a conversation in the focused window, the window's `talk-here`, Switchboard: Talk Here, the status bar item, the composer's button, and a dock row click (`POST /dock/select`, with `voice.enabled` on) for its work item's session when one of its windows is connected, else the click says to open its window. With the focus outside every window, the target is dropped (`gone`) after `voice.awayMinutes`. A target no longer in `targets` is dropped. The hub mirrors the target from `active`.
- **Terminal windows** (slice 11): the dock posts `POST /dock/focus {sessionId, at}` when a Code Mode session's attach terminal window comes to the front and `{sessionId: null, at}` when the window in front is no such terminal ([Dock](#dock)), `at` the epoch milliseconds of the change; the hub answers 404 for a session it does not have and treats it as none. `VoiceControl.terminalFocused` keeps that session as the focus, which wins over a window's, until the dock reports another or none, or a VS Code window or the web page gains the focus later; a report older than the last change it heeded is ignored, so a late one cannot undo a newer one. From its first report until it is no longer `full` the session stays a target, and a message dictated into its terminal asks for a spoken reply, read from the transcript with no view open. The terminal of a session older than its work item's newest is a target too (voice-design decision 9).
- **What is spoken.** A message sent from the view to the target's session while Speak replies is on is typed with `[spoken]` ([Typing a message](#typing-a-message)). The hub offers a reply when its transcript copy (never a screen copy) is a reply, not an aside or a note, with a primary response, not rewritten or withdrawn, whose `answers` message has `spokenRequested`, in the target's session, while Speak replies is on: `speak` with the current generation and `spokenText` of the primary response, its Markdown marks and link targets dropped. A reply always has a primary response, so only `spokenRequested` and Speak replies decide whether it is heard. Each reply is offered once; a reply rewritten after it was offered is cancelled, and turning Speak replies off (one toggle per machine, on when the hub starts) cancels everything offered with `off`: the reply playing stops at once, `interrupted` where it stopped as Stop speaking leaves it, and the rest are skipped, while alert lines play on. Replay offers a reply again while the voice is in its window, whatever Speak replies says, and is refused while that reply is still offered. When a reply offered or replayed has an open card, a second speak item, `card:<reply ID>#<slug>`, follows its passage in the same turn and reads the card's current question only (`questionSpeech`: its place, topic, text, context and options, then "Or say Other"); the rules tell sessions to keep their questions out of the primary response.
- **Speech** (`Speech` in `packages/voice/src/speech.ts`, from claude-collab's `speech-order.js`): one reply at a time, each to its end; the replies of one turn play in order, and a reply whose turn comes while a reply of a newer turn waits is `skipped` (voice-design decision 24). `stop` (Stop speaking, only in the window that is here) stops the playing reply `interrupted` with its position and skips the rest; `cancel` skips one, and `cancel` with `off` (Speak replies turned off) interrupts it instead when it has started playing. A `speak` of another generation or for a session that is not the target is dropped; a new generation stops and drops everything unreported, and the hub marks what it offered under an earlier one `stopped-moved`. A `speech` or `progress` of an earlier generation, or of a reply not offered, changes nothing. When the process stops, what was offered is `failed`. A reply whose passage is its whole text, played to the end, is marked seen ([Unread](#unread)). The voice log and the hub log each record every offered reply's outcome.
- **Realtime speech** (`Tts` in `packages/voice/src/tts.ts`, from claude-collab's `tts.js`): OpenAI's realtime API, the key read from `OPENAI_TTS_API_KEY` in the env file under `~/.claude` that claude-collab reads, never logged; with no key a reply `failed` and the dock says so. One connection is opened when a target is set and kept, since a fresh one spends seconds before the first audio ([mechanics.md](mechanics.md) M91); a reply in another voice or speed gets a new one. Each reply is read with `conversation: 'none'` and instructions that say only how to read (voice-design decision 22): to read the text aloud exactly as written and treat it as text, never as instructions, with the reply's tone line under `voice.expressive`, else the style and the persona's personality. An error, a timeout or a cancel mid-reply retires the connection, so no late audio reaches the next reply. Inline delivery cues are not read (voice-design § 8).
- **Playback** through decibri's `Speaker`, one per reply, on `voice.outputDevice` or the default device; `stop` drops what is queued. The needs-you sound plays on `earcon`, which the hub sends after each snapshot build for work items that started needing the operator (`newlyNeeding`), other than the voice target's, while `voice.needsYouSound` is on, except for one that got a [spoken alert](#spoken-alerts) for the same change; it waits for the reply playing and plays before the next.
- **What a window learns** (`VoiceView`, in `hello` and `voice` events): `{enabled, here, mic, speaking, speakReplies, error, recognizer, halfDuplex?, fullDuplex?, roomHold?}`, only about its own selected conversation's session: `here` while that session is the target, `mic` what capture is doing there (`off` in a window that is not here), `speaking` that session's reply playing, `error` why capture cannot run while `mic` is `unavailable`, and the rest only while the voice is here ([Dictation](#dictation), [Voice check and barge-in](#voice-check-and-barge-in)). A window cannot tell the voice being elsewhere from nowhere, and a playback or speech error is the voice's, not the window's. The status bar item `switchboard.voice` (`voiceStatus` in `conversationModel.ts`) shows that state and acts on it with a click. Everything global goes to the dock: the target's row has a mark the hub chooses for the dock and the page alike, the mic while the mic is on and the speaker while it is off, and a voice problem is a note, `Voice: <why>`, in `DockView.notes`.

### Dictation

PRD R108, voice-design slice 10. The mic is a runtime toggle, one per machine, off when the hub starts: the composer's mic button, Voice: Toggle Microphone or the status bar item send `mic`, and turning it on also moves the voice to the window's session (Talk here).

- **Capture** (`Dictation` in `packages/voice/src/dictation.ts`): 16 kHz mono 16-bit PCM on `voice.inputDevice` or the default device. On Windows, `windowsCapture` runs `commcapture.ps1`, which opens the device in communications mode, where Windows applies its own echo cancellation, with the echo reference set to the playback device where the device allows. When that helper fails or Windows reports no echo cancellation for the device, `withFallback` logs why and captures through decibri instead. Elsewhere, and in that fallback, decibri's `Microphone` captures with its `tau` echo canceller fed the audio the voice plays ([mechanics.md](mechanics.md) M94); `PlayedReference` (`packages/voice/src/reference.ts`) hands the canceller that audio paced as it plays, since pushed as it was written it ran seconds ahead and overflowed the canceller's reference queue. Capture runs while the mic is on, a session is the target, the here window's composer does not have the focus, no other app records, the mic idle timeout (`voice.micIdleMinutes`) has not run out and recognition can run; otherwise the device is closed. `audio.mic` says which: `off`, `starting`, `listening`, `hearing` (an utterance is open), `typing`, `paused-other-app`, `paused-by-voice` (spoken commands, below), `idle-off` (the idle timeout ran out, or no session is the target) or `unavailable` with `error`; turning the mic on again tries again. While the recogniser is what cannot load, each attempt to listen loads it again, so a model put back needs no restart.
- **Mic on's start** ([mechanics.md](mechanics.md) M122, M129): loading the recogniser for a set of terms takes seconds and blocks the voice process, and was most of the wait from a tap to listening. So the recogniser is loaded ahead of Mic on, whether or not a device has the voice, while nothing plays and no utterance is open: once the voice process has its settings, as after it restarts onto a new build, for no repository's terms when no target is set yet; for the target's terms once the target has settled for a moment; and at once for the target set when a phone takes the voice, while its page opens the microphone; a load ahead that fails keeps no error, since Mic on tries again and says why; each load runs a second of silence through it, since its first decode is the slowest. Mic on loads it, when not loaded yet, while the other-app watcher starts rather than after its first answer. The voice log has one line per start with each step's time (`mic on → listening in … ms: recogniser …, other-app check …, capture open …`), and the hub log one from the `mic` command to the voice process's first state past `starting`. A page posts `mic-timing {steps, outcome}` once its tap's start ends, which the hub logs: each step as milliseconds from the tap (the phone's microphone allowed, its audio, voice socket and worklet when the tap started them, capture connected, Mic on sent, the hub's answer, the voice's confirmation); refused with 400 past 12 steps, a step past 120 s, or an outcome past 200 characters. A paired device's tap starts its audio, voice socket and microphone together; its audio worklet is named by a hash of its content, which the browser keeps for good, and the page fetches it once voice is on, so the tap loads it from the cache rather than over the remote host. A page of another build that asks for its own worklet name gets this build's, uncached.
- **Half-duplex listening** (`Dictation`): each capture stream says whether it cancels the echo (`CaptureStream.halfDuplex`). Windows' communications-mode capture does, as does the phone's ([Remote access](#remote-access), Voice on a phone); decibri's does not, since its canceller removed almost none of the echo ([mechanics.md](mechanics.md) M94), and over Remote Desktop the "Remote Audio" device gets no capture effects, so capture falls back to decibri there. On half-duplex capture the audio is dropped unheard while the voice plays and for `voice.halfDuplexTailMs` after, so words said meanwhile are lost and there is no barge-in; an utterance open when the voice starts playing is cut as when the composer takes the focus. `voice.duplex` decides, separately on this computer (`local`) and over Remote Desktop (`remote`): `half` always pauses, `full` never does, so talking over a reply stops it, and `auto` pauses only on capture that cancels no echo, until the echo check hears none. A changed setting applies to the open capture at once. `audio.halfDuplex` and `audio.fullDuplex` carry the reason, which the mic button and the status bar item show and the voice log records.
- **Echo check** (`EchoCheck` in `echoCheck.ts`, `AutoDuplex` in `duplex.ts`), under `voice.duplex` `auto` on capture that cancels no echo, so that headphones get full duplex: after each stretch of playback the process correlates the capture's level envelope with the played audio's and judges it `echo`, `none` or `unclear` ([mechanics.md](mechanics.md) M98). Capture starts half-duplex and turns full duplex after enough `none` in a row (one when the playback device on this computer is headphones or a headset; the hint is not used over Remote Desktop, whose "Remote Audio" says nothing of the client's headphones); `unclear` changes nothing; `echo` makes it half-duplex at once. Full duplex goes on measuring and turns half-duplex at once on `echo` or when the words held over a reply are the reply's own (`novelWords`), as when the headphones come off; those words are then dropped. A change of the mic, the capture's reason, Remote Desktop, or the playback or capture device starts the check over, half-duplex. The voice log records each measurement and each start over.
- **Other apps recording** (`watchMicUse` in `micUse.ts`), while the mic is on: a watcher, Core Audio session notifications on Windows (`micuse.ps1`) and `pactl` on Linux, reports whether an app other than the voice process and its children records; on Windows it also reports the playback and capture devices and whether this is a Remote Desktop session, for the echo check. Capture starts only after its first answer, and a watcher that cannot run counts as no other app. When another app starts recording, the utterance being heard is dropped (no automatic send and no `[partial]`), its pieces already in the draft stay, and listening resumes when that app stops.
- **Leaving the computer** (`watchLock` in `lockWatch.ts`, `VoiceService`): when the session locks, the computer goes to sleep, or the session disconnects, the process turns the mic off with any enrolment, stops speech as Stop speaking does, logs why and sends `mic-off {reason}`, on which the hub sets its mic off. The hub sends its mic to a process it connects to as `mic {on: true, restore: true}`, which the process answers with `mic-off` while it last turned the mic off on its own and the operator has not set the mic since, so a lock no hub heard still keeps the mic off. While any reason holds, a reply offered is `skipped`, a needs-you sound dropped, `mic {on: true}` answered with `mic-off` again and an enrolment start fails. When every reason ends, speech plays again and the mic stays off until the operator turns it on. The watchers are `lockwatch.ps1` (session notifications and power broadcasts) on Windows and logind through `gdbus` on Linux; a watcher that cannot run is logged, and the mic then stays on through a lock.
- **Recognition** (`Transcriber` and `sherpaRecognizer` in `asr.ts`, from claude-collab's `asr-local.js`, and `SherpaRuntime` in `sherpa.ts`): a streaming speech model through sherpa-onnx with hotwords, on the machine: on the GPU when it can run there, else on the CPU, each with the model variant faster on it. The GPU needs Windows, the NVIDIA driver and a CUDA build of sherpa-onnx with its runtime under `<home>/voice/models/`; the extension does not ship these, which, like the models, are the operator's data. The build is chosen once per process, and recognition and the voice check both use it, since Windows binds a second sherpa-onnx addon to whichever `onnxruntime.dll` loaded first. Because sherpa-onnx falls back to the CPU silently when CUDA cannot load, `gpucheck.js` first runs the CUDA build in a child process, and only a check that passes loads it; a GPU recogniser that fails to load is replaced by the CPU's. `voice.log` says once where recognition runs and why, and `audio.recognizer` carries it. One stream runs for a whole utterance; words that stopped growing settle into a piece. The model loads when capture first starts and again when the target's term list changes, never mid-utterance ([mechanics.md](mechanics.md) M97).
- **Hotwords and the glossary** (`terms.ts`, `glossary.ts`, `hotwords.ts`, `vocabulary.ts`, from claude-collab): the fixed terms are the operator's (`<home>/voice/terms/user.txt`) and the target's repository's (`<home>/voice/terms/repos/<owner>/<repo>.txt`, the repository read from its folder's `origin` remote and sent in `targets`), then the glossary's learnt terms. A reply's heard tag (`splitHeard`, read from transcript copies only, once per reply and tag) goes to the voice as `heard`; the glossary (`<home>/voice/glossary.json`, one per home) promotes a meant term after the second identical tag, only for a name or technical term, keeping a bounded number of learnt terms, the most recently used first. The spoken commands' phrases are always hotwords.
- **Turn detection** (`turn.ts`, from claude-collab's `wrapper.js` and `turn-text.js`): an utterance ends after `voice.endPauseMs` with no new words, longer after a dangling last word. A brief quiet asks LiveKit's turn model, with the session's last reply as context (`context`), whether the words so far are a finished turn, and the more likely the end the sooner it comes; a final `.`, `?` or `!` ends it soon too. The turn model runs in its own process (`turn.js`), because onnxruntime cannot load beside sherpa-onnx's runtime. Without the model, the pause alone decides.
- **Spoken commands** (`Dictation`): "stop listening" or "pause listening", and "start listening" or "resume listening" (`SPOKEN_COMMANDS`). A command counts only as a whole utterance that turn detection ended and that passed the voice check; its first pieces are held unreported while they may be a command and released as dictation otherwise. A stop pauses dictation (`paused-by-voice`): capture and recognition keep running but nothing is reported and there is no barge-in, and only a resume phrase whose voice match clears `voice.matchThreshold` itself, without the short-piece allowance, resumes it. Turning the mic on also resumes. A command goes to no session: it is logged in `voice.log`, and the hub logs `command` in its log and the fragments log. Without an enrolment anyone's command counts.
- **Reports**: `words {gen, utteranceId, sessionId, text}` as the live words change, empty once they settle; `piece {gen, utteranceId, sessionId, pieceId, text, score, f0, dropped}` with the voice check's results ([Voice check and barge-in](#voice-check-and-barge-in)); `utterance {gen, utteranceId, sessionId, text, final, interrupted, timing?}`, `text` its kept pieces, `interrupted` the reply a barge-in spoke over or null, and `final` true when turn detection ended it, false when it was cut off (the composer took the focus, the mic went off, the voice moved, the device failed or another app started recording), so the hub sends nothing. `timing` says when its words last changed, when and how the end was decided and when it was sent, for the message's timing line ([Typing a message](#typing-a-message)).
- **The focus rule, in the hub** (`VoiceControl`): the hub keeps one composer per window and conversation (session): its focus and draft from `composer`, which the page sends as they change, and the dictation in it; the page joins a draft the hub changes while the box has the focus to the end of the box's text, never replacing the operator's edits. Dictation goes to the target's terminal window while it is in front; else to the window the voice is in: the focused window showing the target, else the one that last moved the voice there, else any showing it; else, with no window showing the target, to its terminal when the voice followed it there. In a terminal, which has no composer, a final utterance types the words heard since the last one as a `[voice]` message through `ConversationService.dictate`, by the same input transaction as a message from the view, so the guard against typing over the operator's keys holds it; an utterance cut off, or heard when the voice process stops, is dropped, and a refusal goes only to the logs. In a window, each piece joins that window's draft (`draft {text, sessionId}`); live words, display only, go to every window and page showing the session, and to none while dictation types into its terminal. A final utterance whose window's composer does not have the focus sends the whole draft once as a `[voice]` message and empties it, unless the whole draft is a card command while the session has an open card (`cardUtterance`: a letter with the recogniser's homophones, an ordinal, "the recommended one", "other, …", "back", "next", "repeat" or "send"): it then changes that card's draft instead, and the hub says what it did and reads the next question; once every question of the card's batch has an answer, it sends them as a `[spoken] [voice] [answers]` message; one whose composer has the focus, or that was cut off, sends nothing and leaves the draft. While an utterance is open, its session is in a turn and the composer is not focused, the draft goes as a `[voice] [partial]` message at intervals, keeping the last settled piece, so the message that ends the utterance always carries words; no part goes while another app records. A message the voice typed that is then not sent goes back to the draft of every window showing its session (`giveBack`). Turning `voice.enabled` off turns the mic off. `dictate` refuses a session the window no longer shows, one that is not `full`, a message over the message length limit or a holder that cannot type, storing nothing. The composer's own `send` of a draft that holds dictation types it as a `[voice]` message with its pieces, however much the operator edited it; a slash command never.
- **The composer** (`renderMicButton` in `packages/conversation/src/voiceControls.ts`): one mic button beside Send, whose glyph and tooltip carry the mic's state, including where recognition runs and why listening pauses during replies; while the mic is on, in any state, a click turns it off, and turning it on again retries capture; a paused mic listens again on a click. From a Mic on tap until `audio.mic` confirms it (`MicStart`), the button shows starting, a turning ring around the mic, which turns under reduced motion too, as every spinner does, so the wait for the hub, the phone's microphone and the voice process to open capture is visible; a tap that fails, as when the phone refuses the microphone or the hub refuses `mic`, shows why on the button until the next tap, as does a start not confirmed within 30 seconds. A `draft` sets the box's text, or the draft of its own conversation, and one that comes while a message is being sent takes the box once the hub answered. Live words show dimmed right after the box's text and settle into it in place. Enter while the voice is here with the mic on moves the focus from the box to the timeline, so dictation resumes. A dictated message is marked so under its bubble, with its pieces in the tooltip, and when it spoke over a reply ([Voice check and barge-in](#voice-check-and-barge-in)).
- **Fragments log**: `<home>/voice/fragments-<local date>.jsonl`, one JSON line per piece `heard` or `dropped`, per message `submitted`, `refused`, `held` (a room hold kept its turn), `sent` or `not-sent`, and per spoken `command`.

### Voice check and barge-in

PRD R110, voice-design slice 14, from claude-collab's `voiceprint.js` and `barge.js`.

- **Voiceprint** (`Voiceprint` in `packages/voice/src/voiceprint.ts`): a speaker embedding model, `<home>/voice/models/wespeaker_en_voxceleb_resnet34_LM.onnx`, through sherpa-onnx on the CPU in the build recognition uses ([Dictation](#dictation)). Without it no piece is scored, only the pitch rule of an earlier enrolment applies, and enrolment fails with why. The enrolled print, `<home>/voice/voiceprint.json`, is the normalised mean embedding of a recording, with the recording's pitch range and speaking level, kept only on the machine. A print claude-collab enrolled reads as it is, with no level.
- **Enrolment.** The dock's Voice page posts `/config/voice-enroll {action: 'start' | 'status' | 'cancel'}`; the hub starts the voice process for it if no window wants it and sends `enroll`. The process cuts any utterance short, records a minute of capture that goes to no session, then saves the print, reporting `enrollment {state: 'recording' | 'enrolled' | 'failed' | 'cancelled', error}`; a print that cannot be saved fails it and the earlier print stays. The route answers `{enrollment: {state, endsAt, error, enrolledAt}}`, `state` also `idle` or `starting`, and refuses a start while `voice.enabled` is off (409); turning voice off cancels a recording, and a voice process that stops or cannot start fails it.
- **The voice check**, on every piece of dictation: the piece's recent audio is dropped when its match with the print is under `voice.matchThreshold`, with an allowance for a piece of one or two words, or when too few of its voiced frames are low enough for the enrolled voice by `voice.pitchLowFactor` and `voice.pitchMinLowShare` (voice-design decision 27); audio too short to judge passes. A dropped piece joins neither the utterance nor the draft and is logged `dropped`; an end the turn model judged on words that included it is judged again without them, so someone else's "go ahead" does not end the operator's turn. An end the turn model judged early waits for the check of its last words. Without an enrolment every piece passes.
- **Holding a reply for the operator** (`Speech`, `Dictation.replyHold`): a reply about to start waits while words are being recognised or an utterance holds words that passed the voice check, and until 1.5 s after the operator's last word (`REPLY_HOLD_MS`), so it never starts over the operator mid-thought, as when a short pause ended an utterance and the operator goes on ([mechanics.md](mechanics.md) M127); the voice log says once that it waits. A piece the voice check drops holds nothing, nor does anything heard while paused by voice, and a reply waits at most 30 s (`HOLD_MAX_MS`) on words not yet known to be the operator's, so speech that never stops, as a television's, cannot hold it for good; on the operator's checked words it waits however long they go on. Each offer of a reply waits afresh, so a replay is held as the first offer was. A reply of a newer turn offered meanwhile skips it, as when it waited behind another reply. An alert line does not wait.
- **Barge-in** (`BargeIn` in `barge.ts`), only on full-duplex capture, since half-duplex capture hears nothing while a reply plays ([Dictation](#dictation)): while a reply plays and no utterance is open, words heard are held back as its possible echo, with no live words, pieces or turn checks. Each recent window of loud audio is checked against the operator's print and against the print of the voice the reply is spoken in; it passes when it matches the operator by `voice.matchThreshold`, beats the reply voice by a margin and is pitched as the operator is, with a higher bar before that reply voice's print is learnt. A strong pass fires at once, an ordinary one when confirmed by the next; without an enrolment or the model, words heard that are not the reply's echo fire it. Firing stops the reply `interrupted` (`Speech.interrupt`), skips the replies waiting and any later reply of the same turn, and opens an utterance, starting recognition again from just before the window, that names the reply with what of its passage was played (`said`) and not (`rest`). Words heard just after a reply ends stay held and checked briefly, then are dropped as its echo. The reply voices' prints, `<home>/voice/tts-voiceprints.json`, are learnt from the start of each reply's audio.
- **The room hold** (`voice.roomHold`, on by default): a piece the voice check drops is someone else in the room, unless it may be a reply's echo (a reply playing or just stopped, or a match with a learnt reply voice's print by `voice.matchThreshold`). It starts or restarts a hold of `voice.roomHoldSeconds`, logged in `voice.log` and carried in `audio.roomHold` as its end. In the hub, a spoken turn whose end comes during a hold is not sent: its words stay in the window's draft, its pieces are logged `held`, and the window gets `held {sessionId, note}`, which the composer shows as it shows a refusal, and no `[partial]` goes. A held draft stays held after the hold ends, so a later turn joins it unsent, until Enter sends it or the operator empties the box. A held turn for a session's terminal, which has no composer, is dropped and logged. Turning `voice.roomHold` off ends a hold.
- **The interruption note.** An `utterance` with `interrupted {replyId, said, rest}` leaves it with the window's draft, so the message that sends that dictation stores it as `interrupted` and is typed with a note after its tags (`interruptNote` in the conversation library) that tells Claude how much of its reply was heard: none of it, all but a short unheard end (quoted), or up to a point, quoting the last words heard and the first unheard; none when it was all heard. A `[partial]` part never carries it, an emptied draft drops it, and `stripMessageTags` removes a note only after Switchboard's tags. The dictation rules tell Claude what the notes mean: not to repeat what was heard, and to raise the unspoken part only if it still matters.

### Spoken alerts

PRD R112, voice-design slice 12. With `voice.enabled` and `voice.spokenAlerts` on, the voice calls the operator when a `full` session that is not the voice target, nor the focused conversation, needs them.

- **In the voice process** (`Alerts` in `packages/voice/src/alerts.ts`): an `alert` waits while anything plays or waits to play, for a short gap after the voice last played, while the operator speaks, during a room hold, while another app records and during an enrolment; alerts play one at a time, in order, and a newer alert for a session replaces its earlier one unless that one is being read. Its line names the operator (`voice.operatorName`), the session's persona, the cause and the work item's title (`alertLine`, PRD R112). It plays in the speech queue as an alert line, in the alert's voice, style and personality: it is not reported to the hub, a move of the voice target does not stop it, words heard over it are held as its possible echo as over a reply, so a line never answers itself, and Stop speaking, a lock or sleep stop it. When an answer can be heard (`Dictation.answerable`: the mic on and listening normally, the composer not focused, no enrolment) dictation listens from the line's start even with no target or after the idle timeout, and the next utterance is the answer, which goes to no session. The window closes `voice.alertAnswerSeconds` after the line, later while an answer is still being spoken, and capture then returns to what it was. A refusal said alone ("no", "not now", "later" and the like, `declines`) drops the alert; any other answer moves the voice target to the session with Talk here when it can be a target and reads the alert's `detail`. With nothing heard, or no answer possible, it ends unanswered after its line. It ends cancelled when its cause is resolved (`alert-cancel`), an answer is cut off, its session becomes the voice target or the focused conversation before it is read, the mic stops listening during the window, its line is stopped, spoken alerts are turned off, or the operator leaves the computer, when every waiting alert is dropped too. Each end is `alert-done {alertId, sessionId, outcome}`, `outcome` `announced`, `unanswered`, `declined` or `cancelled`, logged in `voice.log` with the line and the answer.
- **In the hub** (`VoiceControl.sessionsChanged`, after each snapshot build): each live Code Mode session whose conversation is `full` has a kind (`alertKind`): `running`, `idle`, `question` (waiting on a question, or idle with a question open), `permission` or `other`. A change from `running` to `idle` is `turn-finished`, and a change to `question` or `permission` is that cause; the first sight of a session, as after a hub restart, alerts nothing. While `voice.enabled`, `voice.spokenAlerts` and the cause's `voice.alertOn` key are on, a voice process is connected, and the session is neither the voice target nor the focused conversation (a session terminal window in front, else the focused window's selected conversation), the hub sends `alert {alertId, sessionId, cause, title, persona, detail, voice, style, personality}` after a short delay, so the transcript has given the turn's last reply, checking all of it again then. The `detail` (`alertDetail`) says, for a permission prompt or a question menu, that the session waits in its terminal, else gives the latest reply's primary response, else its text, else the latest status, as speech without Markdown and cut short at a sentence, followed, while questions are open, by how many and the current question. Another change of the session's kind, or its end, drops the alert, sending `alert-cancel` once it was sent; `alert-done` is logged in the hub log. A work item alerted gets no needs-you sound for the same change.

### Personas

PRD R106, voice-design slice 13. A persona is a name, a personality and a voice with its speaking style, in the roster `voice.personas` ([Settings](#settings)), empty by default; with no personas every session speaks with `voice.voice` and `voice.style` and its prompt has no tone section. Personas are part of voice: with `voice.enabled` off no session shows or speaks with one, no prompt gets a tone section, and a pin is refused.

- **Resolved at the start** (`resolvePersona` in `packages/core/src/persona.ts`): when the flow starts a Code Mode or Codex app-server session it takes its work item's playbook's persona (`voice.playbookPersonas`), else a persona of the roster no other live session has, else the one the fewest have, earlier in the roster first, and stores it as `Session.personaId`. A playbook's persona may be shared on purpose; the pool shares one only when the roster runs out. The persona is kept for the session's life, across resume and hub restarts; a session that started with none, such as one from before the roster, keeps none until pinned. Background sessions have none.
- **Pin.** The flow event `persona {sessionId, personaId | null}`, an operator event in the activity log, pins a roster persona to a session (`personaPinned`), from the Conversation view's header (`POST /v1/conversation/persona`), the web page's persona dialog (the `persona` page command) or a dock row's Persona menu (`/action`); null clears the pin and resolves the persona again as a start would. The flow refuses a pin while `voice.enabled` is off, and the window's command answers a repeated `opId` with its first result without pinning again. A pin outranks the playbook's persona.
- **Speech.** `VoiceControl` reads the session's persona at each offer, so a pin changes the voice from the next spoken reply: `speak` carries its `voice`, `style` and `personality` ([Voice](#voice)).
- **Tone section** (`toneSection`): a "## Persona" section naming the persona and its personality, saying that it sets only the tone, never how the work is done, what is decided, checked or reported, or the length and format of replies, and that the last Persona section counts. None for a persona with no personality; a resume and the contract hook give a session that has a persona whose section is none (no personality, gone from the roster, or voice off) `PERSONA_RESET` in its place, since the launch's prompt may still carry an earlier section. It comes after the conversation rules at the start, in the resume's appended prompt, and in the contract hook's text on resume and compaction, read from the settings each time. Each delivery stores its `toneVersion`, a hash of the section, as `personaVersion`, so a live session whose stored version differs from its persona's current section shows `tonePending` until its next resume or compaction. A compaction keeps the launch's appended prompt beside the hook's text, so a session can see two Persona sections; it follows the last.
- **Shown.** `SessionView.persona` and `SessionView.canPin` drive the Conversation view header's persona button ([Conversation view](#conversation-view)) and, on the web page, the persona row of the header's view options menu, which always names the persona the session speaks with, pinned or resolved at its start (Persona: Nova), or Persona: None, and opens the persona dialog ([Web page](#web-page)): a dialog as Settings is, the whole screen on a phone, listing each persona with its voice, style and personality and the current one marked, with Clear pin while one is pinned; a pick pins the persona at once and closes the dialog. A paired device may pin too, since `personas` and `persona` are not local-only page commands. A Code Mode row's controls gain a `Persona` group with `voice.enabled` on and a roster: each persona, the session's checked and marked when pinned, then Clear pin while one is; the dock draws it as a submenu ([Dock](#dock)). [Spoken alerts](#spoken-alerts) name the persona.

### Web page

PRD R109: a second front end, a web page the hub serves, for working away from VS Code. It is its own code (`packages/web`), not the Conversation view adapted; it shares with the view the [Conversation API](#conversation-api) and the browser-safe modules both draw from: the question cards' reading and renderer, the provider marks and the voice controls (`packages/conversation`), and the marks, session icons and snooze choices (`packages/core`). The page sees only the work item it selected, as a window sees only its own ([Window scope](#window-scope)).

- **Files.** `packages/web`'s build carries the page's files as strings (`PAGE_ASSETS` in `dist/index.js`) inside the hub bundle, so each hub serves the page that matches its build. The page draws from a copy of VS Code's Dark Modern and Light Modern colours as the `--vscode-*` variables a webview gets (`theme.css`) and follows the operating system's light or dark setting as it changes, with no setting of its own (the operator's decision: light and dark only, no high contrast). Text and marks keep a 4.5:1 contrast in both copies, where the light copy takes VS Code's Light High Contrast values for the colours Light Modern leaves below it (`test/theme.test.ts`). Row stripes, the hidden list's sliver and the Returned pill's outline take status colours of their own, the same on the dock: warning amber, error red and the operator's turn blue, each 3:1 or more on every row background, with warning clearly lighter than error so the two stay apart with protanopia or deuteranopia; text in the warning or error colour keeps VS Code's text colours. Mermaid's build, too large to carry in the bundle, is installed under the Switchboard home with the other carried files ([Hub lifecycle](#hub-lifecycle)); without it diagrams show as their code. Diagrams are drawn in Mermaid's light or dark theme to match the scheme and drawn again when it changes, since Mermaid bakes the colours into each drawing.
- **Port.** An installed page is tied to one origin, so the hub also serves the page's routes, and nothing else, on the fixed port `web.port` of `127.0.0.1` ([Settings](#settings)), read at hub start; the hub's own port serves them too. A taken port is tried again briefly, since a hub being replaced may still hold it, and then the hub logs why and serves the page on its own port only, which changes at each start.
- **Credential.** `POST /page/link` (hub token) answers `{url}`, a link holding a one-time token that works once within two minutes (`PageAccess` in `packages/hub/src/page.ts`), on the page's fixed port, or on the hub's port with `notice` saying why when the page is not on its fixed port. Switchboard: Open Web Page in VS Code and `hub.js web` give it. `GET /page?t=` uses the token up and answers 303 to `/page/` with the cookie `sb_page` (`HttpOnly`, `SameSite=Strict`), and 403 for a used, expired or unknown token. Tokens live in the hub's memory. Each cookie is a remembered sign-in for one device, kept in the store's `pageSessions` table only as its SHA-256 with its device's name, so it outlives a hub restart; a sign-in works only from where it was made, this computer or the remote host and login a device paired through ([Remote access](#remote-access)). A sign-in unused for 30 days is refused and deleted, and use renews it. Signing in again from a browser deletes that browser's old sign-in and ends the page streams opened with it, and the hub keeps a bounded number of sign-ins, dropping the one used longest ago. `POST /page/revoke` (hub token; `hub.js web revoke`) deletes every sign-in, ends the open pages' streams and answers `{revoked}`. `/page/` without a valid cookie answers 401 with a page saying how to sign in. Cookies are not scoped by port, so a browser also sends `sb_page` to any other server on `127.0.0.1`, which another local user's process could run; the hub token, by contrast, is readable only by the operator's account, so the page never holds the hub token.
- **Installing.** The page is a web app a Chromium browser installs in its own window, which `127.0.0.1` allows over plain HTTP since it counts as a secure context; its manifest's `id`, `start_url` and `scope` are `/page/`. Its service worker (`packages/web/src/sw.ts`) keeps only the offline page, its script, the icons and the manifest, and answers only page loads under `/page/` and those files: a page load that cannot reach the hub gets the offline page, "Switchboard is not running", which offers to start the hub through the `switchboard:` link ([Hub lifecycle](#hub-lifecycle)) and reloads once the hub answers. The page's own files, the API and the event stream are never cached, so a page is always the one its hub serves. The manifest, the worker, the offline files, the icons and `/page/ping`, which answers `{build}`, the hub's build, need no cookie, because a browser fetches a manifest and its icons without one; they hold nothing private.
- **iPhone and iPad.** Added to the Home Screen from Safari, the page runs standalone from the manifest under the opaque default status bar (`black-translucent` gets a system blur over the page's top on iOS 26.1 and later, and WebKit treats the key as deprecated). iOS draws its scroll edge blur over the page's top unless WebKit finds a fixed or sticky box at the page's top edge, at least 90% of the width, and paints the status bar in its colour instead. Each view's own top bar is that box, with no room given up above it: the header, the list header, History's bar and full-screen Settings' bar are sticky at the top of a page that never scrolls and opaque in the bars' colour. An open sheet's dimmed backdrop covers the whole screen, for which WebKit keeps the colour it had. In landscape an iPhone shows no status bar, and WebKit paints none. At the bottom the page uses the whole screen, as a native app does, and keeps its last item clear of the home indicator. A text field never makes iOS zoom the page when it takes the focus, and iOS never enlarges a long block's text in landscape, so every text keeps its set size in either orientation. The Home Screen icon is opaque, since iOS fills a transparent icon with black, and needs no cookie, as the other icons; iOS reads these only when the page is added, so an installed copy takes a change to them only once it is removed and added again.
- **Sending.** A send, from the composer or a question card, brings the conversation to its end wherever the operator had scrolled, and the conversation follows its end from there, with the sent message, the turn row and the reply, until the operator scrolls away.
- **Drawing.** A burst of stream events, such as a long transcript read as new, is drawn together rather than once per event, so it cannot hold up the browser; what reads the drawn page, such as the Chrome pane's place, waits for that draw.
- **Width.** The page never scrolls or bounces as a whole; its list and panes scroll only up and down, and a reply's long links and words wrap while its code blocks and tables scroll inside their own box, so nothing makes the page wider than the screen. Nothing outside the scrollers moves either: no pane, popup or dialog that scrolls passes a drag on to the page, at its end or with nothing to scroll, and a one-finger pan that starts outside every scroller does nothing while a pinch still zooms, because WebKit on iOS still pans a page with `overflow: hidden` while its visual viewport is shorter than its layout viewport. A vertical pan that starts on anything inside a pane, such as a table or code block that scrolls sideways, a nested scroller or a title cut short, scrolls that pane, so only the panes, popups and dialogs keep a drag to themselves; Chrome gives a pan to the innermost box that keeps its drags even when that box cannot scroll that way (M125).
- **Reconnecting.** A page whose hub stops keeps its stream's browser reconnect: a hub started again on the same port, with the sign-in kept, gives it a new page key and `hello`, and the page selects its work item again from its address. After a stream error the page asks `/page/ping` until the hub answers, then reloads when the hub's build differs from the one that served it, so a page never runs against a hub of another build, or when the browser gave up reconnecting, so a revoked page reloads into the signed-out page rather than keep showing its conversation (`reconnector` in `packages/web/src/reconnect.ts`). A reload keeps the drafts, which live in local storage.
- **Requests.** Every other page route needs the cookie, and every page route a `Host` of `127.0.0.1:<port>` or `localhost:<port>`, `<port>` being the one the request came in on, so a name that rebinds to this machine is refused (403), unless it comes through `tailscale serve` from a remote host ([Remote access](#remote-access)); `GET /` answers 303 to `/page/`. The page's files go out with `X-Frame-Options: DENY` and a CSP of their own that allows only the page's own scripts, styles, fonts, frames and connections, no objects or forms, and no framing. A page posts a conversation command without the hub token, with its cookie, an `Origin` equal to its own and a page key as `window`; anything else is 403. Only the commands in `PAGE_COMMANDS` (`packages/hub/src/server.ts`) are taken, those in `LOCAL_PAGE_COMMANDS` only from this computer's page, and never `new-conversation`: a page hosts no conversation.
- **Page key.** `GET /v1/conversation/events?page=1` (cookie) registers a page (`WindowScopes.openPage`) and opens its conversation stream; its `hello` carries `key`, the page key, the list's `groups`, and `scope: null` until the page selects. The key dies with the stream, as a window's does. A page's `select` takes any work item the store knows, where a window's takes only one of its conversations; it binds the page to that work item, raises its `scopeGen` and sends `scope` and a fresh `hello`, and from then on the [window scope rule](#window-scope) holds unchanged: the scope is `{kind: 'page', …}` with the work item's title, its window's first folder (else its ticket's `repoRoot`) and its current session, and every other work item's session, reply, status or artifact is refused. A page's binding is never stored; a reload selects again from the address's `#w=<work item ID>`. A selected work item that is deleted unbinds the page, raising `scopeGen`. A `show {workItemId, marker}` event, a dock click with `dock.openIn: web` ([Dock](#dock)), selects that work item as a click on its row does and adds ` [sb-show <marker>]` to the page's title for a moment, by which the dock finds the window. A `needs` event makes the page announce work items that started needing the operator ([Dock](#dock), Needs you).
- **List.** `GET /v1/page/list` and the stream's `list {groups}` events, sent when it changes, carry the dock's groups and rows built from the dock view (`pageList` and `pageRow` in `page.ts`), so the page and the dock group, order and mark a work item alike; [parity.md](parity.md) owns which list and row behaviours the page matches. Pool tickets' rows in Unstarted and Snoozed have no conversation, so they carry their `ticketId` and no `workItemId`. Each row carries the controls the page offers ([Row actions](#web-page)), what it opens, and its search text. Each group's open or closed choice is kept per browser in local storage, as the dock keeps it in `dock.json`. Hosted conversations sit in the group and place the dock gives them, with their host's name. A page's `conversations`, its header's dropdown, are its selected work item's host group (`pageGroups`), which keeps the selected work item when it is done, as a window keeps a selected conversation.
- **Settings.** PRD R54: Open Settings shows the dock's [Settings window](#settings-window) as a dialog over the page (`packages/web/src/settings.tsx`), the whole screen on a phone. Its state, fields, pages, navigation and bar are the dock's, ported to `settingsModel.ts` with the dock's labels, help, defaults, choices and error placement, so a change to one side's Settings makes the same change to the other ([parity.md § Settings](parity.md#settings)); it has every page of the dock's window but the dock's own Theme. ### Remote access

PRD R115: the [web page](#web-page) is reachable from the operator's phone or another of their devices through `tailscale serve`, which takes HTTPS on this machine's Tailscale name, for the tailnet only, and proxies it to the page's fixed port (`web.port`); `tailscale funnel` is never used. The hub still listens on `127.0.0.1` only and serves nothing to the network itself.

- **Hosts and logins.** Remote access is on only with at least one allowed host (`web.remoteHosts`) and one allowed Tailscale login (`web.remoteLogins`); with `web.tailscale` on, the hub adds this machine's Tailscale name and its owner's login from `tailscale status --json` while Tailscale is running (`packages/hub/src/tailscale.ts`). The hub reads these at start and again whenever one of the keys changes, without a restart. A change ends the open streams of every remote device whose host or login is no longer allowed and refuses its later requests, but keeps its sign-in, so allowing it again lets it back in without pairing.
- **Which requests.** The hub classifies every page request before any route (`pageOrigin` in `packages/hub/src/page.ts`). A peer other than the loopback is refused. A request without any header that only a proxy adds is this computer's own and must name `127.0.0.1:<port>` or `localhost:<port>`, against DNS rebinding. A request with any proxy header is never this computer's own: it is a remote request only when its `Host` is an allowed host, it arrived as HTTPS, it is not a Funnel request, and its `Tailscale-User-Login` is an allowed login; anything else is refused with 403 and the reason. This relies on `tailscale serve` setting the `Tailscale-User-*` headers from the connecting device's owner, removing any a client sent, and sending none for a tagged device, a Funnel request or this machine. A remote request's `Origin` must be its own HTTPS origin, and its responses carry HSTS.
- **Pairing.** A remote device signs in only by pairing, which only this computer starts. A pairing gives a one-time link and a short code for the first remote host, both short-lived; using either uses up both, and too many wrong codes drop every outstanding pairing. A pairing token works only through its remote host and a local token only on this computer; a token tried in the wrong place is used up. A remote host shows a device that is not signed in a page where it types the code. A successful pairing stores a sign-in bound to the device's host and login: it is refused through any other host or login and on this computer, as this computer's own sign-ins are refused through a remote host. Pairing tokens, codes and failed-code counts live in the hub's memory and end with it.
- **Devices.** This computer's page, the hub token's routes, and `hub.js web devices` and `hub.js web revoke [<id>]` list and revoke sign-ins; a sign-in's ID tells nothing of its cookie. Revoking a sign-in ends its open streams. The commands in `LOCAL_PAGE_COMMANDS` (`packages/hub/src/server.ts`) are refused with 403 from a remote device, so a paired device cannot pair or sign out devices, allow voice, drive the Chrome pane, open a link with this computer's default browser (`row-open`), restart the terminal holder, or read, change or enrol anything in Settings, Expand replies included (the operator's decision: Settings stay on the computer), and its page leaves those controls out. The [local file routes](#web-page) give a remote device only files in its session's working folder and its work item's worktree and repository root. Everything else the page does works from a paired device, and the browser extension's routes and download work with its sign-in ([Browser extension](#browser-extension)).
- **Voice on a phone** (PRD R119; [mechanics.md](mechanics.md) M111). Voice is off on every paired device until this computer allows it for that sign-in, so signing the device out or pairing it again forgets the permission; this computer's own sign-in has no voice to allow. The phone's page carries voice over the **voice socket**, a WebSocket on the page's origin at `/v1/voice/socket` (`packages/hub/src/voiceSocket.ts`). The upgrade is checked as a page command is and further: a valid sign-in for that host and login, a matching `Origin`, a page key held by the same sign-in's open page stream, a remote device, `voice.enabled`, and voice allowed on the device. Each refusal is an HTTP answer with its reason, never a socket, and `page-voice-state` tells a page why it may not, because a refused upgrade gives a browser no reason. The socket carries JSON messages and binary audio frames; the hub closes it for protocol violations, rate or queue overruns and silence, and every message re-checks the device's sign-in, host, login and voice permission. One device's page holds the voice at a time: a newer socket takes it and closes the older. The hub closes the socket with the reason when the device loses permission, its sign-in is revoked or replaced, remote access no longer allows it, voice turns off, the page stream that opened it ends (so a reload needs a new tap), or the hub stops; a restart onto a new build closes it with its own code instead (Across a hub restart, below).
- **Speech on the phone** (PRD R119). A socket's `hello` moves the voice to the phone and to the page's selected conversation. While the phone has the voice, the voice process (`packages/voice/src/phone.ts`) sends each playback, alert line and needs-you sound to the phone through the hub instead of this computer's speakers, never more than a short lead ahead of what the phone reports its output took, so Stop, a move or a cancel takes effect quickly. The lead counts from what the output took, not from what was heard after the output's latency, because a Bluetooth output's latency can be longer than the lead, which would then never let more audio go. A playback's position, interruption point, what was said and its end count from the phone's reports of what was heard, never from what was sent. A phone that reports no progress while a playback waits, for longer than the page waits for its audio to resume, fails every phone playback and loses the voice. Because iOS lets audio start only in a tap, the tap that asks for the voice creates and resumes the page's audio context.
  - **While the phone has it** only the phone page's own focus is the voice's focus, never a VS Code window, a terminal or the dock, and another paired page can neither take the voice nor bring it back to this computer.
  - **Route changes**: iOS briefly interrupts or suspends the page's audio when its route changes, as Bluetooth earbuds do between playback and play-and-record. The page asks its audio to resume until it runs again, and the playback goes on from where it stopped, keeping the voice and the mic; only audio that stays stopped loses the phone. Mic on's tap sets the audio session to play and record before the audio starts, so the session's mode does not change under a playback while the mic is on; the phone's capture stays open while the voice plays.
  - **Losing the phone**: the socket closing, the page hidden for a few seconds, or its audio interrupted or suspended for a few seconds (a call, Siri) moves the voice to no device: playback stops, the mic goes off, nothing plays on this computer's speakers, and the windows' voice controls show it (the phone's page says why, except for a hidden page, whose loss needs no word), until a tap on the phone, or on this computer Talk here, the mic, Voice on the computer or a message typed to the voice target's session in a window or page there, takes the voice back. Voice off or Mic off on the phone, even one that cuts a starting Mic on short, shows no message on the phone. The dock and the page's list add an untoned note only while the phone was **lost** (`VoiceControl.phoneLost`), never for voice off by the operator's choice: the page sends `leave` before it closes the socket for Voice off or a hidden page's loss and when it unloads, and `visibility {hidden}` on each change, and the hub counts a close as a loss unless the page said `leave`, was hidden, or the hub closed the socket with its refusal code (a sign-out, a forbidden device, remote access dropping it, voice turned off). The page stream ending closes the socket as going away (1001), not refused, since that may be a dropped connection. A stall the voice process reports, a resume that does not come in time and a voice process that greets a fresh hub with another device are losses; a handover carries whether the voice was lost. A new voice process is told the current device. A hub that starts anew, not by a restart's handover, keeps the voice process's device when it is not this computer's, as none, because the phone's socket closed with the hub that stopped, so it never moves the voice to this computer's speakers either. Once the hub has chosen the device itself, as by Talk here before the process's greeting comes, the process is told the hub's device instead.
  - **Across a hub restart** onto a new build ([Hub lifecycle](#hub-lifecycle)): the voice process, which outlives the hub, keeps its device, target and mic, and the hub that takes over starts from the state the old hub handed over. The old hub closes the voice socket with the restart code; the phone's page keeps its audio context and microphone, and once its stream reconnects with a new page key it opens the voice socket again with `hello {resume: true}`, with no tap. The new hub accepts that only from the paired device whose sign-in held the voice, still allowed, within 30 seconds (`PHONE_RESUME_MS`); it refuses any other resume, and a tap on any allowed device takes the voice as usual. Until the phone is back, no window, terminal or dock click is the voice's focus, a reply that asked to be heard waits and plays once the phone is back, as do the replies that came while the hubs changed over, and nothing plays on this computer; the target stays a target though no window shows it until the phone's page shows a conversation again; only an explicit action on this computer (Talk here, the mic, Voice on the computer) takes the voice there. A phone that does not come back in time leaves the voice off, as when the phone is lost.
- **Dictation on the phone** (PRD R119). On a paired device's page the mic is the phone's own microphone; its tap takes the voice to the phone when it is not there and opens the microphone in the same tap. The hub refuses a paired page's Mic on unless that page holds the voice, so a paired device never turns on this computer's microphone. The page sends 16 kHz PCM only while the voice process has the phone's capture open, and the hub relays it only while that page holds the voice. The phone's busy state (no track, a muted or ended track, a hidden page) stands in for this computer's other-app watcher, so this computer's watcher and microphone are never opened for the phone. Phone capture counts as capture that cancels the echo, since the page asks for iOS's voice processing, which cancels the page's own playback: it listens while the voice plays from the first moment, so talking over a reply stops it and the words are heard. What echo is left is rejected by barge-in itself, which passes only the enrolled voice beating the reply voice's print, or without an enrolment only words not in the reply, and the words held over a reply are dropped after it as its echo; the echo check does not run on the phone, and the loudspeaker's leftover echo is not measured ([mechanics.md](mechanics.md) M127). The voice check scores phone audio against the existing voiceprint; enrolment is refused while the voice is not on this computer. Every move of the voice turns the mic off, so the mic is turned on again where the voice now is. In the phone's layout, leaving the conversation for the list turns a mic that is on for it off, since the operator has left the work item; speech already playing goes on.
- **Alerts, the needs-you sound and the voice check on the phone** (PRD R119). While the phone has the voice, the focused conversation that holds an alert back is the phone page's selected one, never a window or terminal on this computer, and a spoken alert or the needs-you sound goes out only while that page is in front; otherwise neither is sent, a waiting alert is dropped rather than kept for the page's return, and the dock and the page keep the unread counts, and no other page plays its own needs-you sound in the voice's place. An alert's answer is heard through the phone's microphone and goes to no session, and the phone's audio gets the voice check against the voiceprint enrolled on this computer. **Voice on the computer**, on this computer's page only while the voice is on a phone or none has it, takes the voice back as Talk here does, with the mic off, and is refused with why when voice is off or the voice is already here.
- **Installing.** The manifest's `start_url`, `scope` and `id` are `/page/`, relative to the origin, and the files needed to install the page need no cookie, so a phone installs the page from the remote host over HTTPS, which a service worker needs; the phone draws the page's phone layout ([Web page](#web-page)).
- **Security.** Tailscale's WireGuard tunnel and certificate give the HTTPS. The hub trusts `tailscale serve`'s headers only because the proxy runs on this machine and connects from the loopback, and it never takes a proxied request for this computer's own. A process on this computer can send any header, as it can already reach `127.0.0.1`, but still needs a token or a sign-in. Another person on the tailnet, a device shared into it, a tagged device or a Funnel visitor carries another login or none and is refused before any route, a pairing link included; a device of the operator's own login still needs pairing. A paired device acts as the operator, except for the local-only commands, until its sign-in goes unused for 30 days or is revoked, so a lost phone is signed out by revoking its sign-in.

## Session reports

Reports from a definitively failed start with no native identity are refused; Retry must create a new session before it reports.

### Handled assignments (R85)

`report handled <sessionId> <ticket URL> [--release <assignment key>]` posts to `/handled`. It registers another ticket's current assignment as already handled by the reporting session, so Switchboard creates, triages and starts no work of its own for that ticket while the registration lasts. The report contract offers it to every session, for use only when a skill directs it. The response contains `assignmentKey`, which the skill keeps for an optional conditional release. Registration requires an open target assigned to the operator and the current session of an open work item, and cannot target the reporting work item's own ticket.

`tickets.handledAssignmentKey` is the only added storage. Events and changes keep the registration and clearing evidence, with the reporting session and work item, and deleting the reporting work item preserves it. After every accepted event, core clears each key whose reporting work item is done, deleted or missing, notes the ended keys for History, and creates a work item for a still-assigned ticket, so no ticket stays hidden after the work that handled it ends. Core refuses ticket identity adoption of an active handled target; consolidation of an inactive target transfers its audit. Ended-key audit prevents a delayed registration retry from restoring handling.

`Source.assignmentAt(url)` returns the ticket, its opaque operator assignment key and fresh queue eligibility, or a read error. For GitHub the key identifies the issue and the event that began the current continuous assignment across the configured operator logins, read from assignees and assignment events and never inferred from status history; the project's current status corrects stale search eligibility. Incomplete history, changed pagination snapshots and failed reads are errors.

Registration and polling are serialized per source. Every poll reads registered targets directly, including those missing from project search, and applies assignment reconciliation with the poll atomically. Core guards work creation, triage and session dispatch. Registration refuses a target whose open work already has a session, including an emitted start; otherwise it removes unstarted duplicates before acknowledging. A new assignment clears the key and permits normal work. An explicit release compares the supplied key and uses freshly read eligibility before scheduling work.

### Report transport

Sessions report through the hub bundle's CLI, which posts to the hub's loopback HTTP server. The prompt carries the Switchboard session ID and the bundle's absolute path, because a background session has no Switchboard environment and `switchboard` is not on PATH. `node` below is `sessions.nodePath`; a session keeps the command its prompt holds. Bash, PowerShell and cmd all run the command, and they agree only on a first word with no spaces, quotes or shell characters, so `sessions.nodePath` must be such a path to `node` or `node.exe`.

```
node "<home>/hub.js" report stage <sessionId> <stage>
node "<home>/hub.js" report worktree <sessionId> <path>
node "<home>/hub.js" report done <sessionId>
node "<home>/hub.js" report approval <sessionId> --prompt <prompt> [--summary <text>] [--report <path>]
node "<home>/hub.js" report link <sessionId> --label <text> --target <url>
node "<home>/hub.js" report playbook <sessionId> <name>
node "<home>/hub.js" report paste <sessionId> --label <text> --file <absolute path>
node "<home>/hub.js" report task <sessionId> --prompt <prompt> [--repo <repo root>] [--title <text>]
node "<home>/hub.js" report question <sessionId> --text <question>
node "<home>/hub.js" register --title <text>
```

- The contract asks for the approval summary; the CLI and the hub accept its omission. The hub refuses a report path that is not absolute; the CLI resolves a relative one against its working directory.
- Git Bash rewrites an argument that starts with `/` to a path under its Windows root, so `/sb-ship 16416` would arrive as `C:/Program Files/Git/sb-ship 16416`; under Git Bash the CLI restores an approval or task prompt that starts with that root (mechanics M20).
- `report ticket <sessionId> <url> [--playbook <name>]` (PRD R83) moves the reporting session to the ticket at the URL. It is outside the report contract's kinds, so no session's stored reports or contract text change. The hub refuses a retired copy, and refuses when no enabled source answers for the URL in time, the lookup fails, or the ticket is closed, because the move needs the ticket's title and state. On success the CLI prints the new key and the session's contract, which `/contract` also restores after compaction; a retry prints them again.
- `register` (PRD R81; mechanics M37) registers the Claude session that runs it, identified by `CLAUDE_CODE_SESSION_ID`, and prints its key and report contract. A native ID that is already a session's current one answers that session again, as does one that an earlier request registered while this one read the roster, so a retry after a lost reply recovers the contract; a native ID that is a retired or related copy of a session is refused; otherwise the Claude runner must find the session live in `claude agents --json`, or the registration is refused.
- The CLI's home is the directory that holds its `hub.js`, so a session started by a hub with `--home` reports to that home. The CLI finds the hub through `hub.json` and never starts one. Repeating a report is safe, because each report sets a value and a repeated `task` adds nothing.
- Exit codes: 0 recorded, 1 usage, 2 no hub, 3 refused (an unknown session, a report the session's contract does not offer, a link its ticket's source refuses, or a path that `git worktree list` in that path does not show as a worktree). A worktree can belong to a different repository than the source's repo root. With no hub, the work item ends `blocked` and the operator marks it done; the hub stays up while sessions are active, so this is rare.
- Done check (PRD R10): before applying a task session's `done`, the hub polls the ticket's source, within the CLI's timeout. When the poll still lists the ticket as assigned, the session's outcome is recorded as an unconfirmed done and the work item's status stays; the hub polls again after a delay, because GitHub issue search can list an issue as assigned for seconds after its unassignment (mechanics M34). Still assigned then blocks the work item; otherwise it is done. A failed or slow read, or a source turned off, accepts the report. A resume, a later approval or done report, or Mark done makes the pending check change nothing, and a hub that stopped schedules the pending checks again at startup. A poll that finds the ticket outside the assigned state marks such a work item done even while its session is still active. A setup session or an ad-hoc ticket skips the check. Reads of one source run one at a time, so an earlier scheduled poll cannot apply after the check's poll.
- A report for a work item that is already done does not reopen it: `done` sets the session's outcome, `worktree` links the ticket's worktree, `link` adds the ticket's link, and `stage`, `approval`, `playbook` and `paste` are ignored.
- `playbook` names a task playbook in the work item's namespace and sets the work item's playbook only, so the session keeps the reports its prompt offered.
- `task` (PRD R68) creates an ad-hoc ticket and an `unstarted` work item whose parent is the reporting session's work item, whether or not that work item is done. Its repo is `--repo` or the reporting ticket's root ([Repo roots](#repo-roots)) and must be one of the configured repo roots, compared ignoring case and separators. A report whose prompt equals that of an open work item from the same parent adds nothing.
- `link` takes only an http(s) URL. A link to a target the ticket already has replaces its label.
- `paste` (PRD R60) takes a non-empty label and a `--file` that names one file wherever it is read (on Windows a drive or UNC path; elsewhere a POSIX absolute path), because the extension reads the file later, outside the session's working directory; the CLI and the hub refuse any other. The hub stores it on the session's work item when the session is the latest, replacing a paste with the same label.

## Friction debriefs

PRD R55, ported from Ground Control's debrief runner (GC M64). Off unless `sessions.debriefs` is true. The hub asks a finished or idle Switchboard session, through a fork of it, what friction it met, and records the answer for the friction-review prompt to read.

- **Files:** under the Claude root (`CLAUDE_CONFIG_DIR` or `~/.claude`): the prompt `skills/friction-review/prompt.md`, the state `.wip/debrief/state.json` and the log `.wip/debrief/log/YYYY-MM.jsonl`. They are the files Ground Control wrote, in the same format, so Ground Control's record still holds and a reader of the log finds both runners' lines. A session's entry has one writer, the hub that started the session.
- **Candidates:** a started session with a native ID is due once its work item is done, or once its last turn has been idle long enough that the operator is unlikely to resume it, and is skipped once the one-hour prompt cache has expired rather than run cold. It also needs enough new tool calls since its last debriefed message, in a range whose debrief has not failed. One fork runs at a time, oldest transcript first.
- **Claude sessions:** before each fork the hub reads `claude agents --json` and skips a session that is running; an idle background session and a stopped one can be forked (mechanics M19). The fork resumes the session as a fork that is not persisted, in its `cwd`, with the prompt on stdin and `FRICTION_DEBRIEF=1`, and with no model, effort, tool or MCP flag, because each changes the prompt prefix and loses the cache. The prompt names the range to cover and the resumable subagents with new work, whose transcripts are copied where the fork looks for them for the run.
- **Codex sessions:** a Codex session's own thread is a candidate on the same terms, read from its rollout, and is forked with `codex exec fork`, read-only and ephemeral. Codex threads that a Claude session delegated to through agent-delegate are marked pending by that session's debrief and asked once each through agent-delegate's debrief command; a missing command skips them.
- **Answer:** the fork's last result, `{"friction": [...]}` or a bare array, each item with non-empty `what`, `source`, `workaround`, `cost` and `evidence`.
- **Record:** a success appends a log line and then merges into the state as it is on disk, so another writer's entries are kept. A failure records the range and its error in the state and the hub log and is not retried; the next debrief covers that range with any later work. A write that fails is held, and no fork starts until it is written. A hub that stops between the two writes asks about that range again.

## Settings

`settings.json` in the config folder, plain JSON, holds the settings and the [playbooks](#playbooks). The operator owns it; this repository holds none of the operator's values. The hub validates it on load and on change (PRD R42): any error outside `playbooks` rejects the whole file and keeps the last valid settings and playbooks, while each playbook is checked on its own. `parseSettings` in `packages/core/src/settings.ts` and each source package's config parser are the authority for keys, values and defaults; the [Settings window](#settings-window) edits them.

Settings owned by other sections: `dock` (PRD R28, R71; [Dock](#dock)), `alerts` (PRD R65), `sessions.codeMode` (PRD R93; [Code Mode sessions](#code-mode-sessions)), `voice` (PRD R105; [Voice](#voice)), `web.port` (PRD R109; [Web page](#web-page)), `web.chromePane` (PRD R113; [Chrome pane](#chrome-pane)), `web.diffLayout` and `web.diffWrap` (PRD R118), `web.remoteHosts`, `web.remoteLogins` and `web.tailscale` (PRD R115; [Remote access](#remote-access)), and `schedules` (PRD R82), whose playbook must be a task playbook that needs no worktree, because a scheduled run has no source `setupPrompt`.

- `sources` (PRD R3): each key names a source, in lowercase letters, digits and hyphens, and not `schedule`; its `kind`, defaulting to the name, picks the source plugin. Polls, tickets, toggles and errors are keyed by the name. A kind with no plugin disables that source. The file is rejected whole for a non-GitHub source named apart from its kind (schema migrations find Zoho and Forum tickets by source name), a source named after another kind, and two GitHub sources that read the same project board, including one that is off, because an issue would then belong to both.
- A source implements core's `Source` (`packages/core/src/source.ts`) and only reads: `poll(current)` returns a complete read or an error, given the source's tickets the store lists as assigned, in the pool or in the queue, and a failed read changes nothing; `context(ticket)` returns the triage context; `keyOfBranch(branch, repo)` reads a ticket key from a worktree branch. The optional `ticketAt(url)` reads the ticket a ticket report names, or answers null for a URL that is not one of its tickets (PRD R83); `assignmentAt(url, anyBoard)` reads the operator's actual assignment (PRD R85), and the poll's reread of a registered ticket passes `anyBoard`, so a registered issue that left the board can still be released. The hub asks the source that stores a ticket with the URL first, and refuses while that source is configured but off. A source with a pool marks each polled ticket `assigned`, `pool` or neither.
- Pick (PRD R48): a picked Support case starts its playbook's task session; Switchboard does not claim the case.
- GitHub keys (PRD R44): a ticket key is the bare issue number in the source's home repository and `owner/name#n` elsewhere, and every read of a stored ticket goes to its key's repository. A pull request link is accepted when a closing reference names the ticket, or, in the ticket's repository, when its branch names the ticket's key. Because bare keys mean the home repository, the hub records each GitHub source's home once it has tickets and refuses a settings change to it. A repository label may not equal a source name, `gh`, `adhoc` or `schedule`, nor label two repositories.
- One source per issue (PRD R44): a polled ticket whose URL already has a ticket in another source is dropped and noted in the snapshot, which the dock lists with the errors.
- Start gate (PRD R44): a triaged work item whose ticket's repository is not its source's home repository waits for Start, whatever the playbook's `autoStart`.
- Display keys (PRD R27): rows show a ticket outside the home repository with its repository's label or name as a prefix, while the stored key still names windows, workspace files, terminals, sessions and History.
- Worktree linking (PRD R25): after each poll the hub lists worktrees in the root of the home repository and of each repository with an assigned, pool or registered ticket in the source, and reads each branch with that repository.
- GitHub reads go through `gh api graphql`. The issue search is scoped by the project board (mechanics M59), then filtered on project status; an issue on another status is not assigned (mechanics M2). With `includeClosed` the search also returns closed issues, which then count as assigned and open (mechanics M60). With `requireAssignee` false (PRD R44) the search has no assignee qualifier and lists only issues in scope, so a poll creates no ticket for an issue never in scope; their scope entry is null (PRD R53). Otherwise the scope entry (PRD R53) is the start of the operator's current continuous assignment, from the assignment events, and the sort time is the later of that and the Status field's `updatedAt`, because status-change events have been missing from the issue timeline since about 2026-09-25. A poll that needs more pages than `maxPages` fails. Each stored assigned ticket that the search leaves out or lists outside scope is read on its own, because issue search can return a successful but incomplete result during a GitHub outage (mechanics M48); a failed read fails the poll. The triage context holds the board status, the issue's body, recent comments and assignment and status history, and a linked pull request's state, reviews, checks and recent comments and threads, each text clipped keeping its start and end. On somebody else's pull request, one line counts the operator's own submitted reviews and pull request comments, so triage can choose between a first review and a follow-up without reading the lists (mechanics M58). Bots show as `<login> (bot)`, since a bot's GraphQL login has no `[bot]` suffix. Comment headings carry an anchor ID, and the optional `rolesFile` adds each listed author's roles; a roles file that cannot be read leaves the roles out, the hub logs a warning, and triage continues. The context read also returns the linked pull request as a link, which a successful triage adds to the ticket's links, keeping earlier ones (PRD R52).
- With `waitForBlockers` (PRD R90) the source keeps each issue's open blockers, keeping only `OPEN` ones because GitHub also lists closed blockers (mechanics M56); with it off every listed issue gets no blockers, which clears stored ones. An issue with more blockers than one read holds loses the rest.
- GitHub errors: offline, timeout and rate limits are temporary; the poll changes nothing and runs again at the next interval. Missing `gh` or failed authentication shows in the dock. Each poll first checks that the configured status field exists and is a single-select field, and fails otherwise, because the poll would read every issue's status as null and end their work items (mechanics M17).
- Zoho Desk and Forum port the intake of the operator's former Support board.
- Zoho reads go through the Desk REST API, read-only, with the access token that `tokenCommand` prints and the `orgId` header. Switchboard reads no secrets file; the operator's runner scripts do. Desk's 19-digit IDs are kept as strings.
  - Each poll reads the Open tickets with the escalation value through `/tickets/search`, because only it returns custom fields (mechanics M46). Creation order does not keep pages stable when a ticket leaves during a multi-page read, so each stored current ticket the search omits is read on its own and kept while it is Open, escalated and not in the trash (mechanics M10); one that is gone is not assigned, and any other failed read fails the poll. A ticket missing from a complete poll has left the assigned state.
  - Assignee classes follow the Support board's: the operator is the assigned state; no assignee, an automation or a support team member is the pool; any other engineer is neither, and the poll leaves the ticket out. A poll whose team map cannot be read is incomplete and changes nothing.
  - Scope entry (PRD R53): from the ticket's history, the latest event that set the escalation value or the ticket's current status, else its creation time; a history too long to find one gives null, so core keeps the time it has. A failed history read fails the poll.
  - Triage context: the subject, the escalation and account custom fields, the thread bodies, the internal notes, and the history of tier and assignee changes.
- Forum reads run read-only SQL on the production forum database through `queryCommand`, the operator's runner script, which holds the connection. The SQL goes to its stdin and rows come back as one JSON object per line. A broken input pipe fails the query even when the command exits successfully, so no rows are accepted from an incomplete SQL write. The runner's exit code 7 means the database is unreachable, usually the VPN, and the poll fails without changing anything. A line that looks like a row but does not parse, or reaching `maxRows`, makes the poll incomplete.
  - Assigned state: an open, unlocked, undeleted topic in the configured forum assigned to `userId`; the pool is such a topic assigned to no one. A topic assigned to anyone else is left out by the query, so it never makes a poll incomplete. The pool sorts by the last public post, else the topic's creation; DATETIME values are UTC.
  - Scope entry (PRD R53): the latest change in the audit store (`auditDatabase`) whose field names include `Status`, since the topic is Open now; the insert row lists every field, so it covers a topic whose status never changed; else the topic's creation. The audit store keeps field names but not values on the database (mechanics M15). A failed read fails the poll.
  - Triage context: the topic title and posts in order, leaving out deleted posts, private notes and the automatic AI analysis.
- `tokenCommand` and `queryCommand` run through `bash -c`. On Windows the hub uses Git Bash, from `CLAUDE_CODE_GIT_BASH_PATH` or beside `git.exe` on PATH, because `bash` on a VS Code-started hub's PATH is WSL's, which lacks the runner scripts' tools.
- A Forum topic and a Zoho ticket about the same case are separate tickets (PRD R26).
- Existing issues (PRD R61): the Zoho and Forum context reads find each distinct GitHub issue or pull request URL in the context's header lines and unclipped bodies, reading the HTML before clipping so that a link whose text is not the URL, or a URL in a clipped-out part, is found; each becomes a link labelled by its issue or pull request number, cut to the issue or pull request and lowercased. A successful triage adds the links, as it does the GitHub source's pull request; the triage context's text is unchanged.

The operator's playbooks live in their settings.json, not in this repository. Each runs one skill, such as `dev:develop`. Scheduled playbooks are in the `ops` namespace, which no source triages into.
