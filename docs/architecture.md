# Switchboard architecture

Requirements live in [prd.md](prd.md). This document describes components, state and protocols. Implemented: the hub lifecycle, the core's store, settings, playbooks and [flow decisions](#core-decisions), the GitHub source, the Claude Code runner and classifier, the hub runtime, the report command, the panel with the ad-hoc prompt box, the Zoho Desk and Forum sources, and the pool with picks, shown with unstarted work items in the Unstarted group, and the settings editor.

Session and triage mechanics come from Ground Control (`D:\git\ground-control`), where they are verified. M IDs below refer to its [mechanics.md](../../ground-control/docs/mechanics.md). Re-verify them in Switchboard's own mechanics.md before relying on a version-fragile one.

## Packages

npm workspaces, TypeScript strict, Node ≥ 22.13, Vitest, esbuild and vsce, following Ground Control's layout. Only `extensions/switchboard` imports `vscode`. Implemented so far: `packages/core`, `packages/github`, `packages/zoho`, `packages/forum`, `packages/claude`, `packages/hub`, `apps/hub`, `extensions/switchboard` and `extensions/chrome`.

| Package | Contents | Depends on |
|---|---|---|
| `packages/core` | Domain types, source and runner interfaces, store, playbook loader and renderer, flow rules | — |
| `packages/claude` | Claude Code runner, classifier and debrief fork | core |
| `packages/github` | GitHub source: assigned state, triage context | core |
| `packages/zoho` | Zoho Desk source | core |
| `packages/forum` | Forum source over the forum database | core |
| `packages/hub` | Polling scheduler, flow execution, loopback HTTP/SSE server, report endpoint, debrief scheduler | core, sources, claude |
| `apps/hub` | Hub entry point and the `switchboard report` CLI, bundled as one file | hub |
| `extensions/switchboard` | Hub process lifecycle, panel webview, attach, open in Claude Code tab, worktree changes and Source Control, Needs you notifications | core, hub client |
| `extensions/chrome` | Chrome extension that hides snoozed cards and shows each card's playbook on GitHub project boards ([Chrome extension](#chrome-extension)) | hub browser endpoint |

The ad-hoc source is local and lives in `packages/hub`. State, the hub bundle, its record and its log live in the Switchboard home, `~/.switchboard`. Settings and playbooks live in the config folder, so the operator can keep them in a git repository. The config folder is the VS Code setting `switchboard.configDir` (machine scope): an absolute path, or one starting with `~` for the user profile. When the setting is empty, it is the Switchboard home. For a relative path, the extension shows an error and uses the Switchboard home. Each window reads the setting on every hub start, so all windows agree on one hub. When the setting changes, an open settings editor closes with a warning, because its drafts and file versions belong to the old folder, and a window whose hub reads another folder stops it; every window then reconnects to one hub started on the new folder, and the keeper does not count that stop as a failure.

## Components

| Component | Responsibility |
|---|---|
| Hub | Separate Node process that runs the core: polls sources, creates work items, runs triage, starts setup and task sessions, enforces one active session per work item, serves the panel and the report command. |
| Source plugins | Supply tickets, decide whether each is in the assigned state, and build each ticket's triage context: GitHub, Zoho Desk, Forum, ad-hoc. |
| Playbook loader | Reads playbook files and renders their templates. |
| Classifier | Runs one-shot triage and returns structured output. |
| Runner | Starts, stops and tracks agent sessions for one provider. Claude Code first. |
| Worktree linker | Links worktrees to tickets from session reports, falling back to branch-name convention. |
| Store | Local SQLite database holding tickets, work items, triage results, sessions and worktrees. |
| VS Code extension | Starts the hub, hosts the panel webview, attaches consoles, opens sessions in Claude Code tabs, opens a worktree's changes and adds it to Source Control. |

## Data model

```
Ticket     id, source, sourceKey, ref, sourceId, title, url, assigned, pool, snoozed, snoozedUntil, sortAt, scopeAt, lastPolledAt, repoRoot
WorkItem   id, ticketId, playbook, status, stage, stageAt, taskPrompt, warning, error, failedStep, unassignedAt, queuedAt, createdAt, statusAt, runStartedAt, scopeAt, doneAt, doneReason, approvalPrompt, approvalSummary, approvalReport
Triage     id, ticketId, workItemId, context, playbook, immediacy, severity, model, startedAt, endedAt, error
Worktree   id, ticketId, path, branch, linkedBy (report | convention)
Link       id, ticketId, label, target, reportedAt
Session    id, workItemId, kind (setup | task), provider, nativeSessionId, shortId, cwd, state, stateAt, stateDetail, outcome, outcomeDetail, startedAt, endedAt, released
```

- `Ticket.assigned` is the assigned state the last complete poll saw, and `Ticket.pool` whether it saw the ticket in the pool. `Ticket.ref` is the reference people use, set by the source when it builds the ticket: `#<n>` for GitHub and ad-hoc, `#<ticket number>` for Zoho, `T<topic id>` for Forum; core holds no per-source rule. `Ticket.sortAt` is the source's sort time, which orders the Unstarted group: Zoho's `customerResponseTime`, Forum's last public post, and for GitHub the later of the operator's latest assignment and the Status field's `updatedAt`. `Ticket.scopeAt` is when the ticket last entered the source's scope (PRD R53). Each polled ticket carries the source's `enteredAt`, or null, and core stores the source's time whenever it has one, because a source's scope can be wider than the assigned state and the pool: a GitHub issue on another status, or a Zoho ticket another engineer holds. Without one, the ticket keeps the time it has, or takes the poll's time when it has none and is assigned or in the pool. Ad-hoc tickets enter scope when created. A pool triage has a `ticketId` and no `workItemId` until a pick creates the work item and attaches it. `Ticket.repoRoot` is the repo an ad-hoc prompt chose; it is empty for other sources, which use their `repoRoot` setting.
- `Ticket.sourceKey` is the key people use, such as a GitHub issue number or a Zoho ticket number. `Ticket.sourceId` is the source's internal ID when API calls need a different one, such as Zoho's internal ticket ID.
- `Triage.context` is the clipped text the classifier received, with the current time. Keeping it shows why a playbook was chosen.
- `WorkItem.status` takes the values in PRD R34. `WorkItem.error` holds the cause shown for `failed` or `blocked`, and `WorkItem.failedStep` (`triage`, `setup` or `task`) is the step Retry repeats (PRD R45).
- `WorkItem.unassignedAt` records that the ticket left the assigned state while a session was active (PRD R10). `WorkItem.queuedAt` orders queued starts.
- `WorkItem.taskPrompt` is the rendered prompt the task session ran, or the typed prompt for an ad-hoc work item.
- `WorkItem.doneReason` is `session`, `operator` or `unassigned`.
- `WorkItem.warning` is set when the work item ends because its ticket left the assigned state with no done report (PRD R10, R11).
- `Session.state` is the observed state, `Session.stateDetail` the error kind of a `failed` turn, and `Session.outcome` the reported or decided outcome (PRD R36). `Session.released` records that the release stop was sent, so it is sent once (PRD R39).
- A session's `cwd` follows its playbook's `workdir`: the ticket's worktree when one exists, otherwise the source's repo root.

## Hub lifecycle

Implemented. Follows Ground Control's hub (GC R35, M25).

- **Start:** extension activation copies `dist/hub.js` to `~/.switchboard/hub.js` when it differs. It accepts a running hub only when the hub's `build`, a hash of its bundle, matches the bundle installed at that moment, and its `configDir` matches the window's config folder. It asks any other hub to stop and starts a new one only after the old one has gone; if the old hub refuses, the window reports it. Otherwise it starts one detached with VS Code's executable and `ELECTRON_RUN_AS_NODE=1`, with `ELECTRON_*`, `VSCODE_*` and `NODE_OPTIONS` removed from its environment. Output goes to `~/.switchboard/hub.log`.
- **Record:** the hub listens on `127.0.0.1` on an ephemeral port and writes `~/.switchboard/hub.json` with `protocol`, `version`, `build`, `configDir`, `port`, `token`, `pid` and `startedAt`. A record without `configDir`, from an older hub, reads as an empty one, so a window replaces that hub. The hub holds a lock for its lifetime: a named pipe `\\.\pipe\switchboard-<hash of home>` on Windows, `~/.switchboard/hub.sock` elsewhere. Only the lock holder writes or removes the record, so concurrent starts leave one hub, and the OS releases the pipe when the hub dies. A hub that cannot take the lock waits up to 5 seconds for the holder's record and otherwise exits. A forced exit on Windows leaves the record behind, so clients accept it only when `GET /status` with the token returns the recorded pid.
- **Endpoints:** `GET /hub` returns identity without a token. `GET /status`, `GET /events`, `POST /shutdown`, `POST /report`, `POST /action`, `POST /open` and `POST /claim` require `Authorization: Bearer <token>`. `/events` sends a `state` event with the whole panel snapshot when it opens and after every change. `/action` takes an operator event (`adhoc`, `start`, `approve`, `retry`, `mark-done`, `retriage`, `stop`) and answers 409 with the core's refusal.
- **Clients:** each window holds one `/events` stream. The hub exits 30 minutes after its last stream closes, but not while any session is active or a debrief runs (PRD R43, R55). A stream that sends no response headers within 5 seconds counts as refused. When a stream ends, the window finds or starts a hub and reconnects. It gives up and shows an error after three consecutive failures; a connection that lasts under 10 seconds counts as a failure.
- **Browser endpoint:** for the Chrome extension, which cannot read `hub.json`, the hub also listens on the fixed port `127.0.0.1:47615` (`BROWSER_PORT` in core). It serves, without a token, `GET /snoozed`: `{"urls": [...]}`, the URLs of tickets snoozed now, from every source; and `GET /cards` (PRD R67): `{"cards": [{url, playbook, group, snoozed}]}`, one per ticket URL, built from the panel snapshot by `cardsOf` in `packages/hub/src/cards.ts`. A card covers each work item and pool ticket of a polled source with a URL that the panel lists, so an unsnoozed done work item only for the panel's 7 days and a snoozed ticket while Snoozed lists it, because a card for a row the panel does not show could not open it; `url` is the ticket's URL as stored, `playbook` the name the panel shows (`<namespace>:triage` during triage, null before triage chooses one), `group` the panel group (`needs`, `working`, `unstarted` or `done`, from `groupOf`; a pool ticket is `unstarted`), and `snoozed` the ticket's flag. A ticket with several work items gives the pool entry, otherwise the open work item, otherwise the latest one. `/snoozed` stays, because the Chrome extension is loaded separately and can be older than the hub. It sends no CORS headers, so web pages cannot read it, and answers 403 to a `Host` other than `127.0.0.1:<port>` or `localhost:<port>`, against DNS rebinding. A hub that cannot take the port, such as a second hub for another home, logs it and runs without the endpoint.
- **Entry point:** `hub.js [--home=<dir>] [--config=<dir>] [--idle-ms=<ms>] [--browser-port=<port>]` serves, reading settings and playbooks from `--config`, or from the Switchboard home without it; `--browser-port=0` serves no browser endpoint, as in the spawn tests; `hub.js --stop` stops the running hub; `hub.js report …` sends a session report.
- **Runtime:** the hub opens the store, loads settings and playbooks and reloads them on change, polls each enabled source every `pollIntervalSeconds`, then reads `git worktree list` in its repo root for the branch convention. Entries that git marks `prunable`, such as one whose directory was deleted, are left out of both the convention and report validation. While any session has started, it reads the roster every 30 seconds and hook markers every 5 seconds. Before a roster read or a release stop can end a setup session, it reads the convention again, so an unreported worktree still counts.
- **Startup:** the hub installs hooks when `sessions.installHooks` is on, runs again any triage it abandoned, fails any session still `starting` with "The hub stopped while the session was starting.", and reads the roster (PRD R43).
- **Home override:** when `SWITCHBOARD_HOME` is set in VS Code's environment, the extension passes it to the hub as `--home`. Both the variable and `--home` name the directory that holds `.switchboard`, in place of the user home, so the Switchboard home is `<override>/.switchboard`. The extension then ignores `switchboard.configDir`, so the config folder is `<override>/.switchboard` too. It does not change the user profile that Claude and `gh` see. Live acceptance depends on it.

## Panel

- The extension contributes a **Switchboard** view container in the activity bar with one webview view, also named **Switchboard**, so VS Code titles the view once rather than as `Switchboard: <view>`. The webview renders each `state` event the window's `/events` stream delivers; it keeps the groups the operator opened or closed and the selected row across redraws. A click, a right-click or keyboard focus selects a row. Rows do not expand.
- Groups follow PRD R27, shown in the order Needs you, Working, Unstarted, Done, Snoozed. Every group collapses: Needs you, Working and Unstarted start open; Done and Snoozed start closed.
- A row shows only its primary control, as a 26px text button with its icon and verb (the verb is hidden, and kept in the tooltip, when the row is narrower than 360px), in an actions column at the right of lines 2 and 3, shown only while the row is hovered, selected or focused (`display: none` otherwise, so lines 2 and 3 take the full width); Approve uses `button.background`, Retry `statusBarItem.errorBackground` on a failed row and `statusBarItem.warningBackground` on a blocked one, and Start and Triage again a muted fill of the foreground colour at 12%. An `awaiting-approval` row whose approval report named a draft (`WorkItem.approvalReport`) puts a Report icon button before it, titled with the draft's filename, which opens the draft in VS Code. No other row shows Report. The primary control is: Start on an Unstarted row (`start` for a work item, `pick` for a pool ticket), Approve or Retry on a Needs you row, or Triage again on a pool row whose triage failed. A pool row has no primary control while its triage runs. A control's verb matches the status: Start for `unstarted` and pool tickets, Approve only for `awaiting-approval`. Every control that applies, the primary one included, is in the row's native right-click menu: the row's `data-vscode-context` sets a `switchboard.row.<key>` context key per control and carries each control's hub action, and the `webview/context` menu shows the matching `switchboard.row.*` commands, which send that action. `preventDefaultContextMenuItems` hides Cut, Copy and Paste.
- The row shows no session-state dot; the group and the mark carry the state. A click on the row outside a control or link, or Enter on the focused row, runs the row's open action (`data-open`): Attach (`claude attach <shortId>` in a terminal) while the active session's background process runs; otherwise Resume, the latest session in a terminal (see [Resume](#claude-code-runner) below); otherwise the ticket's worktree, opened with `vscode.openFolder` in its own window, which VS Code focuses when a window already has it; otherwise, when the work item has no session, the ticket's URL in the browser. A pool row opens its ticket's URL. A row with none of these, such as a session still starting with no worktree or an ad-hoc ticket with no session, has no open action. Ctrl+click (Cmd+click on macOS), or Ctrl+Enter, runs the row's editor action (`data-open-editor`) instead when it has one: the latest session in VS Code, following [Open in VS Code](#claude-code-runner), for any row whose open action is Resume; otherwise the ticket's worktree, when it has one, opened with `vscode.openFolder`. A session running in its background process therefore opens its worktree instead of attaching, because an editor resume of a live background session is refused (M7).
- Controls run the extension's `switchboard.action`, `switchboard.attach`, `switchboard.resume`, `switchboard.open` and `switchboard.openLink` commands. An operator event goes to `POST /action`, and a refusal shows as a warning. Stop applies to a session running in the background. A ticket link opens in the browser. A link badge opens its URL in the browser, and Report opens its draft in a VS Code editor. The webview stops a link click from reaching the window, because the webview host would otherwise open the link a second time (mechanics M16).
- Open Changes and Show in Source Control (PRD R57) run in the extension, not the hub: `controlsOf` adds them for a row with a worktree, and the row's menu context carries their whole message (`changes` with the path, the ticket key such as `gh 18941` and the title; `sourceControl` with the path) where hub controls carry a hub action. `src/git.ts` runs `git.openRepository` with the path, checks that the Git API's repository root is that path, because VS Code can answer with another repository (mechanics M21), and then either focuses `workbench.view.scm` or reads the changes. For changes it awaits `repository.status()`, finds the merge base with `getMergeBase` (never `getBranchBase`, which writes to the git config), reads `diffBetween(base, 'HEAD')`, the index group, and the merge, working-tree and untracked groups, and passes the three lists to `changesPlan` in `src/changes.ts`. `changesPlan` follows each file through the stages to one row, sorts by path and caps at 400 rows, saying so in the title. A rename onto a deleted file's path takes that file's base when the renamed file has none, and otherwise the deletion keeps its own row. `_workbench.openMultiDiffEditor` opens the rows with `git:` URIs at the base and `file:` URIs on disk. VS Code reuses an open editor with the same source URI without updating its rows, so the extension first closes the tabs whose label starts with the ticket key, which outlasts a title change, and whose input has `textDiffs`, even when there are no changes now, then opens with the source URI `switchboard-changes:/<key>/<time>`. A conflict counts as a modification, including a modify/delete conflict, which leaves the modified file on disk.
- Needs you notifications (PRD R65) run in the extension. `NeedsYouTracker` in `src/toast.ts` keeps the window's previous snapshot: the `hello` event that opens each `/events` stream clears it, and each `state` event returns `newlyNeeding(previous, next)`, the work items whose `groupOf` is `needs`, whose ticket is not snoozed, and whose ID was not among those in the previous snapshot, or none when there is no previous snapshot. `NeedsYouToasts` in `src/notify.ts` shows one `showInformationMessage` per returned item when `vscode.window.state.focused` and `switchboard.notifyNeedsYou` (window scope, default true) are both true. The text is `Switchboard: <ticket title> — <mark title>` (`toastOf`). The **Open** item is offered only when the row has an `openAction`; pressing it computes `openAction` again from the panel's latest snapshot and runs it through `runOpen` in `src/panel.ts`, the same path as a row click. The tracker updates on every snapshot, including in an unfocused window or with the setting off, so focusing a window or turning the setting on does not toast the backlog.
- The row mark shows what differs within the group, with its meaning in the tooltip (PRD R27). Needs you: approve the publish (`cloud-upload`), answer a question (`question`, for a waiting session), blocked (`debug-pause`), failed (`error`, red). Working: queued (`clock`), setting up (`tools`), running (spinning `sync`). Done: finished by the session (`check`), marked done by the operator (`account`), left the assigned state (`sign-out`). Unstarted: no mark, except Triaging (spinning `loading`) on a work item or pool ticket being triaged. There is no status text; the mark's tooltip names the state. A snoozed row keeps the mark of the group it returns to, and its line 3 shows the wake time (`clock`, `Mon, Oct 12, 6:00 AM`) unless the snooze is indefinite.
- The priority dot is one orange dot inside the title, before its text, shown only on a priority ticket, in every group. No space is reserved for it, so every line starts at the left edge. The dot's tooltip gives the immediacy and severity (PRD R50).
- A row has two or three lines, with room between rows (PRD R27). The first: the title, led by the priority dot, and the time in queue. The second keeps its height when empty and holds, from the left: the playbook, the source and key linked to the ticket, the link badges to GitHub pull requests, and to GitHub issues when the ticket's source is not `github`, and "Returned ×N", a pill the height and text size of the badges in the warning colour, when the ticket has N earlier work items with the same playbook that started a session (PRD R51), then the controls on the right. The third, left out when empty, holds the mark, any warning or error beside it (clipped, in full in the tooltip), the stage, followed by `…` on a Working row, and its age, an approval report's summary on an `awaiting-approval` row, and the other link badges (PRD R52). A link to the ticket's own URL is not shown, because the key already links there. The key and link badges are pills with no underline. A link badge's kind comes from its target: a GitHub pull request (`git-pull-request`, purple, labelled with the number from its URL, whatever label the session reported), a GitHub issue (rendered as a `gh <number>` key pill with the number from the URL, ignoring the reported label) or any other URL (`link`). The title is bold. The playbook name shows its namespace and colon in the description colour and the name in the foreground colour, not bold. The triage context, task prompt and session history stay in the store and are not shown.
- Time in queue is a whole number of minutes, hours, days or weeks (`40m`, `5h`, `3d`, `2w`), from the start the group gives (PRD R27, R53), with the start in the tooltip. Needs you: `WorkItem.statusAt` for an approval, block or failure, otherwise the waiting session's `stateAt`. Working: `WorkItem.runStartedAt`, else `statusAt`. Unstarted and Snoozed: `Ticket.scopeAt`. Done: `WorkItem.scopeAt` to `doneAt`, never the ticket's, which moves when the ticket returns. Without a scope entry, the work item's creation; a pool ticket without `scopeAt` shows no time. Core sets `statusAt` on every status change and `runStartedAt` when a work item enters triaging, queued, setup or running from another status, so a waiting session or a queued → setup → running sequence stays one run; `done` copies the ticket's `scopeAt`, or the work item's creation, to the work item. Migration 6 estimates the times of existing work items by status: `doneAt` and `createdAt` for done ones, `queuedAt` for queued ones, the latest session's end for blocked, failed and approval ones, and its start for running ones.
- Stage staleness (PRD R58): `staleSince` in `render.ts` marks a Working, unsnoozed row whose active session is `running` when `STALE_STAGE_MS` (20 minutes) or more has passed since the latest of `WorkItem.stageAt`, `WorkItem.runStartedAt` and the session's `stateAt`, which is when it last began running, since a `running` marker carries no detail. The stage age then takes the warning colour in a `.stale` span titled `No stage report for <age since that time>`; a row with no stage shows `No stage report · <age>` instead. Core keeps a stage across a retry or a wait, so the session's `stateAt` keeps an older stage from marking a resumed run. The age updates on each `state` event, which the hub sends at least every minute because of the `tick` timer.
- The Unstarted group holds `unstarted` and `triaging` work items and pool tickets with no open work item, of enabled sources only. The panel sorts them together by importance rank, counting an unrated one as rank 2, then oldest first by the ticket's sort time or the work item's creation; the snapshot's pool is in sort-time order. Pool tickets and work items look alike, with no claim tag. Both show Start, with Snooze and the other controls in the right-click menu; a pool ticket shows Start only once its triage has a result, and the core refuses a pick without one. A failed pool triage shows its error with Triage again (`retriage-pool`); a running one shows the Triaging mark. A triaging work item or pool ticket shows `<namespace>:triage` in the playbook slot, from the snapshot's `namespaces` (each source's `namespace` setting), or `triage` when the source has none; a triaging work item has no primary control.
- The view's title bar has a `+` button, **New Ad-hoc Session…** (`switchboard.newAdhoc`), which asks for a repo from the configured repo roots when there is more than one and a prompt, then sends `adhoc`. Before it, after a disabled separator item (extension menus have no separator in the inline group), the title bar has an on/off icon per configured GitHub, Zoho and Forum source: the GitHub mark, the Zoho Desk mark and the Acme OR mark. The extension sets the context key `switchboard.source.<name>` to `on` or `off` from each state's `sourceStates`, which picks the `switchboard.source.<name>.on` or `.off` command; a click posts the opposite state to `POST /sources`. VS Code menus are static and extension commands have no toggled state, so another source needs its own pair of commands and icons in package.json. The hub sets `sources.<name>.enabled` in settings.json, rewriting it as formatted JSON, and reloads it. A disabled source is not polled and its pool is hidden; its work items stay.
- After the `+` button, a gear button, **Open Settings** (`switchboard.openSettings`), opens the [Settings editor](#settings-editor).
- Endpoint additions for the pool: `/action` also takes `pick` and `retriage-pool` with a `ticketId`.
- Snooze (PRD R49): the row's Snooze control and `switchboard.row.snooze` carry a `snooze` action with no wake time; the extension's `dispatch` opens a quick pick built by `snoozeChoices` in `src/snooze.ts` (days at 6am local, weeks on a Monday at 6am, Indefinitely as null), then posts `{type: 'snooze', ticketId, until}` to `/action`, where `until` is epoch milliseconds or null. The hub refuses a non-numeric `until` with 400 and the core refuses one that has passed with 409. The core ends every due snooze (`snoozedUntil <= now`) at the start of each event, before applying it, and the runtime sends a `tick` every `WAKE_MS` (60 s) so a wake needs no other event. A snoozed row offers Snooze… and Restore, so a new wake time replaces the old one without waking the ticket first; Restore ends a snooze early. A poll that finds a ticket neither assigned nor in the pool clears `snoozed` and `snoozedUntil`; migration 11 clears them on tickets already out of scope. Migration 7 renames `iceboxed` to `snoozed` and adds `snoozedUntil`; an iceboxed ticket becomes an indefinite snooze.
- Activity bar badge (PRD R64): `WorkItemsView` sets `WebviewView.badge` from `needsBadge` in `src/badge.ts` on each `state` event and when VS Code resolves the view, and clears it (`undefined`) at 0. `needsCount` counts work items that are not snoozed and whose `groupOf` is `needs`, the same rule as the Needs you group. VS Code shows a view's badge on its container's activity bar icon. A webview view exists only after VS Code first shows it, so a window that has not shown the panel has no badge. The view, and its badge, stays when the operator switches to another view; VS Code disposes it only when the operator hides it from the view's menu.
- Styles use VS Code's theme variables and codicons from `@vscode/codicons`, copied into `dist/`. Scrollbars use the theme's scrollbar slider colours and show only while their area is hovered. The script runs under a nonce content security policy.

## Chrome extension

`extensions/chrome` is a Manifest V3 extension (PRD R56), built by `npm run build` into `extensions/chrome/dist`, which the operator loads unpacked from `chrome://extensions` with Developer mode on, and reloads there after a rebuild.

- The content script runs on every `https://github.com/*` page, because GitHub opens a project without a page load, and acts only while the page has `[data-board-column]` elements. The service worker reads `GET /snoozed` for it, because a content script on github.com cannot read a loopback address; the manifest's only host permission is `http://127.0.0.1:47615/*`.
- It reads the snoozed URLs when a board appears, every 60 seconds and when the tab becomes visible. A failed read counts as none snoozed.
- A card's issue is its title link (`h3[id^="board-card-title-"]` inside an `a`), compared as `owner/repo#number` in lower case. GitHub empties the content of a card out of view, a hidden one included, so the script keeps each card's issue by `data-board-card-id`; a card it has never seen rendered stays shown until it renders.
- It marks a snoozed card `data-switchboard-snoozed` and a shown column `data-switchboard-shown`, and `content.css` hides marked cards in columns that are not shown. The link is a centred button appended to the column's scrolling card list (`[data-dnd-drop-type="card"]`), so it follows the last card shown. A `MutationObserver` on child lists reapplies the marks 50 ms after GitHub renders; a pass that changes nothing makes no mutation, so the script does not trigger itself.
- Card pills (PRD R67): `src/pills.ts` reads `GET /cards` through the service worker (message type `cards`), with the same triggers as the snoozed read, and runs its own `MutationObserver`. It puts a `.switchboard-pill` span after the card header's issue reference (`[id^="board-card-header-title-"]`) of each card whose title link's issue key matches a card's `url`; GitHub issue URLs are the only ones that match. The pill's text is the playbook, its namespace in a muted span, or the group name when the playbook is null; `data-switchboard-group` is the group, or `snoozed`, and `content.css` gives `needs` GitHub's attention colours. A pass leaves an unchanged pill alone, so it makes no mutation. A failed read, including a 404 from an older hub, removes every pill. `groupOf`, `triageLabel` and the `Card` type are in `packages/core/src/group.ts`, which imports only types, so the panel webview and the Chrome extension import it as `@switchboard/core/group` without bundling the store.
- The DOM hooks are GitHub's, not a contract; `test/fixtures/column.html` records them from the public roadmap board on 2026-10-07.

## Settings editor

PRD R54. A webview editor tab, **Switchboard Settings**, one per window; the command reveals it when it is already open.

- The extension reads and writes the files itself, through `packages/hub`'s `config.ts`, not through the hub. It checks with what the hub applies on load, `parseSettings`, each source's own `parse*Config` and `parsePlaybook`, and adds `templateError` for playbook templates and `setupPrompt`, because the hub finds an unknown variable only when rendering the classifier instructions or a session prompt fails. The hub's file watchers reload what the editor writes, as they do a hand edit. The editor works without a running hub.
- The navigation lists **Sessions and triage**, each configured source with **Add** entries for the sources not configured, and the playbooks by namespace with **New playbook**. A page with unsaved changes shows a dot, and a page with errors or a refused write shows an error icon.
- Save and Revert act on the current page's file. **Save all**, beside Save and beside Create on New playbook, saves settings.json and each changed playbook; each file is written or refused on its own, and a refused file keeps its draft and shows the refusal on its page.
- The settings pages edit one draft of settings.json. A field left empty removes its key, so the default applies, and the placeholder shows that default. `automationAgentIds` is the exception: its default is not empty, so an absent key shows the default list, and an emptied list is saved as `[]`. Keys the editor has no field for are kept. A source's own errors block a save only while the source is enabled, so a disabled source can be saved incomplete. Removing a source deletes its key, and its work items stay.
- A playbook page edits the front matter and the template. A triage playbook shows only its description, its kind and its classifier instructions. A task playbook has a checkbox for each of its `reports`. Saving writes only non-default keys, except `autoStart` and `requiresWorktree` on a task playbook; front matter comments are not kept. Delete asks for confirmation in a modal, which names how many open work items use the playbook. An invalid file shows its error, with Open file and Delete.
- Each draft is checked 250 ms after the last keystroke. The extension answers with the error strings, which the webview places on the field whose path the error names. An error that names no field shows at the top of the page. A refused save, create or delete shows at the top of the page until the next edit, revert or successful write, so a later check or file refresh does not hide it.
- Each file is read with a SHA-256 version. Save sends the version the draft started from, and the extension refuses the save when the file on disk no longer matches. The extension watches settings.json and the playbook directory and sends the files again when they change; a page with no draft shows the new content. A draft whose file changed, broke or was deleted is kept, with a warning; Save then refuses, or creates a deleted playbook again. Writes go through a temporary file and a rename, like the source toggles.

## Store

- One SQLite database, `~/.switchboard/switchboard.db`, opened through Node's built-in `node:sqlite` (M1). No native module, so VS Code's Electron upgrades do not require rebuilds.
- The hub is the only process that opens the database. The extension and the `switchboard report` CLI go through the hub's HTTP server, so there is no cross-process locking.
- WAL mode; one write transaction per flow step, so a crash leaves each work item in its last committed state.
- Core accesses the database only through a store interface, which isolates changes to the `node:sqlite` API. Tests use `:memory:`.
- Schema changes are numbered migrations applied by the hub at startup, recorded in `PRAGMA user_version`.
- Not in the database: playbooks and settings, which are files the operator edits and can keep in git; session transcripts, which Claude Code stores, and which sessions find by `nativeSessionId`; and the [debrief](#friction-debriefs) state and log, which the friction-review skill reads.

## Playbooks

A playbook is a Markdown file whose body is the prompt template and whose front matter holds its settings. `support:defect` lives at `playbooks/support/defect.md` under the config folder. Switchboard has no built-in namespaces or playbooks; the playbook directory defines them.

```markdown
---
description: Zoho ticket reporting behavior that may be a defect
autoStart: false
requiresWorktree: false
permissionMode: auto
reports: done
---
Research Zoho ticket {{ticket.sourceKey}}.
{{ticket.context}}
Report progress with `{{report}} stage {{session.id}} <stage>`.
```

- Template variables: `{{ticket.source}}`, `{{ticket.sourceKey}}`, `{{ticket.ref}}`, `{{ticket.title}}`, `{{ticket.url}}`, `{{ticket.context}}`, `{{session.id}}` and `{{report}}`. `{{report}}` is the report command prefix, `node "<home>/hub.js" report`. Rendering fails on an unknown variable.
- Front matter: `description` (required), `autoStart` (default false), `requiresWorktree` (default false), `permissionMode` and `model` (defaults from `sessions` settings), `kind` (`task` by default, or `triage`), `reports` (a task playbook's comma-separated `done`, `approval`, `worktree` and `playbook`; none by default), `rates` (a triage playbook's classifier rates immediacy and severity, which its body must define; false by default), and `workdir` (`worktree` by default: the ticket's worktree when one exists, otherwise the repo root; or `repoRoot`: always the source's repo root, for playbooks whose skills belong to that repository).
- `description` tells the classifier when to choose the playbook. Adding a playbook is adding its file: the hub reloads it, and the classifier sees its description. Edit the triage playbook only for a rule that must take precedence over the descriptions.
- A triage playbook's body may use only `{{playbooks}}`, which renders the task playbooks in the source's namespace as `- name: description` lines where the instructions need them. A body without it gets the same list appended under "Choose one playbook:". Any other variable fails the triage, and the settings editor refuses to save it.
- A source's triage playbook has `kind: triage`. Its body is the classifier's system prompt. Triage playbooks are never offered to the classifier as choices.
- Each source's `namespace` setting limits the classifier's choices to that namespace's task playbooks, such as `dev` for GitHub and `support` for Zoho Desk and Forum.
- Every session prompt ends with the report contract, which opens with the line `Report to Switchboard with these commands:`, the line the Support `support-process` skill looks for: the commands the session may send, with the session ID, each with its condition and the cap on its text (PRD R23). A playbook's task session gets `stage`, `link` and the playbook's `reports`; with neither `done` nor `approval`, the contract tells it to end its turn when the work is finished, so the row lands in Needs you. Setup and approved-prompt sessions get `stage`, `worktree`, `done` and `link`, and an ad-hoc prompt gets all but `playbook`. The session row stores its reports, and the hub refuses any other report with "This session's prompt does not offer the <kind> report." and CLI exit code 3. It reports a `link` for each GitHub issue or pull request it creates or finds for the work. When the session needs the operator for a question or a choice, or cannot continue without them, it asks with `AskUserQuestion` and waits, which keeps its context live and puts the row in Needs you as `waiting`; it writes no file and sends no report for a question. When its work is ready but posting or publishing it needs the operator's approval, it reports `approval` with the prompt that would do it, such as `/review-pr pr:123 publish`, a summary of what the prompt publishes, and the file holding the drafted text, if any, and ends its turn; Approve runs the prompt in a new session with no memory of this one, so the prompt names what it acts on. The operator's skills read these commands through their `gc-session-reports` skill, which writes each as a `switchboard <kind> <arguments>` call. `{{report}}` lets a template add its own report calls.

## Triage

Triage follows Ground Control's classifier (GC R38, M31).

1. The source plugin builds the triage context: it fetches the ticket's text, clips each field at a word boundary to a size limit, and formats it with authors, status changes and assignees. Ground Control clips the issue body and each comment to 2,000 characters. The hub puts a `Current time: YYYY-MM-DD HH:MM UTC` line before the context, in the form sources use for event times, so the triage playbook can tell how recent a request is.
2. The classifier runs `claude -p --output-format json --json-schema <schema> --no-session-persistence --setting-sources "" --tools "" --strict-mcp-config --system-prompt <triage playbook with the playbook descriptions rendered in>`, with the context on stdin. Stdin avoids the Windows 32,767-character command-line limit (M31).
3. The schema is `{playbook: enum of the source namespace's task playbook names}`, plus `immediacy?: URGENT | BLOCKING | NON-BLOCKING` and `severity?: HIGH | MED | LOW` when the triage playbook has `rates: true` (PRD R50). The classifier reads `structured_output`. Without `rates`, it discards any rating the model returns; a value outside the enum is stored as empty.

Triage has no tools, settings, MCP servers or saved transcript, so it is not a session and does not count toward the one-active-session rule. The hub runs at most one triage per work item at a time, at most `triage.concurrency` at once (default 2), with a `triage.timeoutSeconds` limit (default 180).

A classifier error, an unparsable result, a timeout, or a playbook name outside the enum fails the work item with that error (PRD R37). A triage interrupted by a hub shutdown is not a failure: the work item stays `triaging`, and triage runs again when the hub starts.

## Flow

1. Poll a source. For each ticket, compare its assigned state with `Ticket.assigned`. A poll that fails or is incomplete, such as one that hits the page limit, updates nothing.
2. When a ticket enters the assigned state, create a work item (`triaging`) and run triage.
3. Store the triage result. If the playbook's `autoStart` is false, the work item is `unstarted` until the operator starts it (`start`). `awaiting-approval` is used only for an approval report, and `approve` applies only to it.
4. If the playbook's `requiresWorktree` is true and the ticket has none, start a setup session (`setup`) running the source's `setupPrompt`. The setup session succeeds when a worktree is linked, by report or by the branch convention, and the session reports done or ends. If it ends with no worktree linked, the work item fails with "Setup ended without a worktree."
5. Render the playbook and start the task session (`running`). It reports stages, a worktree link if it creates one, and done or approval.
6. When the task session reports done, the work item is done with reason `session`. When its turn ends with no report, the work item is `blocked`. A turn that ends `failed` blocks it with the error kind, because the session can still be resumed.
7. When a ticket leaves the assigned state with no active session, its work item is done with reason `unassigned` and no warning. With an active session, that is deferred until the session reports or ends (PRD R10).

Pool tickets (PRD R47, R48):

- When a poll shows a ticket newly in the pool, the core starts a pool triage for the ticket; its result or error stays on the ticket.
- A pick of a pool ticket whose triage has a result creates the work item with that playbook, attaches the pool triage, and queues it as an operator start, skipping the wait in step 3. The task session's skill claims the ticket.
- A ticket that enters the assigned state while it has an open work item gets no second work item; the claim made by the task session is seen this way.

An ad-hoc prompt creates a ticket and work item and goes straight to step 5, with the typed prompt as the task prompt and the chosen repo root as the working directory (PRD R6).

Steps 4 and 5 start a session only when no session for the ticket is active and a slot is free; otherwise the work item is `queued` (PRD R38).

## Core decisions

`packages/core` decides; the hub acts. `handle(store, event, context)` runs inside one store transaction, applies one event, and returns the actions for the hub to run, or a refusal for an operator action or report that does not apply. The context carries the clock, settings, loaded playbooks, the report command prefix and a session ID generator. The hub runs each action and sends its result back as an event, so every failure reaches the work item.

| Events | From |
|---|---|
| `poll`, `poll-failed` | A source read. `poll` lists the source's tickets from a complete read; a ticket missing from it has left the assigned state. `poll-failed` changes nothing. |
| `triage-succeeded`, `triage-failed`, `triage-cancelled` | The classifier. A cancelled triage runs again. |
| `session-started`, `session-start-failed` | The runner's `start-session`. |
| `roster`, `marker` | A successful roster read, with each listed session's state; a hook marker for a live session. |
| `report` | The report command: `stage`, `worktree`, `done`, `approval` or `link`. |
| `stop-succeeded`, `stop-failed` | The runner's `stop-session`, for an operator stop or a release. |
| `worktree-found` | The branch convention. It links a worktree only to a ticket that has none. |
| `adhoc`, `start`, `approve`, `retry`, `mark-done`, `retriage`, `stop`, `pick`, `retriage-pool`, `snooze`, `restore`, `tick` | The panel; `tick` re-runs scheduling after settings or playbooks change, and every minute wakes due snoozes. |

Actions are `triage`, `start-session` and `stop-session`. After every event the core starts triage for `triaging` work items, then pool triage for pool tickets without a result, up to `triage.concurrency` in all; then it starts `queued` work items in queue order while fewer than `sessions.concurrency` active sessions are not `waiting`, skipping a ticket that already has an active session. A task that follows a setup session starts when the setup session ends, without waiting for a slot.

## Claude Code runner

- Start: `claude --bg --permission-mode <mode> --settings '{"worktree":{"bgIsolation":"none"}}' -n <name> [--model <model>] <prompt>`, with no shell, so a leading slash command survives. The name is `switchboard · <playbook> · <source> <key>`. Claude's background service owns the process, so sessions survive VS Code and the hub. `--bg` ignores `--session-id`; the runner parses the short ID from `backgrounded · <id> · <name>` and matches it as a prefix against `claude agents --json` (GC M1, M33; mechanics M5). The start is confirmed when the roster lists it with a pid; a new entry has no pid for its first seconds. A session not listed with a pid within 60 seconds fails the start.
- Permission mode: `auto` by default. In 101 Ground Control runs to 2026-10-03, the 95 in `auto` never waited for or were refused a permission; the only permission stall was in manual mode. Questions (`AskUserQuestion`) stall in every mode and show as `waiting`. The operator answers them, so Switchboard neither disallows the tool nor keeps a Bash allowlist.
- Environment: pass `CLAUDE_CONFIG_DIR` through exactly as the hub inherited it, and never set it. Setting it, even to `~/.claude`, moves where Claude reads folder trust (GC M62). Strip `ELECTRON_*`, `VSCODE_*` and `NODE_OPTIONS`.
- Trust: `--bg` exits 1 with `Workspace not trusted` in a directory Claude has not trusted; a linked worktree inherits its main checkout's trust (GC M62). The failed start shows that message (PRD R41).
- Background sessions inherit the service's environment, not the caller's, so per-run values such as the Switchboard session ID travel in the prompt (M33).
- Liveness: poll `claude agents --json` (without `--all`) every 30 seconds for every session a start confirmed, so a session resumed after its release is seen again. The roster alone decides liveness: a session is active while the last successful roster read lists it with a pid, and `ended` once a successful read does not. An entry without a pid is a process that is gone (GC M33). A failed read changes no session. Hook markers only set the state of a live session, because a killed process leaves its last marker behind (GC M20). The roster `state` is the fallback when no hook marker exists: `working` maps to `running`, `blocked` to `waiting`, and `done` or `stopped` to `idle`.
- State: hook markers decide the observed state, following GC's mapping (GC M2, M20):
  - `UserPromptSubmit`, `PostToolBatch` and `PermissionDenied` mean `running`, as does `SessionStart` with `source=compact`.
  - `PermissionRequest`, `Elicitation`, `PreToolUse` for `AskUserQuestion` or `ExitPlanMode`, and `Notification` of type `permission_prompt`, `worker_permission_prompt` or `agent_needs_input` mean `waiting`.
  - `Stop` means `idle`, or `running` while background tasks remain.
  - `StopFailure` means `failed`, with its error kind and message.
- Hooks:
  - The hub installs async command hooks for those events plus `SessionEnd` in `<CLAUDE_CONFIG_DIR or ~/.claude>/settings.json`. It preserves other entries, refuses to edit malformed JSON, and adds missing entries at startup. The `sessions.installHooks` setting is on by default; when it is off, the roster alone decides state.
  - The hook runs `node "<home>/hook.mjs"`. It skips subagent events, always exits 0 and prints nothing, and writes `<home>/activity/<nativeSessionId>.json` atomically: `{v, sessionId, event, at, notificationType, source, toolName, backgroundTasks, error, errorMessage}`, with `errorMessage` capped at 500 characters. `SessionEnd` deletes the marker.
  - A debrief fork runs with `FRICTION_DEBRIEF=1`, and the hook writes no marker for it.
- Release: when a session's turn ends (`idle` or `failed`), run `claude stop <id>` once (PRD R39). A `waiting` session is not released, because it is mid-turn. A session whose background process has ended, by release, stop, failed start or leaving the roster, is never released again, and neither is a session the roster lists as interactive, so a session the operator resumed in a VS Code tab is never stopped by Switchboard. Before a release stop, the hub also reads the roster and skips the stop unless the session is listed as a background process. An interactive roster entry, such as a VS Code tab, has no `state`; its `status` (`idle`, `busy` or `waiting`) gives `idle`, `running` or `waiting`.
- Stop: `claude stop <id>`, 15-second timeout. A failed stop leaves the session stoppable. Never `claude rm`, which can delete the worktree.
- Attach: a VS Code terminal running `claude attach <id>`. Leaving it keeps the session running (M33, M45).
- Resume: a VS Code terminal running `claude --resume <native session ID>` in the session's directory, named `Switchboard · <source> <key>`. The window keeps the terminals it resumed sessions in and shows the open one again instead of resuming twice. A session active elsewhere, such as in a VS Code tab, opens there through Open in VS Code instead, because a second resume of a live session is refused (M7). The roster lists a resumed session as interactive, so it is never released.
- Open in VS Code: `claude-vscode.primaryEditor.open(<native session ID>)`, which resumes the session or focuses its tab. Claude's tab lists only the sessions of its window's first folder, and opening another session there starts an empty one (GC M6, M7, M52). So when the session's directory is the window's first folder, the window opens it directly. Otherwise the window posts `{sessionId, cwd}` to the hub's `POST /open` and opens that folder with `vscode.openFolder` and `forceNewWindow`, which focuses a window already on it. A window claims a pending open for its folder with `POST /claim` when it connects to the hub and whenever it gains focus, and opens it. A pending open expires after 2 minutes and lives only in the hub's memory.

## Session reports

Sessions report through the hub bundle, which posts to the hub's loopback HTTP server. The prompt carries the Switchboard session ID and the bundle's absolute path, because a background session has no Switchboard environment and `switchboard` is not on PATH.

```
node "<home>/hub.js" report stage <sessionId> <stage>
node "<home>/hub.js" report worktree <sessionId> <path>
node "<home>/hub.js" report done <sessionId>
node "<home>/hub.js" report approval <sessionId> --prompt <prompt> [--summary <text>] [--report <path>]
node "<home>/hub.js" report link <sessionId> --label <text> --target <url>
node "<home>/hub.js" report playbook <sessionId> <name>
```

- The contract asks for the approval summary; the CLI and the hub accept its omission, and `done` takes no text. The CLI resolves a relative `--report` against its working directory, and the hub refuses a report path that is not absolute.
- Git Bash rewrites an argument that starts with `/` to a path under its Windows root, so `/legacy-ship 16416` arrives as `C:/Program Files/Git/legacy-ship 16416`. When `MSYSTEM` is set, the CLI reads the root from `cygpath -m /` and restores an approval prompt that starts with it (mechanics M20).
- The CLI's home is the directory that holds the `hub.js` it runs from, so a session started by a hub with `--home` reports to that home.
- The CLI finds the hub through `hub.json` and never starts one. Timeout: 10 seconds. Repeating a report is safe, because each report sets a value.
- When no hub answers, the CLI exits 2 and prints that the hub is not running. The hub stays up while sessions are active, so this is rare; the work item then ends `blocked`, and the operator marks it done.
- Exit codes: 0 recorded, 2 no hub, 1 usage, 3 refused (unknown session, or a path that `git worktree list` run in that path does not show as a worktree). A worktree can belong to a different repository than the source's repo root, as when a Support session in `D:\git\support` reports an widgets worktree.
- Before applying a task session's `done`, the hub polls the ticket's source and applies that poll. When the poll still lists the ticket as assigned, the hub sends the report with `assigned: true` and the flow blocks the work item with "The session reported done, but the ticket is still assigned to you." The CLI still exits 0. A failed poll, a poll that takes over 6 seconds (`DONE_CHECK_MS`, inside the CLI's 10-second timeout), a setup session, or an ad-hoc ticket skips the check (PRD R10). Reads of one source run one at a time, so a scheduled poll that started earlier cannot apply after the check's poll; a scheduled poll is skipped while a read is in flight.
- A report for a work item that is already done does not reopen it: `done` sets the session's outcome, `worktree` links the ticket's worktree, `link` adds the ticket's link, and `stage`, `approval` and `playbook` are ignored.
- `playbook` names a task playbook in the work item's namespace; the hub refuses any other with "<name> is not a task playbook in the <namespace> namespace." It sets the work item's playbook only, so the session keeps the reports its prompt offered and a later Retry or Start renders the new playbook.
- `link` takes an http(s) URL; the CLI and the hub refuse any other target with exit 1. Migration 8 deleted the local-file links of earlier sessions, after copying an open approval's newest one to its `approvalReport`. A link to a target the ticket already has replaces its label.

## Friction debriefs

PRD R55, ported from Ground Control's debrief runner (GC M64). Off unless `sessions.debriefs` is true.

- **Files:** under the Claude root, `CLAUDE_CONFIG_DIR` or `~/.claude`: the prompt `skills/friction-review/prompt.md`, and `.wip/debrief/state.json` and `.wip/debrief/log/YYYY-MM.jsonl`. They are the files Ground Control wrote, in the same format, so Ground Control's record of what it asked still holds, and the friction-review skill reads both runners' lines. Ground Control's `codex` entries that wait for a debrief stay as they are. A session's entry has one writer, the hub that started the session; Ground Control's runner must not run beside it.
- **Candidates:** every minute, the started sessions in the store with provider `claude`, a native session ID, state `idle`, `failed` or `ended`, and no end more than an hour ago. The session's transcript, `<Claude root>/projects/<slug of cwd>/<nativeSessionId>.jsonl`, gives its last turn by its write time. A session is due as soon as its work item is done, otherwise 45 minutes after its last turn, and is skipped from 60 minutes after that turn. It also needs at least 10 main-transcript tool calls after the last debriefed message, in a range whose debrief has not failed. The due session with the oldest transcript goes first, one fork at a time.
- **Roster:** before each fork the hub reads the state and `claude agents --json`, skips a session listed with a pid that is not idle, and checks the setting and the 60-minute limit again. An idle background session and a stopped one can be forked (mechanics M19).
- **Fork:** `claude -p --resume <nativeSessionId> --fork-session --session-id <new uuid> --no-session-persistence --output-format json` in the session's `cwd`, the prompt on stdin, `FRICTION_DEBRIEF=1`, a 10-minute timeout. No model, effort, tool or MCP flag, because each changes the prompt prefix and loses the cache. `{{scope}}` is the whole conversation, or the work after the first message after the last debriefed one, named by its first 200 characters. `{{subagents}}` lists the subagents written within 55 minutes whose type can be resumed (not `codex`, `Explore` or `Plan`), with new messages since their last debrief; their transcripts are copied to `<project>/<forkId>/subagents/` for the run, because a fork looks for them under its own ID, and removed after it.
- **Codex threads:** a session's fork, whether it succeeded or failed, marks `pending` in the state each thread that an `mcp__agent-delegate__*` result names in the range, in the main transcript or a subagent's transcript written after the range starts, and every pending thread is then asked once, at the next scan when the hub stopped or a write was held, through agent-delegate's command: `<node> <Claude root>/tools/agent-delegate/debrief.mjs <thread> --prompt <prompt> [--since <its last debrief>]`, with the hub's own executable, `ELECTRON_RUN_AS_NODE=1` and `FRICTION_DEBRIEF=1`, and a 10-minute timeout. Exit 0 with the friction JSON appends a `codex` log line with the session as `parentSessionId`; exit 3, a thread with no turn since, records nothing new; anything else is reported in the hub log and the state's `lastError`, and not retried. A missing command skips the threads.
- **Answer:** the last `result` event whose text, without a code fence, is `{"friction": [...]}` or a bare array, each item with non-empty `what`, `source`, `workaround`, `cost` and `evidence`. The last `result` event gives the cache use and cost.
- **Record:** a success appends a log line (`v`, `at`, `provider`, `sessionId`, `parentSessionId`, `cwd`, `fromMessageUuid`, `throughMessageUuid`, `skills`, `toolCalls`, `cache`, `friction`, `startedAt`, `subagents`, `delegated`), on a fresh line when the file ends inside one, then merges into the state as it is on disk, so another writer's entries are kept: the last message covered, and the fork's start as each shown subagent's last debrief. A failure, including a fork that throws, records the range and its error in the state and the hub log, and is not retried; the next debrief covers that range with any later work. A write that fails is held, and no fork starts until a later scan writes it. A hub that stops between the two writes asks about that range again.
