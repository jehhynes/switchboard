# Switchboard architecture

Requirements live in [prd.md](prd.md). This document describes components, state and protocols. Implemented: the hub lifecycle, the core's store, settings, playbooks and [flow decisions](#core-decisions), the GitHub source, the Claude Code runner and classifier, the hub runtime, the report command, the Zoho Desk and Forum sources, the pool with picks, shown with unstarted work items in the Unstarted group, the [dock](#dock) with its [Settings window](#settings-window), and the [VS Code extension](#vs-code-extension) that serves each item window.

Session and triage mechanics come from Ground Control (`D:\git\ground-control`), where they are verified. M IDs below refer to its [mechanics.md](../../ground-control/docs/mechanics.md). Re-verify them in Switchboard's own mechanics.md before relying on a version-fragile one.

## Packages

The application icon is a patch panel with four thick socket rings and a bold bright cyan connection, on a rose-to-plum gradient tile that stays visible against a dark taskbar, with transparency outside its rounded tile. `extensions/switchboard/assets/icon.png` supplies the VS Code extension listing at 256 pixels. The dock executable, main window and Settings window use `apps/dock/src/Switchboard.Dock/Assets/dock.ico`, containing 16, 20, 24, 32, 40, 48, 64, 128 and 256 pixel versions of that artwork. Chrome's extension icon uses 16, 32, 48 and 128 pixel PNGs in `extensions/chrome/assets`, copied into its unpacked build.

History tabs use light and dark monochrome SVGs of the patch panel; the status bar uses the `switchboard-logo` product icon from `assets/switchboard.woff`. Their vector source is `extensions/switchboard/assets/mark.svg`. Run `python tools/build-icon-font.py` with `fonttools` installed to regenerate the font, the History SVGs and a simplified colour vector variant `apps/dock/src/Switchboard.Dock/Assets/dock.svg`. For future raster exports, use `extensions/switchboard/assets/icon.png`: resize it with bicubic interpolation and preserve alpha for each listed Chrome PNG size and each PNG frame in the dock ICO. The vector generator does not rewrite these raster files.

npm workspaces, TypeScript strict, Node ≥ 22.13, Vitest, esbuild and vsce, following Ground Control's layout. Only `extensions/switchboard` imports `vscode`. Implemented so far: `packages/core`, `packages/github`, `packages/zoho`, `packages/forum`, `packages/claude`, `packages/hub`, `apps/hub`, `apps/dock`, `extensions/switchboard` and `extensions/chrome`. `apps/dock` is C# on .NET 10 with Avalonia 12; its workspace scripts run `dotnet build` and `dotnet test`, so `npm run verify` covers it.

| Package | Contents | Depends on |
|---|---|---|
| `packages/core` | Domain types, source and runner interfaces, store, playbook loader and renderer, flow rules | — |
| `packages/claude` | Claude Code runner, classifier and debrief fork | core |

| `apps/hub` | Hub entry point and the `switchboard report` CLI, bundled as one file | hub |
| `apps/dock` | The dock: a Windows app that lists the work beside VS Code, switches to each work item's window, and edits the settings ([Dock](#dock), [Settings window](#settings-window)) | the hub's dock stream and config routes |
| `extensions/switchboard` | Hub process lifecycle, claimed sessions and the dock's commands in each item window, worktree changes, ticket history, notifications of work on the operator's turn, Open in Switchboard, the status bar item ([VS Code extension](#vs-code-extension)) | core, hub client |

The ad-hoc source is local and lives in `packages/hub`. State, the hub bundle, its record and its log live in the Switchboard home, `~/.switchboard`. Settings and playbooks live in the config folder, so the operator can keep them in a git repository. The config folder is the VS Code setting `switchboard.configDir` (machine scope): an absolute path, or one starting with `~` for the user profile. When the setting is empty, it is the Switchboard home. For a relative path, the extension shows an error and uses the Switchboard home. Each window reads the setting on every hub start, so all windows agree on one hub. When the setting changes, a window whose hub reads another folder stops it; every window then reconnects to one hub started on the new folder, and the keeper does not count that stop as a failure.

## Components

| Component | Responsibility |
|---|---|
| Hub | Separate Node process that runs the core: polls sources, creates work items, runs triage, starts setup and task sessions, enforces one session in a turn per ticket (PRD R17), serves the windows, the dock and the report command. |
| Source plugins | Supply tickets, decide whether each is in the assigned state, and build each ticket's triage context: GitHub, Zoho Desk, Forum, ad-hoc. |
| Playbook loader | Reads playbook files and renders their templates. |
| Classifier | Runs one-shot triage and returns structured output. |
| Runner | Starts, stops and tracks agent sessions for one provider. Claude Code first. |
| Worktree linker | Links worktrees to tickets from session reports, falling back to branch-name convention. |
| Store | Local SQLite database holding tickets, work items, triage results, sessions and worktrees. |
| VS Code extension | Starts the hub, opens claimed sessions in the item window's Claude view, runs the dock's commands, opens a worktree's changes, shows a ticket's history and notifications of work on the operator's turn, and shows the dock from its status bar item. |
| Dock | Lists the work items beside VS Code, switches to each item window, runs the controls, and edits the settings. |

## Data model

```
Ticket     id, source, sourceKey, ref, sourceId, title, url, assigned, pool, snoozed, snoozedUntil, sortAt, scopeAt, lastPolledAt, repoRoot
WorkItem   id, ticketId, playbook, status, stage, stageAt, taskPrompt, warning, error, unassignedAt, queuedAt, createdAt, statusAt, runStartedAt, readyAt, orderAt, scopeAt, doneAt, doneReason, approvalPrompt, approvalSummary, approvalReport, approvalHeld, parentId
Triage     id, ticketId, workItemId, context, playbook, immediacy, severity, model, startedAt, endedAt, error
Worktree   id, ticketId, path, branch, linkedBy (report | convention)
Link       id, ticketId, label, target, reportedAt
Paste      id, workItemId, label, file, reportedAt
Session    id, workItemId, kind (setup | task), provider, nativeSessionId, shortId, cwd, state, stateAt, stateDetail, outcome, outcomeDetail, startedAt, endedAt, released
```

- `Ticket.assigned` is the assigned state the last complete poll saw, and `Ticket.pool` whether it saw the ticket in the pool. `Ticket.ref` is the reference people use, set by the source when it builds the ticket: `#<n>` for GitHub and ad-hoc, `#<ticket number>` for Zoho, `T<topic id>` for Forum; core holds no per-source rule. `Ticket.sortAt` is the source's sort time, which orders the Unstarted group: Zoho's `customerResponseTime`, Forum's last public post, and for GitHub the later of the operator's latest assignment and the Status field's `updatedAt`. `Ticket.scopeAt` is when the ticket last entered the source's scope (PRD R53). Each polled ticket carries the source's `enteredAt`, or null, and core stores the source's time whenever it has one, because a source's scope can be wider than the assigned state and the pool: a GitHub issue on another status, or a Zoho ticket another engineer holds. Without one, the ticket keeps the time it has, or takes the poll's time when it has none and is assigned or in the pool. Ad-hoc tickets enter scope when created. A pool triage has a `ticketId` and no `workItemId` until a pick creates the work item and attaches it. `Ticket.repoRoot` is the repo an ad-hoc prompt chose; it is empty for other sources, which use their `repoRoot` setting.
- `Ticket.sourceKey` is the key people use, such as a GitHub issue number or a Zoho ticket number. `Ticket.sourceId` is the source's internal ID when API calls need a different one, such as Zoho's internal ticket ID.
- `Triage.context` is the clipped text the classifier received, with the current time. Keeping it shows why a playbook was chosen.
- `WorkItem.status` takes the values in PRD R34. `WorkItem.error` holds the cause shown for `failed` or `blocked`.
- `WorkItem.readyAt` is when the work item first became `awaiting-approval` or `finished`, set by the flow's `setStatus`; nothing else changes it, and Triage again clears it with `orderAt`. A new work item, a returned ticket's included, starts with both null. `WorkItem.orderAt` is the operator's position in Ready for review (PRD R73), or null. Migration 20 adds both, turns `blocked` work items whose error is "The session finished its turn." or "The session ended." into `finished` with no error, and sets `readyAt` to `statusAt` on `awaiting-approval` and `finished` work items.
- `WorkItem.unassignedAt` records that the ticket left the assigned state while a session or the triage of a sessionless work item was running (PRD R10). `WorkItem.queuedAt` orders queued starts.
- `WorkItem.taskPrompt` is the rendered prompt the task session ran, or the typed prompt for an ad-hoc work item.
- `WorkItem.doneReason` is `session`, `operator` or `unassigned`.
- `WorkItem.parentId` is the work item whose session sent the `task` report that created this one (PRD R68), or null. Migration 15 adds it.
- Migration 16 rebuilds `workItems` with `AUTOINCREMENT` IDs and deletes the work items done as `unassigned` that never had a session and have no child work item (PRD R10). Migrations run with foreign keys off, because a table rebuild drops a parent table, and each fails unless `PRAGMA foreign_key_check` is empty before it commits.
- `WorkItem.warning` is set when the work item ends because its ticket left the assigned state with no done report (PRD R10, R11).
- `Session.state` is the observed state, `Session.stateDetail` the error kind of a `failed` turn, and `Session.outcome` the reported or decided outcome (PRD R36). `Session.released` records that the release stop was sent, so it is sent once (PRD R39).
- A session's `cwd` follows its playbook's `workdir`: the ticket's worktree when one exists, otherwise the source's repo root.
- `Paste` is a drafted text a session named for the operator to copy (PRD R60). It belongs to the work item, not the ticket, because a returned ticket's new work item drafts new texts; `(workItemId, label)` is unique, so a later paste with the same label replaces the file and keeps its place. Migration 14 adds the table.

## Hub lifecycle

Implemented. Follows Ground Control's hub (GC R35, M25).

- **Start:** extension activation copies `dist/hub.js` to `~/.switchboard/hub.js` when it differs. It accepts a running hub only when the hub's `build`, a hash of its bundle, matches the bundle installed at that moment, and its `configDir` matches the window's config folder. It asks any other hub to stop and starts a new one only after the old one has gone; if the old hub refuses, the window reports it. Otherwise it starts one detached with VS Code's executable and `ELECTRON_RUN_AS_NODE=1`, with `ELECTRON_*`, `VSCODE_*` and `NODE_OPTIONS` removed from its environment. Output goes to `~/.switchboard/hub.log`.
- **Record:** the hub listens on `127.0.0.1` on an ephemeral port and writes `~/.switchboard/hub.json` with `protocol`, `version`, `build`, `configDir`, `port`, `token`, `pid` and `startedAt`. A record without `configDir`, from an older hub, reads as an empty one, so a window replaces that hub. The hub holds a lock for its lifetime: a named pipe `\\.\pipe\switchboard-<hash of home>` on Windows, `~/.switchboard/hub.sock` elsewhere. Only the lock holder writes or removes the record, so concurrent starts leave one hub, and the OS releases the pipe when the hub dies. A hub that cannot take the lock waits up to 5 seconds for the holder's record and otherwise exits. A forced exit on Windows leaves the record behind, so clients accept it only when `GET /status` with the token returns the recorded pid.
- **Endpoints:** `GET /hub` returns identity without a token. `GET /status`, `GET /events`, `GET /dock/events`, `POST /window`, `POST /window/withdraw`, `POST /dock/show`, `POST /config/read`, `POST /config/check`, `POST /config/save`, `POST /config/delete`, `POST /shutdown`, `POST /report`, `POST /action`, `POST /open`, `POST /claim` and `POST /history` require `Authorization: Bearer <token>`. `/events` sends a `state` event with the whole snapshot when it opens and after every change, and `claim` when something is left for a window ([VS Code extension](#vs-code-extension)), and `/dock/events` a `dock` event with the [dock view](#dock) the same way, plus `show` when `POST /dock/show` asks for the dock's list (409 when no dock stream is open) and `config` after the hub reloads the settings or playbooks. The `/config/*` routes serve the [Settings window](#settings-window). `/action` takes an operator event (`adhoc`, `start`, `approve`, `mark-done`, `retriage`, `stop`, `answer` with `{workItemId, nativeSessionId, question, answer}`, `open-question` with `{workItemId, nativeSessionId}`, `move` with `{workItemId, after}`, where `after` is a work item ID or null, `reset-position` with `{workItemId}`) and answers 409 with the core's refusal; for `answer`, `open-question` and `move` it keeps only those fields. The hub sends an `answer` only while the job state holds one question and it is the `question` the row showed, and once per question: it refuses another answer until the job state file changes, or until the reply fails. It logs those refusals as the core logs its own. `/history` takes `{ticketId, revision?}` (PRD R59).
- **Clients:** each window holds one `/events` stream, and the dock one `/dock/events` stream; either counts as a client. The hub exits 30 minutes after its last stream closes, but not while any session is active or a debrief runs (PRD R43, R55). A stream that sends no response headers within 5 seconds counts as refused. When a stream ends, the window finds or starts a hub and reconnects. It gives up and shows an error after three consecutive failures; a connection that lasts under 10 seconds counts as a failure.
- **Browser endpoint:** for the Chrome extension, which cannot read `hub.json`, the hub also listens on the fixed port `127.0.0.1:47615` (`BROWSER_PORT` in core). It serves, without a token, `GET /snoozed`: `{"urls": [...]}`, the URLs of tickets snoozed now, from every source; and `GET /cards` (PRD R67): `{"cards": [{url, playbook, group, snoozed, links}]}`, one per ticket URL, built from the snapshot by `cardsOf` in `packages/hub/src/cards.ts`. A card covers each work item and pool ticket of a polled source with a URL that the dock lists, so an unsnoozed done work item only for the dock's 7 days and a snoozed ticket while Snoozed lists it, because a card for a row the dock does not show could not open it; `url` is the ticket's URL as stored, `playbook` the name the dock shows (`<namespace>:triage` during triage, null before triage chooses one), `group` the dock's group (`blocked`, `review`, `progress`, `unstarted` or `done`, from `groupOf`; a pool ticket is `unstarted`), `snoozed` the ticket's flag, and `links` the targets of the ticket's links (PRD R52, R69), from `WorkItemView.links` or `PoolView.links`. A ticket with several work items gives the pool entry, otherwise the open work item, otherwise the latest one. `/snoozed` stays, because the Chrome extension is loaded separately and can be older than the hub. It also takes `POST /snooze {url, until}`, where `until` is epoch milliseconds or null, finds the assigned or pool ticket whose URL matches, ignoring case, and sends the core's `snooze` event (PRD R66): 200 `{done: true}`, 404 when no ticket in scope has the URL, 409 with the core's refusal for a past time, 400 for another body or one over 16 KB. `POST /unsnooze {url}` finds the ticket the same way and sends the core's `restore` event, with the same answers. Both POST routes answer 403 to an `Origin` that does not start with `chrome-extension://` and 415 to a content type other than `application/json`, before reading the body. A web page's JSON request needs a CORS preflight, which fails because the endpoint sends no CORS headers, and a `no-cors` request goes out as `text/plain`, so only an extension with host permission for the port can snooze or unsnooze; any such extension can, because an unpacked extension's ID depends on its folder ([mechanics.md](mechanics.md) M23). The routes send no CORS headers, so web pages cannot read them, and answers 403 to a `Host` other than `127.0.0.1:<port>` or `localhost:<port>`, against DNS rebinding. A hub that cannot take the port, such as a second hub for another home, logs it and runs without the endpoint.
- **Entry point:** `hub.js [--home=<dir>] [--config=<dir>] [--idle-ms=<ms>] [--browser-port=<port>]` serves, reading settings and playbooks from `--config`, or from the Switchboard home without it; `--browser-port=0` serves no browser endpoint, as in the spawn tests; `hub.js --stop` stops the running hub; `hub.js report …` sends a session report.
- **Runtime:** the hub opens the store, loads settings and playbooks and reloads them on change, polls each enabled source every `pollIntervalSeconds`, then reads `git worktree list` in its repo root for the branch convention. Entries that git marks `prunable`, such as one whose directory was deleted, are left out of both the convention and report validation. While any session has started, it reads the roster every 30 seconds and hook markers every 5 seconds. Before a roster read or a release stop can end a setup session, it reads the convention again, so an unreported worktree still counts.
- **Startup:** the hub installs hooks when `sessions.installHooks` is on, runs again any triage it abandoned, fails any session still `starting` with "The hub stopped while the session was starting.", and reads the roster (PRD R43).
- **Home override:** when `SWITCHBOARD_HOME` is set in VS Code's environment, the extension passes it to the hub as `--home`. Both the variable and `--home` name the directory that holds `.switchboard`, in place of the user home, so the Switchboard home is `<override>/.switchboard`. The extension then ignores `switchboard.configDir`, so the config folder is `<override>/.switchboard` too. It does not change the user profile that Claude and `gh` see. Live acceptance depends on it.

## Rows

- The row rules, the groups and their order, each row's controls, click, time, priority and texts, live in `packages/hub/src/rows.ts`, which imports only types and browser-safe core modules, so the History webview bundles it as `@switchboard/hub/rows`; `dockView` in `dock.ts` turns them into the texts the [dock](#dock) draws.
- Groups follow PRD R27, in the order Ready for review (`review`), Blocked on you (`blocked`, only when it has rows), In progress (`progress`), Unstarted, Snoozed, Done (`dockView` orders them; `listGroups` builds them). `groupOf` in `packages/core/src/group.ts` checks Done, then Unstarted (`unstarted`, `triaging`), then Blocked on you (`blocked`, `failed`, or a `waiting` active session), then Ready for review (`readyAt` set, `queued` included), then Unstarted for `queued`, else In progress. Blocked on you, Ready for review, In progress and Unstarted start open; Done and Snoozed start closed. An empty Ready for review says "Nothing is ready for review.", an empty In progress "Nothing is in progress."
- `listGroups` orders Blocked on you by `clockOf`'s start, oldest wait first; Ready for review by `reviewOrder` in `group.ts`, `orderAt ?? readyAt` then ID, which the flow's `move` also uses; In progress by `clockOf`'s start, `runStartedAt`; each then by ID.
- `turnOf` in `group.ts` gives `operator` in Blocked on you and for an `awaiting-approval` or `finished` work item in Ready for review or In progress, `agent` for the other work items there, and null in Unstarted and Done. `needsYou` is an unsnoozed work item on the operator's turn; the status bar counts it and the notifications follow it. `stripeOf` gives an unsnoozed row on the operator's turn `error` (failed), `warning` (blocked or a question) or `turn` (Ready for review), and null on the agent's turn and elsewhere.
- The main control (`mainControl`) is: Open in Claude on a row whose active session waits in its background process (PRD R70), even when it is `awaiting-approval`; Start on an Unstarted row (`start` for a work item, `pick` for a pool ticket), Approve on an `awaiting-approval` row, Triage again on a `failed` row that offers it, or Triage again on a pool row whose triage failed; a `blocked` or `finished` row has none, because a click opens its session, and neither does an In progress or Done row. A pool row has no main control while its triage runs. `controlsOf` lists every control that applies: Start, Approve, Copy, Open in Claude, Stop on a session in its background process, Triage again, Mark done, Snooze and Restore, Open Changes on a row with a worktree, and History; `poolControls` a pool row's. `dockView` adds `moveControls` to a Ready for review row (PRD R73): Move to top (`move` after null) and Move up (after the row two above, or null) except on the first row, Move down (after the next row) except on the last, and Reset position (`reset-position`) when `orderAt` is set. Hub controls carry the action the dock posts to `POST /action`; Copy, Open Changes and History carry the message their handler reads.
- The row mark shows what differs within the group, with its meaning in the tooltip (PRD R27). Blocked on you: answer a question (`question`, for a waiting session), blocked, failed. Ready for review, on the operator's turn: an approval report, as `send` (Approve to send) when the playbook has `approvalSends: true` and `review` (Review, then approve) otherwise, including a work item whose playbook is gone or an ad-hoc prompt, or `finished` (Review the finished turn, an eye); on the agent's turn: setting up, running (spins), queued. In progress: setting up, running (spins). Done: finished by the session, marked done by the operator, left the assigned state. Unstarted: no mark, except Triaging (spins) on a work item or pool ticket being triaged and Queued on a `queued` work item. `markOf` in `group.ts` decides it, and `MARK_GLYPHS` gives each mark's codicon, which the dock and the Chrome pills draw. A queued row's line 3 follows the mark with one text per entry of `WorkItemView.waits`, which the hub fills from `queueWaits` in `packages/core/src/queue.ts`, the check the scheduler uses before it starts a queued work item: `slot` (held slots, from `heldSlots`, at `sessions.concurrency`), `session` (a live session of the ticket, this work item's own or another's), and `snoozed`. A snoozed row keeps the mark of the group it returns to, and its line 3 shows the wake time (`Wakes Mon, Oct 12, 6:00 AM`) unless the snooze is indefinite.
- The priority dot is shown only on a priority ticket, in every group, with the immediacy and severity in its tooltip (PRD R50).
- Line 2 holds the playbook, the key and "Returned ×N" when the ticket has N earlier work items with the same playbook that started a session (PRD R51). Line 3 holds the mark, the wait reasons or wake time, any warning or error (clipped, in full in the tooltip), `From <key>` on a work item a `task` report created (PRD R68), and the stage and its age. While the session waits on a known question, the question replaces the stage (PRD R70). Otherwise, on an `awaiting-approval` row with a summary, the summary, its first letter capitalised and cut at its cap, and ` · ` with the age since `statusAt` replace the stage; the tooltip holds the whole summary and `Last stage: <stage>` when there is a stage. The triage context, task prompt and session history stay in the store; History shows the session history.
- Questions (PRD R70): `WorkItemView.question` is `{text, options: [{label, description}], parts}` or null. The hub fills it only while the active session is `waiting`, has a short ID and is not released, from `readJobQuestion`: `text` and `options` are the first question's, `parts` the number of questions. It keeps each read by short ID until the job state file's modification time changes, and sends the snapshot again `QUESTION_READ_MS` (1 second) after a background session starts waiting, because Claude can write the job state after the waiting marker. When `parts` is 1, each option is an `answer` action `{type: 'answer', workItemId, nativeSessionId, question: <text>, answer: <label>}`.
- Time in queue is a whole number of minutes, hours, days or weeks (`40m`, `5h`, `3d`, `2w`), from the start the group gives (PRD R27, R53), with the start in the tooltip. Blocked on you: `WorkItem.statusAt` for a block or failure, otherwise the waiting session's `stateAt`. Ready for review: `WorkItem.readyAt` (`Ready since`); line 3 keeps the approval summary's age since `statusAt` or the stage's age. In progress: `WorkItem.runStartedAt`, else `statusAt` (`Working since`). Unstarted and Snoozed: `Ticket.scopeAt`. Done: `WorkItem.scopeAt` to `doneAt`, never the ticket's, which moves when the ticket returns; the row shows the done time (`doneStamp`). Without a scope entry, the work item's creation; a pool ticket without `scopeAt` shows no time. Core sets `statusAt` on every status change and `runStartedAt` when a work item enters setup or running from another status, so a waiting session or a setup → running sequence stays one run and time spent queued is not counted; `done` copies the ticket's `scopeAt`, or the work item's creation, to the work item. Migration 6 estimates the times of existing work items by status: `doneAt` and `createdAt` for done ones, `queuedAt` for queued ones, the latest session's end for blocked, failed and approval ones, and its start for running ones.
- Stage staleness (PRD R58): `staleSince` marks an unsnoozed row whose work item holds a slot (`holdsSlot`: `setup` or `running`, not waiting on a question), in Ready for review or In progress, and whose active session is `running`, when `STALE_STAGE_MS` (20 minutes) or more has passed since the latest of `WorkItem.stageAt`, `WorkItem.runStartedAt` and the session's `stateAt`, which is when it last began running, since a `running` marker carries no detail. The stage age then takes the warning tone with the title `No stage report for <age since that time>`; a row with no stage shows `No stage report · <age>` instead. Core keeps a stage across a new session or a wait, so the session's `stateAt` keeps an older stage from marking a resumed run. The age updates on each view, which the hub sends at least every minute because of the `tick` timer.
- The Unstarted group holds `unstarted` and `triaging` work items, `queued` work items without `readyAt` whose live session does not wait on the operator, and pool tickets with no open work item, of enabled sources only, sorted together by importance rank, counting an unrated one as rank 2, then oldest first by the ticket's sort time or the work item's creation; the snapshot's pool is in sort-time order. A pool ticket shows Start only once its triage has a result, and the core refuses a pick without one. A failed pool triage shows its error with Triage again (`retriage-pool`). A triaging work item or pool ticket shows `<namespace>:triage` in the playbook slot, from the snapshot's `namespaces` (each source's `namespace` setting), or `triage` when the source has none; a triaging or queued work item has no main control.
- Endpoint additions for the pool: `/action` also takes `pick` and `retriage-pool` with a `ticketId`.
- Snooze (PRD R49): the Snooze control carries a `snooze` action with no wake time; the dock offers the view's `snooze` choices, built by `snoozeChoices` in `packages/core/src/snooze.ts`, which the Chrome extension also uses (days at 6am local, weeks on a Monday at 6am, Indefinitely as null), and posts `{type: 'snooze', ticketId, until}` to `/action`, where `until` is epoch milliseconds or null. The hub refuses a non-numeric `until` with 400 and the core refuses one that has passed with 409. The core ends every due snooze (`snoozedUntil <= now`) at the start of each event, before applying it, and the runtime sends a `tick` every `WAKE_MS` (60 s) so a wake needs no other event. A snoozed row offers Snooze and Restore, so a new wake time replaces the old one without waking the ticket first; Restore ends a snooze early. A poll that finds a ticket neither assigned nor in the pool clears `snoozed` and `snoozedUntil`; migration 11 clears them on tickets already out of scope. Migration 7 renames `iceboxed` to `snoozed` and adds `snoozedUntil`; an iceboxed ticket becomes an indefinite snooze.
- Source toggles (PRD R3): `POST /sources {name, enabled}` sets `sources.<name>.enabled` in settings.json, rewriting it as formatted JSON, and the hub reloads it. A disabled source is not polled and its pool is hidden; its work items stay.

## VS Code extension

The extension makes each VS Code window an item window's helper; it has no view of its own (PRD R71).

- **Claims.** On `hello`, whenever the window gains focus, and on a `claim` event naming its workspace file (`claimIsFor` in `src/claims.ts`) it posts `POST /claim` ([Open in VS Code](#claude-code-runner)) and runs the dock's commands for the window with `runCommand`: `openTabs` first, then it opens the claimed session, so a session in an editor tab is in front, then `changes` (Open Changes), `history` (History) and `openUrl` (a Markdown report or file in the Markdown preview, another file in an editor, a URL in the browser). `openLink` checks that a Markdown file exists, then opens it with `vscode.openWith(uri, 'vscode.markdown.preview.editor', {preview: false})`, the Markdown extension's preview editor: one tab per file, which Toggle Preview (`markdown.togglePreview`) turns into the text editor in place, so editing the draft adds no second tab (mechanics M27). The hub logs each window command left, withdrawn and claimed. When `POST /window` or `POST /open` names a workspace file, the hub sends `claim {workspace}` on every `/events` stream, because VS Code reports no focus change to a window the dock brings forward when it is already open (observed 2026-10-09: Open report's commands waited unclaimed until `code <workspace>` focused the window); a command for any window is not announced.
- **Item window tabs** (PRD R72): `ItemTabs` in `src/tabs.ts` holds this window's workspace file, null in a folder window, which opens nothing. `windowTabs(snapshot, file, windows)` in `packages/hub/src/dock.ts` lists the tabs of every work item whose `windowOf` file is that file, each once: `urls`, the ticket URLs, then the http(s) links that are not pull requests, then the pull request links (`linkKind` `pr`), and `reports`, the `approvalReport` of each `awaiting-approval` work item. `ItemTabs` keeps every URL it has seen and the reports of the last state: the first `state` after activation only records them, and each later one opens a URL not seen before and a report not in the previous state, so a report whose work item leaves `awaiting-approval` and returns opens again, and a URL whose work items leave the snapshot does not; `openTabs` waits up to 15 seconds for a state and opens all of them. `openTab` in `src/open.ts` opens a URL with `workbench.action.browser.open {url, reuseUrlFilter: url}`, VS Code's integrated browser, which reuses a browser tab already on that URL and opens it pinned, and fails with the URL when the command fails; the Simple Browser is not a fallback, because it shows one page at a time. It opens a Markdown file as `openLink` does, in the Markdown preview editor, pinned, and another file with `showTextDocument` and `preview: false`. The command IDs come from VS Code 1.141.0's workbench bundle and are not a public API.
- **Open Changes** (PRD R57): `src/git.ts` runs `git.openRepository` with the path, checks that the Git API's repository root is that path, because VS Code can answer with another repository (mechanics M21), awaits `repository.status()`, finds the merge base with `getMergeBase` (never `getBranchBase`, which writes to the git config), reads `diffBetween(base, 'HEAD')`, the index group, and the merge, working-tree and untracked groups, and passes the three lists to `changesPlan` in `src/changes.ts`. `changesPlan` follows each file through the stages to one row, sorts by path and caps at 400 rows, saying so in the title. A rename onto a deleted file's path takes that file's base when the renamed file has none, and otherwise the deletion keeps its own row. `_workbench.openMultiDiffEditor` opens the rows with `git:` URIs at the base and `file:` URIs on disk. VS Code reuses an open editor with the same source URI without updating its rows, so the extension first closes the tabs whose label starts with the ticket key, which outlasts a title change, and whose input has `textDiffs`, even when there are no changes now, then opens with the source URI `switchboard-changes:/<key>/<time>`. A conflict counts as a modification, including a modify/delete conflict, which leaves the modified file on disk.
- **History** (PRD R59): `src/historyPanel.ts` opens a `switchboard.history` webview tab per ticket, titled `<key> History`, or reveals the open one. The page (`src/webview/historyMain.ts`, `history.css`) posts `ready` when its script runs and `{type: 'shown', revision}` after rendering a history, and the extension then posts `{ticketId}` to the hub's `POST /history`, which answers with `Store.ticketHistory`: the ticket, its work items newest first with their sessions, triages and pastes (no task or approval prompt), its pool triages, worktree and links, its activity events oldest first with their changes to this ticket's rows, `recordedSince` and `revision`; or 409 `Unknown ticket <id>.`, shown as a warning, which closes a tab that showed nothing. Later reads send the `revision` the tab shows, and the hub answers `{unchanged: true}` when it is current, without building the history. Every stream `state` makes a visible tab read again at most once a second and marks a hidden one stale, which reads when shown again. A read that fails shows its error on a page with nothing yet and is read again from the hub whose stream sends `hello`, because the keeper names that hub as current only after the hello. The page stores the ticket, key and the operator's filters and open sections with `setState`, so `registerWebviewPanelSerializer` restores the tab after a reload (activation event `onWebviewPanel:switchboard.history`). The pure `historyView` (`src/webview/historyModel.ts`) turns the reply into a header and sections of entries: each event becomes one entry per work item whose rows it changed, worded from the event type and detail, with one line per other change; a work item's changes caused by another work item's event, such as a session the queue started, are worded from those changes alone. Waiting time is the union of logged needs-you statuses and logged `waiting` session states, and `renderHistory` (`historyRender.ts`) draws the chips, filter, day headings, gaps and collapsed runs. A link posts `{type: 'open', action}`: `open` opens a session with [Open in VS Code](#claude-code-runner), offered only while the session is not running in its background process; `openFolder` opens a worktree with `vscode.openFolder`; `openUrl` opens a URL or file.
- **A row's click from VS Code** (PRD R65, R69): `openRow` in `src/open.ts` builds the dock view from the window's latest snapshot with `dockView` and runs the row's click as the dock's `Switcher.Click` does: a row without a window opens its ticket URL; otherwise it writes the workspace file with the hub's `writeWorkspaceFile`; for `question` it posts `open-question` and waits up to 20 seconds for a snapshot in which that session is `ended`; for `session` it posts `POST /open {sessionId, cwd, workspace}`. It then runs `vscode.openFolder` on the workspace file with `forceNewWindow`, which VS Code answers by bringing the window that has the file forward, or opening one (switcher spike Q4); VS Code holds the foreground after the operator's click on its notification or link, so Windows lets it, where it would refuse the dock (M26). The item window claims the session when it gains focus; a click whose item window is this window claims at once, because it does not gain focus again. The window is not maximized or moved to the dock's monitor. A second click on the row being opened is ignored, and a click on another row replaces it, which then makes no further request or switch, as in the dock. The extension API's `openRow` takes a stand-in hub record for the integration suite.
- **Notifications of work on the operator's turn** (PRD R65): `NeedsYouTracker` in `src/toast.ts` keeps the window's previous snapshot: the `hello` event that opens each `/events` stream clears it, and each `state` event returns `newlyNeeding(previous, next)`, the work items for which `needsYou` holds and did not hold in the previous snapshot, or none when there is no previous snapshot. An item whose previous snapshot had `approvalHeld` set is left out unless its ticket was snoozed then, so a held run's turn end, question or new report does not notify, and a wake still does. `NeedsYouToasts` in `src/notify.ts` shows one `showInformationMessage` per returned item when `vscode.window.state.focused` and `switchboard.notifyNeedsYou` (window scope, default true) are both true. The text is `Switchboard: <ticket title> — <mark title>` (`toastOf`). **Open** is offered when the row has an item window (`windowOf`) or a ticket URL; pressing it runs `openRow` for the row `rowFor` finds for the work item in the latest snapshot, which for a snoozed work item is its ticket's row. The tracker updates on every snapshot, including in an unfocused window or with the setting off, so focusing a window or turning the setting on does not toast the backlog.
- **Open in Switchboard** (PRD R69): the extension registers a `UriHandler` and activates `onUri`, so `vscode://switchboard.switchboard/open?url=<ticket URL>` reaches it. VS Code decodes the URI's query once; `openUrlOf` in `src/search.ts` takes everything after `url=` as the ticket URL, so a URL with its own `&` survives. A URI before the window's first state, such as one that started VS Code, waits up to 15 seconds for it, then reports that the hub did not answer. `targetForUrl` walks the rows `listGroups` lists, in list order, for the first whose ticket URL matches, then the first whose ticket has a matching link (`WorkItemView.links`, or `PoolView.links` on a pool row), and `openRow` runs that row's click. URLs compare by `urlKey` in `packages/core/src/group.ts`: a GitHub issue or pull request URL, any tab such as `/files` included, as `github.com/<owner>/<repo>/<issues|pull>/<number>` in lower case, any other URL as parsed without a trailing slash. With no row it shows `Switchboard has no work item for <url>`, and a URI with another path or no `url=` gets `Switchboard cannot open <uri>.` The extension API's `openUri` runs the same handler for the integration suite, whose portable VS Code does not register for `vscode://` links.
- **Status bar item** (PRD R64, R71): a left-aligned item, `$(switchboard-logo) N` with the tooltip `Switchboard: N need(s) you. Click to show the dock.` from `needsStatus` in `src/needs.ts`, or `$(switchboard-logo)` alone at 0; `needsCount` counts the work items for which `needsYou` holds. Its command, `switchboard.showDock`, posts `POST /dock/show`, which activates the running dock; when the hub answers 409, because no dock stream is connected, or no hub answers, it starts `<Switchboard home>/dock/Switchboard.Dock.exe --home <home>` detached, without the `ELECTRON_*` and `VSCODE_*` variables, or warns that the dock is not installed there.
- The extension contributes the `switchboard-logo` icon, the `switchboard.showDock` command and its settings (`switchboard.configDir`, `switchboard.notifyNeedsYou`); it has no activity bar view, title-bar buttons or row commands.

## Dock

PRD R71. `apps/dock` (`Switchboard.Dock.exe`) is a C# .NET 10 app with Avalonia 12.1.3. Window management sits behind `IWindows` and `IVsCode` (`Switching/Platform.cs`); `Win32Windows`, `VsCodeInstall` and `AppBar` in `Platform/` are the only implementations, because Switchboard runs only on Windows. `npm run publish --workspace @switchboard/dock` publishes it to `~/.switchboard/dock/`.

- **View.** `dockView(snapshot, now, windows)` in `packages/hub/src/dock.ts` builds what the dock shows from the snapshot with the functions in `rows.ts` ([Rows](#rows)), so the dock has no rules of its own: `notes` (`snapshotErrors`, then `setupNotes`), the `groups` in list order, each with its codicon `glyph` (`GROUP_GLYPHS`), its `empty` text and `yours`, Ready for review's rows on the operator's turn (null for the other groups), with Blocked on you and Snoozed only when they have rows, and `snooze`, the R49 choices from `snoozeChoices` with their wake times. A row has `key` (`item:<work item ID>` or `ticket:<pool ticket ID>`), `title`, `priority` (the dot's tooltip, or null), `time` (`rowTime`, or the pool's scope time), `playbook`, `ticket` (`gh 18941`), `source`, `url`, `mark` (`kind`, its codicon `glyph` from `MARK_GLYPHS` in `group.ts`, which the Chrome pills also use, and `title`), `details` (line 3 after the mark: wait reasons, wake time, warning and error, `From <key>`, then the question, else the capitalised approval summary with its age, else the stage with its age or `No stage report`, each `{text, title, tone}`, cut at the caps with the whole text as `title`, and the stale age in `warning`), `stripe` (`stripeOf`), `turn` (`turnOf`, null on a snoozed row), `dim` (a Ready for review row on the agent's turn), `movable` (a Ready for review row), `window`, `open`, `controls`, the hub actions of `controlsOf` or `poolControls`, Snooze without a wake time, `main` with `mainGlyph`, `answers`, `pastes`, `commands` and `search` (see Controls and Header), each control and command with its codicon `glyph` (`glyphOf` in `dock.ts`, which throws for an icon it has no glyph for, so a new control icon fails the tests), `band` (`doneBand` in `rows.ts` for a Done work item row, else null), `links` (the ticket's links once each, without one to the ticket itself, each with `label`, named `PR #<n>` or `gh <n>` from a GitHub pull request or issue URL, else by its label, for the menu; `kind`; and `badge` and `glyph` for its pill on line 2, a pull request's number after the pull request codicon) and `returned` (PRD R51); and the view's `sources` (`sourceStates`) and `repoRoots`. `apps/dock/test/fixtures/dock.json` is a recorded view: `dock.test.ts` compares `dockView` with it and the C# tests parse it.
- **Window.** `windowOf`: the first folder is the latest session's `cwd`, else the worktree, and the worktree is the second folder when it differs; no window without either. `name` is the ticket key with a `-` for the space, then `-<first folder name>` when the first folder is not the worktree, then `-` and the first 6 hex digits of the SHA-256 of the first folder's path (lower case, `/` separators, no trailing separator), with any run of characters other than letters, digits, `.`, `_` and `-` replaced by `-`, such as `gh-18941-3f2a91`; `title` is the ticket title; `file` is `<Switchboard home>/windows/<name>.code-workspace`. The hash keeps each name's first folder fixed: two folders with the same name, or a moved worktree, get different windows. `open` is `question` (`{workItemId, sessionId, cwd}`) while the active session waits in its background process, `session` (`{sessionId, cwd}`) for the latest session when no session is active or the active one was released, `url` for a row without a window whose ticket has a URL, and null otherwise, as while a session runs in its background process.
- **Workspace file.** The hub writes each row's workspace file with `writeWorkspaceFile` before it sends a dock view, and the extension before its own [row click](#vs-code-extension), so one writer serves both: the folders, a `window.title` of `<title>${separator}${activeEditorShort}${separator}sb:<name>` with each `$` in the title replaced by a fullwidth `＄`, because VS Code drops the text after a `$` up to the next `}` (M26), and a `window.titleSeparator` of ` · ` (`workspaceText`). It writes only a file whose text differs, because VS Code applies any change to the open window, and the hub keeps the text of each file it wrote, so a view writes only the files that changed. A file it cannot write is logged. A view from a hub older than the dock names no file, and the dock asks for a window reload.
- **Click.** `Switcher.Click` opens the ticket URL for a row without a window. Otherwise it uses the row's workspace file. For `question` it posts `open-question` and waits up to 20 seconds on the stream for the row's `open` to become `session` with the same session ID, then continues as for `session`; for `session` it posts `POST /open {sessionId, cwd, workspace}` with the workspace file, which only the window opened from that file claims when it gains focus or connects, so another window on the same folder does not take it ([Open in VS Code](#claude-code-runner)). It then finds the visible top-level `Code` process window whose title `DockWindow.NameOf` reads as the row's name; without one it runs `Code.exe <file>`, which opens it in the profile VS Code gives the workspace, with `Code.exe` beside the `bin\code.cmd` on PATH and no `ELECTRON_*` or `VSCODE_*` variables, and looks again every 100 ms for 20 seconds. Before it opens a window, it posts `POST /window {workspace, command: {type: 'openTabs'}}` for that workspace file, so the new window opens its [tabs](#vs-code-extension) (PRD R72), and withdraws it when the window does not appear or the click is cancelled; a hub that refuses it does not stop the click. The hub refuses `openTabs` without a workspace. `Win32Windows.Show` restores a minimized window; moves a window whose nearest monitor is not the dock's (`Win32Windows.DockMonitor`, which the window sets each time it docks) into that monitor's work area with `SetWindowPos`, after restoring it if it was maximized, because VS Code opens a new window on the monitor of the window used last; maximizes it; calls `SetForegroundWindow`, and checks `GetForegroundWindow` for 100 ms, twice. Each failure, including a missing workspace file, VS Code or the browser not starting, and any exception, shows on the dock's status line until the next click. A click on another row cancels the running click, which then makes no further request or switch and shows nothing; a click on the row already being switched to is ignored, and a click on a question whose stop is still under way, such as after a click on another row in between, waits for that stop instead of sending another, so a question is never stopped twice. Windows lets a process bring another window forward only while its own input is the latest (M26), so this runs from the click.
- **Foreground.** `Win32Windows.WatchForeground` installs an out-of-context `SetWinEventHook` for `EVENT_SYSTEM_FOREGROUND` on the UI thread and passes each new foreground window's title to `MainWindow.ShowForeground`. `DockWindow.NameOf` reads the name from the last `sb:<name>` in a title that is at its start or after ` · ` and ends at a space or the end, which allows the text VS Code adds before and after the title (M26); `DockViewModel.SelectWindow` selects the first row in list order with that window, opening its group as a kept choice, and the row is scrolled into view. Any other title changes nothing. A new item window's title lacks the name for its first half second, so its own foreground change selects nothing; the click that opened it already selected the row.
- **Controls** (PRD R71). A row's `main` is the label of the main control (`mainControl`, or a pool row's from `poolControls`), shown as a button while the row is selected, with `mainTitle` as its tooltip (`mainTitle` in `rows.ts`, which for Approve names the prompt it runs): Open in Claude runs the click; any other posts the matching control's action. `answers` holds a one-part question's options with their `answer` actions, shown as buttons under line 3. `pastes` holds an `awaiting-approval` row's drafts: Copy reads the file when clicked (`Paste.Read`, without a byte order mark or trailing whitespace) and puts it on Avalonia's clipboard, from a menu of labels when there is more than one. `commands` holds the controls a VS Code window runs, with the message the extension's handler takes: Open Changes from `controlsOf` on a row with a worktree (not Show in Source Control: the item window's Source Control view already holds the worktree), History on every row, and Open report (`openUrl` with the approval's draft). `Switcher.Run` posts `POST /window {workspace, command}` with the row's workspace file and switches to its item window as a click does; for a row without a window, and for a Settings file, it posts a null workspace and brings the VS Code window nearest the front forward (`Win32Windows.FindVsCode`, the first visible top-level window of a `Code` process in z-order), or says to open one when there is none. A control that runs in VS Code replaces a row click or control still switching windows, as another click does, so an earlier switch does not take the front back. `/window` answers the command's `id`; when the switch is cancelled or fails, the dock posts `POST /window/withdraw {id}`, so the window that comes to the front next does not run it. A right-click selects the row and opens a context menu: Open in Claude on a row whose session waits on a question, the row's hub `controls` (Snooze as a submenu of the `snooze` choices that posts the action with `until`), Copy, the `commands`, and after a separator Open ticket and an Open item per entry of `links`, which opens its URL in the browser. A failure or refusal shows on the status line, as does `Copied <label>.` The row menu (`MainWindow.RowMenu`) is anchored to the window at the pointer's last position, which the window tracks from `PointerMoved` and `PointerPressed`, because `ContextRequested`'s own position was wrong for a right-click; a menu opened from the keyboard opens at the row's corner. It extends right of the pointer on a left dock and left of it on a right dock, and allows only vertical adjustment (`FlipY | SlideY`): Avalonia keeps popups inside the monitor's working area, which leaves out the dock's app bar strip, so a horizontal adjustment moved every menu beside the dock.
- **Order** (PRD R73). A press on a `movable` row and a vertical move of more than 4 pixels starts a drag instead of a click, and Escape cancels it; a line between Ready for review rows shows the drop place, and a drop there posts `{type: 'move', workItemId, after}` with the row above the line, or null at the top, from the group's shown order; a drop elsewhere posts nothing. Alt+Up and Alt+Down on the selected row post its Move up or Move down control. F8 and Shift+F8 (`DockViewModel.SelectNextTurn`) select the next or previous row whose `turn` is `operator` in Blocked on you and Ready for review, after the selection in list order and wrapping, open its group, clear a search that hides it, scroll to it and run its click.
- **Header.** The title row holds one toggle per entry of the view's `sources`, drawn as the source's logo (`SourceGithub`, `SourceZoho` and `SourceForum` geometries in `App.axaml`, from the VS Code panel's icons) in `DockSourceGithub`, `DockKeyZoho` or `DockKeyForum`, or `DockSourceOff` when the source is off; then a separator, shown when there are sources, and Search, which sets `DockViewModel.SearchOpen` to show or hide the search box (hidden at start; hiding it clears the filter), New Ad-hoc Session, Open Settings, which opens the [Settings window](#settings-window), a second separator, and Close. A toggle click posts `POST /sources {name, enabled}` with the opposite state. A search box sets `DockViewModel.Filter`: a row shows when its `search` text, the title, `searchDescription` (key, linked pull requests and issues as `PR #<n>` and `gh <n>`, playbook, group) and the worktree branch, contains every word ignoring case; while it filters, every group and date band with a match shows open and the others hide, and Escape clears it and hides the box. New Ad-hoc Session opens a form under the header with a repo list, shown only when `repoRoots` has more than one, a prompt box and Start, which posts `adhoc` with the prompt and repo and closes the form on success; Start is disabled until the hub answers, so a second click cannot start a second session; with no repo roots it says to set one. A foreground item window whose row the search hides clears the search, so its row shows selected.
- **Docking.** `AppBar` subclasses the window with `SetWindowSubclass`, registers it with `SHAppBarMessage(ABM_NEW)` and a callback message, and reserves `ABE_LEFT` or `ABE_RIGHT` on the kept monitor (`Native.MonitorNamed`, which finds the monitor whose `MONITORINFOEX` device name matches, else the primary one): `ABM_QUERYPOS` with the monitor's height, then `ABM_SETPOS` with the width from the outer edge Windows lets it keep (`DockPlacement.Strip`); the window takes the returned bounds through `SetWindowPos`, and `AppBar.Strip` holds every later move and resize to them in `WM_WINDOWPOSCHANGING`, keeping only what the call's `SWP_NOMOVE` or `SWP_NOSIZE` leaves alone, because Avalonia moves a window it resizes into the monitor's work area, which starts at the dock's own inner edge, and at some fractional scales its rounded size is one pixel short, such as 452 of 453 pixels at 175%. The width in pixels is the kept width in device-independent pixels at the monitor's scale (`GetDpiForMonitor`). The window is cloaked (`DWMWA_CLOAK`) from its creation, with DWM transitions off, until it has drawn two frames in its strip, or for at most a second, so it never shows at Avalonia's first size and position. It reserves the strip again, resolving the kept monitor by name again, on `ABN_POSCHANGED`, on `TaskbarCreated` and on `WM_DISPLAYCHANGE`, so a dock whose monitor was unplugged docks on the primary one; it turns Topmost off while `ABN_FULLSCREENAPP` reports a full-screen app, forwards `WM_ACTIVATE` and `WM_WINDOWPOSCHANGED`, and removes the bar on close. Dragging the inner edge (the right edge of a dock on the left, the left edge of one on the right) resizes the window the same way, keeping its outer edge; on release, or when another window takes the pointer capture, the width is kept and the strip reserved again, so other windows move once.
- **Moving.** Dragging the header's title and dropping it, or losing the pointer capture during the drag, which ends it without moving, docks the dock at the left or right edge, whichever is nearer the drop point (`DockPlacement.EdgeAt`), of the monitor under it (`MonitorFromPoint`, nearest); the dock keeps the edge and the monitor's device name, or no name for the primary monitor, and reserves its strip there.
- **State.** `<Switchboard home>/dock.json` keeps `width` (200 to 800, default 320), `edge` (`left` or `right`; anything else reads as `left`), `monitor` (a device name such as `\\.\DISPLAY2`, or null for the primary monitor), and `groups`, the groups and Done's date bands (as `done:<band>`) the operator opened or closed; Blocked on you, Ready for review, In progress, Unstarted and the Today and Yesterday bands start open. Kept choices under keys the view does not send, such as `needs` and `working`, have no effect. `GroupViewModel` splits its shown rows into `BandViewModel`s by `band`; a group other than Done has one band with no heading. One dock runs per desktop (`Local\Switchboard.Dock` mutex); closing it ends the app, even with the Settings window open. `--home` or `SWITCHBOARD_HOME` names the folder holding `.switchboard`, as for the hub.
- **Connection.** `HubClient` reads `hub.json`, opens `/dock/events` with the token, and reads `hub.json` again 2 seconds after the stream ends or fails. Besides `dock`, the stream sends `show`, from a VS Code window's status bar item (`POST /dock/show`), which activates the dock, and `config`, which makes an open Settings window read the files again; the dock skips any other event. Each attempt sets the state: a 404 means a hub older than the dock, and the dock asks for a window reload; anything else without a stream reads as not running. The dock never starts the hub.
- **Look.** Colours are VS Code's Light Modern and Dark Modern theme values, chosen by Windows' app mode. `App.axaml` defines the dock's own brushes and also redefines the Fluent theme's control keys (`TextControl*`, `ComboBox*`, `Button*`, `AccentButton*`), so the Settings window's inputs and buttons take VS Code's input, secondary-button and button colours without per-control styles; a `link` button class draws the Settings window's file path in VS Code's link colour; marks use `codicon.ttf` from `@vscode/codicons`, and Running and Triaging spin.

## Chrome extension

`extensions/chrome` is a Manifest V3 extension (PRD R56), built by `npm run build` into `extensions/chrome/dist`, which the operator loads unpacked from `chrome://extensions` with Developer mode on, and reloads there after a rebuild.

- The content script runs on every `https://github.com/*` page, because GitHub opens a project without a page load, and acts only while the page has `[data-board-column]` elements. The service worker reads `GET /snoozed` and sends `POST /snooze` for it, because a content script on github.com cannot read a loopback address; the manifest's only host permission is `http://127.0.0.1:47615/*`.
- It reads the snoozed URLs when a board appears, every 60 seconds, when the tab becomes visible and after a snooze from the page. A failed read counts as none snoozed.
- A card's issue is its title link (`h3[id^="board-card-title-"]` inside an `a`), compared as `owner/repo#number` in lower case. GitHub empties the content of a card out of view, a hidden one included, so the script keeps each card's issue by `data-board-card-id`; a card it has never seen rendered stays shown until it renders.
- It marks a snoozed card `data-switchboard-snoozed` and a shown column `data-switchboard-shown`, and `content.css` hides marked cards in columns that are not shown. The link is a centred button appended to the column's scrolling card list (`[data-dnd-drop-type="card"]`), so it follows the last card shown. A `MutationObserver` on child lists reapplies the marks 50 ms after GitHub renders; a pass that changes nothing makes no mutation, so the script does not trigger itself.
- Card pills (PRD R67): `src/pills.ts` reads `GET /cards` through the service worker (message type `cards`), with the same triggers as the snoozed read, and runs its own `MutationObserver`. It puts a `.switchboard-pill` span after the card header's issue reference (`[id^="board-card-header-title-"]`) of each card whose title link's issue key matches a card's `url`; GitHub issue URLs are the only ones that match. The pill's text is the playbook, its namespace in a muted span, or the group name when the playbook is null; `data-switchboard-group` is the group, or `snoozed`; an unsnoozed card in `blocked`, or in `review` with the mark `send`, `review` or `finished`, also gets `data-switchboard-yours`, which `content.css` gives GitHub's attention colours. ## Settings window

PRD R54. A separate, resizable dock window, **Switchboard Settings**, one at a time; Settings in the dock's header brings the open one forward. The page logic is plain C# in `apps/dock/src/Switchboard.Dock/Settings/` (`EditorState`, `SettingsFields`, `SettingsPages`, `SettingsEditor`), and `Views/SettingsWindow.cs` draws it.

- The hub reads and writes the files, through `packages/hub`'s `config.ts`: `POST /config/read` answers the settings file and every playbook file with their versions, valid or not, the permission modes, template variables and source kinds the fields offer, `inUse`, the open work items per playbook, and `configDir`; `POST /config/check {target: 'settings', settings}` or `{target: 'playbook', name, playbook}` answers `{errors}`; `POST /config/save {target, value | name and playbook, version}` writes or answers 409 `{errors}`; `POST /config/delete {name, version}` the same. Saves and deletes carry the `configDir` the window read, and the hub refuses one for another folder with 409. Checks use what the hub applies on load, `parseSettings`, each source's own `parse*Config` and `parsePlaybook`, plus `templateError` for playbook templates and `setupPrompt`, because the hub finds an unknown variable only when rendering the classifier instructions or a session prompt fails. The hub's file watchers reload what the window writes, as they do a hand edit, and then send `config` on the dock stream, which makes the window read the files again; so does each new connection of the dock's stream, such as to a hub started on another config folder. A read from another folder drops every draft and says so on the window's status line. The window needs a running hub.
- The navigation lists **Sessions and triage**, each configured source with **Add** entries for the sources not configured, and the playbooks by namespace with **New playbook**. A page with unsaved changes shows a dot, and a page with errors or a refused write shows an error mark.
- Save and Revert act on the current page's file. **Save all**, beside Save and beside Create on New playbook, saves settings.json and each changed playbook; each file is written or refused on its own, and a refused file keeps its draft and shows the refusal on its page.
- The settings pages edit one draft of settings.json. A field left empty removes its key, so the default applies, and the placeholder shows that default. `automationAgentIds` is the exception: its default is not empty, so an absent key shows the default list, and an emptied list is saved as `[]`. Keys the window has no field for are kept. A source's own errors block a save only while the source is enabled, so a disabled source can be saved incomplete. Removing a source deletes its key, and its work items stay.
- A playbook page edits the front matter and the template. A triage playbook shows only its description, its kind, Rates importance and its classifier instructions. A task playbook has a checkbox for each of its `reports`, and, while `approval` is checked, an **Approve sends the work** checkbox below it; unchecking `approval` clears `approvalSends`. Saving writes only non-default keys, except `autoStart` and `requiresWorktree` on a task playbook; front matter comments are not kept. Delete asks in a modal window, which names how many open work items use the playbook, read from the hub when Delete is pressed. An invalid file shows its error, with its path and Delete.
- Each draft is checked 250 ms after the last edit; an answer to an older check is dropped. The window places each error on the field whose path it names (`FieldOfError`, `PlaybookFieldOfError`); an error that names no field shows at the top of the page. A refused save, create or delete shows at the top of the page until the next edit, revert or successful write, so a later check or file refresh does not hide it. While the operator types, only the navigation, buttons, notes and errors are redrawn, so the field keeps focus; a full redraw, such as after a reload, puts focus and the caret back in the same field.
- Each file is read with a SHA-256 version. Save sends the version the draft started from, and the hub refuses the save when the file on disk no longer matches. A page with no draft shows the files as read again; a draft whose file changed, broke or was deleted is kept, with a warning, and Save then refuses, or creates a deleted playbook again. Writes go through a temporary file and a rename, like the source toggles.
- A file's path opens the file in the VS Code window used last, through the dock's `openUrl` window command.

## Store

- One SQLite database, `~/.switchboard/switchboard.db`, opened through Node's built-in `node:sqlite` (M1). No native module, so VS Code's Electron upgrades do not require rebuilds.
- The hub is the only process that opens the database. The extension and the `switchboard report` CLI go through the hub's HTTP server, so there is no cross-process locking.
- WAL mode; one write transaction per flow step, so a crash leaves each work item in its last committed state.
- Core accesses the database only through a store interface, which isolates changes to the `node:sqlite` API. Tests use `:memory:`.
- Schema changes are numbered migrations applied by the hub at startup, recorded in `PRAGMA user_version`.
- Activity log (PRD R59): `events` holds each flow event that wrote a row or was refused (`at`, `type`, `actor` of `operator`, `session`, `source`, `triage` or `hub`, the ticket, work item and session it names, `detail` as JSON without prompts, contexts or polled lists, and `refused`), and `changes` each row it wrote (`entity`, `entityId`, `op` of insert, update or delete, the owning ticket, work item and session, and `fields` mapping each changed field to its old and new value). `handle` opens an event with `Store.beginEvent` before applying it, and a `wake` event first for snoozes that end; `#insert`, `#update`, the worktree, link and paste upserts and `deleteTriage` read the row before writing and log the difference in the same transaction. Operator actions, reports, failed starts and failed stops are stored even when they change nothing; other events only when they change a logged field. Fields that change on every poll or status change (`lastPolledAt`, `sortAt`, `scopeAt`, `statusAt`, `runStartedAt`, `stageAt`, `queuedAt`, `stateAt`, a link's or paste's `reportedAt`) and the order fields `readyAt` and `orderAt` are not logged, so a move shows in History as its `move` event, with `after` as its detail; `taskPrompt`, `approvalPrompt` and `context` are logged as `true`; text over 2000 characters is cut. A refusal naming no known ticket is not stored. The hub logs a refusal the flow never sees with `Runtime.refuseReport`, which calls `recordRefusal`: a `/report` request that fails validation and names a session, a worktree report naming no git worktree, and a link report its source refuses. It keeps only the report's kind and short text fields, never a prompt. `deleteWorkItem` deletes the work item's changes and its triages' (found by `entityId`, because a pick attaches pool triages logged without a work item) and events left with no changes. The migration stores a `recording` event, whose time is `recordedSince`, and `reconstructed` events with a `fact` for what the existing rows showed: work item created, done, last stage and an approval, blocked or failed status; triage start and end; session start and end; links and pastes. The tables have no foreign keys and are kept forever. `historyRevisions` holds a counter per ticket that every write to its log advances, deletions included; `historyRevision` reads it.
- Not in the database: playbooks and settings, which are files the operator edits and can keep in git; session transcripts, which Claude Code stores, and which sessions find by `nativeSessionId`; the [debrief](#friction-debriefs) state and log, which the friction-review skill reads; and the pending opens and window commands in `window-queue.json` ([Open in VS Code](#claude-code-runner)), which expire after 2 minutes.

## Playbooks

A playbook is a Markdown file whose body is the prompt template and whose front matter holds its settings. `support:defect` lives at `playbooks/support/defect.md` under the config folder. Switchboard has no built-in namespaces or playbooks; the playbook directory defines them.

```markdown
---
description: Zoho ticket reporting behavior that may be a defect
autoStart: false
requiresWorktree: false
permissionMode: auto
reports: done
---
Research Zoho ticket {{ticket.sourceKey}}.
{{ticket.context}}
Report progress with `{{report}} stage {{session.id}} <stage>`.
```

- Template variables: `{{ticket.source}}`, `{{ticket.sourceKey}}`, `{{ticket.ref}}`, `{{ticket.title}}`, `{{ticket.url}}`, `{{ticket.context}}`, `{{session.id}}` and `{{report}}`. `{{report}}` is the report command prefix, `node "<home>/hub.js" report`. Rendering fails on an unknown variable.
- Front matter: `description` (required), `autoStart` (default false), `requiresWorktree` (default false), `permissionMode` and `model` (defaults from `sessions` settings), `kind` (`task` by default, or `triage`), `reports` (a task playbook's comma-separated `done`, `approval`, `worktree`, `playbook` and `paste`; none by default), `approvalSends` (Approve sends the session's work, which sets the approval row's mark; false by default, and allowed only when `reports` lists `approval`), `rates` (a triage playbook's classifier rates immediacy and severity, which its body must define; false by default), and `workdir` (`worktree` by default: the ticket's worktree when one exists, otherwise the repo root; or `repoRoot`: always the source's repo root, for playbooks whose skills belong to that repository).
- `description` tells the classifier when to choose the playbook. Adding a playbook is adding its file: the hub reloads it, and the classifier sees its description. Edit the triage playbook only for a rule that must take precedence over the descriptions.
- A triage playbook's body may use only `{{playbooks}}`, which renders the task playbooks in the source's namespace as `- name: description` lines where the instructions need them. A body without it gets the same list appended under "Choose one playbook:". Any other variable fails the triage, and the settings editor refuses to save it.
- A source's triage playbook has `kind: triage`. Its body is the classifier's system prompt. Triage playbooks are never offered to the classifier as choices.
- Each source's `namespace` setting limits the classifier's choices to that namespace's task playbooks, such as `dev` for GitHub and `support` for Zoho Desk and Forum.
- Every session prompt ends with the report contract, which opens with the line `Report to Switchboard with these commands:`, the line the Support `support-process` skill looks for: the commands the session may send, with the session ID, each with its condition and the cap on its text (PRD R23). The contract leaves out `task`, which the hub still accepts, so a session sends one only through a skill the operator invokes (PRD R68). A playbook's task session gets `stage`, `link`, `task` and the playbook's `reports`; with neither `done` nor `approval`, the contract tells it to end its turn when the work is finished, so the work item becomes `finished`, in Ready for review. Setup and approved-prompt sessions get `stage`, `worktree`, `done`, `link` and `task`, and an ad-hoc prompt gets all but `playbook`. The session row stores its reports, and the hub refuses any other report with "This session's prompt does not offer the <kind> report." and CLI exit code 3. It reports a `link` for each GitHub issue or pull request that tracks or delivers the work, not a related, base or parent one. Before applying a `link`, the hub calls the ticket's source's `checkLink`, when it has one: the GitHub source reads a pull request in its configured repository (`PULL_REQUEST_QUERY`) and refuses it unless it closes the issue in that repository or its head branch names the issue by `branchPattern`, which covers a stacked pull request that does not close the issue, and refuses a pull request number GitHub cannot resolve. A pull request URL is recognised by `new URL` on `http` or `https` and the host `github.com`, so a port, a tab such as `/files` or a fragment does not skip the check. A pull request that closes more issues than the 50 one read lists, none of them the ticket, is left unchecked. The hub logs the refusal with `Runtime.refuseReport` and the CLI exits 3. Other links, other sources, a failed check and a check over `REPORT_CHECK_MS` accept the link, the last two with a log line (PRD R52). When the session needs the operator for a question or a choice, or cannot continue without them, it asks with `AskUserQuestion` and waits, which keeps its context live and puts the row in Blocked on you as `waiting`; it writes no file and sends no report for a question. When its work is ready but posting or publishing it needs the operator's approval, it reports `approval` with the prompt that would do it, such as `/review-pr pr:123 publish`, a summary of what the prompt publishes, and the file holding the drafted text, if any, and ends its turn; Approve runs the prompt in a new session with no memory of this one, so the prompt names what it acts on. Before an approval, a session offered `paste` reports each drafted text the operator pastes into the source by hand, such as a Support customer reply, with its label and file. The operator's skills read these commands through their `gc-session-reports` skill, which writes each as a `switchboard <kind> <arguments>` call. `{{report}}` lets a template add its own report calls.

## Triage

Triage follows Ground Control's classifier (GC R38, M31).

1. The source plugin builds the triage context: it fetches the ticket's text, clips each field at a word boundary to a size limit, and formats it with authors, status changes and assignees. Ground Control clips the issue body and each comment to 2,000 characters. The hub puts a `Current time: YYYY-MM-DD HH:MM UTC` line before the context, in the form sources use for event times, so the triage playbook can tell how recent a request is.
2. The classifier runs `claude -p --output-format json --json-schema <schema> --no-session-persistence --setting-sources "" --tools "" --strict-mcp-config --system-prompt <triage playbook with the playbook descriptions rendered in>`, with the context on stdin. Stdin avoids the Windows 32,767-character command-line limit (M31).
3. The schema is `{playbook: enum of the source namespace's task playbook names}`, plus `immediacy?: URGENT | BLOCKING | NON-BLOCKING` and `severity?: HIGH | MED | LOW` when the triage playbook has `rates: true` (PRD R50). The classifier reads `structured_output`. Without `rates`, it discards any rating the model returns; a value outside the enum is stored as empty.

Triage has no tools, settings, MCP servers or saved transcript, so it is not a session and does not count toward the one-session-in-a-turn rule (PRD R17). The hub runs at most one triage per work item at a time, at most `triage.concurrency` at once (default 2), with a `triage.timeoutSeconds` limit (default 180).

A classifier error, an unparsable result, a timeout, or a playbook name outside the enum fails the work item with that error (PRD R37). A triage interrupted by a hub shutdown is not a failure: the work item stays `triaging`, and triage runs again when the hub starts.

## Flow

1. Poll a source. For each ticket, compare its assigned state with `Ticket.assigned`. A poll that fails or is incomplete, such as one that hits the page limit, updates nothing.
2. When a ticket enters the assigned state, create a work item (`triaging`) and run triage.
3. Store the triage result. If the playbook's `autoStart` is false, the work item is `unstarted` until the operator starts it (`start`). `awaiting-approval` is used only for an approval report, and `approve` applies only to it.
4. If the playbook's `requiresWorktree` is true and the ticket has none, start a setup session (`setup`) running the source's `setupPrompt`. The setup session succeeds when a worktree is linked, by report or by the branch convention, and the session reports done or ends. If it ends with no worktree linked, the work item fails with "Setup ended without a worktree."
5. Render the playbook and start the task session (`running`). It reports stages, a worktree link if it creates one, and done or approval.
6. When the task session reports done, the work item is done with reason `session`. When its turn or process ends with no report, the work item is `blocked`, with the done or approval report the prompt offered as its reason, or `finished` when the prompt offered neither (`endRun`). A turn that ends `failed` blocks it with the error kind, because the session can still be resumed. A `blocked` or `finished` work item whose session runs again becomes `running`.
   - When a session of an `awaiting-approval` work item changes to `running`, as when the operator answers its question or resumes it, the work item becomes `running` with `approvalHeld` set and keeps its approval fields. A change to `waiting` leaves it in `awaiting-approval`. A new approval or done report from that run applies as usual. A turn end, a process end or an operator stop with no report returns it to `awaiting-approval` with the kept approval, and `error` holds the cause of a failed turn or a stop. Any other status, such as `blocked` after a done report while the ticket is assigned, keeps the approval fields; only Approve starts their prompt, and Triage again clears them. Core clears `approvalHeld` on every other status change. A run whose `running` state Switchboard never sees change, such as a resume between two roster reads with hooks off, holds nothing.
7. When a ticket leaves the assigned state, an open work item that never had a session is deleted with its triages and pastes, and one with no active session is done with reason `unassigned` and no warning. A sessionless work item whose triage is running gets `unassignedAt` instead, so the triage row keeps its `triage.concurrency` slot; the triage's success, failure or cancellation deletes it, unless the ticket returned and cleared `unassignedAt`. Work item IDs are `AUTOINCREMENT`, so a deleted ID is never reused, and a late result for a deleted triage finds no row and is ignored. With an active session, that is deferred until the session reports or ends (PRD R10).

Pool tickets (PRD R47, R48):

- When a poll shows a ticket newly in the pool, the core starts a pool triage for the ticket; its result or error stays on the ticket.
- A pick of a pool ticket whose triage has a result creates the work item with that playbook, attaches the pool triage, and queues it as an operator start, skipping the wait in step 3. The task session's skill claims the ticket.
- A ticket that enters the assigned state while it has an open work item gets no second work item; the claim made by the task session is seen this way.

An ad-hoc prompt creates a ticket and work item and goes straight to step 5, with the typed prompt as the task prompt and the chosen repo root as the working directory (PRD R6). A `task` report creates the same ticket and work item, but `unstarted`, with its `parentId` set; Start then goes to step 5 (PRD R68).

Steps 4 and 5 start a session only when no other session of the ticket is `starting`, `running` or `waiting` and a slot is free; otherwise the work item is `queued` (PRD R17, R38). An `idle` or `failed` session, such as the approval session kept open in the VS Code Claude view, holds nothing back, so a work item can have several live sessions. Its active session is its latest session while that has not ended; only the active session holds a slot, and only the latest session changes the work item's status.

## Core decisions

`packages/core` decides; the hub acts. `handle(store, event, context)` runs inside one store transaction, applies one event, and returns the actions for the hub to run, or a refusal for an operator action or report that does not apply. The context carries the clock, settings, loaded playbooks, the report command prefix and a session ID generator. The hub runs each action and sends its result back as an event, so every failure reaches the work item.

| Events | From |
|---|---|
| `poll`, `poll-failed` | A source read. `poll` lists the source's tickets from a complete read; a ticket missing from it has left the assigned state. `poll-failed` changes nothing. |
| `triage-succeeded`, `triage-failed`, `triage-cancelled` | The classifier. A cancelled triage runs again. |
| `session-started`, `session-start-failed` | The runner's `start-session`. |
| `roster`, `marker` | A successful roster read, with each listed session's state; a hook marker for a live session. |
| `report` | The report command: `stage`, `worktree`, `done`, `approval`, `link`, `playbook`, `paste` or `task`. |
| `stop-succeeded`, `stop-failed` | The runner's `stop-session`, for an operator stop, a release, or Open in Claude (`open`). An `open` stop that succeeds blocks the work item, or returns it to `awaiting-approval`, as an operator stop does, with "Opened in Claude to answer." |
| `reply-failed` | The runner's `reply-session`. It sets the work item's `error` to `Answer failed: <message>` and leaves the session waiting. |
| `worktree-found` | The branch convention. It links a worktree only to a ticket that has none. |
| `move`, `reset-position` | The dock (PRD R73). Both apply only to a work item in Ready for review, open and unsnoozed, and `move` only after another such work item or null. `move` lists `readyWorkItems`, every open work item with `readyAt`, snoozed and blocked ones included, without the moved one, and sets its `orderAt`: the midpoint of the keys (`orderAt ?? readyAt`) around its new place, the first key − 60 000 ms at the top, the midpoint of the last key and now at the bottom. When the keys before and after are under 2 ms apart, it first sets every listed work item's `orderAt` to `now − (n − i) × 1000`, keeping the order. `reset-position` clears `orderAt`. |
| `adhoc`, `start`, `approve`, `mark-done`, `retriage`, `stop`, `answer`, `open-question`, `pick`, `retriage-pool`, `snooze`, `restore`, `tick` | The dock; `tick` re-runs scheduling after settings or playbooks change, and every minute wakes due snoozes. `answer` and `open-question` apply only while the active session is the one the row showed (its native session ID), runs in its background process (started, with a short ID, not released) and is `waiting`, and `answer` refuses an empty answer (PRD R70). |

Actions are `triage`, `start-session`, `stop-session` and `reply-session`. `answer` gives `reply-session` with the answer text; its success changes nothing, because the hook marker moves the session to `running`. `open-question` gives `stop-session` with reason `open`. After every event the core starts triage for `triaging` work items, then pool triage for pool tickets without a result, up to `triage.concurrency` in all; then it starts `queued` work items in queue order while fewer than `sessions.concurrency` active sessions hold a slot (each work item's active session holds one while `holdsSlot` holds for its work item, `setup` or `running` with no `waiting` active session, and its ticket is not snoozed), skipping a ticket that has another session `starting`, `running` or `waiting` (PRD R17). A task that follows a setup session starts when the setup session ends, without waiting for a slot.

## Claude Code runner

- Start: `claude --bg --permission-mode <mode> --settings '{"worktree":{"bgIsolation":"none"}}' -n <name> [--model <model>] <prompt>`, with no shell, so a leading slash command survives. The name is `switchboard · <playbook> · <source> <key>`. Claude's background service owns the process, so sessions survive VS Code and the hub. `--bg` ignores `--session-id`; the runner parses the short ID from `backgrounded · <id> · <name>` and matches it as a prefix against `claude agents --json` (GC M1, M33; mechanics M5). The start is confirmed when the roster lists it with a pid; a new entry has no pid for its first seconds. A session not listed with a pid within 60 seconds fails the start.
- Permission mode: `auto` by default. In 101 Ground Control runs to 2026-10-03, the 95 in `auto` never waited for or were refused a permission; the only permission stall was in manual mode. Questions (`AskUserQuestion`) stall in every mode and show as `waiting`. The operator answers them, so Switchboard neither disallows the tool nor keeps a Bash allowlist.
- Environment: pass `CLAUDE_CONFIG_DIR` through exactly as the hub inherited it, and never set it. Setting it, even to `~/.claude`, moves where Claude reads folder trust (GC M62). Strip `ELECTRON_*`, `VSCODE_*` and `NODE_OPTIONS`.
- Trust: `--bg` exits 1 with `Workspace not trusted` in a directory Claude has not trusted; a linked worktree inherits its main checkout's trust (GC M62). The failed start shows that message (PRD R41).
- Background sessions inherit the service's environment, not the caller's, so per-run values such as the Switchboard session ID travel in the prompt (M33).
- Liveness: poll `claude agents --json` (without `--all`) every 30 seconds for every session a start confirmed, so a session resumed after its release is seen again. The roster alone decides liveness: a session is active while the last successful roster read lists it with a pid, and `ended` once a successful read that looked for it does not, so a start confirmed during a read is not ended by it. An entry without a pid is a process that is gone (GC M33). A failed read changes no session. Reads run one at a time; a read asked for during another runs once that one finishes, so an older result never ends a session a newer read revived. Hook markers only set the state of a live session, because a killed process leaves its last marker behind (GC M20). The roster `state` is the fallback when no hook marker exists: `working` maps to `running`, `blocked` to `waiting`, and `done` or `stopped` to `idle`.
- State: hook markers decide the observed state, following GC's mapping (GC M2, M20). The hub watches `<home>/activity/` and reads all markers 50 ms after a change, and also every 5 seconds. When the folder is removed or replaced, or the watch fails, it watches again after 1 second. Each new marker from an ended session can mean the operator resumed it, so the hub reads the roster once for it instead of waiting for the 30-second timer, and reads it again when another such marker arrives during that read:
  - `UserPromptSubmit`, `PostToolBatch` and `PermissionDenied` mean `running`, as do `SessionStart` with `source=compact` and `PostToolUse` or `PostToolUseFailure` for `AskUserQuestion` or `ExitPlanMode`, which end a question's wait before the rest of its batch resolves. A result of another tool does not end a wait, because a parallel tool can finish while one still waits for permission. After the operator approves a permission, the session stays `waiting` until the approved tool's batch resolves.
  - `PermissionRequest`, `Elicitation`, `PreToolUse` for `AskUserQuestion` or `ExitPlanMode`, and `Notification` of type `permission_prompt`, `worker_permission_prompt` or `agent_needs_input` mean `waiting`.
  - `Stop` means `idle`, or `running` while background tasks remain.
  - `StopFailure` means `failed`, with its error kind and message.
- Hooks:
  - The hub installs async command hooks for those events plus `SessionEnd` in `<CLAUDE_CONFIG_DIR or ~/.claude>/settings.json`. It preserves other entries, refuses to edit malformed JSON, and adds missing entries at startup. The `sessions.installHooks` setting is on by default; when it is off, the roster alone decides state.
  - The hook runs `node "<home>/hook.mjs"`. It skips subagent events, always exits 0 and prints nothing, and writes `<home>/activity/<nativeSessionId>.json` atomically: `{v, sessionId, event, at, notificationType, source, toolName, backgroundTasks, error, errorMessage}`, with `errorMessage` capped at 500 characters. `SessionEnd` deletes the marker.
  - A debrief fork runs with `FRICTION_DEBRIEF=1`, and the hook writes no marker for it.
- Release: when a session's turn ends (`idle` or `failed`), run `claude stop <id>` once (PRD R39). A `waiting` session is not released, because it is mid-turn. A session whose background process has ended, by release, stop, failed start or leaving the roster, is never released again, and neither is a session the roster lists as interactive, so a session the operator resumed in a VS Code tab is never stopped by Switchboard. Before a release stop, the hub also reads the roster and skips the stop unless the session is listed as a background process. An interactive roster entry, such as a VS Code tab, has no `state`; its `status` (`idle`, `busy` or `waiting`) gives `idle`, `running` or `waiting`.
- Stop: `claude stop <id>`, 15-second timeout. A failed stop leaves the session stoppable. Never `claude rm`, which can delete the worktree. Only a `release` stop checks the roster first; an operator stop and an `open` stop do not.
- Job state (mechanics M24): `readJobQuestion` in `packages/claude/src/service.ts` reads `<Claude config dir>/jobs/<short ID>/state.json`, where the config dir is the folder of the Claude settings.json the hooks use. It returns the questions when `tempo` is `blocked` and `block.questions` is a non-empty list of `{question, options: [{label, description}]}`, and null for a missing or unreadable file or any other shape.
- Reply (mechanics M24): `replyToSession` lists `\\.\pipe\` for names matching `cc-daemon-<hex>-control`, refuses when there is none ("Claude's background service is not running.") or more than one, reads `<Claude config dir>/daemon/control.key`, writes one line `{"proto":1,"op":"reply","short":<short ID>,"text":<answer>,"auth":<key>}`, and reads one newline-terminated JSON line within 5 seconds. `{ok: true}` succeeds; any other answer, a closed connection, a timeout or a connection error is the failure message, the service's `error` when it gives one.
- Attach: a VS Code terminal running `claude attach <id>`. Leaving it keeps the session running (M33, M45).
- Resume: a VS Code terminal running `claude --resume <native session ID>` in the session's directory, named `Switchboard · <source> <key>`. The window keeps the terminals it resumed sessions in and shows the open one again instead of resuming twice. A session active elsewhere, such as in a VS Code tab, opens there through Open in VS Code instead, because a second resume of a live session is refused (M7). The roster lists a resumed session as interactive, so it is never released.
- Open in VS Code (from a History link, PRD R59, and in an item window, PRD R29): resumes the session or focuses it where `claudeCode.preferredLocation` puts it. With `sidebar`, the window calls `claude-vscode.editor.open(<native session ID>, …, { programmatic: 'honor-preferred-location' })`, which opens it in Claude's sidebar unless a tab already holds it (GC M63); otherwise `claude-vscode.primaryEditor.open(<native session ID>)`, which always uses a tab. Claude's tab and sidebar list only the sessions of its window's first folder, and opening another session there starts an empty one (GC M6, M7, M52). So when the session's directory is the window's first folder, the window opens it directly. Otherwise the window posts `{sessionId, cwd}` to the hub's `POST /open` and opens that folder with `vscode.openFolder` and `forceNewWindow`, which focuses a window already on it. A window claims a pending open for its folder with `POST /claim {folder, workspace, focused}` when it connects to the hub, whenever it gains focus, and on a `claim` event naming its workspace file, and opens it; `folder` is empty for a window with none, `workspace` is the window's `.code-workspace` file or null, and `focused` is VS Code's window focus. The reply also holds `commands`, the dock's pending window commands (`POST /window`) for that workspace file, and while `focused` also those for any window, oldest first, so a window reconnecting in the background does not take what the dock left for the window it brought forward. The window runs `openTabs` before opening any claimed session and the others (`openChanges`, History, `openLink`) after it; a failure there or in a command shows its error and the rest still run. `/window` accepts only `changes`, `history` and `openUrl` commands with the fields their handlers read, and `openTabs` with a workspace file, and a pending command expires after 2 minutes. An open the dock posts names its item window's workspace file, and only a claim with that file takes it (PRD R71). A pending open expires after 2 minutes. `WindowQueue` in `packages/hub/src/windowQueue.ts` holds the pending opens and commands and writes them, with the next command ID, to `<Switchboard home>/window-queue.json` on each change, and a starting hub reads that file, because the first window started after an extension update replaces the hub before it claims what the dock left for it. `/open` and `/window` answer 500 when the file cannot be written, so no command ID is handed out twice; a claim or withdrawal is kept in memory even then. A pending open is kept per folder and workspace file, so two item windows on one folder each claim their own. The hub logs each session left and claimed.

## Session reports

Sessions report through the hub bundle, which posts to the hub's loopback HTTP server. The prompt carries the Switchboard session ID and the bundle's absolute path, because a background session has no Switchboard environment and `switchboard` is not on PATH.

```
node "<home>/hub.js" report stage <sessionId> <stage>
node "<home>/hub.js" report worktree <sessionId> <path>
node "<home>/hub.js" report done <sessionId>
node "<home>/hub.js" report approval <sessionId> --prompt <prompt> [--summary <text>] [--report <path>]
node "<home>/hub.js" report link <sessionId> --label <text> --target <url>
node "<home>/hub.js" report playbook <sessionId> <name>
node "<home>/hub.js" report paste <sessionId> --label <text> --file <absolute path>
node "<home>/hub.js" report task <sessionId> --prompt <prompt> [--repo <repo root>] [--title <text>]
```

- The contract asks for the approval summary; the CLI and the hub accept its omission, and `done` takes no text. The CLI resolves a relative `--report` against its working directory, and the hub refuses a report path that is not absolute.
- Git Bash rewrites an argument that starts with `/` to a path under its Windows root, so `/legacy-ship 16416` arrives as `C:/Program Files/Git/legacy-ship 16416`. When `MSYSTEM` is set, the CLI reads the root from `cygpath -m /` and restores an approval prompt that starts with it (mechanics M20).
- The CLI's usage text, printed for a malformed report, leaves out `task`, as the contract does (PRD R68).
- The CLI's home is the directory that holds the `hub.js` it runs from, so a session started by a hub with `--home` reports to that home.
- The CLI finds the hub through `hub.json` and never starts one. Timeout: 10 seconds. Repeating a report is safe, because each report sets a value and a repeated `task` adds nothing.
- When no hub answers, the CLI exits 2 and prints that the hub is not running. The hub stays up while sessions are active, so this is rare; the work item then ends `blocked`, and the operator marks it done.
- Exit codes: 0 recorded, 2 no hub, 1 usage, 3 refused (an unknown session, a report the session's prompt does not offer, a link its ticket's source refuses, or a path that `git worktree list` run in that path does not show as a worktree). A worktree can belong to a different repository than the source's repo root, as when a Support session in `D:\git\support` reports an widgets worktree.
- Before applying a task session's `done`, the hub polls the ticket's source and applies that poll. When the poll still lists the ticket as assigned, the hub sends the report with `assigned: true` and the flow blocks the work item with "The session reported done, but the ticket is still assigned to you." The CLI still exits 0. A failed poll, a poll that takes over 6 seconds (`REPORT_CHECK_MS`, inside the CLI's 10-second timeout), a setup session, or an ad-hoc ticket skips the check (PRD R10). Reads of one source run one at a time, so a scheduled poll that started earlier cannot apply after the check's poll; a scheduled poll is skipped while a read is in flight.
- A report for a work item that is already done does not reopen it: `done` sets the session's outcome, `worktree` links the ticket's worktree, `link` adds the ticket's link, and `stage`, `approval`, `playbook` and `paste` are ignored.
- `playbook` names a task playbook in the work item's namespace; the hub refuses any other with "<name> is not a task playbook in the <namespace> namespace." It sets the work item's playbook only, so the session keeps the reports its prompt offered.
- `task` (PRD R68) creates an ad-hoc ticket and an `unstarted` work item whose `parentId` is the reporting session's work item, whether or not that work item is done. The title is `--title`, or the prompt's first line when it is left out or blank. The repo is `--repo`, which the CLI resolves against its working directory, or the reporting ticket's `repoRoot`, else its source's `repoRoot` setting. The core compares it with the configured repo roots (`repoRoots` in core, the list the ad-hoc prompt box offers) ignoring case, separators and a trailing separator, stores the configured spelling, and otherwise refuses with the list of repo roots. The CLI restores a prompt that Git Bash rewrote, as for `approval`. A report whose prompt equals that of an open work item from the same parent adds nothing, so a repeated report is safe.
- `link` takes an http(s) URL; the CLI and the hub refuse any other target with exit 1. Migration 8 deleted the local-file links of earlier sessions, after copying an open approval's newest one to its `approvalReport`. A link to a target the ticket already has replaces its label.
- `paste` (PRD R60) takes a non-empty label and a `--file` that names one file wherever it is read: on Windows a drive or UNC path, not `\x` or `D:x`, which depend on the reader's current drive or directory; elsewhere a POSIX absolute path. The CLI and the hub refuse any other file with exit 1 instead of resolving it, because the extension reads the file later, outside the session's working directory. Under Git Bash with path conversion off (`MSYS_NO_PATHCONV`), the CLI turns a drive path such as `/d/git/support/x.md` into `D:/git/support/x.md`; with conversion on, Git Bash has already done so (mechanics M20). The hub stores it on the session's work item when the session is the latest, replacing a paste with the same label.

## Friction debriefs

PRD R55, ported from Ground Control's debrief runner (GC M64). Off unless `sessions.debriefs` is true.

- **Files:** under the Claude root, `CLAUDE_CONFIG_DIR` or `~/.claude`: the prompt `skills/friction-review/prompt.md`, and `.wip/debrief/state.json` and `.wip/debrief/log/YYYY-MM.jsonl`. They are the files Ground Control wrote, in the same format, so Ground Control's record of what it asked still holds, and the friction-review skill reads both runners' lines. Ground Control's `codex` entries that wait for a debrief stay as they are. A session's entry has one writer, the hub that started the session; Ground Control's runner must not run beside it.
- **Candidates:** every minute, the started sessions in the store with provider `claude`, a native session ID, state `idle`, `failed` or `ended`, and no end more than an hour ago. The session's transcript, `<Claude root>/projects/<slug of cwd>/<nativeSessionId>.jsonl`, gives its last turn by its write time. A session is due as soon as its work item is done, otherwise 45 minutes after its last turn, and is skipped from 60 minutes after that turn. It also needs at least 10 main-transcript tool calls after the last debriefed message, in a range whose debrief has not failed. The due session with the oldest transcript goes first, one fork at a time.
- **Roster:** before each fork the hub reads the state and `claude agents --json`, skips a session listed with a pid that is not idle, and checks the setting and the 60-minute limit again. An idle background session and a stopped one can be forked (mechanics M19).
- **Fork:** `claude -p --resume <nativeSessionId> --fork-session --session-id <new uuid> --no-session-persistence --output-format json` in the session's `cwd`, the prompt on stdin, `FRICTION_DEBRIEF=1`, a 10-minute timeout. No model, effort, tool or MCP flag, because each changes the prompt prefix and loses the cache. `{{scope}}` is the whole conversation, or the work after the first message after the last debriefed one, named by its first 200 characters. `{{subagents}}` lists the subagents written within 55 minutes whose type can be resumed (not `codex`, `Explore` or `Plan`), with new messages since their last debrief; their transcripts are copied to `<project>/<forkId>/subagents/` for the run, because a fork looks for them under its own ID, and removed after it.
- **Codex threads:** a session's fork, whether it succeeded or failed, marks `pending` in the state each thread that an `mcp__agent-delegate__*` result names in the range, in the main transcript or a subagent's transcript written after the range starts, and every pending thread is then asked once, at the next scan when the hub stopped or a write was held, through agent-delegate's command: `<node> <Claude root>/tools/agent-delegate/debrief.mjs <thread> --prompt <prompt> [--since <its last debrief>]`, with the hub's own executable, `ELECTRON_RUN_AS_NODE=1` and `FRICTION_DEBRIEF=1`, and a 10-minute timeout. Exit 0 with the friction JSON appends a `codex` log line with the session as `parentSessionId`; exit 3, a thread with no turn since, records nothing new; anything else is reported in the hub log and the state's `lastError`, and not retried. A missing command skips the threads.
- **Answer:** the last `result` event whose text, without a code fence, is `{"friction": [...]}` or a bare array, each item with non-empty `what`, `source`, `workaround`, `cost` and `evidence`. The last `result` event gives the cache use and cost.
- **Record:** a success appends a log line (`v`, `at`, `provider`, `sessionId`, `parentSessionId`, `cwd`, `fromMessageUuid`, `throughMessageUuid`, `skills`, `toolCalls`, `cache`, `friction`, `startedAt`, `subagents`, `delegated`), on a fresh line when the file ends inside one, then merges into the state as it is on disk, so another writer's entries are kept: the last message covered, and the fork's start as each shown subagent's last debrief. A failure, including a fork that throws, records the range and its error in the state and the hub log, and is not retried; the next debrief covers that range with any later work. A write that fails is held, and no fork starts until a later scan writes it. A hub that stops between the two writes asks about that range again.

The Support skills are project skills of `D:\git\support`, so Support sources use it as their repo root; `/support-fix` makes the widgets worktree when a case needs code. All playbooks live in the operator's config folder, not in this repository.
