# Switchboard PRD

Switchboard is a local software factory for one developer. It ingests work assigned to the operator, triages each assignment to a playbook, runs the playbook's prompt in a background agent session, and shows what each session is doing in the dock, a list docked beside VS Code that switches the screen to a work item's own VS Code window.

## Scope

- Switchboard runs on the operator's machine and handles only the operator's work: tickets assigned to them, and the pool of unclaimed tickets in a queue they work, such as support escalations, from which they pick. It has no shared state, accounts or server.
- All Switchboard state is local. Switchboard reads sources and never writes to them; only the skills its sessions invoke change external state.
- Switchboard manages only sessions it starts. It does not discover or adopt sessions started elsewhere.
- Switchboard tracks worktrees but never creates or deletes them. Skills create worktrees; the operator removes them.
- Switchboard replaces Ground Control and the Support board. Ground Control began as an observability layer linking sessions to GitHub cards; Switchboard is a modular, source-agnostic factory that reuses Ground Control's session mechanics (see [architecture.md](architecture.md)).

## Goals

- Turn each assignment into running work: with no click when the operator trusts the playbook, and with one click when they do not.
- Show at a glance which work needs the operator: waiting for approval, waiting on a question, blocked, or failed.
- Keep sources, playbooks and agent providers pluggable. Adding a source does not change the core.
- Reuse what Ground Control and the operator's skills already do. Switchboard schedules and observes; skills do the work.

## Non-goals

- Writing to sources: no status moves, comments, assignments or labels. Only the skills that sessions run write, including the claim when the operator picks a pool ticket (R48).
- Other people's work, team views, reporting, accounts or shared state.
- Remote, cloud or multi-machine operation. One hub runs per machine.
- Changing git state: no commits, branches, or creating, cleaning up or removing worktrees. Read-only git queries that validate and link worktrees are allowed.
- Answering a session's permission prompts or questions for the operator.
- Inferring state it did not observe: no stuck-session detection, and no check of a session's work beyond whether its ticket is still assigned when it reports done (R10). The dock may colour an observed age, such as the time since a running session's last stage report (R58), but draws no conclusion from it and takes no action.
- Reproducing the source's ticket view or conversation. The dock links to the source.
- Reproducing Ground Control's board, lanes or review views, or the Support board.
- Built-in playbooks or namespaces.
- Unattended overnight operation as a committed goal.
- Complex error handling or support for rare edge cases. A failure shows its cause, and the operator recovers by resuming the session, Triage again, Mark done, or a fix to their configuration.

## Design rules

- **Existing tools are context, not requirements.** Ground Control, the former Support board and the operator's skills show how the work was done before Switchboard. Switchboard adopts a behavior from them only when it serves this PRD's goals, and states its own reason.
- **Skills drive the work; Switchboard is the harness.** Switchboard finds tickets, triages them, starts and observes sessions, and shows their state. Every change to a source, a repository or a worktree is made by a skill a session runs. When a feature needs a write, add a session that runs a skill, not Switchboard code that writes.
- **Least authority.** An unattended session gets the least permission mode under which it can finish. The default is `auto`; a playbook can override it.
- **The work item first, sessions second.** The operator manages work items; a session is how one runs, and the dock shows it as one control, not as content.
- **Show each fact once.** The dock follows four rules:
  - What the row's group already says is not repeated on the row.
  - What an icon says is not repeated in text; a button whose icon makes its action clear shows the icon, with the verb in its tooltip.
  - An indicator that is the same on every row it can appear on, or that means nothing, is not shown.
  - A label carries the most specific fact available: a playbook name that also names the kind of work, such as `support:defect`, rather than a generic one.
- **Simple first.** Choose the simplest behavior that keeps common work correct. Handle a rare case by showing it, not with special machinery.
- **Visible failure.** Every failure shows on its work item with the cause. Switchboard does not retry work automatically. A failed source poll is tried again at the next interval.
- **Observed state only.** The dock shows what the roster and session reports say, and how old that observation is. A session's report is its claim and is shown as such.
- **Never cut off work.** Switchboard stops a session only when the operator asks, or to release a session that has finished its turn so the operator can resume it in VS Code (R39).
- **Start automatically unless it writes.** A playbook whose session makes no external change without the operator's approval gets `autoStart: true`. Local work, such as reading, drafting, local commits and worktrees, is not an external change. A playbook that pushes, posts, assigns or moves a card before an approval report waits, `unstarted`, for the operator to start it. A skill's own documented gate, such as `/or-merge` pushing only clean or high-confidence merges and halting otherwise, is the operator's approval policy and counts as approval. A playbook for a ticket whose requested action is unclear also waits, because an action read from older activity is more likely wrong. A concurrency limit caps running sessions (R38).
- **A failed read changes nothing.** A failed or incomplete source poll never moves a ticket out of the assigned state.
- **Files for configuration, the store for state.** Settings and playbooks are files the operator edits and can keep in git. Work items, sessions and history live in the store.

## Terms

| Term | Meaning |
|---|---|
| Source | A plugin that supplies tickets: GitHub, Zoho Desk, Forum, or ad-hoc prompts. |
| Ticket | Switchboard's local copy of a source record, identified by source and source key. |
| Assigned state | A source-defined condition meaning the ticket is the operator's to work, such as assignee plus status. |
| Work item | One assignment of one ticket to the operator. The primitive Switchboard schedules and displays. |
| Pool | A source's open, unclaimed tickets that the operator may pick, such as support cases assigned to no one or still held by the escalating General agent. Pool tickets are triaged but are not work items. |
| Pick | Starting a pool ticket: the operator presses Start on it. It creates a work item and starts its task session, whose skill assigns the ticket to the operator before it works the ticket. |
| Playbook | A named prompt template and its settings, such as `support:defect` or `dev:qa-failure`. A source's triage playbook holds the classifier's instructions. |
| Triage | A one-shot classification of a new work item, or of a ticket entering the pool, that chooses its playbook. Triage is not a session. |
| Session | One agent conversation for a work item. Kinds: `setup`, `task`. |
| Active session | A session whose process is running, in the background or in a VS Code tab. |
| Stage | A free-text label a session reports about its progress. Switchboard displays it and does not act on it. |
| Dock | Switchboard's native Windows app, which lists the work items at the edge of the screen (R27, R71). |
| Item window | The VS Code window the dock opens for one work item's folder (R71). |

## Requirements

### Sources

- R1. Each source is a plugin behind one interface that lists the operator's tickets and reports whether each is in the assigned state. The plugin defines the assigned state and builds the triage context: the ticket's text, clipped to size limits and formatted with authors, status changes and assignees. The GitHub source can show each comment author's roles, such as tester, from a file the operator names, so triage can tell a tester's report from a developer's question.
- R2. Switchboard polls each enabled polling source and stores each ticket's last-seen state locally.
- R3. Each source has its own settings: enabled, poll interval, repo root, and its triage playbook. The operator turns sources on and off with an on/off toggle per source in the dock's header (R71), because some work, such as Support, is done only some weeks; a disabled source is not polled and its pool is hidden, while its work items stay.
- R4. GitHub is the first source. Zoho Desk and Forum follow.
- R44. A GitHub ticket is in the assigned state when it is an open issue in the configured repository, it is assigned to one of the configured logins, and its project item's status is one of the configured statuses. All of these are settings. The operator's values for `acme/widgets` are in [architecture.md](architecture.md#settings). GitHub is read through the `gh` CLI with `gh`'s own authentication. A poll fails, changing nothing, when the project has no single-select field with the configured status name, because every issue would otherwise read as unassigned.
- R5. The Forum source reads forum topics from the production forum database. A topic is in the assigned state when it is open in the Forum forum and assigned to the operator. An open topic assigned to no one is in the pool (R47). A topic another person has claimed is neither.
- R46. The Zoho Desk source reads tickets through the Desk API. A ticket is in the assigned state when its status type is Open, its escalation field is `Support`, and it is assigned to the operator. Such a ticket assigned to no one, or to a support agent or team, is in the pool (R47): General escalations stay assigned to the escalating General agent, so a support assignee counts as unclaimed. A ticket assigned to another engineer is neither.
- R47. A source can have a pool. Switchboard triages each ticket when it enters the pool, keeps the result with the ticket, and shows the pool with each ticket's chosen playbook. A failed pool triage shows its error on the pool row with Triage again; a pool ticket offers Start only once its triage has a result. A ticket that leaves the pool without a pick, because someone else claimed it or it closed, disappears from it. GitHub has no pool.
- R48. The operator picks a triaged pool ticket by pressing Start on it in the dock. Switchboard creates a work item that reuses the pool triage and starts its playbook's task session, because the pick is the operator's start, whatever the playbook's `autoStart`. The playbook's skill claims the ticket for the operator as its first step, as `/support-process` does through `support-bind`, then works the ticket; when anyone else holds the ticket or the claim fails, the skill reports it and stops, so the work item is `blocked`. Switchboard does not claim and does not check the claim. A ticket that returns to the assigned state on its own, such as a case reopened after On Hold, follows its playbook's `autoStart` like any other new work item.
- R6. The ad-hoc source creates a ticket and a work item from a prompt the operator enters through the dock's New Ad-hoc Session (R71), choosing the repository when more than one is configured. The typed prompt replaces the playbook template: triage does not run, and the task session runs the typed prompt.
  - The operator picks the repository from the configured repo roots; the first one is the default. The session runs there with no worktree requirement and no playbook, using the `sessions` permission mode and model.
  - It starts at once, subject to the concurrency limit.
  - The ticket key is a local sequence number, and its title is the prompt's first line.

### Work items

- R7. Switchboard creates a work item each time a ticket enters the assigned state with no open work item. A ticket assigned again after its work item is done gets a new work item; one that returns while its work item is still open, such as during that item's active session, continues that work item.
- R8. On first run, every ticket already in the assigned state gets a work item.
- R9. Work item status is local and never mirrored to the source.
- R10. A work item is done when its task session reports done, when the operator marks it done, or when its ticket leaves the assigned state while no session is active. An open work item that never had a session is deleted instead when its ticket leaves, because nothing was done on it, so it does not appear in Done or History, and its activity, including its pool triages', is deleted from the log; an operator action that named only the ticket, such as the pick that created it, stays; during its triage, the deletion waits for the triage to end, and a return before then keeps it. If the ticket leaves while a session is active, the work item stays open until that session reports done or ends, because skills such as `/finalize-issue` unassign the operator before the session finishes. When a task session reports done, the hub reads the ticket's source again; if the ticket is still in the assigned state, the session did not hand it off, which is a skill defect, so the work item becomes `blocked` for the operator instead of done, and the session is not told. The blocked work item is done when its ticket leaves the assigned state. A read that fails or takes over 6 seconds accepts the report.
- R11. A work item with a session that ends because its ticket left the assigned state, without a done report, stays listed in Done with no warning; leaving the assigned state is routine.
- R34. Work item statuses are `triaging`, `unstarted`, `queued`, `setup`, `running`, `awaiting-approval`, `blocked`, `failed` and `done`.
  - `unstarted` waits for the operator to start it, because its playbook does not start automatically.
  - `awaiting-approval` means a session's work is finished and waits for the operator to approve the prompt that publishes it (R23). When its session runs again, as when the operator answers its question or resumes it, the work item is `running` until that run ends; the run's own approval or done report applies, and a run that ends or is stopped without one returns the work item to `awaiting-approval` with the earlier approval and the cause of a failed turn or a stop.
  - `queued` waits for a session slot (R38), for a live session of the same ticket to end (R17), including the work item's own earlier session kept open in VS Code, or for its ticket to wake (R49). Its row's line 3 lists each reason that holds, such as `Waits for a slot · 10/10 in use` or `Waits for its session to end`, with what ends it in the tooltip.
  - `blocked` means a session ended its turn or its process without reporting done or approval, or the operator stopped it while no approval was pending (R40), or the operator opened its waiting question in a Claude tab (R70), or a task session reported done while its ticket was still in the assigned state (R10). Its reason names only a report the session was offered: "The session finished its turn." when it was offered neither. The operator resumes it, triages it again, or marks it done.
  - `failed` means a Switchboard step failed: triage, a session start, or a setup session that ended without a worktree. The dock shows the cause and offers Triage again, which triages the ticket again and then starts or waits for Start as the chosen playbook says; for a failed ad-hoc work item, the operator marks it done and submits a new prompt.
- R35. The operator can triage a work item again while it has no active session. There is no control to choose a playbook by hand; the operator handles that rare case outside Switchboard, for example with Mark done and an ad-hoc session.
- R45. Only reports from a work item's latest session change the work item. Reports from earlier sessions are recorded on those sessions.

### Playbooks

- R12. A playbook name is `<namespace>:<name>`, such as `support:defect`, `support:question`, `dev:qa-question`, `dev:qa-failure` or `dev:new-dev`. A namespace is the role the operator works the ticket in, such as `support` for support support or `dev` for development.
- R13. Namespaces and playbooks are not built into Switchboard. Any playbook defined in configuration is valid, and triage chooses among them.
- R14. A playbook owns a prompt template. Switchboard renders it with the ticket's fields, the triage context and the Switchboard session ID.
- R15. Each playbook is configured to start its task session automatically after triage or to wait, `unstarted`, for the operator to start it.
- R16. Each playbook states whether it requires a worktree to start, and where its session runs (`workdir`): in the ticket's worktree when one exists, or always in the source's repo root. A playbook that requires no worktree and has no worktree yet starts in the repo root, and its skill creates a worktree only if the work turns out to need code. Every `support` playbook runs in the repo root.

### Sessions

- R17. A ticket has at most one active session across all its work items, because its work items share one worktree. Switchboard refuses to start a session while the store shows another session for the same ticket as active. Ended sessions are kept as history.
- R18. A new work item is triaged first. Triage is a one-shot classifier with no tools: it receives the source's triage context, led by the current time, and triage playbook, and returns the playbook that handles the work item. A triage playbook chooses a specific playbook only when the context states the requested action by the source's rules, and otherwise its playbook for an unclear ticket, such as `dev:other` for GitHub, where an assignment alone states no action.
- R19. When the chosen playbook requires a worktree and the ticket has none, a setup session runs after triage to create one.
- R20. The task session runs the rendered playbook prompt and handles the work item from start to finish.
- R21. A session without a worktree runs in the source's repo root. A skill creates the worktree when coding begins and reports it.
- R22. All sessions use Claude Code for now. The provider is stored per session so Codex can be added later.
- R23. A session can report its stage, a worktree link, that it is done, or that its work is ready for the operator's approval with the prompt that finishes it, such as `/review-pr pr:123 publish`, a summary of what that prompt publishes, and the file holding the drafted text it publishes, if any. An approval report puts the work item in `awaiting-approval`; Approve starts a new task session with that prompt. `awaiting-approval` is used only for this. A session can also hand its work item to another task playbook in the work item's namespace, whose skill it then runs, so the row names the work being done; a playbook such as `dev:other`, whose session researches what an unclear ticket needs, offers it. Each task playbook lists the reports its sessions may send besides stage, links and tasks (R68), from done, approval, worktree, playbook and paste (R60), and lists none by default. A playbook that lists approval states whether Approve sends the work, such as posting a reply or pushing a branch, or only finishes it after the operator sends it by hand, as a Support release does after the operator pastes the reply; it does not send by default; a session whose playbook lists neither done nor approval ends its turn in Needs you for the operator to review. The prompt lists the reports the session may send, except tasks (R68), and the hub refuses any other. A setup or approved-prompt session may report its stage, a worktree, done, links and tasks; an ad-hoc prompt may send every report but playbook, because it has no playbook to change. A report is only for work ready to publish: a session that needs the operator's answer or choice, or cannot continue without them, asks with `AskUserQuestion` and waits, so its context stays live, and writes no report for the question. Reports are accepted from the session after it is resumed in VS Code.
  - The reported texts are short, because a row shows about 8 to 10 words: the stage is an -ing phrase of at most four words stating the work now running and what it acts on, such as `fixing tests`, with no ending punctuation because the dock follows it with its age, optionally after a step count such as `2/5`, and the approval summary one phrase of at most 8 words without counts. The contract appended to every prompt states these word caps; the dock cuts a longer text at a character cap, 24 for the stage, 60 for the approval summary and 80 for a warning or error, on a word boundary, and keeps the whole text in the tooltip. A done report carries no summary, because nothing shows it.
- R60. A session can report a paste: a label and the absolute path of a file holding a drafted text the operator pastes into the source by hand, such as a Support case's customer reply and private note for Zoho. Pastes belong to the work item, and a later paste with the same label replaces the earlier one. An `awaiting-approval` row with pastes shows a Copy button before Report, and Copy in its right-click menu: with one paste it copies at once, and with more it asks which by label. Copy reads the file when clicked, so the operator gets the draft as it is on disk, and puts its text on the clipboard without a byte order mark or trailing whitespace, then confirms with "Copied <label>." on the dock's status line. A missing or unreadable file shows a warning and copies nothing. Switchboard still writes nothing to the source; the operator pastes.
- R68. A session can report a task when the operator asks it to queue one, such as a defect it found in other code that the operator wants handled separately. Only the operator initiates a task: a session names a follow-up it finds in its final message and does not queue it. The report carries a prompt, and optionally a repo and a title. Switchboard creates an ad-hoc ticket and work item, as for an ad-hoc prompt (R6), with three differences: the work item waits `unstarted` for the operator to press Start, because the prompt is the session's, not the operator's, and may write; the title defaults to the prompt's first line; and the repo defaults to the reporting ticket's repo root. The repo must be one of the configured repo roots. The new row's line 3 shows "From" and the key of the work item whose session reported it, such as "From gh 18941", and a click on it selects that row. Every session may report tasks, as it may report links, because a task changes nothing outside Switchboard until the operator starts it, but no session prompt lists the task report, so a session sends one only through a skill the operator invokes. An empty prompt or another repo is refused. A repeated report with the same prompt adds nothing while the earlier work item is open.
- R36. A session's observed state is `starting`, `running`, `waiting` (needs the operator: a permission prompt or a question), `idle` (its turn ended), `failed` (the turn stopped on an error, with its kind) or `ended`. Hook markers that Switchboard installs in the operator's Claude settings decide the state. The Claude roster decides whether the session is alive, and supplies the state when no marker exists. A session's outcome is `done`, `failed` or `stopped`.
- R37. A triage or session start that fails makes the work item `failed`, with the error. Switchboard does not retry it automatically.
- R38. At most `sessions.concurrency` sessions run at once (default 2, range 1–10). A start that has no free slot waits as `queued`. A session holds a slot only while its work item is in the Working group (R27); a setup session and the task session that follows it hold one slot. A session whose work item is in Needs you, Done or Snoozed holds none, such as one waiting on a question, awaiting approval, or blocked and kept open in VS Code, so the operator's open items do not stall the queue; when such a session runs again, more than `sessions.concurrency` sessions can run until enough end.
- R39. When a session's turn ends, Switchboard stops its background process, so that the session can resume in VS Code. A session waiting on the operator is not stopped, except by the operator's Open in Claude (R70). This never deletes the session or its worktree.
- R40. The operator can stop an active background session; a session the operator resumed in VS Code is stopped there. The work item becomes `blocked` with the reason "Stopped by you." once `claude stop` succeeds; a work item that is or was `awaiting-approval` in that run (R34) returns to `awaiting-approval` with that reason instead, because a stop never approves. A failed stop shows its error and leaves the session stoppable.
- R41. A failed start shows Claude's own message, which for an untrusted directory says how to trust it. Switchboard never writes Claude's trust settings.

### Worktrees

- R24. A worktree belongs to a ticket, and every work item for that ticket reuses it.
- R25. Switchboard links a worktree from a session report, or by branch-name convention when no report exists, such as branch `15619-fix-foo` for GitHub issue 15619. A worktree that git marks prunable, such as one whose directory was deleted, is never linked.
- R26. Tickets from different sources do not share work items. A Zoho ticket gets its own worktree when coding begins.

### Observation and control

- R27. The dock (R71) lists work items. The list centres on the work item; sessions are secondary: a click on a row switches the screen to its work.
  - Rows do not expand. The first line is the title, led by the priority dot on a priority ticket (R50), and the time in the queue. No space is reserved for the dot, so every line starts at the left edge. The second line is the playbook name, the source and key, with `github` shown as `gh`, a badge for each of the ticket's links (R52): a pull request's number after the pull request icon, a GitHub issue as `gh <number>`, another link by its label; and "Returned ×N" (R51), with the controls at the right. A third line, shown only when it has something, holds the mark, the wait reasons or wake time, any warning or error, the work item a reported task came from (R68), and the stage and its age (R58), or the question (R70). The key and the badges are pills outlined in the source's colour, purple for a pull request, with a muted fill of the same colour, and a click on one opens its link in the browser instead of the row's click; Returned is a pill in the warning colour. On an `awaiting-approval` row the approval summary, with its first letter capitalised, and the time since the work item last became `awaiting-approval` take the place of the stage, whose text moves to the summary's tooltip, because the stage only says the work is ready. Every row has at least two lines, with room between rows; the list stays easy to scan rather than as dense as possible.
  - The title is bold, because it says what the ticket is. The playbook name shows its namespace muted and its name in the foreground colour, such as `dev:review-pr-followup` with `dev:` muted, because the name says what the work is and the namespace follows from the source.
  - There is no status text: the group and the mark already say it, and the mark's tooltip names it.
  - The triage context and the task prompt are not shown; Switchboard keeps them in the store. An approval report's summary is shown, because it says what Approve does, and Approve's tooltip names the prompt it runs.
  - Every group can be collapsed; Needs you, Working and Unstarted start open, Done and Snoozed start closed, and the operator's choice is kept.
  - Groups, in this order: **Needs you** when the status is `awaiting-approval`, `blocked` or `failed`, or the active session is `waiting`; **Working** otherwise, while not done, unstarted, triaging or queued; **Unstarted**; **Snoozed** for snoozed tickets (R49); **Done** when the work item is `done` (the last 7 days), newest done first, under date bands as in Windows Explorer: Today, Yesterday, Earlier this week, Last week and Older, with weeks starting on Monday.
  - The **Unstarted** group holds everything not yet running, from every source: `unstarted` and `triaging` work items, `queued` work items unless they need the operator, and pool tickets. A ticket being triaged shows `<namespace>:triage` in place of the playbook name, with the source's namespace, such as `dev:triage` or `support:triage`, or `triage` when the source has none. It sorts by importance (R50), counting an unrated ticket as rank 2, then oldest first by the source's sort time (Zoho's customer response time, Forum's last public post) or the work item's creation, so the most urgent and then the longest-waiting come first. Pool tickets carry no claim tag: the sources leave out tickets another developer has claimed, and a ticket the operator has claimed is a work item, not a pool ticket.
  - The mark shows what differs between rows of the same group, because the group header already says what they share; its tooltip names it in words:
    - **Unstarted:** no mark, except a spinning Triaging mark on a work item or pool ticket being triaged and a Queued mark on a `queued` work item, followed by its wait reasons (R34); the priority dot on the first line is what differs.
    - **Needs you:** what the operator must do: approve work that Approve sends, review work and then approve when the operator sends it by hand (an approval report, by the playbook's setting, R23), answer a question (`waiting`), look at a block, or deal with a failure (red).
    - **Working:** the phase: setting up, running.
    - **Done:** how it ended: the session reported done, the operator marked it done, or the ticket left the assigned state.
    - **Snoozed:** the mark the item would have in the group it returns to, and the wake time on line 3 unless the snooze is indefinite.
  - In Needs you, a `failed` row has a left stripe in the error colour, and a `blocked` row or one whose session asks a question (`waiting`) one in the warning colour, so what needs an answer or a fix stands out from approvals. No other row has a stripe, including in Snoozed.
  - Controls appear only when they apply: Start, Approve, Open in Claude (R70), Stop, Mark done, Triage again, Snooze and Restore, Open Changes on a row with a worktree (R57), Copy (R60), History on every row (R59), the ticket's links (R52), and Open ticket. Each row shows only its main control, 26 pixels high with its codicon and label as in VS Code's buttons (Start, Approve, Open in Claude on a row whose background session waits on a question (R70), or Triage again on a failed row), at the right of lines 2 and 3, and only while the row is selected, so other rows give their text the full width. The list shows no separate session state: the group and the mark say what the work item needs. Approve takes the accent colour, and its tooltip names the prompt it runs. A one-part question shows its option buttons under line 3 (R70). An `awaiting-approval` row whose approval report named a draft also shows a Report button before Approve, with the draft's filename as its tooltip, which opens the draft; no other row shows Report. An `awaiting-approval` row with pastes shows a Copy button before Report (R60). A click elsewhere on the row runs its click (R71). Right-clicking a row opens a menu with every control that applies to it. A control's verb matches the status it acts on: Start for `unstarted` and pool tickets, Approve only for `awaiting-approval`.
  - The time in the queue is in whole minutes, hours, days or weeks, and depends on the group (R53): **Needs you** counts from when the work item entered its status, or its session began to wait; **Working** from when the run started; **Unstarted** and **Snoozed** from when the ticket entered the source's scope, stopping at done. The tooltip names what it counts. A **Done** row shows when it was done instead, in local time: 24-hour `HH:mm` today, else `m/d`, with the done time and scope entry in the tooltip.
  - The dock takes VS Code's Light Modern or Dark Modern colours, by Windows' app mode, and codicons, and looks like a VS Code sidebar: tinted group headings with their count in a badge, a rule between rows, ticket keys in small outlined badges, and flat inputs and buttons. The Settings window takes the same look. It is not a kanban board.
- R28. Switchboard opens no console on a session: a session running in its background process is left running, a question is answered on the row or with Open in Claude (R70), and a session that is not running opens in its item window (R71).
- R29. A work item's session opens in its item window's Claude view, where `claudeCode.preferredLocation` puts it. A session that is not running resumes there; a session already open in VS Code gets focus.

### Runtime

- R33. Switchboard's core runs in a separate process from VS Code and keeps running when the window reloads or closes.
- R42. Settings and playbooks are files in a config folder the operator chooses, so they can be kept in git; by default it is the Switchboard home. The hub reloads them when they change. An invalid settings file leaves the last valid settings in force; a source with invalid settings is disabled; an invalid playbook is left out. Either error shows in the dock.
- R54. The operator edits settings and playbooks in the dock's Settings window, a separate window opened from Settings in the dock's header; Settings again shows the open one. It shows every setting and playbook front matter key as a field with its default and a one-line explanation, and each playbook's template. It checks changes as the operator types and shows each error on its field. Save writes the current page's file, and Save all writes every changed file. Each save refuses what the hub would reject, disable or leave out: an invalid settings file, an enabled source with invalid settings, or an invalid playbook. It also refuses an unknown template variable, which would otherwise fail the session start. It also refuses to overwrite a file that changed on disk after the window read it, and reads the files again when they change. When the config folder changes, the window reads the new folder, discards unsaved changes and says so, and the hub refuses a write made for the old folder. Delete asks first, and says how many open work items use the playbook. A file's path opens it in the VS Code window used last. The window adds and removes sources and creates and deletes playbooks. It does not rename a playbook, because work items store the playbook's name. The files remain the configuration: the operator can still edit them by hand, and the hub reloads them either way.
- R43. On startup the hub reconciles sessions recorded as active against the Claude roster. The hub stays running while any session is active, so sessions can always report, and while a debrief runs (R55).
- R55. Friction debriefs. With the `sessions.debriefs` setting on (it is off by default), the hub asks each of its Claude sessions what slowed it down, for the operator's friction-review skill. It asks as soon as the session's work item is done, otherwise 45 minutes after the session's last turn, in case the operator resumes it; it does not ask 60 minutes or more after that turn, when the prompt cache has expired. It asks only when the session did at least 10 tool calls since its last debrief, and in a fork that leaves the session unchanged. After each session's debrief it asks each Codex thread the session delegated to through agent-delegate in that work, about the thread's turns since its own last debrief. The answers and the record of what was asked are the files Ground Control wrote, so a session Ground Control asked is not asked again about the same work. A failed debrief is reported in the hub log, not on a work item, and is not tried again; the session's later work is asked about with it. The hub does not stay up for a debrief that is not yet due.
