# Switchboard PRD

Switchboard is a local software factory for one developer. It ingests work assigned to the operator, triages each assignment to a playbook, runs the playbook's prompt in a background agent session, and shows the work on the web page the hub serves, its primary interface (R109). The dock, a list docked beside VS Code that switches the screen to a work item's own VS Code window, and VS Code's Conversation view (R96) still run until the web page replaces them.

## Scope

- Switchboard runs on the operator's machine and handles only the operator's work: tickets assigned to them, and the pool of unclaimed tickets in a queue they work, such as support escalations, from which they pick. It has no shared state, accounts or server.
- All Switchboard state is local. Switchboard reads sources and never writes to them; only the skills its sessions invoke change external state.
- Switchboard manages only sessions it starts. It does not discover or adopt sessions started elsewhere, except a fork of a session it started, which continues that session (R78), and a Claude session the operator registers (R81).
- Switchboard does not host agent conversations itself: Claude background sessions run in Claude's background service, Code Mode sessions (R93) in Switchboard's terminal holder (R94), and new Codex sessions as threads in Codex's built-in app-server daemon (R107).
- Switchboard tracks worktrees but never creates or deletes them. Skills create worktrees; the operator removes them.
- Switchboard runs on Windows, and on Linux under GNOME on Wayland.
- Switchboard replaces Ground Control and the Support board entirely; neither runs beside it. Switchboard is a modular, source-agnostic factory that reuses Ground Control's session mechanics (see [architecture.md](architecture.md)).

## Goals

- Turn each assignment into running work: with no click when the operator trusts the playbook, and with one click when they do not.
- Show at a glance which work needs the operator: ready for review or approval, waiting on a question, blocked, or failed.
- Keep sources, playbooks and agent providers pluggable. Adding a source does not change the core.
- Reuse what Ground Control and the operator's skills already do. Switchboard schedules and observes; skills do the work.

## Non-goals

- Writing to sources: no status moves, comments, assignments or labels. Only the skills that sessions run write, including the claim when the operator picks a pool ticket (R48).
- Managing other people's work, team views, accounts or shared state.
- Remote, cloud or multi-machine operation. One hub runs per machine; reaching its web page from the operator's own paired devices over their tailnet (R115) is not remote operation.
- Changing git state: no commits, branches, or creating, cleaning up or removing worktrees. Read-only git queries that validate and link worktrees are allowed.
- Answering a session's permission prompts or questions for the operator.
- Inferring state it did not observe: no stuck-session detection, and no check of a session's work beyond whether its ticket is still assigned when it reports done (R10). Switchboard may colour an observed age, such as the time since a running session's last stage report (R58), but draws no conclusion from it and takes no action.
- Reproducing the source's ticket view or conversation. Switchboard links to the source.
- Reproducing Ground Control's board, lanes or review views, or the Support board.
- Built-in playbooks or namespaces.
- Unattended overnight operation as a committed goal.
- Complex error handling or support for rare edge cases. A failure shows its cause, and the operator recovers by resuming the session, retrying a failed work item, marking it done, or fixing their configuration.

## Design rules

- **Existing tools are context, not requirements.** The retired Ground Control and Support board, and the operator's skills, show how the work was done before Switchboard. Switchboard adopts a behavior from them only when it serves this PRD's goals, and states its own reason.
- **Skills drive the work; Switchboard is the harness.** Switchboard finds tickets, triages them, starts and observes sessions, and shows their state. Every change to a source, a repository or a worktree is made by a skill a session runs. When a feature needs a write, add a session that runs a skill, not Switchboard code that writes.
- **Least authority.** An unattended session gets the least permission mode under which it can finish. The default is `auto`, and Codex's is `bypassPermissions`, because commands in Codex's sandbox cannot use the operator's sign-ins (R22); a playbook can override it.
- **The work item first, sessions second.** The operator manages work items; a session is how one runs, and the dock shows it as one control, not as content.
- **Show each fact once.** The dock follows four rules:
  - What the row's group already says is not repeated on the row.
  - What an icon says is not repeated in text; a button whose icon makes its action clear shows the icon, with the verb in its tooltip.
  - An indicator that is the same on every row it can appear on, or that means nothing, is not shown.
  - A label carries the most specific fact available: a playbook name that also names the kind of work, such as `support:defect`, rather than a generic one.
- **Simple first.** Choose the simplest behavior that keeps common work correct. Handle a rare case by showing it, not with special machinery.
- **Visible failure.** Every failure shows on its work item with the cause. Switchboard does not retry work automatically. A failed source poll is tried again at the next interval.
- **Observed state only.** The dock shows what the roster and session reports say, and how old that observation is. A session's report is its claim and is shown as such.
- **Never cut off work.** Switchboard stops a session only when the operator asks, such as with Continue in Background (R89), to release a session that has finished its turn so the operator can resume it in VS Code (R39), or to end a Code Mode session's process when R95 allows. A session stopped at a usage or rate limit is never ended for it (R111).
- **Start automatically unless it writes.** A playbook whose session makes no external change without the operator's approval starts automatically (`autoStart`). Local work, such as reading, drafting, local commits and worktrees, is not an external change. A playbook that pushes, posts, assigns or moves a card before an approval report waits, `unstarted`, for the operator to start it. A gate the operator has approved for a skill, which lets it write only when the gate passes, counts as approval. A playbook for a ticket whose requested action is unclear also waits, because an action read from older activity is more likely wrong. A concurrency limit caps running sessions (R38).
- **A failed read changes nothing.** A failed or incomplete source poll never moves a ticket out of the assigned state.
- **One unread mark.** Unread shows everywhere as the same badge in one accent colour, VS Code's activity bar badge colour, holding a count where there is one and a dot where there is not (architecture.md § Unread).
- **Empty states say what comes.** Every empty view, list or group says what is missing and what makes it appear, or what to do, in two short sentences in one style: "No artifacts yet. They appear here when the session writes one."
- **A file for configuration, the store for state.** Settings and playbooks are a file the operator edits and can keep in git. Work items, sessions and history live in the store.

## Terms

| Term | Meaning |
|---|---|
| Source | A plugin that supplies tickets: GitHub, Zoho Desk, Forum, ad-hoc prompts, or schedules. |
| Ticket | Switchboard's local copy of a source record, identified by source and source key. |
| Assigned state | A source-defined condition meaning the ticket is the operator's to work, such as assignee plus status. |
| Work item | One assignment of one ticket to the operator. The primitive Switchboard schedules and displays. |
| Pool | A source's open, unclaimed tickets that the operator may pick, such as support cases assigned to no one or still held by the escalating General agent. Pool tickets are triaged but are not work items. |
| Blocker | An open issue that the source lists as blocking a ticket, such as one in a GitHub issue's "blocked by" dependencies (R90). |
| Pick | Starting a pool ticket: the operator starts it, which creates a work item and starts its task session (R48). |
| Playbook | A named prompt template and its settings, such as `support:defect` or `dev:qa-failure`. A source's triage playbook holds the classifier's instructions. |
| Triage | A one-shot classification of a work item or pool ticket that chooses its playbook. Triage is not a session. |
| Session | One agent conversation for a work item. Kinds: `setup`, `task`. |
| Active session | A session whose process is running, in the background, in the terminal holder or in a VS Code tab. |
| Stage | A free-text label a session reports about its progress. Switchboard displays it and does not act on it. |
| Web page | The page the hub serves, Switchboard's primary interface, which lists the work items and shows their conversations (R109). |
| Dock | Switchboard's native app, which lists the work items at the edge of the screen (R27, R71). It runs until the web page replaces it. |
| Item window | The VS Code window the dock opens for one work item's folder (R71). |
| Terminal holder | Switchboard's process that holds Code Mode sessions in hidden terminals, so they run while no terminal shows them and outlive the hub (R94). |

## Requirements

### Sources

- R1. Each source is a plugin behind one interface that lists the operator's tickets and reports whether each is in the assigned state. The plugin defines the assigned state and builds the triage context: the ticket's text, within size limits, with authors, status changes and assignees. The context lets triage tell whose words it reads: the GitHub source can name comment authors' roles, such as tester, from a file the operator names, marks bot accounts, and on somebody else's pull request states whether the operator has already reviewed or commented, or that the history was too long to tell, so a bot's review does not read as the operator's earlier review round.
- R2. Switchboard polls each enabled polling source and stores each ticket's last-seen state locally.
- R3. Each source has its own settings, including its repo root and its triage playbook. The operator turns each source on and off from the dock's header (R71), because some work, such as Support, is done only some weeks; a disabled source is not polled and its pool is hidden, while its work items stay. Whether a source is on is state in the store, not a setting, so turning one on or off never changes the settings file; a configured source is off until the operator turns it on.
  - A source is named by its settings key and read by the plugin of its kind, which defaults to its name, so one plugin can read several sources, such as a personal GitHub board beside the Acme one. Tickets, toggles and errors belong to the source's name. Only a GitHub source may be named apart from its kind, and no source may take another kind's name, because Switchboard's database upgrades find Zoho and Forum tickets by source name. Two GitHub sources may not read the same project board, even when one is off, because an issue would then belong to both. `schedule` is not a source name, and `adhoc` holds only the ad-hoc repo root.
  - Each source keeps its own toggle when several share a kind.
- R4. The ticket sources are GitHub (R44), Zoho Desk (R46) and Forum (R5), beside ad-hoc prompts (R6) and schedules (R82).
- R44. A GitHub ticket is in the assigned state when it is an open issue in any repository on the source's project board, it is assigned to one of the configured logins, and its project item's status is one of the configured statuses; with no status configured, any status or none qualifies. All of these are settings. For an operator who moves issues on the board without assigning them, the assignee check can be turned off (`requireAssignee`), so the status alone decides; the logins still name the operator's own activity (R80). For a team that closes an issue before its pull request merges, closed issues can count like open ones (`includeClosed`, off by default), leaving the assigned state when their status or assignee does. The operator's values for `acme/widgets` are in [architecture.md](architecture.md#settings). GitHub is read through the `gh` CLI with `gh`'s own authentication. A poll fails, changing nothing, when the board has no single-select field with the configured status name, because every issue would otherwise read as unassigned.
  - A GitHub source covers every repository on its board, so adding a repository to the board needs no setting. Each source names a home repository: its issues keep bare keys, such as `18941`, and an issue in another repository is keyed `owner/name#63`. The home repository cannot change once the source has tickets, because bare keys mean it; settings that change it are refused.
  - An issue belongs to one source: when an issue on two boards already has a ticket in one source, the other source leaves it out and the dock notes which source has it.
  - A work item for an issue outside its source's home repository waits for Start, whatever its playbook's `autoStart`, and its row says why: a source's playbooks and the skills they run are written for its home repository, and one that starts by itself must not run them elsewhere unseen.
- R5. The Forum source reads forum topics from the production forum database. A topic is in the assigned state when it is open in the Forum forum and assigned to the operator. An open topic assigned to no one is in the pool (R47). A topic another person has claimed is neither.
- R46. The Zoho Desk source reads tickets through the Desk API. A ticket is in the assigned state when its status type is Open, its escalation field holds the configured Support value (`Support` by default), and it is assigned to the operator. Such a ticket assigned to no one, or to a support agent or team, is in the pool (R47): General escalations stay assigned to the escalating General agent, so a support assignee counts as unclaimed. A ticket assigned to another engineer is neither.
- R47. A source can have a pool. Switchboard triages each ticket when it enters the pool, keeps the result with the ticket, and shows the pool with each ticket's chosen playbook. A failed pool triage shows its error on the pool ticket, which the operator can triage again; a pool ticket can be started only once its triage has a result. A ticket that leaves the pool without a pick, because someone else claimed it or it closed, disappears from it. GitHub has no pool.
- R48. The operator picks a triaged pool ticket by starting it in the dock. Switchboard creates a work item that reuses the pool triage and starts its playbook's task session, because the pick is the operator's start, whatever the playbook's `autoStart`. Claiming the ticket is the playbook's work; Switchboard does not claim and does not check the claim. A ticket that returns to the assigned state on its own, such as a case reopened after On Hold, follows its playbook's `autoStart` like any other new work item.
- R6. The ad-hoc source creates a ticket and a work item from a prompt the operator enters as the first message of the New session form (R122), on the dock or the web page, run as a task, with the folder, the provider, Claude or Codex, and the model it runs in. The chosen provider and model are kept for delayed starts and retries; cancelling creates nothing. The typed prompt replaces the playbook template: triage does not run, and the task session runs the typed prompt. The work item waits `unstarted` for Start (Task, wait for Start), or is queued and starts as soon as a slot is free (Task, start when a slot is free).
  - The operator picks the folder as New session offers it (R122): among them the repo roots, each source's root for its home repository and the root of each other repository with stored tickets (R21), never a pattern. The session runs there with no worktree requirement and no playbook, using the `sessions` permission mode, and the chosen model or else the `sessions` one.
  - The ticket key shows the repository or folder name before its local sequence number, which remains the stored identity. A prompted task's title is its prompt's first line.
  - The New session form's More options offers **Run now** for each schedule (R82), which queues a run of that schedule at once.
- R82. **Schedules.** A schedule runs a task playbook on a calendar or by hand, with no ticket from a source, for recurring work such as a monthly self-review or a weekly worktree cleanup.
  - Each schedule is a named entry in settings that names its task playbook and the repo root its sessions run in, and, unless it runs only by hand, a daily, weekly or monthly local time; a monthly day that a month lacks runs on that month's last day. The playbook must be a task playbook that needs no worktree, because a schedule has no source to set one up; settings that name another are refused.
  - Each schedule is one ticket of the `schedule` source, keyed by its name, and each run is a work item of that ticket, so History lists every run. A run is not triaged: it takes the schedule's playbook and waits `unstarted` or is queued as the playbook's `autoStart` says. Run now (R6) queues it whatever `autoStart` says, because the operator asked for it. Its sessions run in the schedule's repo root. A done report ends the run without reading a source (R10). A run whose playbook is missing or not a task playbook fails with that cause.
  - A run starts within a minute of its time. Schedules run only while the hub does, so times that passed while the hub was stopped give one run when it next runs, however many passed. A time that passed before the schedule was added, changed, or added again after its removal does not run.
  - A schedule makes no run while its ticket has an open work item; History records the skipped time, so unanswered runs do not collect, and Run now is refused.
  - A run counts no earlier run as a return (R51). A failed run offers Retry (R34). Snoozing the ticket holds a run queued until it wakes (R49). Removing a schedule from settings stops its runs and keeps its work items.
  - A scheduled playbook is an ordinary playbook. One in a namespace that no source triages into is never chosen by triage, and its row names the work, such as `ops:cleanup-worktrees`.

### Work items

- R7. Switchboard creates a work item each time a ticket enters the assigned state with no open work item. A ticket assigned again after its work item is done gets a new work item; one that returns while its work item is still open, such as during that item's active session, continues that work item.
- R8. On first run, every ticket already in the assigned state gets a work item.
- R9. Work item status is local and never mirrored to the source.
- R10. A work item is done when its task session reports done, when the operator marks it done, or when its ticket leaves the assigned state while no session is active. An open work item that never had a session is deleted instead when its ticket leaves, because nothing was done on it, so it appears in neither Done nor History and its activity, including its pool triages', is removed; an operator action that named only the ticket, such as the pick that created it, stays. A work item in triage is deleted only once its triage ends, and a return before then keeps it. If the ticket leaves while a session is active, the work item stays open until that session reports done or ends, because a session can take the ticket out of the assigned state before it finishes.
  - When a task session reports done, Switchboard confirms with the ticket's source that the ticket left the assigned state, allowing for a source that shows an unassignment late, as GitHub's issue search lags one by seconds. If the ticket is still assigned after that allowance, the session did not hand it off, which is a skill defect, so the work item becomes `blocked` for the operator instead of done, and the session is not told. The work item is done once the ticket is found outside the assigned state, even while the session is still active. A read that fails or does not answer promptly accepts the report, so a slow or failing source does not hold up the session. Resuming the session, or an approval report, before the check settles cancels its effect. A held Code Mode session of a done work item keeps running until R95 ends it.
- R88. A ticket leaves the assigned state only when its source confirms it. A source reads a ticket on its own before it reports the ticket as gone when its listing leaves the ticket out or lists it outside the assigned state, because during a GitHub outage the issue search can succeed with an incomplete result. A failed confirming read fails the poll, which changes nothing.
- R11. A work item with a session that ends because its ticket left the assigned state, without a done report, stays listed in Done with no warning; leaving the assigned state is routine.
- R34. Work item statuses are `triaging`, `unstarted`, `queued`, `setup`, `running`, `awaiting-approval`, `finished`, `blocked`, `failed` and `done`.
  - `unstarted` waits for the operator to start it, because its playbook does not start automatically.
  - `awaiting-approval` means a session's work is finished and waits for the operator to approve the prompt that publishes it (R23). When its session runs again, as when the operator answers its question or resumes it, the work item is `running` until that run ends; the run's own approval or done report applies, and a run that ends or is stopped without one returns the work item to `awaiting-approval` with the earlier approval and the cause of a failed turn or a stop.
  - `finished` means a task session ended its turn or its process without a report, and its playbook offers neither done nor approval (R23), or the operator reopened the work item after its session's turn ended (R86), so its work waits for the operator's review. The operator resumes it or marks it done.
  - `queued` waits for a session slot (R38), for the turn of another session of the same ticket to end (R17), including the work item's own earlier session, for its ticket to wake (R49), or for its blockers to close (R90). Its row shows each reason that holds and what ends it.
  - `blocked` means a session ended its turn or its process without the done or approval report its playbook offers, or the operator stopped it while no approval was pending (R40), or a task session reported done while its ticket was still in the assigned state (R10), or a session stopped at a usage limit (R111). Its reason names the report the session was offered, or the limit. The operator resumes it or marks it done; a work item whose setup stopped at a usage limit also offers **Retry**, which retries setup as for a failed one.
  - `failed` means a Switchboard step failed: triage, a session start, or a setup session that ended without a worktree. The dock shows the cause and offers **Retry**, which retries from the step that failed: a failed triage runs again, and the work item then starts or waits as the chosen playbook says; any other failed work item, ad-hoc and scheduled ones included, is queued with its playbook, approved prompt and guidance, so its next start runs setup when it lacks a needed worktree, else the approved prompt, else the task session. Retry does not change readiness (R27). A work item that failed at triage stays in Unstarted (R27).
- R35. A work item has no Triage again control; Retry on a work item that failed at triage (R34) and Reopen of a done work item that has no playbook (R86) triage it again. The operator can choose another task playbook of the namespace of triage's choice when starting with guidance (R77). Starting with another replaces triage's choice: the row, History and every later session take it, and setup runs first when it requires a worktree the ticket lacks (R19). The focus stays as triage set it (R79). An ad-hoc work item has no playbook to change, and a scheduled run keeps its schedule's (R82), so neither offers the choice.
- R86. The operator can reopen a done work item when it is its ticket's latest work item, the ticket has no open one, and no other session handles the ticket's assignment (R85), because a session can report done while work remains or keep working after its done report. Reopen clears how the work item ended and returns it to where its work stands: `running` while its task session is in a turn, which then ends by the usual report and turn-end rules; `awaiting-approval` once that turn has ended when an approval (R23) still waited, or was approved but its run had not started, when the work item became done without a done report, and while in a turn it holds that approval as R34 does; otherwise `finished` once that turn has ended, so the operator resumes the session or marks it done; and `unstarted`, or `triaging` without a playbook or prompt, when it never had a task session. A session that keeps working after its done report does not reopen the work item by itself.
- R45. Only reports from a work item's latest session change the work item. Reports from earlier sessions are recorded on those sessions. A report from a copy that a fork retired is refused (R78).
- R90. A ticket with an open blocker does not start. The check is off by default and turned on per GitHub source (`waitForBlockers`), because stacked work legitimately starts from its blocker's branch; while it is off, no ticket has blockers. With it on, only open blockers count, as the source last read them; other sources have none. Every start of the ticket's work, automatic or by the operator, including Approve and Retry, queues it, and the work item starts once the source reads no open blocker, as a wait for a slot ends (R38); a session already running is not stopped. An open work item's or pool ticket's row names its blockers as a warning, and a queued row names them as its wait reason instead. History records each change to the blockers. While the check is on there is no per-ticket override: to start one ticket's work before its blocker closes, the operator removes the dependency in the source, or turns the check off.

### Playbooks

- R12. A playbook name is `<namespace>:<name>`, such as `support:defect`, `support:question`, `dev:qa-question`, `dev:qa-failure` or `dev:new-dev`. A namespace is the role the operator works the ticket in, such as `support` for support support or `dev` for development.
- R13. Namespaces and playbooks are not built into Switchboard. Any playbook defined in configuration is valid, and triage chooses among them.
- R14. A playbook owns a prompt template. Switchboard renders it with the ticket's fields, the triage context and the Switchboard session ID.
- R15. Each playbook is configured to start its task session automatically after triage or to wait, `unstarted`, for the operator to start it. A work item whose triage found nothing new waits whatever its playbook says (R80).
- R16. Each playbook states whether it requires a worktree to start, and where its session runs: in the ticket's worktree when one exists, or always in the ticket's repo root, as the `support` playbooks do. A playbook that requires no worktree and has no worktree yet starts in the repo root.

### Sessions

- R17. A ticket has at most one session in a turn across all its work items, because its work items share one worktree. Switchboard starts no session while another session of the same ticket is starting, running or waiting on a question. A session whose turn has ended, such as one the operator keeps open idle, does not hold a start back. A work item's active session is its latest session while that session has not ended; an earlier session left open is not. Ended sessions are kept as history.
- R18. A new work item is triaged first. Triage is a one-shot classifier with no tools: from the source's triage context, which includes the current time, and the source's triage playbook, it returns the playbook that handles the work item and its focus (R79). A triage playbook chooses a specific playbook only when the context states the requested action by the source's rules, and otherwise its playbook for an unclear ticket, such as `dev:other` for GitHub, where an assignment alone states no action, nor does activity an earlier work item already handled (R80).
- R79. **Focus.** Triage also returns the work item's focus: the page or comment the operator reads first to do the chosen playbook's work, the earliest such comment when several ask for it. An item window opens only the focus (R72), so the operator lands on the comment that asks for the work.
  - A comment can be the focus only when it is in the triage context and its source gives it a URL that opens at it, as GitHub's issue, pull request and review-thread comments have; Zoho Desk and Forum focus the ticket, because no per-thread or per-post URL has been shown to open at its comment.
  - A task playbook may name the page its work is done on, the ticket or its pull request, and its focus then stays on that page, else the ticket.
  - The focus is set when a triage succeeds and kept through a later triage that runs or fails, a playbook report (R23) or a settings change. A work item never triaged successfully, or a pool ticket being triaged again (R47), focuses its ticket.
- R80. **Nothing new.** A new work item whose ticket had an earlier one acts only on activity newer than that earlier work item, because the earlier one already acted on what was there and anything more would be a guess, as when the operator unassigns and reassigns an issue by mistake.
  - Activity is a comment, a review or a commit by anyone other than the operator, bots included, because the operator's own, such as a session's, ask nothing of the operator; a commit counts because an author who pushes fixes and returns the card asks for another review without a comment. A status or assignment change is not activity; only a first work item acts on one, such as 🎁 Assigned for development.
  - The earlier work item is the ticket's latest one that took in the activity, when the first of its task sessions that started began or when the operator marked it done without a session; a handled-assignment registration (R85) counts as one from when it registered, with the reporting work item's playbook.
  - Triage is told the earlier work item's playbook and time, and treats activity up to then as background. When nothing is newer, triage chooses its playbook for an unclear ticket, and the work item waits `unstarted` for the operator's Start whatever the playbook's `autoStart`, saying why.
  - A source that does not report activity, such as Zoho Desk and Forum, whose playbooks all wait for Start, is not checked.
- R19. When the chosen playbook requires a worktree and the ticket has none, a setup session runs after triage to create one, and the task session starts once the setup session finishes with a worktree linked: at its process's end, or at its turn's end for a session that keeps running, such as one the operator resumed (R70) or a Code Mode one (R95), unless the turn stopped at a limit (R111). A setup session that ended without a worktree because its process was gone, as at a logout, returns its work item to setup when the operator resumes it.
- R20. The task session runs the rendered playbook prompt and handles the work item from start to finish.
- R21. A session without a worktree runs in the ticket's repo root. A session that creates a worktree reports it, and Switchboard links it to the ticket.
  - A ticket's repo root is its own when it has one, as an ad-hoc or schedule ticket does, else the source's `repoRoot`, in which `{name}` and `{owner}` stand for the ticket's repository, such as `D:/git/{name}`. A `repoRoot` without `{name}` serves only the source's home repository, and a ticket in another repository fails to start with the reason. Two repositories that resolve to one folder both fail to start until the pattern adds `{owner}`.
  - Switchboard never clones a repository; a start in a folder that holds no clone fails, naming the repository and the folder, and a linked worktree does not lift a refused repo root.
  - Each ticket records its repository, which a playbook's template can name, with the issue number.
- R22. A session runs in Claude Code or Codex.
  - `sessions.provider` sets the agent for every session, and a playbook's provider overrides it for its work items' sessions. An ad-hoc prompt or hosted conversation uses the provider chosen for it, else `sessions.provider`, until a playbook takes its work item over. Choosing a provider never changes the configured default or an existing session. The session records its agent, and the controls that open it and History name it.
  - Each agent has its own default permission mode and model, and a playbook's own apply to its agent. Codex sessions run without Codex's sandbox by default, because commands in the sandbox cannot use the operator's sign-ins, such as `gh`'s ([mechanics.md](mechanics.md) M31).
  - A Codex session gets the same prompt, with a leading skill command written as Codex runs a skill, and the same report contract, with native questions and permissions handled by R107; existing exec sessions keep their question report and handoff (R70).
  - Triage uses `sessions.provider`, whatever a task playbook's provider. A configured triage model of the other provider falls back to the selected provider's default, with the reason logged; an unknown model name passes through unchanged.

- R83. **Ticket reports.** Work often starts as an ad-hoc prompt (R6) or a registered session (R81), and a skill then files a ticket that records it, such as a GitHub issue. ### Observation and control

- R27. The dock (R71) lists work items. The list centres on the work item; sessions are secondary: a click on a row switches the screen to its work. The web page's list (R109) uses the same groups, order, turns and marks.
  - **Keys.** A row names its ticket by the shortest key that is unambiguous among the operator's sources and repositories, such as `gh 18941`, else `owner/name#63`, and names linked issues the same way. A VS Code window is named from the source and stored key, never a display label, so a label change does not open a new window.
  - **Rows.** Rows do not expand, and every row has at least two lines, so the list stays easy to scan rather than as dense as possible. The first line says what the ticket is: its title, the priority dot (R50) and the time in the queue. The second says what the work is and where it lives: a comment icon (R87), the playbook name with its namespace muted, the key, the ticket's links (R52) and the Returned count (R51). A third line, shown only when it has something, holds the work's state: the mark, wait reasons or the snooze (R49), blockers (R90), warnings and errors, the work item a reported task came from (R68), and the stage and its age (R58) or the question (R70). The key and each link open in the browser instead of running the row's click; a link the ticket's text only names (R61) is drawn apart, so it does not read as the work's own. On an `awaiting-approval` row the approval summary takes the place of the stage, because it says what Approve does and the stage only says the work is ready.
  - An ad-hoc work item has no playbook, so its playbook slot names how it was made: a typed prompt (R6), a session's task report (R68) or a registered session (R81).
  - There is no separate status text: the group and the mark say it, and a mark alone on line 3 shows its words, so the icon never stands alone. The triage context and the task prompt are not shown on the row; an ad-hoc or task work item's prompt shows in Start with prompt… (R77) and History (R59).
  - **Groups**, in this order: **Ready for review**; **Blocked on you**, shown only when it has rows; **In progress**; **Unstarted**; **Snoozed** for snoozed tickets (R49); and **Done**. Every group can be collapsed, and the operator's choice is kept; Done and Snoozed start closed.
    - A work item that is `unstarted` or `triaging`, or failed at triage (R34), is in Unstarted. Any other work item that is not done is in Ready for review when it has been ready; otherwise in Blocked on you when its status is `blocked` or `failed` or a question waits on the operator (R70); otherwise in Unstarted when it is `queued`, and in In progress when it is not.
    - A work item becomes ready the first time it becomes `awaiting-approval` or `finished`. Nothing ends it, Retry included, so it keeps its place in Ready for review while its session runs again, its approved run waits for a slot, or it waits on the operator. A returned ticket's new work item (R51) starts not ready.
    - Unstarted holds everything not yet running, from every source, pool tickets included. It sorts by importance (R50), counting an unrated ticket as rank 2, then oldest first by the source's sort time (such as Zoho's customer response time or Forum's last public post) or the work item's creation, so the most urgent and then the longest-waiting come first. Pool tickets carry no claim tag: the pool excludes tickets another developer has claimed, and a ticket the operator has claimed is a work item, not a pool ticket.
    - Blocked on you lists the oldest wait first; Ready for review lists in the operator's order (R73), else by when each work item became ready, oldest first; In progress lists by when the run started, oldest first.
    - Done holds the work items done from local midnight on the Monday two weeks before this week's, newest first, under bands by local day and week (Today, Yesterday, Earlier this week, Last week and Two weeks ago), so its oldest band holds a whole week. This is the Done window that other requirements name.
  - **Turns.** Each row in Blocked on you, Ready for review and In progress is on the operator's turn or the agent's. It is the operator's in Blocked on you, and on a `blocked`, `failed`, `awaiting-approval` or `finished` row or one with a question waiting on the operator; it is neither's on an idle hosted conversation (R102); it is the agent's on every other row, such as an approved run setting up, running or waiting for a slot. In Ready for review a row on the agent's turn is dimmed. Every unsnoozed row on the operator's turn has a left stripe, in the error colour for a failure, the warning colour for a block or a question, and the accent colour for other Ready for review rows, so what needs an answer or a fix stands out from reviews. Rows on the agent's turn and rows in Unstarted, Done and Snoozed have no stripe.
  - **Marks.** The mark shows what differs between rows of the same group, because the group header already says what they share, and its tooltip names it in words: in Unstarted only triage in progress, a failed triage with its error, or a queued start with its wait reasons (R34); in Blocked on you what the operator must do (answer a question or a permission prompt, R70, look at a block, or deal with a failure); in Ready for review, on the operator's turn what to do (those actions, approve, review and then approve by hand, R23, or review a finished turn) and on the agent's turn the phase; in In progress the phase; in Done how it ended (the session reported done, the operator marked it done, or the ticket left the assigned state); in Snoozed the mark of the group the item returns to.
  - **Controls.** Controls appear only when they apply, and a control's verb matches the status it acts on: Start for `unstarted` work items and pool tickets, Approve only for `awaiting-approval`. The right-click menu has every control that applies (R71). A row shows only its main control, the one action that moves its work on, such as Start, Approve, Retry, Open in Claude for a question (R70) or Open in terminal for a prompt answered there (R41, R70), and only while the row is selected, so other rows keep the full width for their text. The tooltip names what it counts. A **Done** row shows when it was done instead.
  - **Look.** The dock looks like a VS Code sidebar in VS Code's Light Modern or Dark Modern colours, which the operator sets to follow the operating system, the most recently focused VS Code window, or always light or dark. It is not a kanban board.

## Assignments already handled by another session

- R85. A skill may register, through its session's report ([architecture.md § Handled assignments](architecture.md#handled-assignments-r85)), that its session already handles another ticket's current operator assignment. Switchboard records that assignment on the target ticket and creates no duplicate work while it remains the same assignment. The report must succeed before the skill makes the target actionable. Registration removes duplicate work that has never had a session; it is refused when an open work item of the target has already had a session, including a start still in flight, and only the current session of an open work item can register. Ordinary links and playbook names never register handling. The ticket is looked up in each enabled source, the one that already holds a ticket at the URL first; a board-based source answers only for a ticket on its board. A registered ticket is read again through its own source on each poll, on its board or not.
- The registration survives restarts and lasts while the reporting work item is open. When that work item becomes done or is deleted, the registration ends, even if its session keeps working (R86), so the ticket is not hidden once nothing tracks the work; a still-assigned ticket then gets a work item, triaged under R80 with activity up to the registration as earlier work. Reopening the reporting work item does not restore the registration. A verified end of the operator assignment clears it; a new assignment permits normal work, including unassignment and reassignment between polls. Board status and project membership changes alone do not clear it. A skill may explicitly release the matching assignment to resume normal processing during that assignment. A failed or incomplete source read changes nothing and retries normally.
- The source must identify actual operator assignments independently of queue eligibility. Sources without that capability refuse registration, and a source configured not to require an assignee does not make an unassigned ticket count as assigned. The target's History records registration and clearing. Released registrations cannot be restored by a retry, and a reporting session cannot claim a later assignment of the same ticket.
- Skills own publication and approval sequencing. Switchboard has no Support-specific handling rule.

- **Q10. Shell work that outlives a Code Mode session.** **Deferred 2026-11-19 until a real leak shows up.** A shell command a Code Mode session started can keep running after the holder dies and its `claude` exits, outside `claude`'s process tree and the roster ([mechanics.md](mechanics.md) M69). Ending a session lets Claude end its own shell commands (M78), and the check before a resume (R95) looks at the session's last-seen process tree, but neither catches a process that left the tree, a command still running when the holder dies, or one a tree kill after a failed close leaves. A container the holder could end whole, such as a kill-on-close job object on Windows or a process group elsewhere, would; it is added when such a leftover is seen in use.
