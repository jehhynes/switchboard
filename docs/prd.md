# Switchboard PRD

Switchboard is a local software factory for one developer. It ingests work assigned to the operator, triages each assignment to a playbook, runs the playbook's prompt in a background agent session, and shows what each session is doing in the dock, a list docked beside VS Code that switches the screen to a work item's own VS Code window.

## Scope

- Switchboard runs on the operator's machine and handles only the operator's work: tickets assigned to them, and the pool of unclaimed tickets in a queue they work, such as support escalations, from which they pick. It has no shared state, accounts or server.
- All Switchboard state is local. Switchboard reads sources and never writes to them; only the skills its sessions invoke change external state.
- Switchboard manages only sessions it starts. It does not discover or adopt sessions started elsewhere, except a fork of a session it started, which continues that session (R78), and a Claude session the operator registers (R81).
- Switchboard tracks worktrees but never creates or deletes them. Skills create worktrees; the operator removes them.
- Switchboard runs on Windows, and on Linux under GNOME on Wayland. On Linux the dock (R71) reserves the left or right edge of the primary monitor and does not auto-hide; it brings item windows forward through Switchboard's GNOME Shell extension, and without the extension asks VS Code to focus an item window instead ([Implementation gaps](#implementation-gaps)).
- Switchboard replaces Ground Control and the Support board entirely; neither runs beside it. Ground Control began as an observability layer linking sessions to GitHub cards; Switchboard is a modular, source-agnostic factory that reuses Ground Control's session mechanics (see [architecture.md](architecture.md)).

## Goals

- Turn each assignment into running work: with no click when the operator trusts the playbook, and with one click when they do not.
- Show at a glance which work needs the operator: ready for review or approval, waiting on a question, blocked, or failed.
- Keep sources, playbooks and agent providers pluggable. Adding a source does not change the core.
- Reuse what Ground Control and the operator's skills already do. Switchboard schedules and observes; skills do the work.

## Non-goals

- Writing to sources: no status moves, comments, assignments or labels. Only the skills that sessions run write, including the claim when the operator picks a pool ticket (R48).
- Other people's work, team views, reporting, accounts or shared state.
- Remote, cloud or multi-machine operation. One hub runs per machine.
- Changing git state: no commits, branches, or creating, cleaning up or removing worktrees. Read-only git queries that validate and link worktrees are allowed.
- Answering a session's permission prompts or questions for the operator.
- Inferring state it did not observe: no stuck-session detection, and no check of a session's work beyond whether its ticket is still assigned when it reports done (R10). The dock may colour an observed age, such as the time since a running session's last stage report (R58), but draws no conclusion from it and takes no action.
- Reproducing the source's ticket view or conversation. The dock links to the source.
- Reproducing Ground Control's board, lanes or review views, or the Support board.
- Built-in playbooks or namespaces.
- Unattended overnight operation as a committed goal.
- Complex error handling or support for rare edge cases. A failure shows its cause, and the operator recovers by resuming the session, Triage again, Mark done, or a fix to their configuration.

## Design rules

- **Existing tools are context, not requirements.** The retired Ground Control and Support board, and the operator's skills, show how the work was done before Switchboard. Switchboard adopts a behavior from them only when it serves this PRD's goals, and states its own reason.
- **Skills drive the work; Switchboard is the harness.** Switchboard finds tickets, triages them, starts and observes sessions, and shows their state. Every change to a source, a repository or a worktree is made by a skill a session runs. When a feature needs a write, add a session that runs a skill, not Switchboard code that writes.
- **Least authority.** An unattended session gets the least permission mode under which it can finish. The default is `auto`; a playbook can override it.
- **The work item first, sessions second.** The operator manages work items; a session is how one runs, and the dock shows it as one control, not as content.
- **Show each fact once.** The dock follows four rules:
  - What the row's group already says is not repeated on the row.
  - What an icon says is not repeated in text; a button whose icon makes its action clear shows the icon, with the verb in its tooltip.
  - An indicator that is the same on every row it can appear on, or that means nothing, is not shown.
  - A label carries the most specific fact available: a playbook name that also names the kind of work, such as `support:defect`, rather than a generic one.
- **Simple first.** Choose the simplest behavior that keeps common work correct. Handle a rare case by showing it, not with special machinery.
- **Visible failure.** Every failure shows on its work item with the cause. Switchboard does not retry work automatically. A failed source poll is tried again at the next interval.
- **Observed state only.** The dock shows what the roster and session reports say, and how old that observation is. A session's report is its claim and is shown as such.
- **Never cut off work.** Switchboard stops a session only when the operator asks, or to release a session that has finished its turn so the operator can resume it in VS Code (R39).
- **Start automatically unless it writes.** A playbook whose session makes no external change without the operator's approval gets `autoStart: true`. Local work, such as reading, drafting, local commits and worktrees, is not an external change. A playbook that pushes, posts, assigns or moves a card before an approval report waits, `unstarted`, for the operator to start it. A skill's own documented gate, such as `/or-merge` pushing only clean or high-confidence merges and halting otherwise, is the operator's approval policy and counts as approval. A playbook for a ticket whose requested action is unclear also waits, because an action read from older activity is more likely wrong. A concurrency limit caps running sessions (R38).
- **A failed read changes nothing.** A failed or incomplete source poll never moves a ticket out of the assigned state.
- **A file for configuration, the store for state.** Settings and playbooks are a file the operator edits and can keep in git. Work items, sessions and history live in the store.

## Terms

| Term | Meaning |
|---|---|
| Source | A plugin that supplies tickets: GitHub, Zoho Desk, Forum, ad-hoc prompts, or schedules. |
| Ticket | Switchboard's local copy of a source record, identified by source and source key. |
| Assigned state | A source-defined condition meaning the ticket is the operator's to work, such as assignee plus status. |
| Work item | One assignment of one ticket to the operator. The primitive Switchboard schedules and displays. |
| Pool | A source's open, unclaimed tickets that the operator may pick, such as support cases assigned to no one or still held by the escalating General agent. Pool tickets are triaged but are not work items. |
| Pick | Starting a pool ticket: the operator presses Start on it. It creates a work item and starts its task session, whose skill assigns the ticket to the operator before it works the ticket. |
| Playbook | A named prompt template and its settings, such as `support:defect` or `dev:qa-failure`. A source's triage playbook holds the classifier's instructions. |
| Triage | A one-shot classification of a new work item, or of a ticket entering the pool, that chooses its playbook. Triage is not a session. |
| Session | One agent conversation for a work item. Kinds: `setup`, `task`. |
| Active session | A session whose process is running, in the background or in a VS Code tab. |
| Stage | A free-text label a session reports about its progress. Switchboard displays it and does not act on it. |
| Dock | Switchboard's native app, which lists the work items at the edge of the screen (R27, R71). |
| Item window | The VS Code window the dock opens for one work item's folder (R71). |

## Requirements

### Sources

- R1. Each source is a plugin behind one interface that lists the operator's tickets and reports whether each is in the assigned state. The plugin defines the assigned state and builds the triage context: the ticket's text, clipped to size limits and formatted with authors, status changes and assignees. The GitHub source can show each comment author's roles, such as tester, from a file the operator names, so triage can tell a tester's report from a developer's question.
- R2. Switchboard polls each enabled polling source and stores each ticket's last-seen state locally.
- R3. Each source has its own settings: poll interval, repo root, and its triage playbook. The operator turns sources on and off with an on/off toggle per source in the dock's header (R71), because some work, such as Support, is done only some weeks; a disabled source is not polled and its pool is hidden, while its work items stay. Whether a source is on is state, kept in the store, not a setting, so a toggle never changes settings.json; a configured source is off until the operator turns it on.
- R4. GitHub is the first source. Zoho Desk and Forum follow.
- R44. A GitHub ticket is in the assigned state when it is an open issue in the configured repository, it is assigned to one of the configured logins, and its project item's status is one of the configured statuses. All of these are settings. The operator's values for `acme/widgets` are in [architecture.md](architecture.md#settings). GitHub is read through the `gh` CLI with `gh`'s own authentication. A poll fails, changing nothing, when the project has no single-select field with the configured status name, because every issue would otherwise read as unassigned.
- R5. The Forum source reads forum topics from the production forum database. A topic is in the assigned state when it is open in the Forum forum and assigned to the operator. An open topic assigned to no one is in the pool (R47). A topic another person has claimed is neither.
- R46. The Zoho Desk source reads tickets through the Desk API. A ticket is in the assigned state when its status type is Open, its escalation field is `Support`, and it is assigned to the operator. Such a ticket assigned to no one, or to a support agent or team, is in the pool (R47): General escalations stay assigned to the escalating General agent, so a support assignee counts as unclaimed. A ticket assigned to another engineer is neither.
- R47. A source can have a pool. Switchboard triages each ticket when it enters the pool, keeps the result with the ticket, and shows the pool with each ticket's chosen playbook. A failed pool triage shows its error on the pool row with Triage again; a pool ticket offers Start only once its triage has a result. A ticket that leaves the pool without a pick, because someone else claimed it or it closed, disappears from it. GitHub has no pool.
- R48. The operator picks a triaged pool ticket by pressing Start on it in the dock. Switchboard creates a work item that reuses the pool triage and starts its playbook's task session, because the pick is the operator's start, whatever the playbook's `autoStart`. The playbook's skill claims the ticket for the operator as its first step, as `/support-process` does through `support-bind`, then works the ticket; when anyone else holds the ticket or the claim fails, the skill reports it and stops, so the work item is `blocked`. Switchboard does not claim and does not check the claim. A ticket that returns to the assigned state on its own, such as a case reopened after On Hold, follows its playbook's `autoStart` like any other new work item.
- R6. The ad-hoc source creates a ticket and a work item from a prompt the operator enters in the dock's New Ad-hoc Session window (R71), choosing the repository when more than one is configured. The typed prompt replaces the playbook template: triage does not run, and the task session runs the typed prompt. The work item waits `unstarted` for Start unless the operator checks Start automatically, which is unchecked each time the window opens; then it is queued and starts as soon as a slot is free.
  - The operator picks the repository from the configured repo roots; the one used last is the default, else the first. The session runs there with no worktree requirement and no playbook, using the `sessions` permission mode and model.
  - The ticket key is a local sequence number, and its title is the prompt's first line.
  - The window also offers **Run now** for each schedule (R82) in a list above the prompt: choosing one hides the repo, the prompt and Start automatically, and Run queues a run of that schedule at once. With schedules and no repo roots, the window opens for Run now alone.
- R82. **Schedules.** A schedule runs a task playbook on a calendar or by hand, with no ticket from a source, for recurring work such as a monthly self-review or a weekly worktree cleanup.
  - Each schedule is an entry under `schedules` in settings.json, keyed by a name of lowercase letters, digits and hyphens: its `playbook`, the `repoRoot` its sessions run in, and, unless it runs only by hand, `every` (`day`, `week` or `month`), a `day` (a weekday such as `fri` for a weekly one, or 1 to 31 for a monthly one, where a month without that day runs on its last day) and `at`, a 24-hour local time such as `09:00`. The playbook must be a task playbook that needs no worktree, because a schedule has no source to set one up; the Settings window refuses another (R54).
  - Each schedule is one ticket of the `schedule` source, keyed by its name and titled by its playbook's description, and each run is a work item of that ticket, so History lists every run. A run is not triaged: it takes the schedule's playbook and waits `unstarted` or is queued as the playbook's `autoStart` says. Run now (R6) queues it whatever `autoStart` says, because the operator asked for it. Its sessions run in the schedule's `repoRoot`. A done report ends the run without reading a source (R10). A run whose playbook is missing or not a task playbook fails with that cause.
  - The hub checks schedules on its minute tick: a schedule whose time passed since its last check gets a run, so a run starts within a minute of its time. Switchboard runs only while the hub does, so a time that passed while the hub was stopped runs once at its next tick, however many times passed. A time that passed before the schedule was added, moved, or added again after its removal does not run.
  - A schedule makes no run while its ticket has an open work item; History records the skipped time, so unanswered runs do not collect. Run now refuses then with "<name> already has an open work item."
  - A run counts no earlier run as a return (R51), and offers no Triage again. Snoozing the ticket holds a run queued until it wakes (R49). Removing a schedule from settings.json stops its runs and keeps its work items.
  - A scheduled playbook is an ordinary playbook. One in a namespace that no source triages into is never chosen by triage, and its row names the work, such as `ops:cleanup-worktrees`.

### Work items

- R7. Switchboard creates a work item each time a ticket enters the assigned state with no open work item. A ticket assigned again after its work item is done gets a new work item; one that returns while its work item is still open, such as during that item's active session, continues that work item.
- R8. On first run, every ticket already in the assigned state gets a work item.
- R9. Work item status is local and never mirrored to the source.
- R10. A work item is done when its task session reports done, when the operator marks it done, or when its ticket leaves the assigned state while no session is active. An open work item that never had a session is deleted instead when its ticket leaves, because nothing was done on it, so it does not appear in Done or History, and its activity, including its pool triages', is deleted from the log; an operator action that named only the ticket, such as the pick that created it, stays; during its triage, the deletion waits for the triage to end, and a return before then keeps it. If the ticket leaves while a session is active, the work item stays open until that session reports done or ends, because skills such as `/finalize-issue` unassign the operator before the session finishes. When a task session reports done, the hub reads the ticket's source again; if the read still lists the ticket in the assigned state, the work item stays as it is and the hub reads the source again 30 seconds later, because GitHub issue search lags an unassignment by seconds. If that read also lists it, the session did not hand it off, which is a skill defect, so the work item becomes `blocked` for the operator instead of done, and the session is not told. The work item is done when either read finds the ticket outside the assigned state, or when the ticket leaves it later, even while the session is still active. A read that fails or takes over 6 seconds accepts the report. Resuming the session, an approval report after the done report, or Triage again before the second read cancels that read's effect.
- R11. A work item with a session that ends because its ticket left the assigned state, without a done report, stays listed in Done with no warning; leaving the assigned state is routine.
- R34. Work item statuses are `triaging`, `unstarted`, `queued`, `setup`, `running`, `awaiting-approval`, `finished`, `blocked`, `failed` and `done`.
  - `unstarted` waits for the operator to start it, because its playbook does not start automatically.
  - `awaiting-approval` means a session's work is finished and waits for the operator to approve the prompt that publishes it (R23). When its session runs again, as when the operator answers its question or resumes it, the work item is `running` until that run ends; the run's own approval or done report applies, and a run that ends or is stopped without one returns the work item to `awaiting-approval` with the earlier approval and the cause of a failed turn or a stop.
  - `finished` means a task session ended its turn or its process without a report, and its playbook offers neither done nor approval (R23), so its work waits for the operator's review. The operator resumes it, triages it again, or marks it done.
  - `queued` waits for a session slot (R38), for the turn of another session of the same ticket to end (R17), including the work item's own earlier session, or for its ticket to wake (R49). Its row's line 3 lists each reason that holds, such as `Waits for a slot · 10/10 in use` or `Waits for its session's turn to end`, with what ends it in the tooltip.
  - `blocked` means a session ended its turn or its process without the done or approval report its playbook offers, or the operator stopped it while no approval was pending (R40), or a task session reported done while its ticket was still in the assigned state (R10). Its reason names the report the session was offered, such as "The turn ended without a done report." The operator resumes it, triages it again, or marks it done.
  - `failed` means a Switchboard step failed: triage, a session start, or a setup session that ended without a worktree. The dock shows the cause and offers Triage again, which triages the ticket again and then starts or waits for Start as the chosen playbook says; for a failed ad-hoc work item, the operator marks it done and submits a new prompt.
- R35. The operator can triage a work item again while it has no active session. There is no control to choose a playbook by hand; the operator handles that rare case outside Switchboard, for example with Mark done and an ad-hoc session.
- R45. Only reports from a work item's latest session change the work item. Reports from earlier sessions are recorded on those sessions. A report from a copy that a fork retired is refused (R78).

### Playbooks

- R12. A playbook name is `<namespace>:<name>`, such as `support:defect`, `support:question`, `dev:qa-question`, `dev:qa-failure` or `dev:new-dev`. A namespace is the role the operator works the ticket in, such as `support` for support support or `dev` for development.
- R13. Namespaces and playbooks are not built into Switchboard. Any playbook defined in configuration is valid, and triage chooses among them.
- R14. A playbook owns a prompt template. Switchboard renders it with the ticket's fields, the triage context and the Switchboard session ID.
- R15. Each playbook is configured to start its task session automatically after triage or to wait, `unstarted`, for the operator to start it. A work item whose triage found nothing new waits whatever its playbook says (R80).
- R16. Each playbook states whether it requires a worktree to start, and where its session runs (`workdir`): in the ticket's worktree when one exists, or always in the source's repo root. A playbook that requires no worktree and has no worktree yet starts in the repo root, and its skill creates a worktree only if the work turns out to need code. Every `support` playbook runs in the repo root.

### Sessions

- R17. A ticket has at most one session in a turn across all its work items, because its work items share one worktree. Switchboard starts no session while another session of the same ticket is starting, running or waiting on a question. A session whose turn has ended, such as one kept open idle in the VS Code Claude view, does not hold a start back, because the operator commonly keeps that view open. A work item's active session is its latest session while that session has not ended; an earlier session left open is not. Ended sessions are kept as history.
- R18. A new work item is triaged first. Triage is a one-shot classifier with no tools: it receives the source's triage context, led by the current time, and triage playbook, and returns the playbook that handles the work item and its focus (R79). A triage playbook chooses a specific playbook only when the context states the requested action by the source's rules, and otherwise its playbook for an unclear ticket, such as `dev:other` for GitHub, where an assignment alone states no action, nor does activity an earlier work item already handled (R80).
- R79. **Focus.** Triage also returns the work item's focus: the page or comment the operator reads first to do the chosen playbook's work, and the earliest such comment when several ask for it. An item window opens only the focus (R72), so the operator lands on the comment that asks for the work.
  - The triage context tags the ticket's page `[ticket]`, the pull request it includes `[pr]`, and each comment that has a URL `[c1]`, `[c2]` and so on in time order. The classifier returns one of those ids, which Switchboard turns into the URL, so the context does not repeat each comment's URL. GitHub tags issue, pull request and review-thread comments, whose URLs end in `#issuecomment-<id>` or `#discussion_r<id>`. Zoho Desk and Forum tag nothing, so their focus is the ticket, because no per-thread or per-post URL has been shown to open at its comment. Only comments in the clipped context can be the focus, so an earlier comment outside it cannot.
  - A task playbook may set `focus` to `ticket` or `pr`, the page its work is done on. The triage prompt names that page beside the playbook, and a chosen comment on another page is replaced by the playbook's page; a `pr` playbook whose context has no pull request focuses the ticket. A missing or unknown id focuses the playbook's page, else the ticket.
  - The focus is the latest successful triage's and is kept while a later triage runs or after it fails. It is fixed when triage completes: a later playbook report (R23) or settings change does not change it. A work item never triaged successfully, or triaged before focus existed, focuses its ticket. A pool ticket's Triage again discards its earlier triage (R47), so it focuses its ticket until the new triage completes.
- R80. **Nothing new.** A new work item whose ticket had an earlier one acts only on activity newer than that earlier work item: a comment, a review or a commit, not a status or assignment change, which only a first work item acts on, such as 🎁 Assigned for development, because the earlier one already acted on what was there, so anything more would be a guess, as when the operator unassigns and reassigns an issue by mistake. The earlier work item took in the activity when the first of its task sessions that started began, so a start that failed does not count, or when the operator marked it done without a session; the latest of the ticket's earlier work items counts, and one with neither, such as one unassigned during setup, does not. A source reports the time of its latest activity by anyone other than the operator: for GitHub, the latest issue, pull request or review-thread comment, pull request review or pull request head commit in the triage context by an author outside the configured logins, bots included, because the operator's own comments and commits, such as a session's, ask nothing of the operator. A commit counts because an author who pushes fixes and returns the card for another review asks for that review without a comment. Triage gets a line naming the earlier work item's playbook and time, so it treats activity up to then as background. The hub compares exact times; the line shows the minute, as the context does. When nothing is newer, the line says so, the triage playbook chooses its playbook for an unclear ticket, and the work item waits, `unstarted`, for the operator's Start whatever the chosen playbook's `autoStart`; its row says `Nothing is newer than the earlier work item` until Start or Triage again, and History says why. The pull request line of the GitHub context shows the head commit's author and time, so triage can see a push. A source that does not report activity, such as Zoho Desk and Forum, whose playbooks all wait for Start, is not checked.
- R19. When the chosen playbook requires a worktree and the ticket has none, a setup session runs after triage to create one.
- R20. The task session runs the rendered playbook prompt and handles the work item from start to finish.
- R21. A session without a worktree runs in the source's repo root. A skill creates the worktree when coding begins and reports it.
- R22. A session runs in Claude Code or Codex. `sessions.provider` sets the agent for every session, `claude` by default, and a playbook's `provider` overrides it for its work items' setup, task and approved sessions; an ad-hoc prompt takes `sessions.provider`. Each agent has its own default permission mode and model: Claude's `sessions.permissionMode` and `sessions.model`, and Codex's `sessions.codex.permissionMode` and `sessions.codex.model`; a playbook's own mode and model apply to its agent. A Codex session runs only in `auto`, `plan`, `dontAsk` or `bypassPermissions`, because the others need a person to approve each action, and Codex's default is `bypassPermissions`, because commands in Codex's sandbox cannot use the operator's sign-ins, such as `gh`'s ([mechanics.md](mechanics.md) M31). A Codex session gets the same prompt, with a leading `/<skill>` written `$<skill>`, which is how Codex runs a skill, and the same report contract, except that it asks with a `question` report and ends its turn instead of asking with `AskUserQuestion` (R70). Triage stays on Claude. The session records its agent, and the row's controls and History name it, such as Open in Codex.
- R23. A session can report its stage, a worktree link, that it is done, or that its work is ready for the operator's approval with the prompt that finishes it, such as `/review-pr pr:123 publish`, a summary of what that prompt publishes, and the file holding the drafted text it publishes, if any. An approval report puts the work item in `awaiting-approval`; Approve starts a new task session with that prompt. `awaiting-approval` is used only for this. A session can also hand its work item to another task playbook in the work item's namespace, whose skill it then runs, so the row names the work being done; a playbook such as `dev:other`, whose session researches what an unclear ticket needs, offers it. Each task playbook lists the reports its sessions may send besides stage, links and tasks (R68), from done, approval, worktree, playbook and paste (R60), and lists none by default. A playbook that lists approval states whether Approve sends the work, such as posting a reply or pushing a branch, or only finishes it after the operator sends it by hand, as a Support release does after the operator pastes the reply; it does not send by default; a session whose playbook lists neither done nor approval ends its turn `finished` (R34), in Ready for review (R27), for the operator to review. The session's report contract lists the reports it may send, except tasks (R68), and the hub refuses any other. The contract is part of the session's system prompt, not its first message, so Claude's session list shows only the task prompt, and the session gets it back after each compaction. A setup or approved-prompt session may report its stage, a worktree, done, links and tasks; an ad-hoc prompt may send every report but playbook, because it has no playbook to change. A report is only for work ready to publish: a session that needs the operator's answer or choice, or cannot continue without them, asks with `AskUserQuestion` and waits, so its context stays live, and writes no report for the question. Reports are accepted from the session after it is resumed in VS Code.
  - The reported texts are short, because a row shows about 8 to 10 words: the stage is an -ing phrase of at most four words stating the work now running and what it acts on, such as `fixing tests`, with no ending punctuation because the dock follows it with its age, optionally after a step count such as `2/5`, and the approval summary one phrase of at most 8 words without counts. The report contract states these word caps; the dock cuts a longer text at a character cap, 24 for the stage, 60 for the approval summary and 80 for a warning or error, on a word boundary, and keeps the whole text in the tooltip. A done report carries no summary, because nothing shows it.
- R60. A session can report a paste: a label and the absolute path of a file holding a drafted text the operator pastes into the source by hand, such as a Support case's customer reply and private note for Zoho. Pastes belong to the work item, and a later paste with the same label replaces the earlier one. An `awaiting-approval` row with pastes shows a Copy button before Report, and Copy in its right-click menu: with one paste it copies at once, and with more it asks which by label. Copy reads the file when clicked, so the operator gets the draft as it is on disk, and puts its text on the clipboard without a byte order mark or trailing whitespace, then confirms with "Copied <label>." on the dock's status line. A missing or unreadable file shows a warning and copies nothing. Switchboard still writes nothing to the source; the operator pastes.
- R68. A session can report a task when the operator asks it to queue one, such as a defect it found in other code that the operator wants handled separately. Only the operator initiates a task: a session names a follow-up it finds in its final message and does not queue it. The report carries a prompt, and optionally a repo and a title. Switchboard creates an ad-hoc ticket and work item, as for an ad-hoc prompt (R6), with three differences: the work item always waits `unstarted` for the operator to press Start, because the prompt is the session's, not the operator's, and may write; the title defaults to the prompt's first line; and the repo defaults to the reporting ticket's repo root. The repo must be one of the configured repo roots. The new row's line 3 shows "From" and the key of the work item whose session reported it, such as "From gh 18941", and a click on it selects that row. Every session may report tasks, as it may report links, because a task changes nothing outside Switchboard until the operator starts it, but no report contract lists the task report, so a session sends one only through a skill the operator invokes. An empty prompt or another repo is refused. A repeated report with the same prompt adds nothing while the earlier work item is open.
- R81. **Registered sessions.** The operator can register a Claude session they started outside Switchboard, such as one in a VS Code window on a repository, as a work item, by running the `/switchboard-register` skill in it, which runs Switchboard's register command. As for the task report (R68), no report contract, usage text or other skill names the command, so only the operator registers a session.
  - Switchboard creates an ad-hoc ticket and work item (R6), `running`, titled by the command's title, with the session's working directory, as Claude's roster lists it, for its repo. Claude must list the session with a process. A copy of a Switchboard session, newer or older, such as a fork or a copy a fork retired, is refused (R78). A session Switchboard already has gets its key and contract again, so a command whose reply was lost can be run again.
  - The command prints the session's report contract, which offers the ad-hoc reports; the session follows it from then on and gets it back after each compaction (R23). The work item then behaves as an ad-hoc one: a turn that ends without a done report blocks it, and a done report finishes it.
  - The session is the operator's, so Switchboard never releases or stops it (R39), and refuses Stop. Until the session ends, its row has no item window, so a click switches nothing, and offers no Open in terminal, because Switchboard cannot find the operator's window and opening the live session elsewhere starts a copy ([mechanics.md](mechanics.md) M18). Once it ends, the row opens it in its item window as for any session.
  - Only Claude sessions can register: the command reads the session ID from `CLAUDE_CODE_SESSION_ID`, which Claude sets in its Bash tool ([mechanics.md](mechanics.md) M36).
- R36. A session's observed state is `starting`, `running`, `waiting` (needs the operator: a permission prompt or a question), `idle` (its turn ended), `failed` (the turn stopped on an error, with its kind) or `ended`. For a Claude session, hook markers that Switchboard installs in the operator's Claude settings decide the state; the Claude roster decides whether the session is alive, and supplies the state when no marker exists. A Codex session runs one `codex exec` process per turn, whose output decides its state and whose process its liveness; hook markers that Switchboard installs in Codex's hooks.json show a session the operator resumed in VS Code or a terminal. A session's outcome is `done`, `failed` or `stopped`.
- R37. A triage or session start that fails makes the work item `failed`, with the error. Switchboard does not retry it automatically.
- R38. At most `sessions.concurrency` sessions run at once (default 2, range 1–10). A start that has no free slot waits as `queued`. A session holds a slot only while its work item is `setup` or `running`, its session does not wait on a question, and its ticket is not snoozed; a setup session and the task session that follows it hold one slot. Any other session holds none, such as one waiting on a question, awaiting approval or review, or blocked and kept open in VS Code, so the operator's open items do not stall the queue; an approved work item queued for a slot stays in Ready for review (R27); when such a session runs again, more than `sessions.concurrency` sessions can run until enough end.
- R39. When a session's turn ends, Switchboard stops its background process, so that the session can resume in VS Code. A session waiting on the operator is not stopped, except by the operator's Open in Claude (R70). This never deletes the session or its worktree. A fork of a session in its background process waits for this release, or for the operator's Stop (R78).
- R40. The operator can stop an active background session; a session the operator resumed in VS Code is stopped there. The work item becomes `blocked` with the reason "Stopped by you." once `claude stop` succeeds; a work item that is or was `awaiting-approval` in that run (R34) returns to `awaiting-approval` with that reason instead, because a stop never approves. A failed stop shows its error and leaves the session stoppable.
- R78. **Forks.** A fork of a Claude session that Switchboard started, such as one made with Fork conversation in the VS Code Claude view, continues that session: the fork becomes the work item's session, and the copy it was forked from is retired. The operator forks mostly to rewind past turns they do not want, and leaves the original.
  - Switchboard finds a fork on a roster read that lists it with a process, in the session's project directory. A fork copies its source's API request IDs into a new transcript, so a fork belongs to a session when its first request ID is in the transcript of the session's current copy or of a copy a fork retired, and its transcript was created after the current copy's. Of several forks, the newest wins.
  - Only the work item's latest session is continued. While the current copy holds Switchboard's background process, the fork waits until R39 releases it, or the operator stops a copy that waits on a question, so no work is cut off. History shows the waiting fork, and the row offers Stop in place of Open in Claude, which would open the copy the fork retires.
  - From then on the row, Open in Claude, Open in terminal, the report contract after compaction and the debrief follow the fork. A retired copy changes nothing when resumed, and its reports are refused with the fork's ID; a report from a newer fork not yet continued is recorded. History shows "The session continues in fork <id>", and earlier entries keep the copy's own ID.
  - A fork that no roster read lists with a process, such as one opened and closed between reads, is continued when it is next opened. A fork from another workspace's project directory, or one made before the first reply, is not found. Codex threads are not forked.
- R41. A failed start shows the agent's own message: Claude's for an untrusted directory says how to trust it, and Codex, in its sandboxed modes, refuses a directory outside a git repository. Switchboard never writes Claude's trust settings, and never passes Codex's `--skip-git-repo-check`.

### Worktrees

- R24. A worktree belongs to a ticket, and every work item for that ticket reuses it.
- R25. Switchboard links a worktree from a session report, or by branch-name convention when no report exists, such as branch `15619-fix-foo` for GitHub issue 15619. A worktree that git marks prunable, such as one whose directory was deleted, is never linked.
- R26. Tickets from different sources do not share work items. A Zoho ticket gets its own worktree when coding begins.

### Observation and control

- R27. The dock (R71) lists work items. The list centres on the work item; sessions are secondary: a click on a row switches the screen to its work.
  - Rows do not expand. The first line is the title, led by the priority dot on a priority ticket (R50), and the time in the queue. No space is reserved for the dot, so every line starts at the left edge. The second line is the playbook name, the source and key, with `github` shown as `gh`, a badge for each of the ticket's links (R52): a pull request's number after the pull request icon, a GitHub issue as `gh <number>`, another link by its label; and "Returned ×N" (R51), with the controls at the right. A third line, shown only when it has something, holds the mark, the wait reasons or wake time, any warning or error, the work item a reported task came from (R68), and the stage and its age (R58), or the question (R70). The key and the badges are pills outlined in the source's colour, purple for a pull request, with a muted fill of the same colour, and a click on one opens its link in the browser instead of the row's click; Returned is a pill in the warning colour. On an `awaiting-approval` row the approval summary, with its first letter capitalised, and the time since the work item last became `awaiting-approval` take the place of the stage, whose text moves to the summary's tooltip, because the stage only says the work is ready. Every row has at least two lines, with room between rows; the list stays easy to scan rather than as dense as possible.
  - An ad-hoc work item has no playbook, so its playbook slot names how it was made: `ad-hoc` for a typed prompt (R6), `task` for a session's task report (R68) and `registered` for a registered session (R81).
  - The title is bold, because it says what the ticket is. The playbook name shows its namespace muted and its name in the foreground colour, such as `dev:review-pr-followup` with `dev:` muted, because the name says what the work is and the namespace follows from the source.
  - There is no separate status text: the group and the mark already say it, and the mark's tooltip names it. A line 3 that would hold only the mark shows the mark's words after it, such as `Setting up`, so the icon never stands alone.
  - The triage context and the task prompt are not shown; Switchboard keeps them in the store. An approval report's summary is shown, because it says what Approve does, and Approve's tooltip names the prompt it runs.
  - Every group can be collapsed; Blocked on you, Ready for review, In progress and Unstarted start open, Done and Snoozed start closed, and the operator's choice is kept.
  - Groups, in this order: **Ready for review**; **Blocked on you**, shown only when it has rows; **In progress**; **Unstarted**; **Snoozed** for snoozed tickets (R49); and **Done**. While not done, unstarted or triaging, a work item is in Ready for review when it has been ready; otherwise it is in Blocked on you when its status is `blocked` or `failed`, or its active session is `waiting`, and in In progress when it is not queued. Done holds a work item when it is `done`, from local midnight on the Monday two weeks before this week's, newest done first, under date bands by local day with weeks starting on Monday: Today, Yesterday, Earlier this week, Last week and Two weeks ago, so Two weeks ago holds that whole week.
  - A work item becomes ready the first time it becomes `awaiting-approval` or `finished`. It stays ready through Approve, an answer, a resumed run, a stop, a snooze, a question, a block and a failure, so it keeps its place in Ready for review while its session runs again, its approved run waits for a slot, or it waits on the operator; only Triage again ends it. A returned ticket's new work item (R51) starts not ready. A row in Blocked on you returns to In progress when the block ends.
  - **Blocked on you** lists the oldest wait first; **Ready for review** lists in the operator's order (R73), else by when each work item became ready, oldest first; **In progress** lists by when the run started, oldest first.
  - Each row in Blocked on you, Ready for review and In progress is on the operator's turn or the agent's: the operator's in Blocked on you and on a `blocked`, `failed`, `awaiting-approval` or `finished` row or one whose session waits on a question, the agent's on every other row, such as an approved run setting up, running or waiting for a slot. In Ready for review a row on the agent's turn is dimmed.
  - The **Unstarted** group holds everything not yet running, from every source: `unstarted` and `triaging` work items, `queued` work items that have not been ready, unless their session waits on the operator, and pool tickets. A ticket being triaged shows `<namespace>:triage` in place of the playbook name, with the source's namespace, such as `dev:triage` or `support:triage`, or `triage` when the source has none. It sorts by importance (R50), counting an unrated ticket as rank 2, then oldest first by the source's sort time (Zoho's customer response time, Forum's last public post) or the work item's creation, so the most urgent and then the longest-waiting come first. Pool tickets carry no claim tag: the sources leave out tickets another developer has claimed, and a ticket the operator has claimed is a work item, not a pool ticket.
  - The mark shows what differs between rows of the same group, because the group header already says what they share; its tooltip names it in words:
    - **Unstarted:** no mark, except a spinning Triaging mark on a work item or pool ticket being triaged and a Queued mark on a `queued` work item, followed by its wait reasons (R34); the priority dot on the first line is what differs.
    - **Blocked on you:** what the operator must do: answer a question (`waiting`, or opened in Claude or Codex and not yet answered, R70), look at a block, or deal with a failure (red).
    - **Ready for review:** on the operator's turn, what to do: the Blocked on you marks, then approve work that Approve sends, review work and then approve when the operator sends it by hand (an approval report, by the playbook's setting, R23), or review a finished turn (`finished`); on the agent's turn, the phase: setting up, running or queued.
    - **In progress:** the phase: setting up, running.
    - **Done:** how it ended: the session reported done, the operator marked it done, or the ticket left the assigned state.
    - **Snoozed:** the mark the item would have in the group it returns to, and the wake time on line 3 unless the snooze is indefinite.
  - Every unsnoozed row on the operator's turn has a left stripe: the error colour on a `failed` row, the warning colour on a `blocked` row or one whose session asks a question (`waiting`), and the accent colour on a Ready for review row, so what needs an answer or a fix stands out from reviews. Rows on the agent's turn, such as a running session, and rows in Unstarted, Done and Snoozed have no stripe.
  - Controls appear only when they apply: Start, Start with guidance… (R77), Approve, Open in Claude (R70), Stop, Mark done, Delete (R76), Triage again, Snooze and Restore, Open Changes on a row with a worktree (R57), Open in terminal (R28), Copy (R60), Move to top, Move up, Move down and Reset position on a Ready for review row (R73), History on every row (R59), the ticket's links (R52), and Open ticket. Each row shows only its main control, 26 pixels high with its codicon and label as in VS Code's buttons (Start, Approve, Open in Claude on a row whose background session waits on a question (R70), or Triage again on a failed row), at the right of lines 2 and 3, and only while the row is selected, so other rows give their text the full width. The list shows no separate session state: the group and the mark say what the work item needs. Approve takes the accent colour, and its tooltip names the prompt it runs. An `awaiting-approval` row whose approval report named a draft also shows a Report button before Approve, with the draft's filename as its tooltip, which opens the draft; no other row shows Report. An `awaiting-approval` row with pastes shows a Copy button before Report (R60). A click elsewhere on the row runs its click (R71). Right-clicking a row opens a menu with every control that applies to it. A control's verb matches the status it acts on: Start for `unstarted` and pool tickets, Approve only for `awaiting-approval`.
  - The time in the queue is in whole minutes, hours, days or weeks, and depends on the group (R53): **Blocked on you** counts from when the work item entered its status, or its session began to wait; **Ready for review** from when the work item became ready; **In progress** from when the run started; **Unstarted** and **Snoozed** from when the ticket entered the source's scope, stopping at done. The tooltip names what it counts. A **Done** row shows when it was done instead, in local time: 24-hour `HH:mm` today, else `m/d`, with the done time and scope entry in the tooltip.
  - The dock takes VS Code's Light Modern or Dark Modern colours, by Windows' app mode, and codicons, and looks like a VS Code sidebar: tinted group headings with their count in a badge, a rule between rows, ticket keys in small outlined badges, and flat inputs and buttons. The Settings window takes the same look. It is not a kanban board.

The dock asks for the guidance in a dialog with a multi-line box; Start is unavailable while the box is blank, and Cancel starts nothing. - R49. The operator can snooze a pool ticket or a work item, as in Gmail, and restore it early. A day starts at 6am local time, so a day choice wakes at 6am that many days after the current day, and a week choice wakes at 6am on a Monday: Next week is the first Monday after the current day. Indefinitely has no wake time: the snooze ends when the operator restores the ticket or it leaves scope. A snoozed ticket shows only in a collapsed Snoozed group, as one row with its wake time: its pool entry, otherwise its open work item, otherwise its latest one. It gets no automatic triage or start, and returns to its group when it wakes or is restored; a queued start then runs. A snoozed ticket that leaves the assigned state and the pool stops being snoozed, so it leaves the Snoozed group; its done work item shows in Done. A snoozed ticket still offers Snooze, and a new snooze replaces the earlier one without waking it. Snoozing is local and never written to the source.

- R50. Triage can rate a ticket's importance as immediacy (`URGENT`, `BLOCKING` or `NON-BLOCKING`) and severity (`HIGH`, `MED` or `LOW`), when the source's triage playbook is marked as rating and defines the levels; triage under any other playbook stores neither, whatever the model returns. - R52. A session can report links for its work item: a label and a URL, such as the GitHub issue that tracks the work and the pull request that delivers it; a related, base or parent pull request is not a link. The row's right-click menu has an Open item per link of the work item or pool ticket, which opens the URL in the browser. - R61. A successful triage of a Zoho Desk or Forum ticket also adds a link for each distinct GitHub issue or pull request URL in the ticket's subject, fields, thread and comments, labelled `Issue #n` or `Pull request #n`, so a case that already names its issue or pull request shows it on its work item or pool row (R52) before any session runs. - R53. Switchboard records when each ticket entered its source's scope, the assigned state or the pool, and when it last did after leaving it. Only a move from out of scope into scope restarts it; a status change within scope does not. A done work item keeps the time its ticket entered scope, so the time from entering scope to done can serve as a service-level measure.
  - GitHub: when the operator's current assignment began, by Ground Control's rule: the start of the unbroken span in which one of the configured logins was assigned. A status change, including one outside the configured statuses and back, does not restart it.
  - Zoho Desk: the later of the last escalation to `Support` and the last change to Open, so a ticket back from Deferred or On Hold re-enters scope. Who holds it does not matter, including an engineer who held it and let it go.
  - Forum: when the topic last became Open, from the change-history store, whether or not it is assigned to the operator.
  - When the source records no change, the ticket's creation. When the source cannot tell, such as a GitHub issue whose assignment began before the last 100 assignment events, Switchboard keeps the time it has, or the time it first saw the ticket.
- R58. A row in Ready for review or In progress whose work item is `setup` or `running` and whose active session is `running` and has reported no stage for 20 minutes shows its stage age in the warning colour, with the tooltip "No stage report for 25m"; a row with no stage shows `No stage report · 25m` in the same colour. The 20 minutes count from the latest of the last stage report, the start of the run, and the time the session last began running, so a stage from before a new session or an answered question does not mark the resumed run. A `waiting` session, a queued or setting-up row with no running session, and a snoozed row are never marked. This colours an observed age; it is not stuck-session detection, and Switchboard takes no action on it.

  - **Open in Claude.** The row's main control and its click action. ### Runtime

- R33. Switchboard's core runs in a separate process from VS Code and keeps running when the window reloads or closes.
- R42. Settings and playbooks are one file, `settings.json`, in a config folder the operator chooses, so it can be kept in git; by default it is the Switchboard home. The hub reloads it when it changes. An invalid file, or an error outside its playbooks, leaves the last valid settings and playbooks in force; a source with invalid settings is disabled; an invalid playbook is left out. Each error shows in the dock.
- R54. The operator edits settings and playbooks in the dock's Settings window, a separate window opened from Open Settings in the dock's header menu; Open Settings again shows the open one. It shows every setting and playbook key as a field with its default, and each playbook's template; a playbook's permission mode offers the modes of its agent; a field whose label does not explain it has an info icon whose tooltip does, and rarely changed source settings are under a collapsed Advanced heading. Each schedule (R82) has a page, under Schedules, whose day and time fields show only for the period that uses them; New schedule asks for its name and adds an empty entry whose errors name the fields to fill. Each playbook namespace also has a table page, one row per playbook and one checkbox column per playbook flag, so the operator compares and changes playbooks side by side. The window edits one draft of the whole file and saves only when the operator presses Save or Ctrl+S; Save and Discard sit in a bar across the window, not on a page, because each acts on the whole file, and the bar says whether the file is saved, has unsaved changes or has errors. The navigation marks each page with unsaved changes or errors. It checks the draft as the operator types and shows each error on its field. Save refuses what the hub would reject, disable or leave out: an invalid file, a source that is on with invalid settings, or an invalid playbook. It also refuses an unknown template variable, which would otherwise fail the session start, and is unavailable while the file has changed on disk since the window read it; Discard drops every unsaved change and reads the file again. Closing the window with unsaved changes asks whether to save, discard or keep editing. When the config folder changes, the window reads the new folder, discards unsaved changes and says so, and the hub refuses a save made for the old folder. Add source, Remove source, New playbook and Delete change the draft; Delete asks first, and says how many open work items use the playbook. The file's path opens it in the VS Code window used last. The window does not rename a playbook, because work items store the playbook's name. The file remains the configuration: the operator can still edit it by hand, and the hub reloads it either way.
- R43. On startup the hub reconciles sessions recorded as active against the Claude roster and Codex's run records. The hub stays running while any session is active, so sessions can always report, and while a debrief runs (R55).
- R55. Friction debriefs. With the `sessions.debriefs` setting on (it is off by default), the hub asks each of its Claude and Codex sessions what slowed it down, for the operator's friction-review skill. It asks as soon as the session's work item is done, otherwise 45 minutes after the session's last turn, in case the operator resumes it; it does not ask 60 minutes or more after that turn, when the prompt cache has expired. It asks only when the session did at least 10 tool calls since its last debrief, and in a fork that leaves the session unchanged. A session continued by a fork (R78) is asked about the fork, including the turns it copied, which may already have been asked about. After each session's debrief it asks each Codex thread the session delegated to through agent-delegate in that work, about the thread's turns since its own last debrief. The answers and the record of what was asked are the files Ground Control wrote, so a session Ground Control asked is not asked again about the same work. A failed debrief is reported in the hub log, not on a work item, and is not tried again; the session's later work is asked about with it. The hub does not stay up for a debrief that is not yet due.
