# Switchboard PRD

Switchboard is a local software factory for one developer. It ingests work assigned to the operator, triages each assignment to a playbook, runs the playbook's prompt in a background agent session, and shows what each session is doing in the dock, a list docked beside VS Code that switches the screen to a work item's own VS Code window.

## Scope

- Switchboard runs on the operator's machine and handles only the operator's work: tickets assigned to them, and the pool of unclaimed tickets in a queue they work, such as support escalations, from which they pick. It has no shared state, accounts or server.
- All Switchboard state is local. Switchboard reads sources and never writes to them; only the skills its sessions invoke change external state.
- Switchboard manages only sessions it starts. It does not discover or adopt sessions started elsewhere, except a fork of a session it started, which continues that session (R78), and a Claude session the operator registers (R81).
- Claude background sessions run in Claude's background service; Code Mode sessions (R93) run in Switchboard's terminal holder (R94). New Codex sessions run as threads in Codex's built-in app-server daemon (R107).
- Switchboard tracks worktrees but never creates or deletes them. Skills create worktrees; the operator removes them.
- Switchboard runs on Windows, and on Linux under GNOME on Wayland. On Linux the dock (R71) reserves the left or right edge of a monitor, or auto-hides there as on Windows; at an edge another monitor adjoins it docks without reserving the strip, so maximized windows can cover it; it brings item windows forward through Switchboard's GNOME Shell extension, and without the extension asks VS Code to focus an item window instead ([Implementation gaps](#implementation-gaps)).
- Switchboard replaces Ground Control and the Support board entirely; neither runs beside it. Ground Control began as an observability layer linking sessions to GitHub cards; Switchboard is a modular, source-agnostic factory that reuses Ground Control's session mechanics (see [architecture.md](architecture.md)).

## Goals

- Turn each assignment into running work: with no click when the operator trusts the playbook, and with one click when they do not.
- Show at a glance which work needs the operator: ready for review or approval, waiting on a question, blocked, or failed.
- Keep sources, playbooks and agent providers pluggable. Adding a source does not change the core.
- Reuse what Ground Control and the operator's skills already do. Switchboard schedules and observes; skills do the work.

## Non-goals

- Writing to sources: no status moves, comments, assignments or labels. Only the skills that sessions run write, including the claim when the operator picks a pool ticket (R48).
- Managing other people's work, team views, accounts or shared state.
- Remote, cloud or multi-machine operation. One hub runs per machine; reaching its web page from the operator's own paired devices over their tailnet (R115) is not remote operation.
- Changing git state: no commits, branches, or creating, cleaning up or removing worktrees. Read-only git queries that validate and link worktrees are allowed.
- Answering a session's permission prompts or questions for the operator.
- Inferring state it did not observe: no stuck-session detection, and no check of a session's work beyond whether its ticket is still assigned when it reports done (R10). The dock may colour an observed age, such as the time since a running session's last stage report (R58), but draws no conclusion from it and takes no action.
- Reproducing the source's ticket view or conversation. The dock links to the source.
- Reproducing Ground Control's board, lanes or review views, or the Support board.
- Built-in playbooks or namespaces.
- Unattended overnight operation as a committed goal.
- Complex error handling or support for rare edge cases. A failure shows its cause, and the operator recovers by resuming the session, Retry on a failed work item, Mark done, or a fix to their configuration.

## Design rules

- **Existing tools are context, not requirements.** The retired Ground Control and Support board, and the operator's skills, show how the work was done before Switchboard. Switchboard adopts a behavior from them only when it serves this PRD's goals, and states its own reason.
- **Skills drive the work; Switchboard is the harness.** Switchboard finds tickets, triages them, starts and observes sessions, and shows their state. Every change to a source, a repository or a worktree is made by a skill a session runs. When a feature needs a write, add a session that runs a skill, not Switchboard code that writes.
- **Least authority.** An unattended session gets the least permission mode under which it can finish. The default is `auto`; a playbook can override it.
- **The work item first, sessions second.** The operator manages work items; a session is how one runs, and the dock shows it as one control, not as content.
- **Show each fact once.** The dock follows four rules:
  - What the row's group already says is not repeated on the row.
  - What an icon says is not repeated in text; a button whose icon makes its action clear shows the icon, with the verb in its tooltip.
  - An indicator that is the same on every row it can appear on, or that means nothing, is not shown.
  - A label carries the most specific fact available: a playbook name that also names the kind of work, such as `support:defect`, rather than a generic one.
- **Simple first.** Choose the simplest behavior that keeps common work correct. Handle a rare case by showing it, not with special machinery.
- **Visible failure.** Every failure shows on its work item with the cause. Switchboard does not retry work automatically. A failed source poll is tried again at the next interval.
- **Observed state only.** The dock shows what the roster and session reports say, and how old that observation is. A session's report is its claim and is shown as such.
- **Never cut off work.** Switchboard stops a session only when the operator asks, such as with Continue in Background (R89), or to release a session that has finished its turn so the operator can resume it in VS Code (R39), or to end a Code Mode session's process as R95 says: after an hour with no terminal attached and no input or output, after its turn, or at any point while hooks are off and it is unobserved. A session stopped at a usage or rate limit is never ended for it (R111).
- **Start automatically unless it writes.** A playbook whose session makes no external change without the operator's approval gets `autoStart: true`. Local work, such as reading, drafting, local commits and worktrees, is not an external change. A playbook that pushes, posts, assigns or moves a card before an approval report waits, `unstarted`, for the operator to start it. A gate the operator has approved for a skill, which lets it write only when the gate passes, counts as approval. A playbook for a ticket whose requested action is unclear also waits, because an action read from older activity is more likely wrong. A concurrency limit caps running sessions (R38).
- **A failed read changes nothing.** A failed or incomplete source poll never moves a ticket out of the assigned state.
- **One unread mark.** Unread shows everywhere as the same filled round badge in one accent colour, VS Code's activity bar badge colour, holding a count where there is one and a dot where there is not (architecture.md § Unread).
- **Empty states say what comes.** Every empty view, list or group says what is missing and what makes it appear, or what to do, in two short sentences in one style: "No artifacts yet. They appear here when the session writes one."
- **A file for configuration, the store for state.** Settings and playbooks are a file the operator edits and can keep in git. Work items, sessions and history live in the store.

## Terms

| Term | Meaning |
|---|---|
| Source | A plugin that supplies tickets: GitHub, Zoho Desk, Forum, ad-hoc prompts, or schedules. |
| Ticket | Switchboard's local copy of a source record, identified by source and source key. |
| Assigned state | A source-defined condition meaning the ticket is the operator's to work, such as assignee plus status. |
| Work item | One assignment of one ticket to the operator. The primitive Switchboard schedules and displays. |
| Pool | A source's open, unclaimed tickets that the operator may pick, such as support cases assigned to no one or still held by the escalating General agent. Pool tickets are triaged but are not work items. |
| Blocker | An open issue that the source lists as blocking a ticket, such as an issue GitHub's issue dependencies list under "blocked by" (R90). |
| Pick | Starting a pool ticket: the operator presses Start on it. It creates a work item and starts its task session (R48). |
| Playbook | A named prompt template and its settings, such as `support:defect` or `dev:qa-failure`. A source's triage playbook holds the classifier's instructions. |
| Triage | A one-shot classification of a work item or pool ticket that chooses its playbook. Triage is not a session. |
| Session | One agent conversation for a work item. Kinds: `setup`, `task`. |
| Active session | A session whose process is running, in the background, in the terminal holder or in a VS Code tab. |
| Stage | A free-text label a session reports about its progress. Switchboard displays it and does not act on it. |
| Dock | Switchboard's native app, which lists the work items at the edge of the screen (R27, R71). |
| Item window | The VS Code window the dock opens for one work item's folder (R71). |
| Terminal holder | Switchboard's process that holds Code Mode sessions in hidden terminals, so they run while no terminal shows them and outlive the hub (R94). |

## Requirements

### Sources

- R1. Each source is a plugin behind one interface that lists the operator's tickets and reports whether each is in the assigned state. The plugin defines the assigned state and builds the triage context: the ticket's text, clipped to size limits and formatted with authors, status changes and assignees. The GitHub source can show each comment author's roles, such as tester, from a file the operator names, so triage can tell a tester's report from a developer's question. It marks bot accounts, and on somebody else's pull request it states whether the operator has submitted a review or commented, and says so when the history was too long to read in full, so a bot's review does not read as the operator's earlier review round.
- R2. Switchboard polls each enabled polling source and stores each ticket's last-seen state locally.
- R3. Each source has its own settings: poll interval, repo root, and its triage playbook. The operator turns sources on and off with an on/off toggle per source in the dock's header (R71), because some work, such as Support, is done only some weeks; a disabled source is not polled and its pool is hidden, while its work items stay. Whether a source is on is state, kept in the store, not a setting, so a toggle never changes settings.json; a configured source is off until the operator turns it on.
  - A source is named by its key under `sources` and read by the plugin its `kind` names, which is the name when unset, so one plugin reads several sources, such as a personal GitHub board beside the Acme one. Tickets, toggles and errors belong to the name. Only a GitHub source may be named apart from its kind, and no source may take another kind's name, because Switchboard's database upgrades find Zoho and Forum tickets by source name. Two GitHub sources may not read the same project board, even when one is off. A name is lowercase letters, digits and hyphens, and is not `schedule`; `adhoc` holds only the ad-hoc repo root and takes no kind.
  - The header shows one icon per kind, on while any of its sources is on. A kind with one source toggles it on click. A kind with several opens a menu on click instead, with a check box per source that turns only that source on or off; the menu stays open, so several can be changed, and its tooltip lists each source and whether it is on.
- R4. GitHub is the first source. Zoho Desk and Forum follow.
- R44. A GitHub ticket is in the assigned state when it is an open issue in any repository on the source's project board, it is assigned to one of the configured logins, and its project item's status is one of the configured statuses; with no status configured, any status or none qualifies. All of these are settings. With `requireAssignee` off, for an operator who works alone and moves issues on the board without assigning them, the status alone decides, whoever is assigned; the logins still name the operator's own activity (R80). With `includeClosed` on (Include closed issues in the Settings window, off by default), a closed issue counts like an open one, for a team that closes an issue before its pull request merges or its checks pass; the issue then leaves the assigned state when its status or assignee does. The operator's values for `acme/widgets` are in [architecture.md](architecture.md#settings). GitHub is read through the `gh` CLI with `gh`'s own authentication. A poll fails, changing nothing, when the project has no single-select field with the configured status name, because every issue would otherwise read as unassigned.
  - A GitHub source reads its whole board in one search per poll, so adding a repository to the board adds no setting and no request. Each source names a home repository (`repo`): its issues keep bare keys, such as `18941`, and an issue in another repository is keyed `owner/name#63`. The home repository cannot change once the source has tickets, because bare keys mean it; the hub refuses such a settings file at load and at Save.
  - An issue belongs to one source: when an issue on two boards already has a ticket in one source, the other source's poll leaves it out and the dock notes which source has it.
  - A work item for an issue outside its source's home repository waits for Start, whatever its playbook's `autoStart`, and its row says why: a source's playbooks and the skills they run are written for its home repository, and one that starts by itself must not run them elsewhere unseen.
- R5. The Forum source reads forum topics from the production forum database. A topic is in the assigned state when it is open in the Forum forum and assigned to the operator. An open topic assigned to no one is in the pool (R47). A topic another person has claimed is neither.
- R46. The Zoho Desk source reads tickets through the Desk API. A ticket is in the assigned state when its status type is Open, its escalation field is `Support`, and it is assigned to the operator. Such a ticket assigned to no one, or to a support agent or team, is in the pool (R47): General escalations stay assigned to the escalating General agent, so a support assignee counts as unclaimed. A ticket assigned to another engineer is neither.
- R47. A source can have a pool. Switchboard triages each ticket when it enters the pool, keeps the result with the ticket, and shows the pool with each ticket's chosen playbook. A failed pool triage shows its error on the pool row with Triage again; a pool ticket offers Start only once its triage has a result. A ticket that leaves the pool without a pick, because someone else claimed it or it closed, disappears from it. GitHub has no pool.
- R48. The operator picks a triaged pool ticket by pressing Start on it in the dock. Switchboard creates a work item that reuses the pool triage and starts its playbook's task session, because the pick is the operator's start, whatever the playbook's `autoStart`. Claiming the ticket is the playbook's work; Switchboard does not claim and does not check the claim. A ticket that returns to the assigned state on its own, such as a case reopened after On Hold, follows its playbook's `autoStart` like any other new work item.
- R6. The ad-hoc source creates a ticket and a work item from a prompt the operator enters in the dock's New ad-hoc session window (R71), choosing the repository when more than one is configured and Claude or Codex, with the configured default preselected. The chosen provider is kept for delayed starts and retries; cancelling creates nothing. The typed prompt replaces the playbook template: triage does not run, and the task session runs the typed prompt. The work item waits `unstarted` for Start unless the operator checks Start automatically, which is unchecked each time the window opens; then it is queued and starts as soon as a slot is free.
  - The operator picks the repository from the repo roots: each source's root for its home repository and the root of each other repository with stored tickets (R21), never a `{name}` pattern; the one used last is the default, else the first. The session runs there with no worktree requirement and no playbook, using the `sessions` permission mode and model.
  - The ticket key is a local sequence number, and its title is the prompt's first line.
  - The window also offers **Run now** for each schedule (R82) in a list above the prompt: choosing one hides the repo, the prompt and Start automatically, and Run queues a run of that schedule at once. With schedules and no repo roots, the window opens for Run now alone.
- R82. **Schedules.** A schedule runs a task playbook on a calendar or by hand, with no ticket from a source, for recurring work such as a monthly self-review or a weekly worktree cleanup.
  - Each schedule is an entry under `schedules` in settings.json, keyed by a name of lowercase letters, digits and hyphens: its `playbook`, the `repoRoot` its sessions run in, and, unless it runs only by hand, `every` (`day`, `week` or `month`), a `day` (a weekday such as `fri` for a weekly one, or 1 to 31 for a monthly one, where a month without that day runs on its last day) and `at`, a 24-hour local time such as `09:00`. The playbook must be a task playbook that needs no worktree, because a schedule has no source to set one up; the Settings window refuses another (R54).
  - Each schedule is one ticket of the `schedule` source, keyed by its name and titled by its playbook's description, and each run is a work item of that ticket, so History lists every run. A run is not triaged: it takes the schedule's playbook and waits `unstarted` or is queued as the playbook's `autoStart` says. Run now (R6) queues it whatever `autoStart` says, because the operator asked for it. Its sessions run in the schedule's `repoRoot`. A done report ends the run without reading a source (R10). A run whose playbook is missing or not a task playbook fails with that cause.
  - The hub checks schedules on its minute tick: a schedule whose time passed since its last check gets a run, so a run starts within a minute of its time. Switchboard runs only while the hub does, so a time that passed while the hub was stopped runs once at its next tick, however many times passed. A time that passed before the schedule was added, moved, or added again after its removal does not run.
  - A schedule makes no run while its ticket has an open work item; History records the skipped time, so unanswered runs do not collect. Run now refuses then with "<name> already has an open work item."
  - A run counts no earlier run as a return (R51). A failed run offers Retry (R34). Snoozing the ticket holds a run queued until it wakes (R49). Removing a schedule from settings.json stops its runs and keeps its work items.
  - A scheduled playbook is an ordinary playbook. One in a namespace that no source triages into is never chosen by triage, and its row names the work, such as `ops:cleanup-worktrees`.

### Work items

- R7. Switchboard creates a work item each time a ticket enters the assigned state with no open work item. A ticket assigned again after its work item is done gets a new work item; one that returns while its work item is still open, such as during that item's active session, continues that work item.
- R8. On first run, every ticket already in the assigned state gets a work item.
- R9. Work item status is local and never mirrored to the source.
- R10. A work item is done when its task session reports done, when the operator marks it done, or when its ticket leaves the assigned state while no session is active. An open work item that never had a session is deleted instead when its ticket leaves, because nothing was done on it, so it does not appear in Done or History, and its activity, including its pool triages', is deleted from the log; an operator action that named only the ticket, such as the pick that created it, stays; during its triage, the deletion waits for the triage to end, and a return before then keeps it. If the ticket leaves while a session is active, the work item stays open until that session reports done or ends, because a session can take the ticket out of the assigned state before it finishes. When a task session reports done, the hub reads the ticket's source again; if the read still lists the ticket in the assigned state, the work item stays as it is and the hub reads the source again 30 seconds later, because GitHub issue search lags an unassignment by seconds. If that read also lists it, the session did not hand it off, which is a skill defect, so the work item becomes `blocked` for the operator instead of done, and the session is not told. The work item is done when either read finds the ticket outside the assigned state, or when the ticket leaves it later, even while the session is still active. A read that fails or takes over 6 seconds accepts the report. Resuming the session or an approval report after the done report, before the second read, cancels that read's effect. A held Code Mode session of a done work item keeps running until the idle limit ends it (R95).
- R88. A ticket leaves the assigned state only when its source confirms it. The GitHub source reads each assigned issue that its issue search leaves out, or lists outside the assigned state, on its own before it reports the issue as gone, because during a GitHub outage the search can succeed with an incomplete result. A failed confirming read fails the poll, which changes nothing.
- R11. A work item with a session that ends because its ticket left the assigned state, without a done report, stays listed in Done with no warning; leaving the assigned state is routine.
- R34. Work item statuses are `triaging`, `unstarted`, `queued`, `setup`, `running`, `awaiting-approval`, `finished`, `blocked`, `failed` and `done`.
  - `unstarted` waits for the operator to start it, because its playbook does not start automatically.
  - `awaiting-approval` means a session's work is finished and waits for the operator to approve the prompt that publishes it (R23). When its session runs again, as when the operator answers its question or resumes it, the work item is `running` until that run ends; the run's own approval or done report applies, and a run that ends or is stopped without one returns the work item to `awaiting-approval` with the earlier approval and the cause of a failed turn or a stop.
  - `finished` means a task session ended its turn or its process without a report, and its playbook offers neither done nor approval (R23), or the operator reopened the work item after its session's turn ended (R86), so its work waits for the operator's review. The operator resumes it or marks it done.
  - `queued` waits for a session slot (R38), for the turn of another session of the same ticket to end (R17), including the work item's own earlier session, or for its ticket to wake (R49), or for its blockers to close (R90). Its row's line 3 lists each reason that holds, such as `Waits for a slot · 10/10 in use` or `Waits for its session's turn to end`, with what ends it in the tooltip.
  - `blocked` means a session ended its turn or its process without the done or approval report its playbook offers, or the operator stopped it while no approval was pending (R40), or a task session reported done while its ticket was still in the assigned state (R10). Its reason names the report the session was offered, such as "The turn ended without a done report." The operator resumes it or marks it done.
  - `failed` means a Switchboard step failed: triage, a session start, or a setup session that ended without a worktree. The dock shows the cause and offers **Retry**, which retries from the step that failed: a work item that failed at triage, because its latest triage failed, triages again and then starts or waits for Start as the chosen playbook says; any other failed work item, ad-hoc and scheduled ones included, is queued with its playbook, approved prompt and guidance, so its next start runs setup when its playbook needs a worktree it lacks, else the approved prompt, else the task session. Retry does not change readiness (R27). A work item that failed at triage stays in Unstarted (R27).
- R35. A work item has no Triage again control; Retry on a work item that failed at triage (R34) and Reopen of a done work item that has no playbook (R86) triage it again. The operator chooses another playbook by hand in Start with guidance… (R77), which lists the task playbooks of the namespace of triage's choice, in settings order, with triage's choice selected, when there is more than one. Starting with another replaces triage's choice: the row, History and every later session take it, and setup runs first when it requires a worktree the ticket lacks (R19). The focus stays as triage set it (R79). An ad-hoc work item has no playbook to change, and a scheduled run keeps its schedule's (R82), so neither offers the choice.
- R86. The operator can reopen a done work item when it is its ticket's latest work item, the ticket has no open one, and no other session handles the ticket's assignment (R85), because a session can report done while work remains or keep working after its done report. Reopen clears how the work item ended and returns it to where its work stands: `running` while its task session is in a turn, which then ends by the usual report and turn-end rules; `awaiting-approval` once that turn has ended when an approval (R23) still waited, or was approved but its run had not started, when the work item became done without a done report, and while in a turn it holds that approval as R34 does; otherwise `finished` once that turn has ended, so the operator resumes the session or marks it done; and `unstarted`, or `triaging` without a playbook or prompt, when it never had a task session. A session that keeps working after its done report does not reopen the work item by itself.
- R45. Only reports from a work item's latest session change the work item. Reports from earlier sessions are recorded on those sessions. A report from a copy that a fork retired is refused (R78).
- R90. A ticket with an open blocker does not start. The check is off by default and turned on with the GitHub source's `waitForBlockers` setting (Wait for blockers in the Settings window), because stacked work legitimately starts from its blocker's branch; while it is off, no ticket has blockers. With it on, the GitHub source reads each issue's blockers with every poll whose search lists the issue and counts only open ones; an issue missing from the search keeps the blockers last read; other sources have none. Every start of the ticket's work queues it as usual, Start, Start with guidance…, a pick, an automatic start after triage, Approve and Retry alike, and the queued work item starts once a poll sees no open blocker, as a wait for a slot ends (R38); a session already running is not stopped. Line 3 of an open work item's or pool ticket's row names the blockers in the warning colour, as `Blocker: #12` or `Blockers: #12, #15 and owner/repo#7`, with each blocker's reference and title in the tooltip; a blocker in another repository is named `owner/repo#<n>`. A queued row names them as its wait reason instead, as `Starts when #12 closes`. History records each change to the blockers. While the check is on there is no per-ticket override: to start one ticket's work before its blocker closes, the operator removes the dependency in the source, or turns the check off.

### Playbooks

- R12. A playbook name is `<namespace>:<name>`, such as `support:defect`, `support:question`, `dev:qa-question`, `dev:qa-failure` or `dev:new-dev`. A namespace is the role the operator works the ticket in, such as `support` for support support or `dev` for development.
- R13. Namespaces and playbooks are not built into Switchboard. Any playbook defined in configuration is valid, and triage chooses among them.
- R14. A playbook owns a prompt template. Switchboard renders it with the ticket's fields, the triage context and the Switchboard session ID.
- R15. Each playbook is configured to start its task session automatically after triage or to wait, `unstarted`, for the operator to start it. A work item whose triage found nothing new waits whatever its playbook says (R80).
- R16. Each playbook states whether it requires a worktree to start, and where its session runs (`workdir`): in the ticket's worktree when one exists, or always in the ticket's repo root. A playbook that requires no worktree and has no worktree yet starts in the repo root. Every `support` playbook runs in the repo root.

### Sessions

- R17. A ticket has at most one session in a turn across all its work items, because its work items share one worktree. Switchboard starts no session while another session of the same ticket is starting, running or waiting on a question. A session whose turn has ended, such as one kept open idle in the VS Code Claude view, does not hold a start back, because the operator commonly keeps that view open. A work item's active session is its latest session while that session has not ended; an earlier session left open is not. Ended sessions are kept as history.
- R18. A new work item is triaged first. Triage is a one-shot classifier with no tools: it receives the source's triage context, led by the current time, and triage playbook, and returns the playbook that handles the work item and its focus (R79). A triage playbook chooses a specific playbook only when the context states the requested action by the source's rules, and otherwise its playbook for an unclear ticket, such as `dev:other` for GitHub, where an assignment alone states no action, nor does activity an earlier work item already handled (R80).
- R79. **Focus.** Triage also returns the work item's focus: the page or comment the operator reads first to do the chosen playbook's work, and the earliest such comment when several ask for it. An item window opens only the focus (R72), so the operator lands on the comment that asks for the work.
  - The triage context tags the ticket's page `[ticket]`, the pull request it includes `[pr]`, and each comment that has a URL `[c1]`, `[c2]` and so on in time order. The classifier returns one of those ids, which Switchboard turns into the URL, so the context does not repeat each comment's URL. GitHub tags issue, pull request and review-thread comments, whose URLs end in `#issuecomment-<id>` or `#discussion_r<id>`. Zoho Desk and Forum tag nothing, so their focus is the ticket, because no per-thread or per-post URL has been shown to open at its comment. Only comments in the clipped context can be the focus, so an earlier comment outside it cannot.
  - A task playbook may set `focus` to `ticket` or `pr`, the page its work is done on. The triage prompt names that page beside the playbook, and a chosen comment on another page is replaced by the playbook's page; a `pr` playbook whose context has no pull request focuses the ticket. A missing or unknown id focuses the playbook's page, else the ticket.
  - The focus is the latest successful triage's and is kept while a later triage runs or after it fails. It is fixed when triage completes: a later playbook report (R23) or settings change does not change it. A work item never triaged successfully, or triaged before focus existed, focuses its ticket. A pool ticket's Triage again discards its earlier triage (R47), so it focuses its ticket until the new triage completes.
- R80. **Nothing new.** A new work item whose ticket had an earlier one acts only on activity newer than that earlier work item: a comment, a review or a commit, not a status or assignment change, which only a first work item acts on, such as 🎁 Assigned for development, because the earlier one already acted on what was there, so anything more would be a guess, as when the operator unassigns and reassigns an issue by mistake. The earlier work item took in the activity when the first of its task sessions that started began, so a start that failed does not count, or when the operator marked it done without a session; the latest of the ticket's earlier work items counts, and one with neither, such as one unassigned during setup, does not. A handled-assignment registration (R85) counts as an earlier work item that took in the activity when it registered, with the reporting work item's playbook. A source reports the time of its latest activity by anyone other than the operator: for GitHub, the latest issue, pull request or review-thread comment, pull request review or pull request head commit in the triage context by an author outside the configured logins, bots included, because the operator's own comments and commits, such as a session's, ask nothing of the operator. A commit counts because an author who pushes fixes and returns the card for another review asks for that review without a comment. Triage gets a line naming the earlier work item's playbook and time, so it treats activity up to then as background. The hub compares exact times; the line shows the minute, as the context does. When nothing is newer, the line says so, the triage playbook chooses its playbook for an unclear ticket, and the work item waits, `unstarted`, for the operator's Start whatever the chosen playbook's `autoStart`; its row says `Nothing is newer than the earlier work item` until Start, and History says why. The pull request line of the GitHub context shows the head commit's author and time, so triage can see a push. A source that does not report activity, such as Zoho Desk and Forum, whose playbooks all wait for Start, is not checked.
- R19. When the chosen playbook requires a worktree and the ticket has none, a setup session runs after triage to create one. The task session starts once the setup session's process ends with a worktree linked, or, for a setup session the operator resumed, such as one opened in Claude to answer its question (R70), once its turn ends with one, because the open tab keeps its process. A Code Mode setup session succeeds at its turn end with a worktree linked, because its process keeps running between turns (R95), unless the turn stopped at a usage or rate limit, after which it continues (R111). A setup session that ended without a worktree because its process was gone, as at a logout, and that the operator resumes, returns its work item from `failed`, or from `blocked` after a limit wait (R111), to setup.
- R20. The task session runs the rendered playbook prompt and handles the work item from start to finish.
- R21. A session without a worktree runs in the ticket's repo root. A session that creates a worktree reports it, and Switchboard links it to the ticket.
  - A ticket's repo root is its own when it has one, as an ad-hoc or schedule ticket does. Otherwise it is the source's `repoRoot`, in which `{name}` and `{owner}` stand for the ticket's repository, such as `D:/git/{name}` for `acme/widgets-dashboard`. A source's `repoRoot` without `{name}` serves only its home repository, its `repo` setting: a ticket in another repository then has no repo root, and its start fails with the reason. Two repositories, in any sources, whose tickets resolve to one folder, such as `alice/project` and `bob/project` under `D:/git/{name}`, both fail to start until the pattern adds `{owner}`. Switchboard never clones a repository; a start in a folder that holds no clone fails, naming the repository and the folder, and a linked worktree does not lift a refused repo root. Each ticket records its repository, and a playbook's template can name it with `{{ticket.repo}}` and the issue number with `{{ticket.number}}`.
- R22. A session runs in Claude Code or Codex. `sessions.provider` sets the agent for every session, `claude` by default, and a playbook's `provider` overrides it for its work items' setup, task and approved sessions; an ad-hoc prompt or hosted conversation uses its explicit provider choice, or `sessions.provider` when the caller omits it, until a playbook takes its work item over, whose provider, else `sessions.provider`, then starts its sessions. Choosing a provider never changes the configured default or an existing session. Each agent has its own default permission mode and model: Claude's `sessions.permissionMode` and `sessions.model`, and Codex's `sessions.codex.permissionMode` and `sessions.codex.model`; a playbook's own mode and model apply to its agent. A Codex session runs in `auto`, `plan`, `dontAsk` or `bypassPermissions`, and Codex's default is `bypassPermissions`, because commands in Codex's sandbox cannot use the operator's sign-ins, such as `gh`'s ([mechanics.md](mechanics.md) M31). A Codex session gets the same prompt, with a leading `/<skill>` written `$<skill>`, which is how Codex runs a skill, and the same report contract, with native questions and permissions handled by R107; existing exec sessions keep their question report and handoff (R70). Triage uses `sessions.provider`, regardless of task playbook provider overrides. `triage.model` overrides that provider's default model; a recognized model from the other provider falls back to the selected provider's default, with the reason logged and the configured value preserved. Unknown model names pass through unchanged. The session records its agent, and the row's controls and History name it, such as Open in Codex. A Claude session runs in Code Mode when R93 says so; History and tooltips name it, not the row.
- R23. A session can report its stage, a worktree link, that it is done, which means the entire work item is done, every part of its task is complete, and the session has nothing left to do and can be retired, or that its work is ready for the operator's approval with the prompt that finishes it, such as `/review-pr pr:123 publish`, a summary of what that prompt publishes, and the file holding the drafted text it publishes, if any. An approval report puts the work item in `awaiting-approval`; Approve starts a new task session with that prompt. `awaiting-approval` is used only for this. A session can also hand its work item to another task playbook in the work item's namespace, whose skill it then runs, so the row names the work being done; a playbook such as `dev:other`, whose session researches what an unclear ticket needs, offers it. Each task playbook lists the reports its sessions may send besides stage, links and tasks (R68), from done, approval, worktree, playbook and paste (R60), and lists none by default. A playbook that lists approval states whether Approve sends the work, such as posting a reply or pushing a branch, or only finishes it after the operator sends it by hand, as a Support release does after the operator pastes the reply; it does not send by default; a session whose playbook lists neither done nor approval ends its turn `finished` (R34), in Ready for review (R27), for the operator to review. The session's report contract lists the reports it may send, except tasks (R68), and the hub refuses any other. The contract is part of the session's system prompt, not its first message, so Claude's session list shows only the task prompt, and the session gets it back after each compaction. A setup or approved-prompt session may report its stage, a worktree, done, links and tasks; an ad-hoc prompt may send every report but playbook, because it has no playbook to change. A report is only for work ready to publish: a session that needs the operator's answer or choice, or cannot continue without them, asks with `AskUserQuestion` and waits, so its context stays live, and writes no report for the question; a Code Mode session asks in a reply instead (R103). Reports are accepted from the session after it is resumed in VS Code.
  - The reported texts are short, because a row shows about 8 to 10 words: the stage is an -ing phrase of at most four words stating the work now running and what it acts on, such as `fixing tests`, with no ending punctuation because the dock follows it with its age, optionally after a step count such as `2/5`, and the approval summary one phrase of at most 8 words without counts. The report contract states these word caps; the dock cuts a longer text at a character cap, 24 for the stage, 60 for the approval summary and 80 for a warning or error, on a word boundary, and keeps the whole text in the tooltip. A done report carries no summary, because nothing shows it.
- R60. A session can report a paste: a label and the absolute path of a file holding a drafted text the operator pastes into the source by hand, such as a Support case's customer reply and private note for Zoho. Pastes belong to the work item, and a later paste with the same label replaces the earlier one. An `awaiting-approval` row with pastes shows a Copy button before Report, and Copy in its right-click menu: with one paste it copies at once, its tooltip naming the paste, and with more it asks which by label, its tooltip "Copy a draft…". Copy reads the file when clicked, so the operator gets the draft as it is on disk, and puts its text on the clipboard without a byte order mark or trailing whitespace, then confirms with "Copied <label>." on the dock's status line. A missing or unreadable file shows a warning and copies nothing. Switchboard still writes nothing to the source; the operator pastes.
- R68. A session can report a task when the operator asks it to queue one, such as a defect it found in other code that the operator wants handled separately. Only the operator initiates a task: a session names a follow-up it finds in its final message and does not queue it. The report carries a prompt, and optionally a repo and a title. Switchboard creates an ad-hoc ticket and work item, as for an ad-hoc prompt (R6), with three differences: the work item always waits `unstarted` for the operator to press Start, because the prompt is the session's, not the operator's, and may write; the title defaults to the prompt's first line; and the repo defaults to the reporting ticket's repo root (R21). The repo must be one of the repo roots the ad-hoc prompt offers (R6). The new row's line 3 shows "From" and the key of the work item whose session reported it, such as "From gh 18941", and a click on it selects that row. Every session may report tasks, as it may report links, because a task changes nothing outside Switchboard until the operator starts it, but no report contract lists the task report, so a session sends one only through a skill the operator invokes. An empty prompt or another repo is refused. A repeated report with the same prompt adds nothing while the earlier work item is open.
- R81. **Registered sessions.** The operator can register a Claude session they started outside Switchboard, such as one in a VS Code window on a repository, as a work item, by running a skill in it that runs Switchboard's register command, such as `/sb-register`. As for the task report (R68), no report contract or usage text names the command, so a session runs it only through a skill the operator invokes.
  - Switchboard creates an ad-hoc ticket and work item (R6), `running`, titled by the command's title, with the session's working directory, as Claude's roster lists it, for its repo. Claude must list the session with a process. A copy of a Switchboard session, newer or older, such as a fork or a copy a fork retired, is refused (R78). A session Switchboard already has gets its key and contract again, so a command whose reply was lost can be run again.
  - The command prints the session's report contract, which offers the ad-hoc reports; the session follows it from then on and gets it back after each compaction (R23). The work item then behaves as an ad-hoc one: a turn that ends without a done report blocks it, and a done report finishes it. A ticket report moves it onto a source's ticket (R83).
  - The session is the operator's, so Switchboard never releases or stops it (R39), and refuses Stop. Until the session ends, its row has no item window, so a click switches nothing, and offers no Open in terminal, because Switchboard cannot find the operator's window and opening the live session elsewhere starts a copy ([mechanics.md](mechanics.md) M18).
  - Once it ends, opening it resumes it in the terminal holder as a Code Mode session's resume does (R95): the row's click, Open in terminal and the web page's Resume. It is then a held session Switchboard keeps, with the Conversation view, the web page's Console and composer, and voice, and ends, stops and resumes as R95 says. It resumes in Code Mode only when it ran in Code Mode, because Claude resumes a session only in the mode it ran in ([mechanics.md](mechanics.md) M68, M117), otherwise as a plain `claude` with the operator's own API settings, which need neither Code Mode nor `sessions.codeMode`; with the permission mode and model its transcript last recorded, else the defaults (R22); and with its report contract in its system prompt, because its contract was only in its conversation. The resume is refused while Claude lists the session with a process, as in the operator's window, because two copies would run, and while Switchboard cannot read that list.
  - Only Claude sessions can register: the command reads the session ID from `CLAUDE_CODE_SESSION_ID`, which Claude sets in its Bash tool ([mechanics.md](mechanics.md) M36). A Claude session ID that the terminal holder holds for a Code Mode session (R93) cannot register.
- R83. **Ticket reports.** Work often starts as an ad-hoc prompt (R6) or a registered session (R81), and a skill then files a ticket that records it, such as a GitHub issue. A ticket report moves the session's ad-hoc work item onto that ticket, so the work continues as the ticket's work item instead of a poll creating a second one whose new session lacks the context.
  - Each enabled source is asked in turn, the one that already holds a ticket at the URL first. A GitHub source answers for an issue on its board in any status, because a ticket report often precedes the issue's assignment, and leaves an issue on another board to the next source. A failed read refuses the report, and so does an issue whose ticket belongs to a source that is off, so no other source stores it again; when no source has the issue on its board, the report is refused with `No enabled source has <url> on its board.`
  - The skill sends `ticket` with the ticket's URL and, optionally, a playbook. As for the task report (R68), no report contract or usage text lists it, so a session sends it only through a skill the operator invokes. Only the latest session of an open ad-hoc work item can send it.
  - An enabled source must recognise the URL and read the ticket within 6 seconds; GitHub reads issues of its configured repository. A closed ticket, except a GitHub issue while its source's `includeClosed` is on (R44), a failed or late read, and a ticket Switchboard already has with a work item, triage, worktree or link are refused. A playbook must be a task playbook in the source's namespace.
  - The ad-hoc ticket becomes the source's ticket, so the work item, its sessions, worktree, links and History stay together. It keeps its repo, so later sessions start where the ad-hoc ones did, and its item window, so an open one is still found. The row keeps its ad-hoc label until the work item has a playbook. Its earlier ad-hoc key is not used again.
  - The ticket starts out of the assigned state, so the poll that first finds it in scope continues the open work item (R7). The skill therefore sends the report before it gives the ticket an in-scope status or assignee. A ticket a poll stored with nothing on it, such as an issue assigned to the operator on a status outside scope, gives way to the move.
  - With a playbook, the work item takes it: the row and History name it, and later sessions run its template and contract. A registered session takes the playbook's reports at once, because its contract is only in its conversation; the command prints the new contract, which the session follows in place of the earlier one, and which returns after compaction. A session Switchboard started keeps the contract in its system prompt until it ends. Without a playbook the work item stays ad-hoc.
  - From then on the ticket's source decides done (R10). A repeated report for the same ticket changes nothing and prints the contract again.
- R36. A session's observed state is `starting`, `running`, `waiting` (needs the operator: a permission prompt or a question), `idle` (its turn ended), `failed` (the turn stopped on an error, with its kind) or `ended`. For a Claude session, hook markers that Switchboard installs in the operator's Claude settings decide the state; the Claude roster decides whether the session is alive, and supplies the state when no marker exists. New Codex sessions use native app-server thread and turn events and reads, never hook markers. Existing Codex exec sessions keep their output, process and hook observations. A session's outcome is `done`, `failed` or `stopped`. A Code Mode session's liveness comes from the terminal holder, and only hook markers of its current launch decide its state (R93).
- R37. A triage or session start that fails makes the work item `failed`, with the error. Switchboard does not retry it automatically.
- R38. At most `sessions.concurrency` sessions run at once (default 2, range 1–10). A start that has no free slot waits as `queued`. A session holds a slot only while its work item is `setup` or `running`, its session does not wait on a question, and its ticket is not snoozed; a setup session and the task session that follows it hold one slot. Any other session holds none, such as one waiting on a question, awaiting approval or review, or blocked and kept open in VS Code, so the operator's open items do not stall the queue; an approved work item queued for a slot stays in Ready for review (R27); when such a session runs again, more than `sessions.concurrency` sessions can run until enough end. A Code Mode session held idle after its turn (R95) holds none, and neither does an older session kept after a newer one started; one waiting for a usage limit to reset holds its work item's slot (R111).
- R39. When a session's turn ends, Switchboard stops its background process, so that the session can resume in VS Code. A session waiting on the operator is not stopped, except by the operator's Open in Claude (R70). This never deletes the session or its worktree. A fork of a session in its background process waits for this release, or for the operator's Stop (R78). A Code Mode session is never released at its turn end; it keeps running between turns, and R95 decides when it ends. Codex app-server task threads stay available between turns until an hour passes with no turn, when their subscription is released as a Code Mode session's idle end (R95) ends its process, and a message resumes them; setup, done and superseded sessions release their subscriptions after their turn. A thread waiting for a usage limit to reset is never released for idleness (R111). Release never interrupts a new turn or stops the shared daemon (R107).
- R40. The operator can stop an active background session; a session the operator resumed in VS Code is stopped there. The work item becomes `blocked` with the reason "Stopped by you." once `claude stop` succeeds; a work item that is or was `awaiting-approval` in that run (R34) returns to `awaiting-approval` with that reason instead, because a stop never approves. A failed stop shows its error and leaves the session stoppable. Stop of a Code Mode session ends its process in the terminal holder in any state, including after its turn (R95).
- R89. **Continue in Background.** The operator can move a session running in an item window's Claude tab back to its background process and close the window, to free the window's memory while the work goes on.
  - The Claude tab's title bar, and the Claude sidebar's, have **Continue in Background** beside New Claude Session in Editor Tab (R75). It acts on the session in that tab, or the window's one Claude session for the sidebar, which has no tab; the session must be its work item's latest Switchboard session in this window, released to the operator (R39) and running a turn. A session that has ended its turn has nothing to continue, and one waiting on a question or a permission prompt is not supported; both are refused, as are a session that never ran in Switchboard's background process, such as a registered session (R81) or a fork (R78), a Codex session, and a Code Mode session, which the terminal holder keeps running when the window closes (R93).
  - The window must be able to close, or the command is refused and nothing changes: it holds no other Claude session, in a tab or the Claude sidebar, and no terminal Open in terminal (R28) opened, whose session would end with it, and no unsaved changes. A Claude CLI the operator started in another terminal of the window is not detected and ends with the window.
  - The tab closes, which ends the session's process mid-turn ([mechanics.md](mechanics.md) M55), then the window; from the sidebar, which hiding does not end, the window closes and ends it. Once that process has exited, Switchboard resumes the session in its background process with its own permission mode and contract, telling it that its last tool call may have been cut off. The row stays In progress under the same short ID, History shows "You asked to continue the session in the background" and then that the session continues in the background, and R39 releases the session again when its turn ends.
  - If another Claude session starts in the window while Switchboard answers, the window stays open. If the Claude tab closes while Switchboard answers, nothing else closes, so a new tab with the same label stays open; the session continues in the background.
  - A tab whose process has not exited 30 seconds after the request keeps its session, which Switchboard observes as before. A resume that fails ends the session, and the work item shows "Continue in Background failed:" with Claude's message; a resume that starts a copy is stopped.
  - While the session moves, Stop ends it as R40 does; once its background process is starting, Stop waits for it to start.
- R78. **Forks.** A fork of a Claude session that Switchboard started, such as one made with Fork conversation in the VS Code Claude view, continues that session: the fork becomes the work item's session, and the copy it was forked from is retired. The operator forks mostly to rewind past turns they do not want, and leaves the original. A Code Mode session follows the ID changes made in its terminal instead, and no fork (R93).
  - Switchboard finds a fork on a roster read that lists it with a process, in the session's project directory. A fork copies its source's API request IDs into a new transcript, so a fork belongs to a session when its first request ID is in the transcript of the session's current copy or of a copy a fork retired, and its transcript was created after the current copy's. Of several forks, the newest wins.
  - Only the work item's latest session is continued. While the current copy holds Switchboard's background process, the fork waits until R39 releases it, or the operator stops a copy that waits on a question, so no work is cut off. History shows the waiting fork, and the row offers Stop in place of Open in Claude, which would open the copy the fork retires.
  - From then on the row, Open in Claude, Open in terminal, the report contract after compaction and the debrief follow the fork. A retired copy changes nothing when resumed, and its reports are refused with the fork's ID; a report from a newer fork not yet continued is recorded. History shows "The session continues in fork <id>", and earlier entries keep the copy's own ID.
  - A fork that no roster read lists with a process, such as one opened and closed between reads, is continued when it is next opened. A fork from another workspace's project directory, or one made before the first reply, is not found. Codex threads are not forked.
- R41. A failed start shows the agent's own message: Claude's for an untrusted directory says how to trust it, and Codex, in its sandboxed modes, refuses a directory outside a git repository. A Claude session that waits on a prompt before it starts, such as approving the project's MCP servers, starts waiting on the operator: its row is in Blocked on you, says it waits on a prompt before it starts, and its main control is Open in terminal, which attaches to it so the operator answers there (R28); Open in Claude is not offered, because the session has nothing to open in a tab yet. The roster lists a session whose process died at that prompt the same way, so its row keeps waiting until the operator stops it. Switchboard never writes Claude's trust settings or MCP server choices, and never passes Codex's `--skip-git-repo-check`. A Code Mode session's prompts before it starts, including folder trust and Claude's first Code Mode confirmation, are answered the same way, because Claude in an interactive terminal asks to trust a folder instead of refusing it (R95).
- R93. **Code Mode sessions (experimental).** With `sessions.codeMode` on (off by default), each new Claude session Switchboard starts, setup, task, approved, ad-hoc and scheduled alike, runs with Claude Code's Code Mode, in an interactive `claude` held by the terminal holder (R94), because Code Mode refuses background sessions ([mechanics.md](mechanics.md) M63).
  - It talks to the Anthropic API directly with the operator's subscription sign-in, skipping any gateway and API key in their Claude settings: Code Mode refuses a gateway, and the subscription is Switchboard's choice ([mechanics.md](mechanics.md) M64). An `apiKeyHelper` in the operator's Claude settings cannot be skipped, so it fails every Code Mode start.
  - A start that Claude makes without Code Mode, such as with an unsupported model, or because the operator declined Claude's first Code Mode confirmation, fails with Claude's reason and its process is ended ([mechanics.md](mechanics.md) M70, M71).
  - Code Mode needs Switchboard's hooks, because only hook markers give a held session's state: with `sessions.installHooks` off, a Code Mode start fails with "Code Mode sessions need sessions.installHooks.", and background sessions are unaffected. Held sessions keep running when hooks are turned off: each keeps its last state, its row says it is unobserved, and the idle limit ends it (R95); turning hooks back on observes it again.
  - A session keeps the mode it started in when it resumes, because Claude resumes a Code Mode session only with Code Mode on ([mechanics.md](mechanics.md) M68); changing the setting changes only later starts. Codex sessions, triage and debriefs are unchanged, and so are registered sessions (R81) until one that ended resumes in the holder.
  - History names a Code Mode start, and the tooltips of the controls that open the session say it runs in Code Mode. The row shows no mark, because with the setting on nearly every Claude session is a Code Mode one.
  - A session whose ID changes in its terminal through `/clear`, `/branch` or `/resume` continues as the new ID, as a fork does (R78), and the old ID's reports are refused from then on ([mechanics.md](mechanics.md) M73). Forks made outside its terminal are not followed, and reports from another Claude session ID are refused. It cannot Continue in Background (R89), and it is not debriefed (R55, [mechanics.md](mechanics.md) M74).
- R94. **Terminal holder.** A Switchboard process, the terminal holder, holds Code Mode sessions in hidden terminals and keeps each one's screen and scrollback, so a session runs while no terminal shows it and survives hub restarts, extension updates and VS Code closing.
  - One runs per Switchboard home. The hub starts it when a Code Mode session starts or resumes, and it exits 10 minutes after it last held a live session, whatever terminals or other programs are connected.
  - When it stops otherwise, such as by a crash or a logoff, each session it held ends with "The terminal holder stopped.": a session in a turn or waiting on the operator blocks its work item, setup included; a starting one fails its start; and one whose turn had ended leaves its work item's status and any held approval as they were. The operator resumes each from its row; Switchboard does not resume them by itself.
  - No held session is lost: `hub.js holder list` and the dock's held sessions window, opened from More Actions (R71), list every held session with its work item, Switchboard and Claude session IDs, folder, state, idle time, memory and attached terminals, including sessions no work item owns, and stop any of them. While any held session has no work item, a note above the dock's groups counts them, and a click on it opens the held sessions window. Switchboard never ends a session no work item owns by itself.
  - The holder has a version of its own, its build, which changes only when the holder's own code changes. While the running holder is from an older build than the installed one, a notice above the dock's groups and the web page's list says so and how many sessions a restart resumes, with Restart and resume. It asks first, naming each session a restart interrupts mid-turn, then stops every held session, ends the holder, starts the installed build and resumes each session that was active, and the notice reports any that did not resume. Switchboard never restarts the holder by itself, because sessions are rarely all idle.
  - Other programs on the machine that hold the holder's token, such as a voice front end, can attach to a held session and type into it; the token also lets them start and stop sessions.
- R95. **Opening and ending a Code Mode session.** A Code Mode session opens in a terminal attached to the terminal holder, in the item window or the dock's terminal app as `dock.openTerminal` says (R28), never in the Claude view, which refuses Code Mode: Open in terminal, the row's click where it would open the Claude view (R29, R71), Open in terminal in Open in Claude's place on a question (R70), a start prompt (R41) and History's link (R59).
  - Opening an ended session resumes it in the holder first. The resume is refused, naming the processes, while a process that Switchboard last saw in the session's previous run, such as a shell command it started, still runs; Stop, offered on the ended session meanwhile, ends them ([mechanics.md](mechanics.md) M69).
  - Closing the terminal leaves the session running. When the session ends, its terminal stays open, and Enter there resumes it.
  - The session keeps running in the holder between turns, never released (R39), also when it is a setup session whose task session has started (R19), when its work item is done, and when a newer session of its work item has started, so opening it attaches to the live session and its conversation goes on there. The hub ends its process, so that it can be resumed, only when it has had no terminal attached and no input or output for an hour, after its turn, or at any point while it is unobserved (R93), and never while it waits for a usage or rate limit to reset (R111). While a terminal is attached that end waits until the last terminal detaches; a session waiting so never holds back the next session's start, because only sessions in a turn count (R17, R38). Otherwise it never ends a session; Stop and Delete end it in any state (R40, R76).
- R111. **Usage and rate limits.** A session whose turn stops at a usage limit or a rate limit of its provider, such as Claude's 5-hour or weekly limit or Codex's usage limit, waits for the limit to reset and then continues, instead of failing its work item.
  - Switchboard reads the limit and its reset time from Claude's transcript or Codex's turn error ([mechanics.md](mechanics.md) M100), including a Claude turn that ended normally in the grace allowance Claude gives before a limit.
  - The work item stays `setup` or `running`. Its row stays in In progress with the Rate limited mark, a watch, and line 3 says when it resumes, as `Rate limited · resumes 1:20 PM`, or `retries` at Switchboard's next attempt when no reset time is known; the Conversation view's header shows the watch with the same text.
  - A Code Mode session or Codex app-server thread is never ended or released for idleness while it waits (R95, R107), however long the wait, such as for a weekly limit, until it continues or Switchboard gives up, so Claude Code's own wait in a Code Mode session's process continues it after the reset. Switchboard continues a Code Mode session or a Codex app-server thread that has not started a turn 3 minutes after the reset, or 1 minute after it when Claude Code does not wait itself, by typing Claude Code's own continue text through the Conversation view's input (R97); with no reset time it tries after 5, 10, 20, 40 and 60 minutes. It does so only while the session is its work item's latest, under the same launch, and the work item still runs, checked again just before it types; a key typed in the session's terminal during the wait leaves the session to the operator, and its work item becomes `blocked` with why. When the work item becomes done or a newer session of it starts, Switchboard stops waiting for that session. After 6 attempts with no new turn, or 26 hours after the first was due, the work item becomes `blocked` with why.
  - A background session (not Code Mode) is released as before (R39); its work item becomes `blocked` with "The turn stopped at a usage limit. Open the session to continue it after the reset.", and line 3 shows when the limit resets. A background setup session that ends at a limit fails its work item with "Setup stopped at a usage limit. Retry it after the reset."

## Assignments already handled by another session

- R85. A skill may register that its session already handles another ticket's current operator assignment with `handled <ticket URL>`. Switchboard records that assignment on the target ticket and creates no duplicate work while it remains the same assignment. The report must succeed before the skill makes the target actionable. Registration removes duplicate work that has never had a session; it refuses when an open work item has already had a session, including a start still in flight. Ordinary links and playbook names never register handling. Each enabled source is asked in turn, the one that already holds a ticket at the URL first; a GitHub source answers only for an issue on its board. A registered ticket is read again through its own source on each poll, on its board or not.
- The registration survives restarts and lasts while the reporting work item is open. When that work item becomes done or is deleted, the registration ends, even if its session keeps working (R86), so the ticket is not hidden once nothing tracks the work; a still-assigned ticket then gets a work item, triaged under R80 with activity up to the registration as earlier work. Reopening the reporting work item does not restore the registration. A verified end of the operator assignment clears it; a new assignment permits normal work, including unassignment and reassignment between polls. Board status and project membership changes alone do not clear it. A skill may explicitly release the matching assignment key to resume normal processing during that assignment. A failed or incomplete source read changes nothing and retries normally.
- The source adapter must identify actual operator assignments independently of queue eligibility. Sources without that capability refuse registration; `requireAssignee: false` does not invent an assignment for an unassigned ticket. The target's History records registration and clearing. Released registrations cannot be restored by a retry, and a reporting session cannot claim a later assignment of the same ticket.
- Skills own publication and approval sequencing. Switchboard has no Support-specific handling rule.

## Open questions

- **Q10. Shell work that outlives a Code Mode session.** **Deferred 2026-11-19 until a real leak shows up.** A shell command a Code Mode session started kept running after the holder died and its `claude` exited, outside `claude`'s process tree and the roster ([mechanics.md](mechanics.md) M69). The holder ends a session by closing its pseudo-terminal, so Claude ends its own shell commands (M78), and the check before a resume (R95) looks at the session's last-seen process tree. Neither catches a process that left the tree, such as M78's `sleep.exe`, a command still running when the holder dies (M69), or one a tree kill after a failed close leaves. A container the holder could end whole, such as a kill-on-close job object on Windows, which node-pty does not offer, or a process group elsewhere, would; it is added when such a leftover is seen in use.
