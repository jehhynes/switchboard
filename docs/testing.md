# Testing

Use automated checks for behavior and integration, and visual inspection for presentation. A passing suite does not replace review against [prd.md](prd.md).

## Required checks

| Change | Verification |
|---|---|
| Executable code, while working | The pre-commit hook, or `npm run verify:staged` |
| Executable code, before merging into `main` | `npm run verify` |
| VS Code host wiring or UI-visible behavior | Also `npm run test:integration` in a real VS Code |
| Extension packaging | `vsce package --no-dependencies` succeeds |
| Runner, source fetch or report path | Also [live acceptance](#live-acceptance) from step 7 on |
| The web page console's layout: `console.ts`, its rules in `page.css`, or an xterm.js upgrade | Also `npm run build`, then `npm run check:console --workspace @switchboard/web` |
| A behaviour listed in [parity.md](parity.md) | The same change on the dock and the web page, or a Differs row the operator approved or decided, and parity.md updated in the same commit ([AGENTS.md](../AGENTS.md#dock-and-web-parity)) |
| Markdown only | Accuracy, links, and consistency across documents |

`npm run verify` builds, typechecks, and runs workspace tests with coverage thresholds. Build first: spawn tests run built bundles.

While working, run only the tests the change affects; run `npm run verify` before merging a branch into `main`. No git hook runs it at merge, because merges into `main` fast-forward, so the merging session runs it.

The pre-commit hook (`.githooks/pre-commit`, installed by `npm install` through `core.hooksPath`) runs [tools/precommit.mjs](../tools/precommit.mjs), which `npm run verify:staged` also runs. It maps the staged files to workspaces, takes those workspaces and every workspace that depends on them, builds them and their dependencies, then typechecks and tests them with each workspace's own scripts and coverage thresholds. It also counts dependencies the manifests do not declare and files another workspace's tests read; both are listed in the script and need updating when such a dependency is added. A staged file outside every workspace, such as `package.json`, `package-lock.json`, `tsconfig.base.json` or a file in `tools/`, runs the full `npm run verify`, as does `SWITCHBOARD_VERIFY=full`; otherwise the dock's `dotnet build` and `dotnet test` run only when `apps/dock` files are staged, and the pane helper's only when `apps/pane-helper` files are, which also build and test the extension that publishes it. Markdown and text files, and the hook's own files, run no checks.

`npm run verify` ([tools/verify.mjs](../tools/verify.mjs)) and the pre-commit hook run their checks, and `npm run test:integration` its VS Code run after the build, without the caller's `GIT_*` variables, and fail when the run changed `core.bare`, `core.worktree`, `core.hooksPath` or a `user`, `author` or `committer` key in the repository's shared git config, and the pre-commit hook also when they moved the checkout's HEAD or its branch, or changed its index entries or their flags ([tools/git-guard.mjs](../tools/git-guard.mjs)); a plain `npm run verify` leaves those out, because the session that runs it, or its coordinator, can stage, commit or rebase in that checkout meanwhile, while in the hook staging by anyone in the same checkout fails the commit, since it can change what the commit holds; the message names each change and how to undo a config change, and the guard changes nothing itself. Shared refs such as `refs/remotes/origin/main`, other branches' refs and other config keys are not watched, because a fetch, push or commit in another worktree changes them during a run. A test that runs `git add` or `git commit` with the hook's variables changes the commit being made, and `git update-ref` with them moves the repository's shared refs. A commit hook runs with `GIT_DIR` and `GIT_INDEX_FILE` set to the checkout being committed to, and in a worktree that `GIT_DIR`'s config is the main repository's `.git/config`, which every worktree shares: `git init` run with it in a temp folder reinitializes that repository as bare, and `git config user.name` sets the author of every later commit.

The dock's build and tests need the .NET 10 SDK, on Linux as on Windows. node-pty, the terminal holder's optional native dependency, has prebuilt binaries for Windows; on Linux npm builds it from source, which needs Python and a C++ toolchain, and without them the holder builds with no pseudo-terminals and its spawn tests fail.

## What earns a test

Test behavior that types cannot establish:

- Parsing source data and CLI output, malformed payloads, and clipping.
- Assigned-state transitions: first run, entering, leaving, and reassignment creating a new work item.
- The one-session-in-a-turn-per-ticket rule (R17), approval gates, and `requiresWorktree` handling.
- A failed or incomplete poll leaving every ticket's assigned state unchanged.
- Unassignment during an active session deferring the done decision, and unassignment deleting a work item that never had a session.
- Work item status transitions, the concurrency limit, and `queued`.
- Hook installation: entries preserved, malformed settings refused, missing entries added. The event-to-state mapping from recorded markers, and the roster fallback.
- Playbook loading from settings.json, playbook errors, and template rendering.
- Classifier output validation, including an unknown playbook name; default-provider routing and reload, model/provider fallback, Codex schema and temporary-file cleanup, and CLI failures.
- Report command handling, including unknown session IDs and worktree paths `git worktree list` does not show.
- Required CLI arguments for `claude --bg`, `claude -p`, `claude attach`, `claude stop`, `codex exec` and `codex exec fork`.

## Live acceptance

Automated tests prove decisions against recorded fixtures. Live acceptance proves that the recorded mechanisms still hold and that the parts work together. The developing agent runs it, not the operator, at delivery step 7 and again after any change to the runner, a source's fetch, or the report path.

Run it with an isolated home (`hub.js --home=<repo>/.wip/acceptance-home`, so the Switchboard home is `.wip/acceptance-home/.switchboard`) and its own hub.
