# Testing

Use automated checks for behavior and integration, and visual inspection for presentation. A passing suite does not replace review against [prd.md](prd.md).

## Required checks

| Change | Verification |
|---|---|
| Executable code, while working | The pre-commit hook, or `npm run verify:staged` |
| Executable code, before merging into `main` | `npm run verify` |
| Every push, any branch | GitHub Actions runs `npm run verify:full` on Linux and Windows, and the four browser checks on Linux ([tests.yml](../.github/workflows/tests.yml)); it gates no commit, push or merge |
| Runner, source fetch or report path | Also [live acceptance](#live-acceptance) |
| The web page console's layout: `console.ts`, its rules in `page.css`, or an xterm.js upgrade | Also `npm run build`, then `npm run check:console --workspace @switchboard/web` |
| The web page's shell on a phone: the page's height, safe areas, top bars, scrollers, overscroll or touch-action in `page.css` or `settings.css`, the layout of a list row's line 2, or the tab strips' sizing and More | Also `npm run build`, then `npm run check:shell --workspace @switchboard/web` |
| Fold reply details' fade on the web page: `replyFade.ts`, the fade's rules in `page.css`, or how `timeline.tsx` draws a folded reply or the newest reply | Also `npm run build`, then `npm run check:fade --workspace @switchboard/web`; `--shots <dir>` saves each size folded and opened, the long reply alone, and the newest reply whole and folded; `--linear` draws the same fade with a linear mask, to compare the curve against |
| The web page's connection, requests, opening a work item, service worker, boot screen or route: `connection.ts`, `request.ts`, `opening.tsx`, `sw.ts`, `boot.js`, `index.html` or `route.ts` | Also `npm run build`, then `npm run check:offline --workspace @switchboard/web`, which drives the page in a headless Chrome or Edge against its own fake hub on a loopback port, with faults, latency and restarts, never a running hub; `--shots <dir>` saves a screenshot of each scenario and `--assets` runs another build |
| Markdown only | Accuracy, links, and consistency across documents |

Tests are unit tests or integration tests. An integration test starts a real process, pseudo-terminal, built bundle or git repository, or depends on the machine, and lives in a file named `*.int.test.ts`; every other test is a unit test, which must not do any of those and must not wait a fixed time. `npm run test:unit` runs every workspace's unit tests in one vitest run (the root [vitest.config.ts](../vitest.config.ts) lists each workspace as a project), without coverage. `npm run verify` ([tools/verify.mjs](../tools/verify.mjs)) builds, then runs each workspace's typecheck and the unit tests at once; keep it under 15 seconds. `npm run verify:full`, which GitHub Actions runs, builds, typechecks and runs every workspace's tests, integration tests included, with their coverage thresholds. Live acceptance, and anything that reaches a real model, a source or the network, runs only on demand. A failed GitHub Actions run on `main` is fixed next, before other work.

In a checkout with no changed or untracked files whose tree already passed it with the same installed packages (`node_modules/.package-lock.json`), in any worktree, it runs nothing, so a merge that fast-forwards `main` to a verified branch head does not run it again; `npm run verify -- --force` runs it anyway. It records a tree in the common git folder's `switchboard-verified` file when the checkout was clean, with the same tree, when the run started and when it ended; it does not watch for a file changed and restored during the run.

Run the browser check the table names for a change once, when the change is finished, not after each edit; GitHub Actions runs all four on every push. On GitHub Actions (`CI` set) tests and hooks get 30 seconds instead of Vitest's 5 and 10 ([vitest-timeouts.ts](../tools/vitest-timeouts.ts)), because its Windows runner with coverage runs CPU-heavy tests 5 to 25 times slower; locally the defaults stand, so a test that grows slow still fails there. A failed hub entry-point test prints its hub.log.

The pre-commit hook and `npm run verify` each take a machine-wide check slot ([tools/check-lock.mjs](../tools/check-lock.mjs)), a lock file in the OS temp folder, before they build and test, and wait while another session's checks hold every slot, so sessions committing at the same time do not slow each other down. `SWITCHBOARD_CHECK_SLOTS` sets the number of slots, 1 by default. A slot is taken over when its process is gone, when it was made over an hour ago, or when it is still empty 10 seconds after it was made; a `npm run verify` the hook starts uses the hook's slot.

To run a workspace's tests on their own, build first, because spawn tests run built bundles.

While working, run only the tests the change affects. No git hook runs `npm run verify` at a merge, because merges into `main` fast-forward, so the merging session runs it.

The pre-commit hook (`.githooks/pre-commit`, enabled through `core.hooksPath` by `npm install`) runs [tools/precommit.mjs](../tools/precommit.mjs), as `npm run verify:staged` does. It builds the workspaces the staged files touch, every workspace that depends on them and their dependencies, then runs those workspaces' typechecks and unit tests at once, without coverage or integration tests. Where the script's `narrow` list names a dependency for a dependent, such as `packages/web` for `packages/hub`, a change to that dependency runs only the test files the list gives, such as hub's page tests, and `npm run verify` runs the rest before the merge. A dependency the manifests do not declare, or a file another workspace's tests read, must be added to the lists in that script. A staged file outside every workspace, such as `package.json` or a file in `tools/`, runs `npm run verify`, as `SWITCHBOARD_VERIFY=full` does. Markdown and text files, and the hook's own files, run no checks.

`npm run verify` and the pre-commit hook run their checks without the caller's `GIT_*` variables and fail when a check changed `core.bare`, `core.worktree`, `core.hooksPath` or a `user`, `author` or `committer` key in the repository's shared git config ([tools/git-guard.mjs](../tools/git-guard.mjs)); the failure names each change and how to undo a config change, and the guard changes nothing itself. The pre-commit hook also fails when the checkout's HEAD, branch or index changed, because staging during the hook can change what the commit holds; `npm run verify` does not watch them, because a session can stage, commit or rebase in that checkout while it runs. Shared refs and other config keys are not watched, because work in another worktree changes them during a run. The guard exists because a commit hook runs with `GIT_DIR` and `GIT_INDEX_FILE` set to the checkout being committed to, and in a worktree that `GIT_DIR`'s config is the main repository's `.git/config`: a test's `git init` with it reinitializes that repository as bare, `git config user.name` sets the author of every later commit, and `git add`, `git commit` or `git update-ref` change the commit being made or the shared refs.

node-pty, the terminal holder's optional native dependency, has prebuilt binaries for Windows, macOS and Linux on x64 and arm64; on another platform npm builds it from source, which needs Python and a C++ toolchain, and without them the holder builds with no pseudo-terminals and its spawn tests fail.

## What earns a test

Test behavior that types cannot establish, such as:

- Parsing source data, CLI output, transcripts and screens, including malformed and partial input and clipping.
- State transitions of tickets, work items and sessions, including first runs, reassignment, unassignment during a session, and a failed or incomplete poll leaving every ticket's assigned state unchanged.
- Rules that hold work back: the one-session-in-a-turn-per-ticket rule (R17), approval gates, the concurrency limit, input guards and reservations.
- Every refusal a protocol, route or command makes, such as a stale `scopeGen`, another page's key, a forged session ID or a malformed body, and the idempotence of a repeated `opId`.
- Delivery to the right recipients only: events and streams to the pages showing a session, and nothing to the others.
- Ordering and settlement under restarts, reconnects and lost answers: nothing delivered twice or lost, and a pending operation settled once.
- Settings and playbook loading, with their defaults, refusals and template rendering; hook installation that preserves entries and refuses malformed settings.
- The required arguments and environment of each agent CLI Switchboard starts, such as the held `claude`, `claude -p` and `codex app-server`.
- Path and file access limits: real paths, junctions and `..` refused where the design keeps access inside a folder, such as a paired device's folders in the New session form, tested with junctions the test makes under its temp folder.
- Cleanup: temporary files, processes and stored data removed with what owns them.

Do not test type declarations, pass-through property bags, or simple settings reads.

## Live acceptance

Automated tests prove decisions against recorded fixtures. Live acceptance proves that the recorded mechanisms still hold and that the parts work together. The developing agent runs it, not the operator, after any change to the runner, a source's fetch, or the report path.

Run it with an isolated home (`hub.js --home=<repo>/.wip/acceptance-home`, so the Switchboard home is `.wip/acceptance-home/.switchboard`), a config folder of its own under it (`--config`), and its own hub, never the operator's. Drive it from that hub's web page, opened with a sign-in link from `hub.js web` with the same `--home`, in a browser profile of its own; attach to its sessions from the page's Console tab and from the terminal app (Windows Terminal, or Ptyxis on Linux) that Open in terminal starts. Claude keeps the operator's profile, its sign-in and its trust. Start the acceptance hub with `CODEX_HOME` set to `.wip/acceptance-home/.codex`, holding a copy of `~/.codex/auth.json`, so its Codex hooks and their `hooks.state` trust entries stay out of `~/.codex`. Reports reach the isolated hub because the CLI takes its home from the `hub.js` it runs from. The acceptance hub's hook entries point at its own home; remove them when the run ends. Use real Claude and read-only GitHub, Zoho Desk and configured plugin source reads only; never a pick or any source write.

1. **GitHub read.** Configure the GitHub source with the operator's settings and every playbook set to `autoStart: false`. Confirm that the work items match the issues currently assigned to the operator in the configured statuses, and that each has a triage result. Never approve a GitHub work item during acceptance, because its playbook would run the operator's skills against a real issue.
2. **Ad-hoc session.** Use a scratch git repository under `.wip/`, trusted by running `claude` there once. Run an ad-hoc prompt that writes a file, reports a stage, reports a worktree, and reports done. Observe `running`, the state, `done` and the release stop in the page's list.
3. **Controls.** Open an ended session's work item and click **Resume** above the composer, which resumes the session in the terminal holder; its Console tab then shows it. Stop a session with Stop session; it should end up `blocked` with "Stopped by you." Reach `waiting` with a prompt that asks an `AskUserQuestion`; the row shows the Answer a question mark, and Open in terminal attaches to the session in the terminal app, where answering returns the row to In progress. Repeat a start with `sessions.codeMode` off and on, and get the start prompt from an untrusted directory. Run Open in VS Code on the work item; VS Code opens its workspace file, titled `sb:<name>`, with no Switchboard extension.
4. **Forks** (PRD R78). Register a Claude session running in Claude's own VS Code panel with `hub.js register` (PRD R81), fork it with Fork conversation, and continue the fork; the row follows it, History shows that the session continues in the fork, a report run from the original is refused with the fork's ID, and resuming the original changes nothing. A held session follows its ID changes instead ([mechanics.md](mechanics.md) M73).
5. **Code Mode** (prd.md R93–R95). Turn `sessions.codeMode` on in the acceptance config folder's `settings.json`, or with **Code Mode** under Advanced → Experiments in the page's Settings, and start its hub with `--code-mode-idle-ms` set to a few minutes. Run an ad-hoc session that reports a stage and done. Run one that asks an `AskUserQuestion`, and answer it once in the Console tab and once through Open in terminal in the terminal app. Leave a session idle after its turn with no terminal attached until the short idle limit ends it, then resume it with **Resume** above the composer and open its Console tab. Attach to a session live, stop it with Stop session, and resume it with Enter in the terminal still open. Delete a work item while its terminal is attached. Restart the hub while a session runs; it keeps running and its reports land. Kill the holder; the running session's work item is blocked with "The terminal holder stopped.", and Open in terminal resumes it in a new holder. In the Console tab and in the terminal app, close an attached terminal and open it again; check by eye that the replay shows the screen as Claude drew it and that typing, a paste, Shift+Tab, Ctrl+O and Esc reach Claude ([mechanics.md](mechanics.md) M72, M84). Show an orphan in `hub.js holder list` and in the page's More actions › Background sessions, and stop it there. Check the gateway: the session's `/status` shows the direct API and the subscription sign-in. Have a session ask question cards in the rules' shape (PRD R103): answer one from the web page on a phone, by touch and by voice, leave one open across an unrelated message, skip one, and check that the session receives the `[answers]` text and that the work item waits until no question is open. Steps 1–4 run too, to show that sessions without Code Mode and Codex sessions are unchanged.

Record each run in [mechanics.md](mechanics.md) with the date, the Claude CLI, Codex CLI and browser versions, and the result of each step. A failed step is a defect or a new mechanics finding, not a skipped check.

## Codex app-server

Codex app-server tests (R107) inject an app-server transport or a recorded-protocol peer; they never start the operator's daemon or call a live model. Record fixtures under an isolated Codex home and scrub their paths and IDs. Test native request cards in jsdom, and the terminal app's arguments against fakes.

For live acceptance, use a scratch repository and a separate `CODEX_HOME` with a temporary copy of the sign-in, removed afterwards. Start threads through the built hub and send follow-ups through its conversation route. Restart the hub during a tool call and confirm the replay has no duplicate messages. Answer a native request before and after a reconnect. Connect the same thread in the native terminal. Stop one of two threads and confirm the other continues. Verify a report and an artifact. Never stop or update the operator's daemon; stop only the isolated acceptance daemon afterwards. Record the CLI versions and results in mechanics.md.

## Session provider choice

No provider-choice test starts a real agent: hub and package tests use fake runners, and the web page's tests check the requests it sends.

## Fixtures and isolation

- Record and scrub source payloads and Claude and Codex CLI output (`claude agents --json`, `--bg` output, classifier JSON, `codex exec --json` output and stderr, rollout records, the process query's answer). Never call GitHub, Zoho Desk, a plugin’s service or a real Claude session from a test.
- Record and scrub Code Mode screens and markers from the runs in [mechanics.md](mechanics.md) M63–M77. Never run a real Claude or a real pseudo-terminal holding Claude in a test.
- Inject the Switchboard home, clock and process spawner.
- Test each platform's process table and path rules on any platform by passing the platform and recorded fixtures, such as `packages/codex/test/fixtures/proc/`. A test that needs real processes or the platform's own path rules runs only on that platform (`it.runIf`, `it.skipIf`), and the other platform's code has a test of its own, against a recorded answer such as `cim-tagged.json` where it cannot run here. Write expected path keys literally, with a fixed mixed-case name where case rules differ by platform.
- Every vitest config's `testTemp()` ([vitest-temp.ts](../tools/vitest-temp.ts)) points `TEMP`, `TMP` and `TMPDIR` at a folder of the run's own, `run-<pid>-*` under the shared test temp folder `switchboard-tests`, removes it when the run exits, and at its start removes any other folder there a day after the folder last changed, except the shared homes and the folder of a run whose process is still alive. A run started from a test keeps the starting run's folder. A folder a killed run left, or one a process still held at exit, goes a day later.
- Give a spawned hub its own `CLAUDE_CONFIG_DIR` and `CODEX_HOME`; it installs hooks in both. `testTemp()` points both at shared folders under the shared test temp folder, so a test that forgets cannot reach the operator's.
- Run git in a test only against a scratch repository the test made under the OS temp folder: pass `-C <repo>` or `--file` to every command, drop every `GIT_*` variable from the child's environment, set `GIT_CEILING_DIRECTORIES` to the temp folder, and check after `git init` that `git rev-parse --absolute-git-dir` names the scratch repository's `.git`. Never run `git config` without them. Every vitest config's `testTemp()` drops the `GIT_*` variables its workers inherit and sets `GIT_CEILING_DIRECTORIES` to the shared test temp folder; a script outside vitest that starts git or a test run uses `cleanGitEnv()` from [tools/git-guard.mjs](../tools/git-guard.mjs).
- Make a test's waits independent of machine load. Wait for a condition, such as a process's exit, a stored delivery, a replay or backpressure, never for a fixed time; give a wait on work that runs real timers, such as a screen replayed in xterm, the test's own timeout as its limit; give a fake clock's `sleep` a macrotask (`setImmediate`) so a polling loop never starves the test's timers. Count `taskkill` failing on a process that then turns out gone as success, await a worker's or process's end before removing its folder, and remove temp folders with `maxRetries`, since Windows can hold a file just closed for a moment longer.
- Use literal expected values. Do not derive an expectation by calling the code under test.
- Assert counts where an empty result would pass a contents check.
- Make fakes fail on unexpected calls.
- Never run a skill that claims or writes to a source, such as a support-case skill, in a test or a live check, and never Pick or Approve a support work item. Test picks with fake runners.

## Handled assignments

Test handled-assignment rules (R85) in core with arbitrary source and playbook names, and GitHub's event interpretation in the GitHub adapter. Live acceptance uses isolated storage, real read-only GitHub assignment queries and the report CLI; it changes no source assignments or project status.

## Source plugins

Cover module loading, validation and duplicate kinds; draft settings resolving plugins without activating them; rejected and overlapping reloads; source names independent of kinds; and plugin labels and fields in the Settings editor. Malformed field descriptions must not break an editor.
